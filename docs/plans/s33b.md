## 1. 做什么

agent 问一道要填密码这类敏感信息的题时，群里的卡不显示输入框，写明"已经私聊了能回答的人"；bot 私聊每个能回答的人一张带输入框的卡，在私聊里回答。答完群卡只显示"已在私聊里回答（内容不显示）"，答案不进日志、不进任何卡。敏感卡在等时，能回答的人在群里打字不算回答，bot 提示一次去私聊，消息照常处理。

产品依据：`docs/product.md` 3.8"等待和超时"最后一条（`docs/product.md:540`，"要填密码这类敏感信息的问题，不在群里显示输入框，请用户去私聊回答"）、第 11 节第 20 条（`:847`）；"谁能点"的表（`:523-530`）。

依赖：
- s30 卡片的发送、谁能点、等待和超时（#376，已合入）；
- s32 Codex 的服务端请求（#377，已合入）；
- s33 打字回答、打字题（未合入，照 `s33.md`）；
- s33c 旧卡自愈（未合入，照 `s33c.md`）。私聊里的旧卡被点时走 s33c 的 `healDeadAskCard`，本片不另写。

## 4. 怎么改

### 4.1 Codex：`D/agent/codex-appserver/server-requests.ts`

- `userInputRequest` 入口那行判断去掉 `q.isSecret` 一项和"s33b 映成 sensitive"的注释。线程不对、题 id 重复的退回留着。
- 映题不用改（s33 已写好）：`isSecret` 的题即使带选项也映成 `selection: 'text', sensitive: true` 的打字题，不带 `options`。Codex 的 `isSecret` 说的是答案是密文，选项没有意义。
- 标题照 s33：有打字题时"Codex 需要你回答"。
- 答案照 s33 的 `answerTexts` 回：私聊里打字是请求级 `kind: 'text'`，每道原题都得到这段文字；私聊卡的表单是每题的 `text`。
- 答案文字不进日志（本文件没有日志，`D/provider/transport/jsonrpc.ts` 不记发出的帧，保持）。

### 4.2 卡片：`D/card/ask-card.ts`

- `buildAskCard` 加参数 `scope: 'group' | 'dm'`，缺省 `group`。
- 敏感请求的群卡（`scope: 'group'` 且 `isSensitiveAsk(request)`）：不放表单，不放 `ASK_CONTROLS_EID`，放一行 `md('🔒 这个问题要填敏感信息，不在群里显示输入框。我已经私聊了能回答的人，请在和我的私聊里回答；答完这里会更新。')`。
- 私聊卡（`scope: 'dm'`）：开头多一行 `md('这是群里 agent 问的问题。答案只交给 agent，不会出现在群里。')`，不放"可回答"那一行（私聊里就是本人），表单照 `pending` 的写法，敏感题也放输入框，带 `ASK_CONTROLS_EID`（重启后私聊里的旧卡也能被 s33c 换元素）。
- `parseAskSubmission` 不认 scope。敏感请求从群卡来的提交（群卡没有控件，能来的只有伪造）由协调器挡（4.3）。
- `answerSummary`：敏感请求先照 s33 的规则验证，再返回固定的"已在私聊里回答（内容不显示）"，不含答案文字。
- 终态：
  - `unavailable` 的 `reason` 加一种 `'dm-failed'`，文字"没能私聊到能回答的人，这题没法回答"（私聊卡全部发不出，和名单为空，都用它）；
  - 群卡的 `answered`：敏感请求显示上面的固定文字加 `note('${actor} · ${at}')`；
  - 私聊卡的 `answered`：本人答的显示 `note('已提交 · ${at}（内容不显示）')`，别人答的显示 `note('已由 ${actor} 回答 · ${at}')`。`AskCardState.answered` 加可选 `by: 'self' | 'other'`，只有 `scope: 'dm'` 看它；
  - 私聊卡的 `timed-out`、`stopped`、`unavailable` 和群卡一样。

### 4.3 协调器：`D/bot/ask-coordinator.ts`

数据：

```ts
interface Entry { …; dm?: Map<string, { kind: 'sending' } | { kind: 'visible'; messageId: string; shownAt: number } | { kind: 'failed' }> }
private readonly carriers = new Map<string, { turn: Turn; entry: Entry; dm?: string }>();  // dm = 收卡人的 open_id
private readonly dmIndex = new Map<string, Set<Entry>>();  // open_id → 这个人手上待答的敏感卡
```

发卡（`promote` 的成功分支之后）：
- 群卡照旧先发（没有控件，4.2），`carriers.set` 照旧，15 分钟计时照旧从群卡发出算。带 @ 的那条 post 照旧发，敏感请求的文字改成" 请在和我的私聊里回答上方问题"。
- `isSensitiveAsk(entry.request)` 时，对 `this.eligible(turn, request)` 里的每个 open_id（owner 2026-10-19：能回答的人都发）：`entry.dm.set(id, { kind: 'sending' })`，`dmIndex` 登记，`this.effect(async () => { const sent = await sendManagedCard(this.channel, id, buildAskCard({ request, state: { kind: 'pending' }, respondents: [], scope: 'dm' }), undefined, false, 'open_id'); … })`：
  - 发出时 `entry` 已 `settled` → 马上把这张私聊卡更新成终态（和群卡迟到的做法一样），不登记 `carriers`；
  - 否则 `entry.dm.set(id, { kind: 'visible', messageId, shownAt: Date.now() })`，`carriers.set(messageId, { turn, entry, dm: id })`；
  - 失败：`entry.dm.set(id, { kind: 'failed' })`，`log.fail('card', error, { phase: 'ask-dm-send' })`；`entry.dm.size > 0 && [...entry.dm.values()].every(v => v.kind === 'failed')` 时 `settle(turn, entry, { kind: 'unanswered', reason: 'unavailable' })`，并让群卡的终态用 `{ kind: 'unavailable', reason: 'dm-failed' }`（`settle` 加一个可选 `presentation` 覆盖）。
  - 部分失败：发出的照常等；失败的只记日志，群卡不提示（Claude 2026-10-19 定）。
- 名单为空（没配主人和管理员，发起人又是 bot）：一张私聊卡也发不出，也不会有失败回调。群卡变成可见以后马上 `settle(turn, entry, { kind: 'unanswered', reason: 'unavailable' })`，群卡终态同样用 `dm-failed`，不让群卡写着"已经私聊了能回答的人"挂 15 分钟。

点击（`submit`）：
- `found.dm` 有值：跳过 `placement.chatId` 的核对（私聊 chat 发卡时拿不到），改成 `input.operatorOpenId === found.dm`，不等 → `'denied'`（不提示；私聊里只有本人能点，这只可能是伪造）。名单核对照旧（点的时候可能已不是管理员）。
- 群卡来的提交而请求敏感：回 `'invalid'`，提示"这个问题请在私聊里回答"，去重照 `entry.denied`。
- 通过后 `settle(..., { actor, byDm: operator })`。

群里打字（`typed`）：s33 已经对敏感卡回 `'sensitive'`，不改。

私聊里打字（新 `dmText({ openId, text, messageId, createTime }): boolean`）：
- `const waiting = [...(this.dmIndex.get(openId) ?? [])].filter(e => e.state.kind === 'visible' && e.dm?.get(openId)?.kind === 'visible')`，再去掉 `createTime` 缺失或早于这个人那张私聊卡 `shownAt` 的（和 s33 `typed` 的时间一条同理：私聊卡出现前在私聊控制台里说的话，晚到了也不算答案）。
- 名单：上面滤完以后、按张数分支之前，`waiting` 再去掉这个人已经不在名单上的卡。和 `submit` 同一个判断，按每张卡自己的轮核（`isAdmin(cfg, openId)`，或者是那一轮的真人发起人；私聊卡发出以后这个人可能已不是管理员）。不在名单上的卡一律不算，不管剩几张；一张都不剩就是下面的 0 张，`false`，不发提示。
- 0 张 → `false`，消息进今天的私聊控制台。
- 1 张 → `text = text.trim()`，空 → `false`；超过 4000 截断；`settle(turn, entry, { kind: 'answered', answer: { kind: 'text', text } }, { actor, byDm: openId })` → `true`。
- 2 张以上 → 发一条私聊文字（3.5 的写法，`receive_id_type: 'open_id'`）"有 N 个问题在等你回答，请分别用上面的卡片回答"，`entry.denied` 里用 `dm-many:${openId}` 去重 → `true`。消息不进控制台。
- 日志 `log.info('card', 'ask-dm-typed', { len })`。不记正文、不记 id。

收尾（`settle`）：
- 群卡终态照旧（敏感的显示"已在私聊里回答（内容不显示）"）。
- 每张 `visible` 的私聊卡：`updateManagedCard` 成终态，`by: options.byDm === id ? 'self' : 'other'`；`carriers.delete`；`dmIndex` 删掉这个 entry（集合空了就删键）。
- `sending` 中的私聊卡：发出后发现已 `settled`，由发卡那一路补终态（上面）。
- `unanswered` 的私聊卡显示和群卡一样的 `timed-out`、`stopped`、`unavailable`。

这一片不碰 `eligible`、15 分钟、看门狗、一次一张卡。

### 4.5 并发、出错和停机

| 场景 | 结果 | 怎么保证 |
|---|---|---|
| 敏感卡在等，名单上的人在群里打字 | 提示一次"这题要在私聊里回答"，消息照常走（插话或排队）；60 秒以后再打字会再提示一次 | 4.4 第 2、3 条；owner 2026-10-19 |
| 敏感卡在等，名单外的人在群里打字 | 不提示，消息照常走 | s33 的 `typed` 先核名单，不在名单回 `'none'` |
| 私聊里打字，恰好一张在等 | 收成答案；群卡显示"已在私聊里回答（内容不显示）"，私聊卡显示"已提交" | 4.3 `dmText` |
| 私聊里打字，两张以上在等 | 提示用卡片分别答，消息不进控制台 | 4.3 |
| 私聊里没有卡在等时打字 | 进今天的私聊控制台 | `dmText` 回 `false` |
| 私聊卡出现以前在私聊里发的消息，晚到 | 进今天的私聊控制台，不算答案 | 4.3 `dmText` 的 `shownAt` |
