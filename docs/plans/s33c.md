## 1. 做什么

daemon 重启后点到旧的提问卡（选项卡、确认卡、权限卡都算），卡片上的按钮和输入框换成一行"已失效（后台服务重启过）"，点的人收到一句说明。没重启、卡刚收尾（别人刚答完、超时、停止）时被点，只回一句"已经有结果了"，不动卡，卡由收尾那一路更新。

产品依据：`docs/product.md` 3.8"卡片"第 3 条（`docs/product.md:520`，"每种结局都改卡，不让按钮一直挂着"，例子里有"已失效（后台服务重启过）"）、"等待和超时"第 4 条（`:538`，"后台服务重启后，挂着的请求就没了。点到旧卡时，卡片自愈成'已失效（后台服务重启过）'，和今天的 `healDeadRunCard` 一样"）；`docs/v1-plan.md` M6"给 owner 什么"第 1 条的"重启后点旧卡，卡片会说明已失效"（`docs/v1-plan.md:209`）。

依赖：
- s30 卡片的发送、谁能点、等待和超时（#376，已合入）；
- s33 打字回答、打字题（未合入，照 `s33.md`）。本片要用它的两样：`D/card/ask-card.ts` 导出的 `ASK_CONTROLS_EID = 'ask_controls'`（卡上的 `form` 和两处 `actions` 都带这个 `element_id`；飞书不认 `form` 上的 `element_id` 时，s33 改挂在包着表单的 `column_set` 上，看 s33 的 PR 描述），和 `T/ask-typed-answer.test.ts` 里的 mock。

等 s33 合入后，从当时的 `main` 开分支 `codex/s33c`（#422 第 2 节第 1 步的 `codex/<片>`）。s33b 等本片合入后再开。三片都改 `ask-coordinator.ts` 和 `handle-message.ts`，不并行。

## 2. 范围

本片做：
- 协调器：`submit` 把"卡不属于这个群"分出来，回 `'foreign'`（4.1）。
- 卡片处理器：`submit` 回 `'inactive'` 时调 `healDeadAskCard`（4.2）。
- 自愈：本进程发过的卡只回一句；本进程没发过的（重启前的旧卡）回一句，再把控件换成"已失效（后台服务重启过）"（4.3）。

不做：
- 不持久化挂着的提问。重启后请求就没了（product.md 3.8），只做点到旧卡的自愈。
- 不在启动时扫旧卡、主动改卡：只在有人点的时候改。
- 本进程里刚收尾的卡，终态更新两次都失败时不补（4.3 第 2 条）。
- 私聊里的旧卡：s33b 发私聊卡以后，私聊里的旧卡也走本片这条路（`evt.chatId` 是私聊的 chat），s33b 不用另写。
- 不改 15 分钟超时、一次一张卡、谁能点（s30），不改打字回答（s33）。

## 3. 现在的代码

### 3.1 协调器（`D/bot/ask-coordinator.ts`）

- `carriers`：卡发出后 `promote`（`:114-131`）`carriers.set(messageId, { turn, entry })`。`settle`（`:157-174`）和 `close`（`:104`）都先删 `carriers`（`:166`、`:104`），所以 `carriers` 里有的卡一定是本轮的队首。
- `submit`（`:132-156`）：按 `carriers` 找卡；`turn.open`、`turns.get(sessionKey) === turn`、`queue[0] === entry`、`placement.chatId === input.chatId` 任一不满足回 `'inactive'`，什么也不做；解析失败回 `'invalid'` 并提示一次；点的人不在名单回 `'denied'` 并提示一次；通过回 `'accepted'`。
- 卡发出时带 `forward: false`（`D/card/ask-card.ts:158`），转发出去的卡点不了，所以 `placement.chatId !== input.chatId` 只可能是伪造的回调。

### 3.2 卡片处理器和死卡自愈（`handle-message.ts`）

- 卡片动作：`:3674-3682`，`dispatcher.on('ask_submit', …)`（`:3680`）调 `asks.submit`，返回值没用。`'inactive'` 被丢掉：重启后点旧卡，什么都不发生，按钮一直挂着。这就是要自愈的地方。

## 4. 怎么改

### 4.1 协调器：`submit` 的 `'foreign'`

`submit` 的返回值加一种 `'foreign'`，用在 `turn.placement.chatId !== input.chatId`（只可能是伪造的回调，3.1）。原来其他几个条件仍回 `'inactive'`。`'inactive'` 实际上就是"`carriers` 里没有这张卡"：重启前的卡，或本进程里已经收尾的卡。

### 4.2 卡片处理器（`:3680-3682`）

```ts
dispatcher.on('ask_submit', ({ evt, value, formValue }) => {
  const result = asks.submit({ messageId: evt.messageId, chatId: evt.chatId, operatorOpenId: evt.operator?.openId, value, formValue });
  if (result === 'inactive') healDeadAskCard(evt);
});
```

对 `'foreign'` 什么也不做（和今天一样）。`'accepted'`、`'invalid'`、`'denied'` 照今天，协调器自己处理。

### 4.3 自愈：`healDeadAskCard`（`handle-message.ts`，放在 `healDeadRunCard` 后面）

`'inactive'` 有两种来源（4.1）：重启前发的卡，和本进程里刚收尾的卡（别人刚答完、超时、停止，终态更新还在路上；或者同一个人双击）。两种分开处理，照 `healDeadRunCard` 分进程内和重启后的做法。分法用 `isManaged(evt.messageId)`：本进程发过的托管卡都在 `byMessageId` 里，从不清理（3.3）。

```ts
const ASK_EXPIRED = '已失效（后台服务重启过）';
const healDeadAskCard = (evt: CardActionEvent): void => {
  if (runControlNotes.seen(`dead-ask:${evt.messageId}`)) return;
  if (isManaged(evt.messageId)) {
    // 本进程的卡，刚收尾：终态更新由 settle 发（updateManagedCard 自带一次重试），这里不动卡，
    // 也不能用下面的秒级序号：它会让这张卡之后的 updateManagedCard（序号从 0 自增）被飞书拒掉。
    void trackTask(channel.send(evt.chatId, { markdown: 'ℹ️ 这个问题已经有结果了（有人回答、超时或已停止），卡片会更新。' }, { replyTo: evt.messageId }).catch(() => undefined));
    log.info('card', 'action', { actionId: 'ask_submit', settled: true });
    return;
  }
  void trackTask(channel.send(evt.chatId, { markdown: `ℹ️ 这张提问卡${ASK_EXPIRED}，这一轮已经结束。要继续，请重新发消息。` }, { replyTo: evt.messageId }).catch(() => undefined));
  log.info('card', 'action', { actionId: 'ask_submit', orphan: true });
  void trackTask((async () => {
    try {
      await new Promise(r => setTimeout(r, CARD_SETTLE_MS));
      const res = await channel.rawClient.im.v1.message.get({ path: { message_id: evt.messageId } });
      const item = …items?.[0];                                // 照 healDeadRunCard
      if (item?.chat_id && item.chat_id !== evt.chatId) return; // 卡不在点它的这个群里：不改
      const content = item?.body?.content;
      const cardId = content ? cardIdFromMessageContent(content) : undefined;
      if (!cardId) return;
      const seq = Math.floor(Date.now() / 1000);
      await channel.rawClient.cardkit.v1.cardElement.update({
        path: { card_id: cardId, element_id: ASK_CONTROLS_EID },
        data: { element: JSON.stringify(note(ASK_EXPIRED)), sequence: seq, uuid: `ha_${cardId}_${seq}` },
      });
    } catch (err) { log.fail('card', err, { phase: 'ask-card-heal' }); }
  })());
};
```

1. `isManaged` 从 `D/card/managed.ts` 引，和 `sendManagedCard`、`updateManagedCard` 放在一起；`ASK_CONTROLS_EID` 从 `D/card/ask-card.ts` 引（s33 加的）；`note` 从 `D/card/cards.ts` 引。
2. 本进程的卡：去重和孤儿卡共用 `dead-ask:` 这个键，60 秒内同一张卡只回一句。不改卡，"已失效（后台服务重启过）"不出现在本进程的卡上。终态更新两次都失败时按钮会留着，点了只会再收到这一句，接受：`updateManagedCard` 失败本来就少（3.3 的重试），要补就得让协调器记住刚收尾的卡和终态，代码多，不做。
3. 重启前的卡：用 `cardElement.update` 换元素（3.2 的写法），不是删：卡上要留下那一行字（product.md 3.8 `:538`）。
4. 这段元素里没有 agent 文字，不用过 `<at>` 守卫（s27a0 的说明同 `outbound-files.ts:324`）。
5. 序号用秒级时间戳：重启后这张卡的计数已经丢了，秒级时间戳必大于上一个进程按次自增的计数（`healDeadRunCard` 的注释）。只走在本进程没发过的卡上，不会和 `updateManagedCard` 的计数打架。
6. `message.get` 返回的 `chat_id` 和 `evt.chatId` 不同就不改卡（伪造的回调不能改别的群的卡）。字段取不到就照常改。
7. s33 之前发的卡没有 `ASK_CONTROLS_EID`，`update` 报错只记日志，那一句说明已经发了。
8. s33 把 `ASK_CONTROLS_EID` 挂在 `column_set` 上的（飞书不认 `form` 的 `element_id`，看 s33 的 PR），这里照样换那个 id，代码不用变。
9. `CardActionEvent` 的类型和 `healDeadRunCard` 用的一样。

### 4.4 并发、出错和停机

| 场景 | 结果 | 怎么保证 |
|---|---|---|
| 重启后点旧卡 | 回一句，控件换成"已失效（后台服务重启过）"；一张卡只处理一次 | 4.3，`runControlNotes` 60 秒去重；再点一次 60 秒后再回一次，和 `healDeadRunCard` 一样 |
| 重启后点 s33 之前发的旧卡 | 回一句；换元素失败只记日志 | 4.3 第 7 条 |
| 没重启，卡刚收尾（别人刚答完、超时、停止）时被点，或者同一个人双击 | 回一句"已经有结果了"，不动卡；卡由 `settle` 的终态更新改 | 4.3 的 `isManaged` 分支；不用秒级序号，不打乱 `updateManagedCard` 的计数 |
| chatId 对不上的回调（卡带 `forward: false`，只可能是伪造） | 什么也不做 | `submit` 回 `'foreign'` |
| `message.get` 返回的卡在别的群 | 只回那一句，不改卡 | 4.3 第 6 条 |
| 卡发出后 daemon 停机 | `asks.shutdown()` 按 `stopped` 收尾（`:7721`），卡的更新是分离任务，可能来不及；来不及的卡下次被点时自愈 | s30 现状 + 4.3 |
