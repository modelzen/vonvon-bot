## 1. 做什么

- 用量页多一组"智能模式的判断次数"：最近 14 天，每天一行写判断了几次，分语言模型（Codex、Claude）和决策模型（TypeSafe）；能按 Bot 看。daemon 重启，数不清零。
- 只算真发给语言模型或决策模型的判断。没填 key、冷却中、到了每小时上限这类没发出去的不算，也不单列（Claude 2026-10-19 定，第 9 节）。
- 依赖：
  - 已合入：s25（#405，智能入站和判断）、s23f（#412，决策模型）、s23g（#415，密钥接口）。
  - 已合入：s23g2（#419，密钥页）：用量页的出错文字用它的 `errorText`。
  - 不依赖 s27a、s28a、s28c。
- 从最新的 `main` 开分支 `codex/s28b`，现在就能开工。

## 4. 怎么改

### 4.1 每个 bot 进程记判断次数：`D/judge/usage.ts`（新）

```ts
export const JUDGE_USAGE_KEEP_DAYS = 30;
export const JUDGE_USAGE_FLUSH_MS = 5_000;
export const JUDGE_USAGE_CLOSE_MS = 2_000;
/** 这台电脑时区的日期 YYYY-MM-DD */
export function localDay(ms: number): string;
/** 往前第 n 天（0 是今天）的本地日期：用 new Date(y, m, d - n) 算，不减 n×24 小时（夏令时那天不是 24 小时） */
export function localDayBefore(ms: number, n: number): string;
/** `llm:<后端>` 或 `decision:<服务>`；形状不对返回 undefined */
export function usageKey(result: Pick<JudgeResult, 'backend' | 'provider'>): string | undefined;
export type JudgeUsageDays = Record<string, Record<string, number>>;
/** newer：文件是更新的版本写的（version 是比 1 大的整数） */
export class JudgeUsageUnreadable extends Error { readonly code?: string; readonly newer?: boolean }
/** 文件不在给 {}；读不了、不是 JSON、版本不对、形状不对抛 JudgeUsageUnreadable，带原错误的 code；版本比 1 大的另带 newer: true */
export async function readJudgeUsage(file: string): Promise<JudgeUsageDays>;
export interface JudgeUsage { add(result: JudgeResult): void; flush(): Promise<void>; close(): Promise<void> }
export function createJudgeUsage(opts: {
  file: string; now?: () => number; flushMs?: number; closeMs?: number;
  write?: (file: string, text: string) => Promise<void>;   // 默认 writeFileAtomic
  read?: (file: string) => Promise<JudgeUsageDays>;        // 默认 readJudgeUsage
}): JudgeUsage;
```

文件 `bots/<appId>/judge-usage.json`：

```json
{"version":1,"days":{"2026-10-19":{"llm:codex-appserver":12,"decision:typesafe":3}}}
```

- 日期键 `^\d{4}-\d{2}-\d{2}$`；计数键 `^(llm|decision):[a-z0-9][a-z0-9-]{0,39}$`；值是非负整数。用 zod 查。只存日期、键和次数，不存群、消息、模型名。
- `usageKey`：`result.provider` 有值就是 `decision:<provider>`，否则 `llm:<backend>`；不合键的形状返回 undefined，`add` 跳过它，记一次 `log.warn('judge', 'usage-key-skipped', { backend, provider })`（每个值只记一次）。
- `add(result)`：关了就不收。在内存的增量表里给 `localDay(now())` 这一天的这个键加 1。没有定时器就起一个 `flushMs` 的（`unref`）。同步，不抛错。
- `flush()`：挂在一条 promise 链上，一次只写一个。
  1. 增量表空就返回。取走增量表，换一个空的。
  2. 读文件。
     - 抛的 `JudgeUsageUnreadable` 带 `newer`（用户退回了旧版本，文件是新版本写的）：不覆盖，这批增量丢掉，返回。`log.warn('judge', 'usage-newer-file')`，每个进程只记一次。用量页上这个 Bot 算"读不了"（4.3），换回新版本以后数还在。
     - 别的读不了（不是 JSON、形状不对、版本不是数）：按空的算，`log.warn('judge', 'usage-unreadable', { code })`，每个进程只记一次；接着会用新数覆盖它，这个 Bot 以前的数丢掉。只是统计，接受（第 9 节"风险"）。
  3. 把增量加进去，删掉早于 `localDayBefore(now, JUDGE_USAGE_KEEP_DAYS - 1)` 的天（字符串比较）。
  4. `write(file, JSON.stringify({version: 1, days}))`。
  5. 写失败：把取走的增量加回增量表，`log.warn('judge', 'usage-write-failed', { code })`，起一个 `flushMs * 12`（60 秒）的定时器再试。不抛给调用方。
- `close()`：标记关闭，清定时器，`Promise.race([flush(), 等 closeMs])`；等超时记 `log.warn('judge', 'usage-close-timeout')`。永不 reject。
- 只有这个 bot 自己的进程写这个文件（一个 bot 一个进程，有单实例锁）。daemon 重启时旧进程补写、新进程第一次写，都是"读、加、写"，不会互相盖掉增量。崩溃最多丢最近 5 秒的数，接受。

### 4.2 接上判断：`D/judge/judge.ts`、`D/bot/handle-message.ts`、`D/bot/bridge.ts`、`D/cli/commands/run.ts`、`D/config/paths.ts`

### 4.6 并发、出错和停机

- 判断次数只是统计：读写失败都只记日志，不影响判断、不影响回复。`onResult` 已经在 `finish` 里 try/catch（264-268）。
- 写盘一次只有一个，增量在内存，写失败加回去下次再写。
- 停机顺序：
  1. `judge.shutdown()`（`D/judge/judge.ts:430-436`）同步 abort 在飞的判断，返回的 promise 要等后端调用都落定。
  2. 被 abort 的判断在 abort 之后的几个微任务里走 `finish`（`aborted` 的 reject → `Promise.race` → `catch` → `fail`），中间没有 I/O，所以等一个 `setImmediate` 就都记上了；不用等 `settling`。第 5 节第 2 条最后一条用例钉住。
  3. 接着 `judgeUsage.close()` 补写，最多等 2 秒。它和 `judge.shutdown()`、别的清理并行（各自一个 `startCleanup`），不串在后端清理后面。
  4. supervisor 停 bot 子进程时等 8 秒再强杀（`D/host/lifecycle.ts:299` 的 `CHILD_SHUTDOWN_GRACE_MS`，用在 `D/bot/supervisor.ts:368`）。bridge 停的时候一开始就调 orchestrator 的 `shutdown()`（`D/bot/bridge.ts:94`），补写从那里起最多 2 秒多一点，8 秒里放得下，后端清理慢也不挤它。第 5 节第 4 条用 `judge.shutdown()` 一直不落定的 mock 钉住。
  5. 真被强杀（比如进程卡死），丢的最多是最后 5 秒的数。
- 汇总时 bot 进程可能正在写：`writeFileAtomic` 是 rename，读到的不是旧的就是新的。
