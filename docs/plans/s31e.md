## 1. 做什么

- 用户能看到的变化：Linux 上用 Codex 的群，权限的"只读""工作区可写"不再置灰，能选、能跑；被拉进的已有群（默认只读）在 Linux 上用 Codex 时直接能用，不用再改成完全访问。Codex 版本低于第 0 步测过的版本时照旧置灰，原因写"这台电脑上的 Codex 版本太旧（{版本}），只读和工作区可写要 {最低版本} 以上，升级后就能选。"
- 依赖：
  - s31c（权限表、`refuseUnavailableTier`）。
  - 不再依赖 #486：用户点过的"总是允许"照样生效，不修也不说明（owner 2026-10-23："点过总是允许为啥还要限制""也不必说明"，product.md 3.8）。agent 在工作区里自己建的规则和配置仍然要挡，见第 0 步 F2、F3。
- 依据：`docs/research/2026-10-23-permissions/report.md` 第 3 节。2026-10-23 在 JP-VPS（Linux 6.8，codex-cli 0.163.0）上测到：vonvon 用的 `feishu` 权限 profile 在 Linux 上挡得住读（R1）；但还差两件事：

### 4.1 Codex 安装目录可读（`workspace-policy.ts`）

```ts
/** Codex 自己的文件：Linux 的沙箱里 Codex 要重新执行自己（report 第 3 节 R3）。 */
export function codexInstallRoot(bin: string): string;
```

- `realpath(bin)` 往上找，第一个 `package.json` 里 `name` 是 `@openai/codex` 的目录就是它（npm 装的，平台的二进制在它下面的 `node_modules/@openai/codex-<平台>/vendor/` 里）。找不到（独立二进制、Codex.app）就用 `dirname(realpath(bin))`。
- 护栏：算出来的目录是根目录、用户的 home、`/usr`、`/usr/bin`、`/usr/local`、`/usr/local/bin`、`/bin`、`/opt` 这类公共目录，或者是 vonvon 数据目录、某个工作区的上级时，不放开整个目录，只放开 `realpath(bin)` 这一个文件（profile 支持单个文件的条目；不支持就这一轮按 4.3 当作挡不住，写原因"找不到 Codex 的安装目录"）。返回值改成 `{ path: string; kind: 'dir' | 'file' }`。
- 结果在进程里按 `bin` 缓存。
- `codexFilesystem(roots, mode, installRoot?)`：有 `installRoot` 时加 `[installRoot]: { '.': 'read' }`，在工作区根的条目前面。
- `codexSessionParams` 用 `resolveCodexBin()` 得到 `bin`；`bin` 拿不到时照今天（没有这一条），会话照旧起不来，走今天"找不到 codex"的路。

### 4.3 什么时候算"挡得住"（`full-only.ts`、`backend.ts`、`codex.ts`）

```ts
export const CODEX_LINUX_MIN_VERSION = '<4.0 G 测到的版本>';
export function codexConfinesReads(platform: NodeJS.Platform, version: string | null): boolean;
// darwin：true（照今天）；linux：version 不是 null 且 >= CODEX_LINUX_MIN_VERSION；其余平台：false
export function codexFullOnlyReason(version: string | null): string;   // 1 节那句；version 是 null 时写"测不出 Codex 的版本"
```

- 按档判断：第 0 步 F2、F3 绕得过时，Linux 上只放开只读、不放开工作区可写。所以不是一个开关管两档：加 `export const CODEX_LINUX_WRITE_OK: boolean`（按 F2、F3 的结果写死，PR 里写依据），`codexConfinesReads` 之外再加 `codexTierUnavailable(tier, platform, version): string | undefined`。qa：照 `codexConfinesReads`；write：`codexConfinesReads` 成立而且（不是 Linux 或 `CODEX_LINUX_WRITE_OK`），否则原因"Linux 上的 Codex 还挡不住工作区里新建的 Codex 配置，工作区可写暂时不能用。"。`sandboxParams`、Codex 表的 `tiers()` 都按档调它；`fullAccessOnly()` 留着给旧代码，只在两档都不能用时有值。
- 版本：`codexVersion`、`codexVersionAsync` 返回的是 `codex --version` 的原样输出（例如 `codex-cli 0.163.0`），先用 `/(\d+)\.(\d+)\.(\d+)/` 取出版本号再比较；取不出算 null。
- `startThread`、`resumeThread`（async）里先 `await codexVersionAsync(bin)`，再交给 `sandboxParams(mode, network, platform, roots, version)`：这里是最终的判断，不成立时照旧抛 `CodexFullOnlyError`，带 `codexFullOnlyReason(version)`。
- `fullAccessOnly()` 在每条消息的路上同步调用，不能在这里第一次跑 `codex --version`（`locate.ts` 的注释不让在事件循环里同步起进程）。它只读已有的缓存：缓存里有版本就照 `codexConfinesReads` 判断；还没有就返回 undefined（先不拦，`startThread` 会拦）。daemon 启动时、doctor 时用 `codexVersionAsync` 预先取一次，把缓存填上。`bin` 拿不到时返回 undefined（找不到 codex 由别的检查管）。
- Codex 表（`D/agent/permission/codex.ts`）的 `strength`：
  - macOS："系统沙箱管住命令的读、写和联网：工作区以外的文件读不到，也改不了。"（照 s31c）
  - Linux，挡得住：同上一句，方案 1 时再加"工作区里原来没有的 .mcp.json、.claude/ 这类配置，能被新建。"
  - Linux，挡不住：照 s31c "暂时只能用完全访问"那句，换成版本原因。
- 版本比较用现有的比较函数（`grep -rn "semver\|compareVersion" D/` 找；没有就照 `D/agent/detect.ts` 里判断 codex 太旧的写法）。

### 规矩（原样照做）

- 临时目录只用 `T=$(mktemp -d)` 建，只用 `rm -rf -- "${T:?}"` 删，或者删刚在 `/tmp/` 下建的字面路径。
- 不对 `$HOME`、`~`、`$PWD`、`$VONVON_HOME` 或任何可能为空、未设置、指向真实 home 的变量拼出来的路径用 `rm`、`find -delete`、`find -exec rm` 或 `xargs rm`。
- 不在 shell 里给 `HOME`、`VONVON_HOME` 赋值或 export，只写在单条命令前面，例如 `HOME=$T/home VONVON_HOME=$T/vh npx vitest run`。
- 每次调用工具是新的 shell，`T` 不会留下来：建完把 `mktemp -d` 打出的路径记下，后面的命令在同一条命令里写 `T=<那个字面路径>` 再用 `$T`。
- 探针的 `CODEX_HOME` 只用 `$T` 下的；真实的 `~/.codex` 不读、不改、不拷，包括 `auth.json` 和 `rules/`。
- 不读 `local-secrets`。不打印、不抄 chat id 和 `projects.json` 的原始 id；PR 里群只写"Codex 测试群"。
- 不发测试以外的飞书消息，只在测试群里 @ 测试 bot。
