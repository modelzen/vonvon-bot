## 1. 做什么

bot 被人拉进一个还没绑定的群，主人一定收到一张设置卡。拉的人是主人或管理员，卡发给这个人。不是，卡发给主人，写明谁拉的、拉进了哪个群。

卡上：
- 工作区留空，就按 3.3 给这个群建目录；
- 后端默认用 bot 的；
- 写明权限档只读、网络关（3.8）；
- 话题群只有两项："按话题聊"和"智能"。选了"按话题聊"、没手选免 @ 时，免 @ 开（和多会话一样）。

设置好之前，群里 @ bot，bot 只回一句"主人还没设置好这个群，设置好就能用"（换文案）。不 @ 的消息不读。这一片不节流：和今天一样每次 @ 都回，话题里照旧回在主区。同一个群 10 分钟最多一次、话题里回在话题里，是 s36b2 的事。

bot 离线时被拉进的群（没收到进群事件），后来有人 @ 它，也只回这一句，不补发设置卡。主人在网页"加入已有的群"里设置（今天网页上是"加入飞书群 → 查找已经加入的群"）。

网页这一片不改，s36b2 改。s36b 合入、s36b2 还没合入时：
- 网页照旧只列管理员拉的群，话题群在网页上给三项（三项在话题群里都能用，4.9）。
- 别人拉的群，主人在私聊的设置卡上设置，或者走网页"查找已经加入的群"。

Linux 上选 Codex 照常绑定。回合开始时 bot 回 s20b 的那句说明。

## 3. 现在的代码

### 3.1 进群事件

`onBotAddedToChat`（:7438-7471），经 `admitEvent`（:1197）登记在 :7802。`admitEvent` 停机时直接返回，否则 `trackTask`，停机会等它（:7718 起）。

事件来自 SDK 1.71.1 的 `BotAddedEvent = {chatId, operator:{openId, userId?}, botName?, external?}`。没有操作人 open_id 的，`normalizeBotAdded` 返回 null，不进来。

现在的顺序：
1. 群已绑定（`getProjectByChatId`）：记 `bot-added-bound`，返回。
2. `!op || !isAdmin(cfg, op)`：记 `bot-added-nonadmin`，什么也不做。所以：
   - 普通成员拉的群，没人收到卡，也不进待绑定记录，网页看不到；
   - bot 自己用 `me_join` 进群（操作人是它自己）也走这里。
3. `pendingGroups.add(chatId, op)`，失败只记日志。再 `void trackTask(pendingGroups.refresh())`。
4. `channel.getChatInfo(chatId)` 读群名。**没有时限**，失败当空名。
5. `sendManagedCard(channel, op, buildJoinGroupFormCard({chatId, name, backends: backendOptionsFor('full')}), undefined, false, 'open_id')`。失败只记 `bot-added-bindcard`。
6. 记 `bot-added {chatId 尾号, op 尾号, named}`。

同一个群的事件重推两次，就发两张卡：`add` 遇到已有记录跳过，但卡照发。

### 4.2 待设置记录（`D/project/pending-groups.ts`）

- `Candidate` 的 `ready` 分支加 `topic?: boolean`。`PendingGroupVerification` 的 `ready` 加 `topic: boolean`。导出的 `PendingGroup` 接口加 `topic?: boolean`。
- `readPendingGroups`：`ready` 的项有 `topic` 时必须是布尔，不是就照旧整份报"待绑定群记录无效"；没有就不带。`verifying` 的项不认 `topic`，多了就忽略（和今天对别的多余键一样）。
- 加常量 `PENDING_REDELIVERY_MS = 10 * 60_000`。
- `add(chatId, operator, now = Date.now()): Promise<boolean>`，返回这次算不算新来的：
  - 没有这个群的记录：加一条 `verifying`，返回 `true`。
  - 有记录、`now - addedAt < PENDING_REDELIVERY_MS`：飞书重推了同一件事，不动，返回 `false`。
  - 有记录、更早：换成新的一条（新 `generation`、新 `operator`、`addedAt = now`、`verifying`），返回 `true`。这种是离线时漏了"被移出群"的事件，后来又被拉进来。
  - 结果在 `update` 的 change 回调里定，用闭包带出来。`update` 本来就按文件排队，同时到的两次 `add` 只有一次返回 `true`。
- `sweep` 写 `ready` 时带上 `topic: result.topic`。
- `retirePendingGroup`、`remove`、`refresh` 不变。

### 4.3 进群事件（`onBotAddedToChat`，:7438）

整个函数照旧包在 `withTrace` 和最外层的 `.catch` 里。日志字段只写尾号。顺序：

1. `op = evt.operator?.openId`，`tail = {chatId: chatId.slice(-6), op: op?.slice(-6)}`。
2. **bot 自己进群**：`op && op === channel.botIdentity?.openId` → 记 `bot-added-self`，返回。不记待设置，不发卡（e10 那段，:1209）。`botIdentity` 没读到时认不出来，按别人拉的走，卡发给主人；第一版不用 `me_join`，不会走到。
3. 已绑定：记 `bot-added-bound`，返回（照旧）。
4. `!op`：记 `bot-added-no-operator`，返回。`normalizeBotAdded` 已挡掉，留着防御。
5. `fresh = await pendingGroups.add(chatId, op).catch(err => { log.fail('intake', err, {phase: 'pending-group-add'}); return true; })`。记不上也当新的发卡：卡是主人唯一能看到的东西，网页那份等下一次事件。然后 `void trackTask(pendingGroups.refresh())`（照旧）。
   - s36b2 会在第 4、5 步之间加一步（清掉这个群"没设置好那一句"的节流）。这一片不加，第 4、5 步之间也不用留别的东西。
6. `!fresh` → 记 `bot-added-again`，返回。不发第二张卡。

### 4.9 并发、出错、停机

- **重复事件**：同一个群 10 分钟内的第二次进群事件只记 `bot-added-again`，不发卡。`add` 在按文件排队的 `update` 里定，两次同时到也只有一次是新的。SDK 的 `botAdded` 不 await 处理函数，两次可能并行进来。
- **记录写不上**：照样发卡，网页那份缺着。下一次进群事件，或主人在网页"查找已经加入的群"能补上。
- **发卡失败**（没开私聊、对方不在可见范围、接口错）：记 `bot-added-bindcard {to}`。待设置记录还在。不重试，不在群里说话。管理员拉的群网页照旧能设置；别人拉的群要等 s36b2 才列在待绑定里，之前走"查找已经加入的群"。
- **读不到群名**：卡上写"一个群（没读到群名）"，项目名空着让人填（必填）。
- **读不到话题群**：按普通群给三项。三项在话题群里都能用，只是多一项。
- **读不到拉人的名字**：写"有人"。联系人和成员接口共用一个 3 秒时限，最多等 3 秒，不是 6 秒。
- **私聊提交时 bot 已不在群里**：明确 `false` 才拒；读不到照常绑定。
- **bot 离线时被拉进的群**：没有进群事件，不发卡，没有待设置记录；有人 @ 时只回那一句（4.6）。主人在网页"查找已经加入的群"设置。
- **停机**：
  - `admitEvent` 停机后不收新事件；
  - 已在读的三件事由 `orStop` 立刻放行，第 9 步看 `shuttingDown`，不发卡；

  - 正在跑的 sweep：成员核对照旧等完；chat.get 和 `topicCtx` 各最多 3 秒（4.8）；
  - 私聊提交在 `trackTask` 里，停机照旧等它，新加的成员检查最多 3 秒。
- **群在读的这几秒里被绑好**：第 10 步再查一次，不发卡。
