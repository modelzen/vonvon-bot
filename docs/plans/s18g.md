# s18g 停止 daemon 不当成断线

行号按 `main` `84162db`。以后会漂，按函数名找。

## 1. 做什么

- 在桌面端"应用与启动"页点"停止 daemon"：按钮转到 daemon 真正退出，显示"daemon 已停止。"，"运行方式"变成"已停止"。马上点"启动 daemon"能起来。不再弹"连接丢失"。
- 在终端 `vonvon daemon stop` 以后，或 daemon 崩溃、桌面正在等它回来的时候，点"启动 daemon"或"启动已安装服务"：先取消等待，再启动、接上。不再提示 `Desktop startup is unavailable.`。
- bot 子进程的父进程没了、排空 20 秒被截断时，日志里写出登记着的 provider PID，和其中没确认退出的。
- 依赖：s18f（#372，合入 `0befaf8`，被动重连）；s18d（#368，合入 `3333fa8`，孤儿排空上限）。都已合入。
- 来源：补做审查 R1-1、R1-2（`docs/research/2026-10-18-codex-period-review/report.md` 第 5 节和 `r1-drain-reconnect.md`）。

## 2. 范围

做：
- 机器页"停止 daemon"改由桌面壳子发：先记成预期断开，发 `stopHost`，等这个 daemon 的进程退出，再显示已停止。
- 被动重连进行中，"启动 daemon"（含"仅运行此 Bot"）和"启动已安装服务"先取消重连，等它收尾，再启动。
- 停止还没等完时点启动：等停止结束再启动，不拒绝。
- 孤儿排空：`owned-work-orphan` 在 PID 集合变化时再记；`orphan-drain-cut` 带上登记着的和没确认退出的 PID。

不做：
- 终端停止后什么都不点，60 秒后桌面仍弹"连接丢失"。要 daemon 留下"正常停止"的记录，让被动重连读到后安静结束。这一片不做，见第 9 节的待 owner 定。
- 终端停止后机器页的状态不会自己变，要点"刷新状态"（显示 `Desktop request failed`、状态未知）以后，"启动 daemon"才能点。这是 s18f 之前就有的，界面留给 owner 最后统一重整。
- 断开期间别的请求显示 `Desktop request failed`。s18f 之前就有（R1 分报告"查过、不报的"最后一条）。
- "停止后台服务"仍然拒绝（`main.ts:422`）。
- 被动重连进行中的"重启 daemon"、"登录电脑时启动"开关仍然拒绝，提示不变。
- 截断时只写 `OwnedProviderProcess` 登记的进程（Codex 的 app-server 和 Claude 的 CLI）。`ProcessHost` 的进程由下次启动的 `sweepOrphans()` 收。
- 网页端（浏览器）点"停止 daemon"的行为不变。
- 不改界面文件。新加的提示用中文；已有的英文提示不改，留给 owner 的统一重整。

### 3.2 停止后马上启动，即使没有被动重连也会失败

这一条 R1 没写，读代码得出。只把断开记成预期还不够：
- daemon 排空期间 PID 锁一直在，最后才 `releasePidLock`（`packages/daemon/src/host/bootstrap.ts:153`）。
- 排空期间新连接照样能认证。排空时只答两种请求（`ws.ts:80-86`，处理在 `packages/daemon/src/server/http.ts:178-190`）：`admin daemonStatus` 照答 `running: own`（183-189 行）；`machine stopHost` 也照答"daemon 正在停止。"（179-182 行）。别的请求一律 1001 关连接。
- 排空中再点停止不会被关连接，但桌面端走不到这一步：停止在等退出时占着 `starting`，再点停止会被 4.7 ⑥ 开头拒绝。
- 所以排空期间点启动：`ensureReady` → `readVerifiedDaemon` 认出这个正在停的 daemon（`packages/desktop/src/daemon-dependencies.ts:68-81`），`attachExisting` 也通过（`packages/desktop/src/attach.ts:79-86`）。`bridge.replaceOwner` 要首个快照时被 1001 关掉，启动报 `The daemon could not start and reconnect.`（`main.ts:407`）。
- 排空一般几秒；bot 子进程排空最长 20 秒再截断（`packages/daemon/src/host/crash-guard.ts:34`）。所以停止要等 daemon 真退出，才能让"马上启动"可靠。
- "真退出"指进程没了，不是锁文件没了。收尾时先放 PID 锁（`bootstrap.ts:153`），再放 host 互斥锁（156 行），之后进程才退出。锁文件刚删、互斥锁还没放时点启动，新 daemon 拿不到互斥锁（`bootstrap.ts:57-61`），启动失败。终端的 `runStop` 也是等 `isPidLockOwnerRunning(lock)` 变 false 才返回（`daemon.ts:142-143`）。

### 3.3 终端停止（R1-1 第二半）

### 3.4 被动重连和启动的关系

- `reconnectPassive`（`main.ts:315-353`）：每 250 毫秒 `attachExisting` 一次。`owner`、`connection`、`identity` 三种失败重试，别的失败马上结束。拿到候选就 `bridge.replaceOwner(next)`（340-349 行）。
- abort 时：`unlessStopped`（318-323 行）马上拒绝，`closeCandidate`（340-341 行）关掉候选。但 `bridge.replaceOwner` 的 `replacing`（`bridge.ts:302-328`）要等候选真关完才清掉。
- 所以如果只 abort、不等 `replacing` 清掉就启动，`reattachReady` 里的 `bridge.replaceOwner` 会在 `bridge.ts:297-299` 被拒（`Desktop connection is unavailable`），启动照样失败。设计里要等。
- `recoverConnection` 的 `.catch`（369-371 行）不分原因，abort 了就弹框。被启动取消时不能弹。

### 3.5 孤儿排空的日志（R1-2）

## 4. 怎么改

产品行为照 `docs/product.md` 3.10："停止走 `vonvon daemon stop`：先排空，再正常退出，管理器就不会再拉起它"。机器页的停止和它一样：发 `stopHost`，等 daemon 退出。

### 4.1 daemon：`packages/daemon/src/agent/owned-process.ts`

加一个导出，放在 `unconfirmedProviderPids` 旁边：

```ts
/** 登记着的 provider 进程组号，给孤儿排空截断时的日志。构造时登记，close() 落定才删；自己退出、没人 close 的也在。 */
export function registeredProviderPids(): number[] {
  return [...ownedProcesses].flatMap(process => process.child.pid === undefined ? [] : [process.child.pid]);
}
```

- 名字和日志字段都叫"登记着的"（`registered`），不说"还活着"。
- 不按 `child.exitCode`、`child.signalCode` 过滤。这个 PID 也是 `close()` 要杀的进程组号（`signalGroup` 用 `-pid`，`owned-process.ts:79-86`）。组长自己退出了，组里的子进程可能还在；`stop()` 也要 `directExit` 和 `groupGone` 都成立才算死（`deathConfirmed`，88-91 行）。按组长退出过滤，会漏掉还活着的组。
- 组还在时，这个号不会分给别的进程；组没了才可能被复用。日志看到的 PID 要对照同一时刻的 `ps` 判断，不能直接当成还活着。

### 4.2 daemon：`packages/daemon/src/host/lifecycle.ts` 的 `closeOwnedProviders`

- 把 `orphanLogged` 换成 `orphanKey: string | undefined`。
- 孤儿分支：`key = [...pids].sort((a, b) => a - b).join(',')`；`key !== orphanKey` 时记 `log.info('daemon-shutdown', 'owned-work-orphan', { pids })`，再更新 `orphanKey`。
- 第一次照旧记（`undefined !== ''`）。之后只在集合变化时记，不每秒记。最后 `report(true)` 也走这条：PID 都确认退出、集合变回空时，再记一条 `{ pids: [] }`。
- 字段不变，还是 `{ pids }`。

### 4.3 daemon：`crash-guard.ts` 的 `capOrphanDrain` 和 `bootstrap.ts`

- `capOrphanDrain` 的参数加 `providers?: () => { registered: number[]; unconfirmed: number[] }`。
- 截断时（替换 54 行）：

```ts
safe(() => {
  let left: { registered?: number[]; unconfirmed?: number[] } = {};
  try { left = options.providers?.() ?? {}; } catch { /* 读不到 PID 也照样截断 */ }
  options.log.warn('run', 'orphan-drain-cut', { waitedMs: Date.now() - since, ...left });

```

- `crash-guard.ts` 不 import `owned-process`。
- `bootstrap.ts:80` 改成 `capOrphanDrain({ log, flush: flushLogs, providers: () => ({ registered: registeredProviderPids(), unconfirmed: unconfirmedProviderPids() }) })`，从 `../agent/owned-process` import 这两个。`lifecycle.ts` 已经 import 了这个模块，不多出副作用。
- 有几份测试 mock 了 `../src/agent/owned-process`、又会 import `bootstrap.ts`，mock 里只有 `closeOwnedProviderProcesses` 和 `unconfirmedProviderPids`：`daemon-lifecycle-runtime.test.ts:13`、`daemon-lifecycle.test.ts:66`、`daemon-release-errors.test.ts:21`。`registeredProviderPids` 只在截断时才读，这些测试平常碰不到。哪份报 `No "registeredProviderPids" export is defined on the mock`，就在它的 mock 里加 `registeredProviderPids: () => []`。

### 4.4 桌面：`packages/desktop/src/daemon-dependencies.ts`

- `createDaemonDependencies` 的返回类型改成 `DaemonManagerDependencies & { ownerRunning(previous: { pid: number; startedAt: string }): Promise<boolean> }`。`DaemonManagerDependencies` 本身不改，`daemon-manager.test.ts` 的假依赖不用动。
- 实现：

```ts
/** `previous` 这个 daemon 的进程还在不在。锁文件没了、进程还在（放了 PID 锁、还没放 host 互斥锁）也算在。 */
async ownerRunning(previous) {
  return isPidLockOwnerRunning({ pid: previous.pid, startedAt: previous.startedAt, listen: null });
},
```

- `isPidLockOwnerRunning` 和 6 行的 `readRunningPidLock` 从同一个 `pid-lock.js` import。
- 只问进程，不读锁文件，不认证，不连 WebSocket。理由见 3.2 最后一条：互斥锁在进程退出前才放，锁文件没了不算停完。进程不在时，锁文件留着也作废（`readRunningPidLock` 对死进程返回 null，`pid-lock.ts:64-67`），所以读锁不会改变结论。和终端 `runStop` 一个标准。
- `isPidLockOwnerRunning`（`pid-lock.ts:36-45`）先比开机时间：没有 bootId 时用 `startedAt` 和 `uptime()`，开机前起的算不在；再 `process.kill(pid, 0)`。
- 旧进程退出后 PID 马上被别的进程复用，会一直当在，等满 60 秒报没停完。macOS 的 PID 按序往上分配，几十秒内复用基本碰不到；`runStop` 也有同样的问题。接受。

### 4.6 桌面：`packages/desktop/src/bridge.ts`

1. 加一个纯函数，service stop（258-260 行）和 stopHost 共用：

```ts
type MachineStatus = Extract<MachineReply, { type: 'status' }>;
/** 停下以后的样子：没有 daemon，服务不在跑，临时运行的 Bot 也没了。 */
function stoppedView(before: MachineStatus): MachineStatus {
  const { temporaryAgent: _stopped, ...rest } = before;
  const state = before.service.state === 'running' || before.service.state === 'detached' ? 'stopped' : before.service.state;
  return { ...rest, host: null, service: { ...before.service, running: false, pid: undefined, ...(state ? { state } : {}) } };
}
```

   service stop 那处的 `stoppedStatus = {...}` 换成 `stoppedView(before)`。

2. 118 行 `stoppedStatus` 旁边加 `let lastStatus: MachineStatus | undefined;`：最近一次从 daemon 读到的 status。

3. machine 通道（226-236 行）的处理函数改成：

```ts
async value => {
  if (value.type === 'stopHost' && activeOwner) {
    const owner = activeOwner;
    // 停之前读一次，停完用它显示"已停止"。读不到（比如 daemon 读服务状态出错）就用最近一次读到的。
    const read = await owner.client.machine({ type: 'status' }).catch(() => undefined);
    const before = read?.type === 'status' ? read : lastStatus;
    const reply = await actions.stopHost(owner.identity, () => owner.client.machine(value));
    // 等停止的时候已经接上了新的 daemon（replaceOwner 换了 activeOwner），就不写。

    return reply;
  }
  const reply = value.type === 'status' && stoppedStatus ? stoppedStatus : await client().machine(value);
  if (reply.type === 'status' && reply !== stoppedStatus) lastStatus = reply;
  return value.type === 'status' && reply.type === 'status'
    ? { ...reply, cli: await actions.observeCli() } : reply;

```

   - 为什么要 `lastStatus`：停止前那次读失败、停止本身成功时，不写 `stoppedStatus`，面板接着读 status 就打到已断的 client（233 行）。`runMachineRequest`（`MachinePanel.tsx:16-27`）读失败会 `update(undefined)` 再抛，面板显示连接错误、状态未知，而不是"daemon 已停止。"。
   - `lastStatus` 不分是哪个 daemon 读到的。`stoppedView` 会改掉跟 daemon 有关的字段（`host`、`running`、`pid`、`state`、`temporaryAgent`），剩下的服务字段说的是这台电脑，不会因为换了 daemon 变。
   - `lastStatus` 实际上总有：面板一打开就读 status（`MachinePanel.tsx:38-39`），没有 status 时"停止 daemon"是灰的（79 行），面板的 status 都走这个处理函数。两样都没有时不写 `stoppedStatus`，和原来一样。
   - `activeOwner` 为 null（正在替换）时照旧落到 `client()`，报 `Daemon connection unavailable`。`replaceOwner` 成功时照旧清掉 `stoppedStatus`（324 行）。`lastStatus` 不清。

4. `onError` 不改。停止期间 `isExpectedDisconnect()` 为 true，断开不报、不重连、不发错误事件。

**③ 新函数 `startBlocker`（同步）**

```ts
/** 启动前要等的东西：被动重连让路，停止等它结束。别的操作在跑就拒绝。 */
function startBlocker(refusal: string): Promise<unknown> | undefined {
  if (terminating || cleanupPromise) throw new StartHostRefusal(refusal);
  if (!starting) return undefined;
  if (passive && starting === passive.done) { passive.cancel.abort(startTakesOver); return passive.done; }
  if (stopping && starting === stopping) return stopping.catch(() => {});
  throw new StartHostRefusal(refusal);
}
```

**④ `startHost`（399-412 行）**
- 400 行换成 `for (let blocker = startBlocker('Desktop startup is unavailable.'); blocker; blocker = startBlocker('Desktop startup is unavailable.')) await blocker;`。
- 循环最后一次检查和下面 `starting = run` 之间不能再有 await，必须在同一段同步代码里。这样两次并发的启动只有一个能占到 `starting`，另一个照旧被拒。

**⑥ 新函数 `stopHost`，接进 `installBridge` 的 actions**

```ts
async function stopHost(previous: AttachedDaemon['identity'], send: () => Promise<MachineReply>): Promise<MachineReply> {
  if (starting || terminating || cleanupPromise) throw new StartHostRefusal('正在启动、重启或重新连接 daemon，等它结束再停止。');
  const cancel = new AbortController();
  const cancelled = (): boolean => cancel.signal.aborted || terminating || cleanupPromise !== undefined || !bridge;
  const refusal = (): StartHostRefusal => new StartHostRefusal('停止已取消。');
  // 照抄 restartHost 248-253 行，只换拒绝信息。不抽共用函数，不动 restartHost 和 reconnectPassive 里的那两份。
  const unlessCancelled = <T>(pending: Promise<T>): Promise<T> => new Promise<T>((resolve, reject) => {
    const stop = (): void => reject(refusal());
    if (cancel.signal.aborted) { stop(); return; }
    cancel.signal.addEventListener('abort', stop, { once: true });
    pending.then(resolve, reject).finally(() => cancel.signal.removeEventListener('abort', stop));
  });
  const run = (async (): Promise<MachineReply> => {
    controlledDisconnect = true;
    try { await unlessCancelled(send()); }
    catch (error) {
      // 退出或更新安装打断了：不等回复也不等退出。controlledDisconnect 留着，窗口马上要关。
      if (cancelled()) throw error;
      // daemon 回了错（比如不支持停止）：没在停。
      if (error instanceof RpcError) { controlledDisconnect = false; throw error; }
      // 别的错是连接在回复前断了：daemon 多半已经在停，照样等它退出。
    }
    const deadline = Date.now() + stopDeadlineMs;
    for (;;) {
      if (cancelled()) throw refusal();
      // 查不了当作还在，接着等。
      const running = await unlessCancelled(managerDependencies.ownerRunning(previous).catch(() => true));
      if (!running) return { type: 'done', message: 'daemon 已停止。' };
      if (Date.now() >= deadline) {
        controlledDisconnect = false;
        throw new StartHostRefusal('daemon 1 分钟内没停完，详情在 daemon.log。稍后点"刷新状态"再看。');
      }
      await unlessCancelled(new Promise(resolve => setTimeout(resolve, 250)));
    }
  })().finally(() => {
    starting = undefined;
    stopping = undefined;
    if (restartCancel === cancel) restartCancel = undefined;
  });
  restartCancel = cancel;
  starting = run;
  stopping = run;
  return run;
}
```

- `RpcError` 从 `@vonvon/client/browser` import，和 19 行的 `ConnectionError` 一起。
- `unlessCancelled` 是 stopHost 自己的一份，形状和 `restartHost`（248-253 行）、`reconnectPassive` 的 `unlessStopped`（318-323 行）一样。不抽共用函数：那两处已有测试守着，抽出来要改它们，diff 和风险都变大。
- `send()` 也包在 `unlessCancelled` 里。daemon 迟迟不回时，退出、更新安装的 `cleanup`（82-100 行）abort 以后马上往下走，不等到连接断开。被打断的 `send()` 之后再落定，`unlessCancelled` 已经落定，结果丢掉，不会变成没处理的拒绝。
- 停成功以后 `controlledDisconnect` 一直是 true，直到下一次接上（`reattachReady` 240 行，或 `restartHost`、被动重连成功时清掉）。旧 client 已经断了，不会再报错。
- 超时以后清掉 `controlledDisconnect`，不再记着这个 daemon。之后点启动，`ensureReady` 找到谁就接谁；如果它还在排空，启动照旧报"could not start and reconnect"，用户过一会儿再点。这是卡住的排空，少见，接受。
- 等退出时不重新认证，不起 CLI，不读锁文件，只问旧进程在不在（`ownerRunning`，见 4.4）。

### 4.8 并发和竞态

| 正在进行 | 新来的 | 结果 |
|---|---|---|
| 被动重连 | 启动 daemon、仅运行此 Bot、启动已安装服务 | 用 `startTakesOver` abort 重连，等 `done` 落定（含进行中的 `replaceOwner` 落定），再启动。不弹框。 |
| 被动重连 | 停止 daemon | 拒绝："正在启动、重启或重新连接 daemon，等它结束再停止。"界面上这时状态未知，按钮本来就点不了；只有界面状态没刷新时才会走到。 |
| 被动重连 | 重启 daemon、登录项开关 | 照旧拒绝，提示不变。 |
| 停止（等退出） | 启动 daemon、启动已安装服务 | 等停止结束（成功、失败或超时都算），再启动。界面忙着时按钮点不了，这条是兜底。 |
| 停止 | 再点停止、重启、登录项开关 | 拒绝，提示照各自原来的。 |
| 停止 | 旧连接报 `ConnectionError` | `isExpectedDisconnect()` 为 true，bridge 吞掉，不重连。 |
| 启动 | 启动 | 照旧拒绝（`Desktop startup is unavailable.`）。 |
| 启动 | 停止 | 拒绝（同上一条停止的提示）。 |
| 服务助手跟随（`guardedService`） | 启动 | 照旧拒绝。 |
| 任何一项 | 退出、更新安装（`cleanup`） | `cleanup` 82-100 行 abort `restartCancel`、等 `starting`。停止马上结束，不管是在等 daemon 回复还是在等退出；被取消的被动重连照旧不弹框；正在等让路的启动，下一次 `startBlocker` 看到 `cleanupPromise` 就拒绝。 |
| 被动重连的 60 秒期限 | 同一刻点了启动 | 先 abort 的那个原因算数。期限先到就照旧弹一次框（模态，点掉后启动接着走）；启动先到就不弹，`finally` 清掉期限计时器。 |
| 任何一项 | 关窗口 | 窗口只是隐藏（218-223 行），什么都不取消。 |
| 任何一项 | 渲染进程崩溃 | `fatal` → `cleanup`，同退出。 |

还有两处接受的：
- 被动重连刚把候选接上、同一刻被启动 abort：`closeCandidate` 可能关掉刚激活的连接。启动接着会再换一次连接，结果对。s18f 的期限也有同样的窗口。
- 停止排空时 daemon 崩了，launchd 又拉起一个：等待看到旧进程没了，就当已停止。界面显示"已停止"，点启动会接上那个新的。

## 8. 验收要点

- [ ] 机器页"停止 daemon"经 `actions.stopHost` 发出，不再直接 `client().machine`；发之前 `controlledDisconnect` 已是 true。
- [ ] 只有 `RpcError` 算 daemon 拒绝了停止；连接在回复前断开照样等退出。
- [ ] stopHost 的 `unlessCancelled` 是局部照抄的一份，拒绝信息"停止已取消。"；`send()` 也包在里面，退出、更新安装时不等 daemon 回复（用例㉑）；`restartHost` 和 `reconnectPassive` 的闭包没动。
- [ ] 等退出只问旧进程在不在（`ownerRunning` → `isPidLockOwnerRunning`），不读锁文件；每 250 毫秒一次，最长 60 秒；退出、更新安装能马上打断。`daemon-dependencies.test.ts` 有㉒㉓。
- [ ] 停完的 status 来自 `stoppedView`：`host:null`、`running:false`、`state` 由 running 或 detached 变 stopped、没有 `temporaryAgent`；等待期间换过连接的不写。停止前读不到 status 时用 `lastStatus`（用例⑳）。
- [ ] 超时清掉 `controlledDisconnect`，提示是中文。
- [ ] `startHost` 和 service `start` 都先跑 `startBlocker` 循环；循环最后一次检查和占住 `starting` 之间没有 await。
- [ ] 被动重连被启动取消时不弹框；被期限取消时照旧弹。
- [ ] 被取消的被动重连等 `replaceOwner` 落定后才让 `done` 落定。
- [ ] 两次并发启动只有一个能跑；被动重连中的"停止"、"重启"、登录项开关照旧拒绝。
- [ ] `crash-guard.ts` 没有 import `owned-process`、logger 或 paths；PID 由 `bootstrap.ts:80` 传进来。
