### 4.2 凭证：归属和生命周期

凭证（grant）是登记表里的一项。Codex 的 grant 带一个令牌；Claude 的不带，工具直接绑在 grant 上。

- R1：一个 `AgentThread` 对象一个 grant。grant 在调 `startThread`、`resumeThread` 之前发，绑定这个 bot（一个 bot 子进程一张表）和这条会话所属的聊天（place），以后不换绑。
- R2：grant 有三段，只能往后走：
  - pending：`issue()` 发出以后、`attach` 之前。Codex 的 MCP 初始化和工具发现可能发生在 `thread/start`、`thread/resume` 返回之前（4.0 C 记实测顺序），所以这一段要能被发现；
  - attached：起会话或恢复成功后 `attach(thread)`；
  - revoked：`revoke(…)` 以后，终态；失败 `revoke('start-failed')`。
  各段能做什么：

  | 段 | 列工具（`tools()`、路由 `list`） | 调工具（`call`） |
  |---|---|---|
  | pending | 能，只回静态定义（名字、描述、参数 schema，各 grant 一样，不含任何会话信息） | 不能：回 `not-ready`，处理函数不跑，不排队 |
  | attached | 能 | 按 4.4 |
  | revoked、令牌不认识 | 不能：路由 401，进程内 `revoked` | 同左 |

  attach 不触发重新发现，也不需要：pending 段已经列过了，列出来的工具定义不变。`not-ready` 回给模型的是一条明确的话，它可以稍后再试。
- R3：每次恢复都是新 grant；Codex 的还是新令牌。Codex 每轮恢复（3.2），所以每轮换令牌。
- R4：作废的时机：
  - `thread.close()` 的第一步（两家的 `close()` 各加一行，在关进程之前）；
  - 调用时 `thread.isAlive()` 为假（进程死了，没人调 `close`）；
  - orchestrator `shutdown()` 一开始 `closeAll('shutdown')`；
  - bot 子进程退出：表只在内存里。daemon 重启后旧令牌一律不认。
- R5：作废后立刻从表里删掉，删掉令牌文件（s46b）。之后拿它来调，一律按"没有这个令牌"处理。
- R6：令牌的明文只在这几处：令牌文件；MCP server 进程的内存；它发给 host 的请求头；host 转发给 bot 子进程的那条 IPC。bot 子进程的表里只存 SHA-256。令牌不进日志、错误信息、卡片、环境变量、命令行参数。
- R7：令牌是 `vvs1_` 加 32 字节随机数的 base64url（43 个字符），共 48 个字符。
- R8：比对：表的键是令牌 SHA-256 的十六进制；查到以后再用 `timingSafeEqual` 比 32 字节摘要，对上才算。代码里不对令牌字符串用 `===`、`startsWith` 一类比较。
- R9：不跨群、不跨 bot：grant 绑 place；host 按路径里的 appId 只交给那个 bot 的子进程，别的 bot 的令牌在那里查不到。
- R10：一个 bot 同时活着的 grant 最多 1024 个。超了，新发的是死的（调用回 `not-ready`），日志 `agent entry-cap`。每次发新的之前，顺手删掉线程已经死了的。
- R11：令牌文件（s46b）：
  - 目录 `botPaths(appId).agentTokensDir` = `bots/<appId>/agent-tokens/`，0700；
  - 文件 `<grantId>.tok`，0600，`open(…, 'wx')` 写完、关掉，才把路径交给 Codex；`grantId` 是 16 字节随机数的十六进制，不是秘密；
  - 登记表建好时（bot 子进程起来时）删掉这个目录里所有名字符合 `^[0-9a-f]{32}\.tok$` 的文件，别的不动，不递归；
  - 同一条会话里 Codex 重起 MCP server，文件还在，照样读得到。
- R12：host 不存令牌，只核格式、转发（4.12）。
- R13：设置调用的授权属于一个具体的回合，不属于 grant：
  - 每个回合有一个回合授权（`TurnAuth`）：`id` 是 entries 里单调递增的整数，不复用；还有触发消息 id、触发人、是不是人触发、一个 `AbortController`。
  - 设置类调用在 `call()` 一进来、同步地绑定到发起它的回合授权上（来源怎么证明见 4.4 第 3b 步），以后排队、开始、提交都认这一个，不再看"现在是哪一轮"。
  - 回合关闭、被新回合替换、被他人插话、失去人触发条件、grant 作废：同步让该回合授权失效，并 abort 它的 `AbortController`，这个回合上所有还没提交的设置调用一起 abort。
  - 管理员被撤、开关被关没有事件可挂：由提交处的现时授权检查（4.4 第 3 步）接住。
  - 读类工具不受影响。已经提交的写入不撤销。
  - Codex 的 grant 只认 attach 之后开的第一个回合，这个回合一关，这个 grant 的设置类调用永远回 `turn-ended`（Codex 每轮恢复，R3，所以一个 grant 本来就只服务一轮）。Claude 的 grant 跨很多轮，靠 tool-use 关联（4.7）。

### 4.4 校验顺序和回复（s46）

`entry.call(name, args, origin)` 和 s46b 的 `callByToken` 走同一个函数，按下面的顺序，第一条不过就回。

**预算**：`call()` 一进来先定截止时间 `deadline = 现在 + 70 秒`，排队的时间算在里面（第 5 步）。

1. 凭证：
   - 作废了：`revoked`（`thread.isAlive()` 为假的顺手作废，R4）。s46b 的路由上对应 401。
   - pending 段（R2）：`call` 回 `not-ready`，不进第 2 步以后。
2. 工具：表里有这个名字。不过：`unknown-tool`。
3. 只对设置类。a 到 c 写成一个函数 `authorizeNow(auth)`，在**接纳（这里）、轮到开始、提交点前的 `guard()`（4.4a）**三处调同一个：
   - a. 私聊：`place.kind === 'p2p'`。不过：`refused`、`not-dm`。
   - b. 来源回合：先确定发起这次调用的回合授权 `auth`（只在接纳时定一次，之后不换）：
     - Claude：用 `origin.toolUseId` 查线程记下的 tool-use 到回合授权的表（4.7）。查不到、没带 id：`refused`、`unknown-origin`。**不**拿"现在是哪一轮"顶替。
     - Codex：`auth` 是这个 grant 的第一个回合授权（R13）；这个回合已经关了：`refused`、`turn-ended`。
     - 查到的 `auth` 已失效（关了、被替换了）：`turn-ended`；不是现在这一轮：也是 `turn-ended`，旧轮的请求晚到就是这样被拒的，用不到新轮的消息当回执。
     - `auth` 还有效，但不算人触发（4.5，含他人插话之后）：`not-human-turn`。再看 `isAdmin(auth.requesterOpenId)`（现查）。不过：`not-admin`。
   - c. 开关：`chatSettingsOn()`（现查）。不过：`switch-off`。
   - d. 排队：同一个 grant 的设置类调用一个接一个跑。排队最多 8 个，满了回 `busy`。队里每一项带着自己的 `auth` 和 `deadline`。轮到时调 `authorizeNow(item.auth)`，不过就按那一条回，处理函数不跑。
4. 参数：zod 校验。不过：`bad-args`，message 只写字段路径和原因，不带值。
5. 跑：
   - 一个 grant 同时最多 4 个调用（读类直接跑，设置类在队里只算一个）。超了 `busy`。
   - 70 秒是绝对截止时间，**从接纳算起，含排队**。每个调用接纳时设一个定时器到 `deadline`：到点时它如果还在队里，就从队里移出、回 `timeout`、处理函数永远不跑；如果已经在跑，回 `timeout` 并 abort。运行时能用的只有剩下的预算。队位同时放掉，不会占住后面的。
   - 传给处理函数的 `ctx.signal` 是三者合一：deadline 到了、grant 作废、该调用的 `auth` 失效，任一个就 abort。已经过了 `guard()` 的调用除外（4.4a）。
   - 写设置只在提交点前的 `guard()` 过了以后生效（4.4a）；超时或失效的调用不会迟到提交。guard 过了的调用已提交，不撤销，按 4.4a 的"结算"回复。
   - grant 作废时 abort 正在跑的，回 `revoked`。已经过了 `guard()` 的除外，按 4.4a 结算。
   - 结果序列化后超过 256 KiB，回 `failed`、"结果太大"，不带内容。
   - 工具抛错，回 `failed`、"vonvon 这一步出错了"；原错只进日志（日志会替换令牌，4.8）。`ToolRefusal` 不算抛错，按它带的 code 回。
6. 每次调用一行日志：`log.info('agent', 'call', { tool, code, kind: place.kind, ms })`。不记参数、结果、令牌、聊天 id。

**超时的先后**：工具 70 秒（从接纳起） < host 等子进程 75 秒（从路由发出 IPC 起） < MCP server 等 host 80 秒 < Codex `tool_timeout_sec` 90 秒。接纳比 IPC 发出晚（只多一次 IPC 往返，本机上远小于 5 秒），所以里层总比外层先超时，外层看到的是 bot 子进程回的明确 `timeout`，不会出现 host 已经超时、bot 里还排着队的项。

给 agent 的话：

| code / reason | message |
|---|---|
| `not-ready` | vonvon 还没准备好这条会话的工具，稍后再试。 |
| `revoked` | 这条会话的 vonvon 工具已经失效（会话结束了，或者 daemon 重启过）。不要重试，接着做别的。 |
| `unknown-tool` | 没有这个工具。 |
| `not-dm` | 设置只能在私聊里改。请对方去私聊里跟我说。 |
| `not-human-turn` | 这一轮不是主人或管理员发消息直接触发的，不能改设置。 |
| `turn-ended` | 发起这次改动的那一轮已经结束了，不能改设置。请对方重新说一遍。 |
| `unknown-origin` | vonvon 认不出这次改动是哪一轮发起的，不能改设置。请对方重新说一遍。 |
| `not-admin` | 只有主人和管理员发消息触发的那一轮能改设置。 |
| `switch-off` | 主人关了私聊里的"聊天改设置"，要改请去桌面端或网页。 |
| `bad-args` | 参数不对：<字段路径>：<原因>。 |
| `busy` | vonvon 手上的事太多，稍后再试。 |
| `timeout` | vonvon 这一步超时了。 |
| `failed` | vonvon 这一步出错了。（或"结果太大"） |
| `failed`（guard 过了以后出错，4.4a） | 提交时出错，设置可能已经改了。先查一下现在的设置，再决定要不要重试。 |

为什么是这个顺序：
- 凭证在最前：没有凭证的调用方什么也问不出来。
- 私聊在触发人之前：群里谁来都拒，不用看是谁。
- 开关在最后：前面都过了才说"主人关了开关"，这句话只对能改的人有意义。
- 来源回合在触发人之前：先知道是哪一轮发起的，才谈得上那一轮是不是人触发。认不出来源的调用不借新一轮的身份，直接拒。

### 4.4a 提交点（s46）

第三轮审查指出：只在 `ctx.commit` 入口查一次不够。回调里 `await` 以后（等锁、读盘、准备），回合可能已经关了、管理员可能已经被撤、截止时间可能已经到了，回调接着写，照样迟到提交。只把类型里的 `Promise` 删掉也不解决：今天的写入口本身就要等锁、读盘。所以把检查下沉到真正生效的那一步前面。

**提交点**：设置真正生效的那一步。按今天的写路径：
- bot 子进程自己写文件（项目登记 `projects.json`、bot 登记、`config.json` 这类）：写入口拿到锁、读盘、校验、写好临时文件以后的那次 `rename(tmp, 文件)`。项目登记就是 `D/project/registry.ts` 里 `writeStored` 末尾的 `rename`；`ownProjects` 的跨进程锁最多等 30 秒，这段等待在提交点之前。
- 交给 host 的设置服务写（s47 按 v1-plan 走 s07a 的同一组命令函数，host 的 `D/admin/settings.ts` 用 `mutateProject` 落盘）：bot 子进程发出那一个写请求的时刻。请求里带 `notAfter`（这次调用的 `deadline`，绝对时间），host 的写入口在它自己的 `rename` 之前同步查 `Date.now() <= notAfter`，过了就不写，回一个"已过期、没改"的错，bot 子进程回 `timeout`。这条 host 侧的检查只看时间，回合和授权以 bot 子进程发出时为准。
- 改内存里的状态：那一句同步赋值。
- 飞书这类外部请求（s47 以后的建群、拉人）：发出请求的时刻。发出以后就算已提交。

**guard**：`commit` 交给 `write` 一个同步函数 `guard`。写的一方在提交点前一行调它，调完在同一个同步段里发出提交，中间没有 `await`。例如 `guard(); await rename(tmp, file)`：`rename` 在 guard 返回的同一段里发出。guard 依次做下面几件事，全在一个同步段里：
1. 这次调用的状态还是 `running`：没有超时、没有被作废、没有被结算过。
2. `authorizeNow(auth)`（4.4 第 3 步）。
3. `Date.now() <= deadline - 3 秒`。留 3 秒给落盘、放锁和回复，见下面"结算"。
4. 都过了，把调用标成 `committed`。从这时起，到期、grant 作废、关回合都不再改这次调用的回复，也不再 abort 它的 `signal`。

guard 不过就抛 `ToolRefusal(code)`，code 和 4.4 第 3、5 步一样：`turn-ended`、`not-human-turn`、`not-admin`、`switch-off`、`revoked`、`timeout`。写的一方删掉自己的临时文件、放锁，原样抛出，什么都没生效。

**`commit` 自己**：
- 入口先调一次 `authorizeNow`，早点拒，省得白等锁。这一次不是提交点。
- 然后调 `write(guard)`，等它结束。
- `write` 正常结束，但 guard 一次也没调过：回 `failed`，记一行 `log.error('agent', 'commit-unguarded', { tool })`。这次写可能没经检查就生效了，测试和开发期就要发现。
- guard 被调第二次：抛普通错，回 `failed`。

**写入口（s46 只改一处）**：
- 项目登记的 `updateProject`、`mutateProject` 加可选的第三个参数 `{ beforeCommit?: () => void }`，经 `ownProjects` 传到 `write`、`writeStored`。
- 在 `await writeFile(tmp)` 之后、`rename` 之前同步调它。
- 它抛错时：`unlink(tmp)`（失败也忽略），照常放锁（`ownProjects` 已经会放），再把错抛出去。
- 不传时行为和今天一样。`removeProject` 和建群绑定不加，设置工具用不到。
- 别的写入口（bot 登记、`saveConfig`、记忆和 skill 文件、host 设置服务的 `notAfter`、飞书请求）由 s47、s55、s56a 在第一次用到时照同样的样子加，每加一个都带一条"停在提交点之前"的测试（5.1 第 38、39 条的写法）。

**结算：已提交、落盘还没完**
- guard 过了以后 `write` 正常结束：回 `ok`。过了 70 秒也回 `ok`，记一行 `late-commit`。这时不回 `timeout`：回了，agent 会以为没改，再改一次。
- guard 过了以后 `write` 抛的是 `ToolRefusal`：写的一方保证什么都没改（比如 host 按 `notAfter` 回了"已过期、没改"，换成 `ToolRefusal('timeout')`），按它的 code 回。
- guard 过了以后 `write` 抛别的错：回 `failed`，用上表"guard 过了以后出错"那一句。项目登记这条路上 `rename` 是原子的，抛错一般就是没改；但登记表分不出写入口是在 `rename` 之前还是之后抛的（比如放锁失败），所以一律说"可能已经改了"。
- 已提交的不回滚（5.1 第 30 条）。回执由 s47 按 daemon 的已提交结果写（product.md 3.7）。
- 3 秒余量：guard 最晚在第 67 秒过，落盘、放锁、回复有 3 秒，加上 host 的 5 秒（4.4"超时的先后"）。正常磁盘下，外层收到的是 bot 回的确定结果。
- 已知限制：磁盘卡住超过这段时间时，外层会先看到超时，写却落了盘。日志 `late-commit` 记下，不为它加取消协议。交给 host 写的那条路由 `notAfter` 兜住：过了 `deadline` 就不写。

- HTTP：`node:http` 的 `request`，`agent: false`；头 `Content-Type: application/json`、`Authorization: Bearer <令牌>`、`Content-Length`；80 秒没回就断开。

  | 路由回的 | 给 agent 的 |
  |---|---|
  | 200，`ok: true` | `content` 一段文字（结果的 JSON）；结果是对象时再带 `structuredContent` |
  | 200，`ok: false`（含 pending 段的 `not-ready`） | `content` 是 `message`，`isError: true` |

  | 502 | "vonvon 的 bot 进程没有回应，稍后再试。"，`isError` |

  | 80 秒超时 | "vonvon 没在 80 秒内回应。"，`isError` |

- 除了协议消息，不往 stdout、stderr 写令牌、地址、文件路径。

### 4.12 host 的路由（s46b）

新建 `D/server/agent-route.ts`：`createAgentRoute({ call })` 回 `{ handle(req, res): boolean; beginDrain(): void; release(): void }`。

`startApi` 的参数加 `agentCall?: (appId: string, req: { token: string; body: AgentCallBody }) => Promise<AgentCallReply | 'unauthorized'>`。不传时不建路由，和今天一样一律 404，旧测试和别的调用方不受影响。

`D/server/http.ts`：
- `createServer` 的处理函数（`:129`）先 `if (route?.handle(request, response)) return;`，再 `serveWebUi`。
- `beginDrain`（`:66`）第一件事 `route?.beginDrain()`（同步置位）。
- `release`（`:90`）在 `server.close` 之前 `route?.release()`：还开着的路由请求，直接 `socket.destroy()`。
- `D/server/ws.ts` 导出 `loopbackHost`。

按顺序查，第一条不过就回：

| # | 条件 | 回 |
|---|---|---|
| 1 | 路径整个匹配 `^/agent/v1/bots/([A-Za-z0-9_-]{1,64})/call$`，不带查询串 | 不匹配：不归路由管，交给 `serveWebUi`，和今天一样 |
| 2 | 没在 drain | 503 `{ ok: false, code: 'draining' }` |
| 3 | 方法是 POST | 405，带 `Allow: POST` |
| 4 | `Host` 是本机（`loopbackHost`），没有 `Origin` 头 | 403 |
| 5 | `Content-Type` 是 `application/json`（可以带 `; charset=utf-8`） | 415 |
| 6 | `Authorization` 是 `Bearer ` 加令牌的格式 | 401 |
| 7 | 请求体不超过 64 KiB，10 秒内收完 | 413（不再读，断开）；408 |
| 8 | JSON，且是 `{ v: 1, op: 'list' }` 或 `{ v: 1, op: 'call', tool, args: 对象 }` | 400 |
| 9 | 正在转发的不到 32 个 | 503 `{ ok: false, code: 'busy' }` |
| 10 | 转发 `agentCall(appId, …)` | `'unauthorized'` → 401；回复 → 200；抛错 → 502 `{ ok: false, code: 'unavailable' }`。内联、托管两种模式都交给 `agent-route.ts` 同一个 `replyOf(result)`，进它的只有未包装的 `AgentCallReply \| 'unauthorized'`（IPC 的包装在 4.13 解开） |

- 所有回复：JSON，`Cache-Control: no-store`，`Connection: close`。
- 401 的回复体永远是同一串字节：`{"ok":false,"code":"unauthorized"}`（34 字节，没有尾换行；状态 401，头同上面，`Content-Type: application/json`）。appId 不存在、子进程没在跑、令牌不对（同 bot 路径下格式对的错令牌、旧令牌）、令牌作废、线程死了，都是它，托管和内联两种模式一样。
- 网页跨域发的 POST：浏览器一定带 `Origin`（第 4 条挡）；带 `Authorization` 的跨域请求要先发 OPTIONS，第 3 条回 405、不带 CORS 头。
- 路由不记每个请求的日志。只有回 5xx 时 `log.warn('agent', 'route', { status })`。不记路径、头、请求体。

### 4.13 IPC 和地址（s46b）

- `D/admin/ipc.ts`：`AdminIpcOp` 加 `{ kind: 'agentCall'; token: string; body: AgentCallBody }`。
