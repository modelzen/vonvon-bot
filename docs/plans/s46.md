### 4.1 选哪种

| 方案 | 做法 | 结论 |
|---|---|---|
| A 令牌放进 agent 的 shell 环境 | v1-plan 原来的写法"经环境变量交给 agent" | 不选。两家都不滤变量（e04、e04b），agent 跑的每个命令都拿得到。Codex 只读、读写档的 shell 里 Node 起不来，关网也连不上本机（e04），拿到也用不上 |
| B 两家都用 stdio MCP，令牌放进 MCP 的启动环境 | 开工要点原来的方向 | Claude 不选：SDK 把 stdio MCP 的 `env` 拼进命令行参数（3.4），同机进程用 `ps` 读得到。Codex 改用 D |
| C Claude 用 SDK 内建 MCP（`createSdkMcpServer`） | 工具跑在 bot 子进程里，不经网络 | Claude 选。没有令牌，也就没有令牌可漏。各档、开网关网都到得了。s31 的实测 J 调通过同样的东西（3.4） |
| D Codex 用 stdio MCP，令牌放进 0600 的文件，启动环境只放地址和文件路径 | 文件在 `bots/<appId>/agent-tokens/` | Codex 选。启动环境、命令行参数、Codex 记下的会话配置里都只有路径，`ps`、`/proc/<pid>/environ` 看不到令牌。读这个目录和读 `local-credential` 是同一类权限：Codex 受限档读不到工作区外，Claude 受限档靠 s31b 的 `denyRead` 挡住 `bots/`，完全访问档本来就读得到 `local-credential` |
| E Codex 的 `dynamicTools` | app-server 0.163.0 的实验字段 | 不选。只有 `ThreadStartParams` 有，`ThreadResumeParams` 没有，而 Codex 每轮都 resume；0.156.1 没验证 |
| F daemon 另开 Unix socket，沙箱放行 | e04b 写的备选 | 不选。要放宽沙箱（`allowUnixSockets`）；Codex 关网档连 socket 也到不了（e04） |
| G 命令函数跑在 MCP server 进程里，用 s07a 的第二种连接 | s47 开工要点原来的写法 | 不选。判断"这一轮是谁触发的"要用 bot 子进程里的回合状态。Codex 每轮 resume 都重起 MCP server，进程越小起得越快。路由只开放"列工具""调工具"两种请求，面比开放管理方法小（s08：会话令牌碰不到机器的 `service`） |

所以：一张登记表在 bot 子进程里，Claude 进程内直接调，Codex 经 MCP server、host 路由、IPC 调到同一张表。校验只写一份。

### 4.2 凭证：归属和生命周期

凭证（grant）是登记表里的一项。Codex 的 grant 带一个令牌；Claude 的不带，工具直接绑在 grant 上。

- R1：一个 `AgentThread` 对象一个 grant。grant 在调 `startThread`、`resumeThread` 之前发，绑定这个 bot（一个 bot 子进程一张表）和这条会话所属的聊天（place），以后不换绑。
- R2：起会话或恢复成功后 `attach(thread)`；失败 `revoke('start-failed')`。还没 attach 的 grant，调什么都回 `not-ready`。
- R3：每次恢复都是新 grant；Codex 的还是新令牌。Codex 每轮恢复（3.2），所以每轮换令牌。
- R4：作废的时机：
  - `thread.close()` 的第一步（两家的 `close()` 各加一行，在关进程之前）；
  - 调用时 `thread.isAlive()` 为假（进程死了，没人调 `close`）；
  - orchestrator `shutdown()` 一开始 `closeAll('shutdown')`；
  - bot 子进程退出：表只在内存里。daemon 重启后旧令牌一律不认。
- R5：作废后立刻从表里删掉，删掉令牌文件（s46b）。之后拿它来调，一律按"没有这个令牌"处理。
- R6：令牌的明文只在这几处：令牌文件；MCP server 进程的内存；它发给 host 的请求头；host 转发给 bot 子进程的那条 IPC。bot 子进程的表里只存 SHA-256。令牌不进日志、错误信息、卡片、环境变量、命令行参数。
- R7：令牌是 `vvs1_` 加 32 字节随机数的 base64url（43 个字符），共 48 个字符。
- R8：比对：表的键是令牌 SHA-256 的十六进制；查到以后再用 `timingSafeEqual` 比 32 字节摘要，对上才算。代码里不对令牌字符串用 `===`、`startsWith` 一类比较。
- R9：不跨群、不跨 bot：grant 绑 place；host 按路径里的 appId 只交给那个 bot 的子进程，别的 bot 的令牌在那里查不到。
- R10：一个 bot 同时活着的 grant 最多 1024 个。超了，新发的是死的（调用回 `not-ready`），日志 `agent entry-cap`。每次发新的之前，顺手删掉线程已经死了的。
- R11：令牌文件（s46b）：
  - 目录 `botPaths(appId).agentTokensDir` = `bots/<appId>/agent-tokens/`，0700；
  - 文件 `<grantId>.tok`，0600，`open(…, 'wx')` 写完、关掉，才把路径交给 Codex；`grantId` 是 16 字节随机数的十六进制，不是秘密；
  - 登记表建好时（bot 子进程起来时）删掉这个目录里所有名字符合 `^[0-9a-f]{32}\.tok$` 的文件，别的不动，不递归；
  - 同一条会话里 Codex 重起 MCP server，文件还在，照样读得到。
- R12：host 不存令牌，只核格式、转发（4.12）。

### 4.4 校验顺序和回复（s46）

`entry.call(name, args)` 和 s46b 的 `callByToken` 走同一个函数，按下面的顺序，第一条不过就回：

1. 凭证：grant 没作废、已 attach、`thread.isAlive()` 为真。不过：`revoked`（进程死了顺手作废）或 `not-ready`。s46b 的路由上这一步对应 401。
2. 工具：表里有这个名字。不过：`unknown-tool`。
3. 只对设置类：
   - a. 私聊：`place.kind === 'p2p'`。不过：`refused`、`not-dm`。
   - b. 触发人：这条线程有打开的回合，回合算"人触发"（4.5）。不过：`not-human-turn`。再看 `isAdmin(requesterOpenId)`（调用时现查）。不过：`not-admin`。
   - c. 开关：`chatSettingsOn()`。不过：`switch-off`。
   - d. 排队：同一个 grant 的设置类调用一个接一个跑。排队最多 8 个，满了回 `busy`。轮到时重查第 1 步、3b（还是同一个回合对象，还算人触发）、3c，不过就按那一条回。
4. 参数：zod 校验。不过：`bad-args`，message 只写字段路径和原因，不带值。
5. 跑：
   - 一个 grant 同时最多 4 个调用（读类直接跑，设置类在队里只算一个）。超了 `busy`。
   - 70 秒超时，回 `timeout`，同时 abort。
   - grant 作废时 abort 正在跑的，回 `revoked`。工具要看 `signal`，提交前查一次（s47 的设置工具照这条写）。
   - 结果序列化后超过 256 KiB，回 `failed`、"结果太大"，不带内容。
   - 工具抛错，回 `failed`、"vonvon 这一步出错了"；原错只进日志（日志会替换令牌，4.8）。
6. 每次调用一行日志：`log.info('agent', 'call', { tool, code, kind: place.kind, ms })`。不记参数、结果、令牌、聊天 id。

给 agent 的话：

| code / reason | message |
|---|---|
| `not-ready` | vonvon 还没准备好这条会话的工具，稍后再试。 |
| `revoked` | 这条会话的 vonvon 工具已经失效（会话结束了，或者 daemon 重启过）。不要重试，接着做别的。 |
| `unknown-tool` | 没有这个工具。 |
| `not-dm` | 设置只能在私聊里改。请对方去私聊里跟我说。 |
| `not-human-turn` | 这一轮不是主人或管理员发消息直接触发的，不能改设置。 |
| `not-admin` | 只有主人和管理员发消息触发的那一轮能改设置。 |
| `switch-off` | 主人关了私聊里的"聊天改设置"，要改请去桌面端或网页。 |
| `bad-args` | 参数不对：<字段路径>：<原因>。 |
| `busy` | vonvon 手上的事太多，稍后再试。 |
| `timeout` | vonvon 这一步超时了。 |
| `failed` | vonvon 这一步出错了。（或"结果太大"） |

为什么是这个顺序：
- 凭证在最前：没有凭证的调用方什么也问不出来。
- 私聊在触发人之前：群里谁来都拒，不用看是谁。
- 开关在最后：前面都过了才说"主人关了开关"，这句话只对能改的人有意义。

### 4.5 回合：哪一轮算"人触发"（s46）

`openTurn(thread, facts)` 用当前这一轮的 `currentTurn` 填 `facts`。人触发 = 下面全都成立：
- `requesterKind === 'user'`，`requesterOpenId` 有值；
- `triggerMessageId` 有值（`currentTurn.seen?.id`，真有一条飞书消息）；
- 不是 🔁 重试（`replayText` 没有值）；
- 不是智能模式自己插话（`initiative`），也不是被叫醒（`wake`）；
- 这一轮里没有别人插过话（下面）。

Rakazo 第二轮列的几种，在这里的结果：

| 回合 | 结果 | 为什么 |
|---|---|---|
| bot 发消息引出的一轮 | 不算 | `requesterKind` 是 `bot` |
| 完成提醒 | 不算 | 它不是一轮，不开回合 |
| 恢复续跑：/goal 自动续 | 不算 | 走 `launchGoalRun`，不开回合 |
| 压缩引出的一轮 | 不算 | `/compact` 在 `:7233`，回合在 `:7049` 已经关了 |
| 两轮之间的后台进程 | 不算 | 没有打开的回合 |
| 🔁 重试 | 不算 | 计划默认，待 owner 定（第 9 节） |
| 云文档评论、桌面端清空后的会话 | 不算 | 不走 `launchRun` 的回合循环；而且不是私聊 |
| 排队的下一条，别人发的 | 按那个人算 | 每轮重新 `openTurn` |

  - `VONVON_AGENT_TOKEN_FILE` 是绝对路径、以 `.tok` 结尾；读出来去掉首尾空白，必须是令牌的格式；
  - 有一样不对：stderr 写一行固定的 `vonvon agent entry: bad launch (url)`（或 `file`、`token`），不带值，退出码 2。
- stdio 上是 JSON-RPC 2.0，一行一条：
  - 一行超过 1 MiB：回 -32600，丢掉这一行。
  - `initialize`：回 `{ protocolVersion, capabilities: { tools: {} }, serverInfo: { name: 'vonvon_bot', version: '1' } }`。客户端给的版本在 `['2024-11-05', '2025-03-26', '2025-06-18']` 里就照抄，否则回 `'2025-06-18'`。4.0 C 记下 Codex 实际发的版本。
  - `notifications/*`：不回。`ping`：回 `{}`。
  - `tools/list`：POST `{ v: 1, op: 'list' }`，回 `{ tools }`；出任何错回 `{ tools: [] }`。
  - `tools/call`：POST `{ v: 1, op: 'call', tool: params.name, args: params.arguments ?? {} }`，按下表回。
  - 别的带 `id` 的方法：-32601。JSON 不合法：-32700，`id: null`。数组（批量）：-32600。
  - 请求并发处理，按 `id` 回。
  - stdin 结束：退出码 0。
- HTTP：`node:http` 的 `request`，`agent: false`；头 `Content-Type: application/json`、`Authorization: Bearer <令牌>`、`Content-Length`；80 秒没回就断开。
- `tools/call` 的结果：

  | 路由回的 | 给 agent 的 |
  |---|---|
  | 200，`ok: true` | `content` 一段文字（结果的 JSON）；结果是对象时再带 `structuredContent` |
  | 200，`ok: false` | `content` 是 `message`，`isError: true` |
  | 401 | "这条会话的 vonvon 工具已经失效（会话结束了，或者 daemon 重启过）。不要重试，接着做别的。"，`isError` |
  | 503 | "vonvon 正在停止或者太忙，稍后再试。"，`isError` |
  | 502 | "vonvon 的 bot 进程没有回应，稍后再试。"，`isError` |
  | 别的状态码、连不上 | "连不上 vonvon。"，`isError` |
  | 80 秒超时 | "vonvon 没在 80 秒内回应。"，`isError` |

- 除了协议消息，不往 stdout、stderr 写令牌、地址、文件路径。

### 4.12 host 的路由（s46b）

新建 `D/server/agent-route.ts`：`createAgentRoute({ call })` 回 `{ handle(req, res): boolean; beginDrain(): void; release(): void }`。

`startApi` 的参数加 `agentCall?: (appId: string, req: { token: string; body: AgentCallBody }) => Promise<AgentCallReply | 'unauthorized'>`。不传时不建路由，和今天一样一律 404，旧测试和别的调用方不受影响。

`D/server/http.ts`：
- `createServer` 的处理函数（`:129`）先 `if (route?.handle(request, response)) return;`，再 `serveWebUi`。
- `beginDrain`（`:66`）第一件事 `route?.beginDrain()`（同步置位）。
- `release`（`:90`）在 `server.close` 之前 `route?.release()`：还开着的路由请求，直接 `socket.destroy()`。
- `D/server/ws.ts` 导出 `loopbackHost`。

按顺序查，第一条不过就回：

| # | 条件 | 回 |
|---|---|---|
| 1 | 路径整个匹配 `^/agent/v1/bots/([A-Za-z0-9_-]{1,64})/call$`，不带查询串 | 不匹配：不归路由管，交给 `serveWebUi`，和今天一样 |
| 2 | 没在 drain | 503 `{ ok: false, code: 'draining' }` |
| 3 | 方法是 POST | 405，带 `Allow: POST` |
| 4 | `Host` 是本机（`loopbackHost`），没有 `Origin` 头 | 403 |
| 5 | `Content-Type` 是 `application/json`（可以带 `; charset=utf-8`） | 415 |
| 6 | `Authorization` 是 `Bearer ` 加令牌的格式 | 401 |
| 7 | 请求体不超过 64 KiB，10 秒内收完 | 413（不再读，断开）；408 |
| 8 | JSON，且是 `{ v: 1, op: 'list' }` 或 `{ v: 1, op: 'call', tool, args: 对象 }` | 400 |
| 9 | 正在转发的不到 32 个 | 503 `{ ok: false, code: 'busy' }` |
| 10 | 转发 `agentCall(appId, …)` | `'unauthorized'` → 401；回复 → 200；抛错 → 502 `{ ok: false, code: 'unavailable' }` |

- 所有回复：JSON，`Cache-Control: no-store`，`Connection: close`。
- 401 的回复体永远是同一串字节：`{"ok":false,"code":"unauthorized"}`。appId 不存在、子进程没在跑、令牌不对、令牌作废，都是它。
- 网页跨域发的 POST：浏览器一定带 `Origin`（第 4 条挡）；带 `Authorization` 的跨域请求要先发 OPTIONS，第 3 条回 405、不带 CORS 头。
- 路由不记每个请求的日志。只有回 5xx 时 `log.warn('agent', 'route', { status })`。不记路径、头、请求体。
