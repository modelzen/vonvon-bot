# s53 飞书应用角色

## 1. 做什么

按 product.md 第 6 节，让飞书应用所有者、管理员和开发者能管理 bot，扫码人和本机管理员继续保留权限。依赖已完成的 s01 可选权限申请。

## 2. 范围

读取应用所有者和协作者，保存十分钟缓存，在全部管理权限判断中使用三种来源的并集。设置页和私聊管理卡标出来源，飞书来源和扫码人不能由本机移除。不修改飞书上的角色，不增加权限申请或产品范围。

## 3. 现在的代码

`config/schema.ts` 的 `resolveOwner` 和 `isAdmin` 只看本机配置；`bot/bridge.ts` 负责一个 bot 的连接生命周期。`admin/settings.ts`、协议的 agent 设置视图以及 `SettingsPanel.tsx` 管理本机名单；`card/dm-cards.ts` 和 `bot/handle-message.ts` 提供私聊名单卡。

## 4. 怎么改

新增 `config/app-roles.ts`。按 bot 的 appId 和租户存 `app-roles.json`，包含所有者、管理员集合与成功时间；完整成功后以临时文件加 rename 发布，host 和 worker 同步读取同一份结果。应用信息用实际 appId、`user_id_type=open_id` 和 `lang=zh_cn`；协作者只纳入 administrator/developer，owner 从应用信息取，operator 不纳入。

bridge 在接收消息前尝试刷新，缓存未过期不请求。下一次请求安排在成功时间十分钟后；错误后十分钟再试，保留上次完整结果。从未成功时只认扫码人和本机名单。整个刷新共用十秒超时，刷新合并并发调用；关闭时取消并等待在途请求，不发布关闭后返回的结果。

`resolveOwner` 优先飞书所有者，`isAdmin` 保留扫码者并加入飞书管理员；配置中的 ownerOpenId 仍代表原扫码人，不被刷新写入。设置和名单卡展示各来源，删除操作在服务端校验，飞书身份和扫码者不可移除。本地同一个人也有飞书身份时仍不可删除其管理身份。

## 5. 测试

新增 main 必败用例：飞书所有者和开发者授权、运营拒绝；扫码和本机来源保持权限；成功刷新撤销已移除协作者；缓存十分钟内不重查，重启复用磁盘缓存；接口失败保留上次结果，没有成功结果回退；并发只查一次；关闭取消请求且迟到结果不发布。协议/设置测试覆盖来源和飞书身份删除保护，现有私聊入口测试验证管理门禁。

## 6. Codex 的自测

JP-VPS 执行。使用 #422 的 Bot 6，只读查询两接口，核对应用所有者和协作者类型，不发群消息。命令通过 bot 自己的 tenant_access_token 调 `GET /application/v6/applications/<appId>?user_id_type=open_id&lang=zh_cn` 和 `/collaborators?user_id_type=open_id`；预期 code 0、所有者 type 2、协作者名单完整。

在隔离 HOME/VONVON_HOME 下运行定向测试、typecheck、lint 和 build，重命令使用 heavy 锁。网页验收查看管理名单来源、飞书行没有移除入口；无可用网页控制时如实记录未操作，不能以代码检查冒充点击验收。无 macOS 外壳改动。

## 7. 文档

product.md 第 6 节的产品行为不变。v1-plan 勾选 s53 并记录实现；十分钟缓存默认值已在第 6 节承诺，无新增配置。

## 8. 验收要点

- 权限是飞书名单、扫码人、本机名单并集；运营不算。
- 完整快照十分钟缓存并持久化，失败保留 last good。
- 租户和 appId 隔离；停止后不发布刷新结果。
- 所有管理入口共用 isAdmin，飞书身份不可在本机删除。
- 页面和私聊名单卡标明来源。
- diff 里没有真实 id、密钥、本机路径。

## 9. 风险和行数

涉及并发刷新、关闭取消和接口错误路径。预计 500–700 行，低于 1500 行；不引入后台子进程或迁移本机名单。
