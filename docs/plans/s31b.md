### 4.2a Linux 上给 Claude 进程套一层挂载命名空间（普通空工作区）

**2026-10-23 起不做**（见开头的修订），换成 4.2b。下面留作当时的分析：为什么起不来那一段仍然是 4.2b 的依据。

**为什么起不来**：查的是 SDK 0.3.296 带的 Claude Code 2.1.296，沙箱代码编在 `claude-agent-sdk-linux-x64/claude` 里，`SRT_DEBUG=1` 打出的字串和下面说的对得上。
- 可写目录里缺了 `.gitconfig`、`.gitmodules`、`.bashrc`、`.mcp.json` 这类危险文件时，沙箱要在那个位置挂一个只读的 `/dev/null` 当占位，免得 agent 新建它们。bubblewrap 挂占位之前，要先在那里建一个挂载点。
- cwd 本身是只读档的 `denyWrite`。正常情况下，运行时知道"只读目录里本来就建不出文件"，会打 `Skipping non-existent deny path inside a read-only denied directory (already uncreatable)`，不挂占位。
- 但这个只读目录如果落在某个 `denyRead` 目录里（那个目录被 tmpfs 盖住，再由 `allowRead` 把 cwd 放回来），运行时就不认这一条，照样挂占位。cwd 是只读的，挂载点建不出来，会话起不来。运行时自己的警告也这么写："bubblewrap cannot create a placeholder's mount point there"。
- 4.2 的名单正好是这样：`denyRead` 有 `<dataRoot>/projects`，`allowRead` 放回 cwd。所以默认位置下的空工作区，在只读档起不来。

**不选的路**：
- 只把 cwd 的上级换成沿路的兄弟（#461 第一版）：不选。沙箱名单在起进程时就定了，一轮里新建的兄弟（比如另一个群刚绑定、建了默认目录、写了文件），这一轮里 Bash 读得到，下一轮重开也收不回已经读到的内容。兄弟的名字也会露出来。
- 关沙箱、删 `denyWrite`、放开数据目录、往用户工作区放占位文件：都不保持原来的边界，不选。

**怎么改**：只在 Linux 的 qa、write 档，而且有 `readScope` 时，vonvon 用 SDK 的官方选项 `spawnClaudeCodeProcess` 自己起 Claude 进程，外面套一层 bubblewrap，只建挂载命名空间。
- 这层命名空间里，4.2 的 deny 项按下面处理：
  - 目录：挂空的 tmpfs（`--tmpfs`）。原样和真实路径不同时，两处都挂。
  - 文件：挂只读的 `/dev/null`（`--ro-bind /dev/null`）。
- 4.2 的 allow 项（cwd、本群记忆、bot 的 skill、`SECRETS_GET_FILES` 里在 `bots/` 下的），落在某个被盖住的目录里时，从主机挂回原处：
  - cwd 和本群记忆：`--bind`，可写不可写由里层沙箱管。
  - 其余：`--ro-bind`。
  - 原样路径和真实路径不同时，两处都挂真实路径。
- 先挂 tmpfs（浅的在前），再挂回 allow 项。bubblewrap 在 tmpfs 里自己建挂载点。
- 其余参数：`--dev-bind / /`（别的都照主机），`--chdir <cwd>`，`--die-with-parent`。不加 `--unshare-pid`、`--unshare-net`，网络由里层沙箱管。
- 进程照判断模型那条路的写法（`backend.ts` 的 `spawnClaudeCodeProcess` 用 `OwnedProviderProcess`），关会话时整组停掉。
- 参数由纯函数 `outerMountArgs(scope, cwd, realCwd, fs)` 算：传进去的 fs 用 `lstat`、`realpath`；不存在的项照 4.2 去掉。

**为什么能挡住，而且整个会话都挡住**：
- 被盖住的目录在这层命名空间里是空的 tmpfs，只有挂回来的那几项。主机上之后新建的兄弟目录、新写的文件，在 tmpfs 里看不到。所以一轮跑到一半另一个群绑定、建目录、写文件，这条会话的 Bash 和 Read 都读不到，连名字也看不到。
- 里层 SDK 沙箱的 `denyRead` 去掉"包含 cwd 的那些项"（它们在外层已经盖住了）；其余项照旧给里层，多挡一层。这样 cwd 上面没有里层的 tmpfs，运行时认得出 cwd 是只读的，不再挂占位，空工作区起得来。
- `decide()` 和钩子照旧用 4.2 的粗名单。
- 本群记忆目录、skill 目录要在起进程前建好，才挂得回来；跑着时才建的，下一条会话才看得到。这和 4.4 第一行原来的结论一样。

**JP-VPS 上已经验过的**（2026-10-20，bubblewrap 0.9.0，`kernel.apparmor_restrict_unprivileged_userns = 1`）：
- 外层 `--dev-bind / / --tmpfs <projects> --bind <g1> <g1>` 里，`ls groups` 只有 `g1`，`g2/in.txt` 不存在。
- 在外层里再跑一层 `bwrap --unshare-user --unshare-pid` 能起来。
- Claude Code 自己那层沙箱（带网络隔离和 seccomp）套在外层里起不起得来，还没测，由 4.0 E 先验。

**macOS 不改**：Seatbelt 按路径规则判，不建挂载点，4.2 的名单在那里有效（e03b），新建的兄弟也马上挡住。

**full 档、没有 `readScope`**：照今天由 SDK 自己起进程，不套这一层。

### 4.5 owner 的决定：凭据先不挡

只读、读写档的会话里，lark-cli 以 bot 身份调用要经数据目录根上的 `secrets-getter` 跑 `vonvon secrets get` 解 App Secret（`D/config/store.ts` 的 `ensureSecretsGetterWrapper`，`docs/v1-plan.md` 里"会话里调"那一条说 `get` 不拒就是为了它）。挡了凭据，这个子进程也在沙箱里，读不到，开网的只读、读写群里 lark-cli 以 bot 身份就用不了。任务 94 实测，光放开文件还不够：getter 在沙箱里死在 CLI 的准入锁上（`listen EPERM`），沙箱外 lark-cli 又因为回复没有 `protocolVersion` 拒收；这两处由 s31b0 修。

owner 2026-10-19 选了 B：凭据先不挡，读名单只挡别的群、记忆和 bot 目录。做法见 4.2 的 `SECRETS_GET_FILES`：`vonvon secrets get` 要读的文件不挡，`local-credential` 和旧 `config.json` 照挡。代价是这两档的 agent 读得到 bot 的加密凭据和主密钥，等 M8 的 vonvon MCP 能代查飞书（s45 到 s48）以后再决定挡不挡，Codex 在 v1-plan s46 的开工要点里加一条提醒。
