# macOS 与 Claude Provider 检测、模型刷新修复

## 做什么与范围

接续 #629，排查并修复 macOS/Linux 的正常 Provider 冷启动被外层超时误判，以及 Claude 模型重复探测、手动刷新无效的问题。遵守 product.md 3.1 的实时 Provider 目录与失败重试语义。只进入 dev，main 提升和公开发布由 owner 后续统一安排。

## 已确认原因与实现

1. `admin/ops.ts` 非 Windows 的 doctor 外层期限仍为 3 秒；Codex 候选按四个一批运行有界版本探测，多个批次可能超过该期限。提高到 30 秒，保留 Windows 的 60 秒；挂死仍明确失败。
2. `admin/ipc.ts` 只给 Windows 的 Provider 设置操作 120 秒，其他系统仍为 15 秒。Claude 模型发现自身有 30 秒预算，Codex 还包括初始化和会话目录约束查询。统一这些操作的跨平台转发预算，普通状态和无关写操作仍为 15 秒。
3. `claude-agent/backend.ts` 模型缓存仅限单个后端实例，忽略 refresh，peek 不校验身份，旧请求可覆盖新目录。按 SDK loader 共享成功目录及并发请求；配置、凭据文件、相关环境和 SDK 版本变化失效；显式刷新替换普通在途请求，同轮刷新合并；旧结果不能发布到新缓存，失败备用列表不作为 ready。
4. `codex-appserver/models.ts` 显式刷新可能加入先前的普通读取。立即发起强刷，并合并这一轮的刷新调用；普通请求尚未完成也不阻塞强刷，旧请求成功或失败均不得覆盖新缓存。
5. Codex 实例供新线程判断思考参数的能力快照也按读取代次保护；旧请求迟到成功或失败都不能清空新快照。用原生协议 fixture 的实际 `turn/start` 验证不支持 effort 的模型不会被错误附加该参数。

## 测试与本机验收

- 先验证旧代码会失败：超过 3 秒的正常 doctor、超过 15 秒的 Codex/Claude 模型 IPC，以及普通发现进行中的显式刷新。
- 验证短状态超时、Provider 挂死、失败重试、并发合并、配置/账号/SDK 失效、迟到结果和关闭清理。
- Mac 使用隔离数据目录，通过构建后的 daemon 和原生协议 fixture 验证 Provider 页的读取、缓存、强刷、失败和恢复。真实 SDK/CLI 元数据验证与 fixture 证据分别记录；不进行模型推理，不发飞书消息。
- 执行构建、类型检查、相关回归；最终 head 经独立审查和风险复核，按自动范围取得 Linux、自托管 macOS、Windows CI 与 CI gate 后合入 dev。

## 文档、验收要点与风险

更新 v1-plan 的修复记录，不改变产品权限、原生会话、安装或发布语义。无真实 ID、密钥或本机路径。缓存并发、身份失效与出错恢复是主要风险；每个失败目录均可重试，只有成功的原生结果可作为 ready。

macOS 钥匙串的外部变化由用户显式重新检测更新；本次不为后台轮询添加额外进程。Codex 会话 cwd 的权限约束仍每次验证，不为性能跳过它。预计改动低于 500 行，整体独立审查并追加并发/错误路径风险复核。
