## 1. 做什么

四件事，都只在智能群：

1. **回答里 @ 真人也变真 @。** s27b 只认名册里的 bot。本片把群成员里名字只有一个人叫的真人也加进候选：agent 在回答里写"@张三 做好了"，回答卡定稿后，程序回复这张卡发一条文字消息，真 @ 张三。真人和 bot 的 @ 合在同一条文字消息里（s27b 的那一条）。agent 用这个提醒发起人、请别人看，都是 agent 自己定的。
2. **发真 @ 的刹车**（3.4"bot 之间"最后一条，v1-plan 第 5 节 :1488）：
   - 永不生成 @所有人：`@所有人`、`@all`、`@everyone`、`@全体成员`、`<at user_id="all">` 都当文字；名字是"所有人""全体成员""all""everyone"的成员和 bot 也不认。text 消息不经 at-guard，所以在 `findHandoffs` 里挡。
   - 引用块（`>` 开头的行）和代码块里的 @ 不认：那是在转述别人的话。
   - 一条最多 @ 5 个，真人和 bot 合计，按在回答里出现的先后；多的不发，回答卡最后一行灰字写"→ 还想 @ 孙八、周九，没发：一条最多 @ 5 个"。
   - 同名（两个成员名字一样，或者成员和 bot 撞名）不发，卡上写一行"→ 想 @ 张三，没发：群里不止一个叫 张三 的成员"。
   - agent 自己写的 `<at id="…">`，只认名单和名册里的 id。
3. **智能群的完成提醒**（3.8"完成提醒"）：智能群不按提醒设置发，运行卡上也没有"完成后提醒我"。只有一轮出错或超时、发起人是真人时，程序回复回答卡发一条 post，@ 发起人说一声（文字用今天的"执行失败""响应超时"那两种）。正常结束、被人停掉、发起人是 bot 的，不发。规则群一切照旧。
4. **每轮输入里的一行说明**：智能群每一轮给 agent 的输入，发信人块前面多一行 daemon 写的说明"（群里还有 bot：小码、小审。要提醒谁、请哪个 bot 接着做，就在回答里写 @名字，会变成真 @；只是提到不要 @。）"。群里没有别的 bot 时只写后半句。只说怎么用，要不要 @ 仍由 agent 定。

用户能看到的：智能群里 agent 回答写的 @张三 真的提醒到张三；回答写的 @所有人 不会 @ 所有人；智能群做完不再按设置发"✅ 已完成"的提醒，运行卡上没有"完成后提醒我"，出错和超时照样 @ 发起人；agent 写的 @ 名字更准。

### 4.1 群里的真人：`D/bot/chat-people.ts`（新）

照 `D/bot/bot-roster.ts` 的样子写，约 105 行（含分页循环）：

```ts
import type { LarkChannel } from '@larksuiteoapi/node-sdk';
import { log } from '../core/logger';
import { feishuError, scopeDenial } from '../utils/feishu-error';
import { deniedScopeName, errorDetail, reportScopeDenied } from './diagnostics';
import { withDeadline } from './names';

/** How long a chat's people are trusted for the answer's @ (s27b2). */
export const PEOPLE_TTL_MS = 10 * 60_000;
/** A failed read is not tried again sooner. */
export const PEOPLE_RETRY_MS = 60_000;
/** The SDK's calls have no timeout of their own: the whole list (all pages together) gets this long. */
export const PEOPLE_READ_MS = 5_000;
/** Most members per page the API gives. */
export const PEOPLE_PAGE_SIZE = 100;
/** The most pages one read takes (1,000 people); a longer list is incomplete. */
export const PEOPLE_MAX_PAGES = 10;
const MEMBERS_SCOPE = 'im:chat:readonly';

export interface ChatPerson { openId: string; name: string }
/** complete: every page was read. false: the budget ran out or a page failed, so a name's uniqueness cannot be known. */
export interface PeopleList { people: readonly ChatPerson[]; complete: boolean }
export interface ChatPeople {
  /** The cached list, maybe stale; undefined until a page was read. */
  peek(chatId: string): PeopleList | undefined;
  /** Reads when the list is stale or unknown; shares a read in flight; settles, never rejects. */
  load(chatId: string): Promise<void>;
}

/**
 * The people in a chat: all pages of `im.v1.chatMembers.get` (which lists no bots), within a page and time budget. Each bot reads its own.
 * A read that cannot finish is marked incomplete; a failed read keeps an old list's names but marks it incomplete until a later read finishes. `stop` is the orchestrator's `orStop`: shutdown does not wait on a read.
 */
export function createChatPeople(
  channel: Pick<LarkChannel, 'rawClient'>,
  opts: { stop: <T>(p: Promise<T>, fallback: T) => Promise<T> },
): ChatPeople
```

- 读：一次 `load` 是一个循环，页与页之间用 `page_token` 接着读：`channel.rawClient.im.v1.chatMembers.get({ path: { chat_id: chatId }, params: { member_id_type: 'open_id', page_size: PEOPLE_PAGE_SIZE, ...(token ? { page_token: token } : {}) } })`，每页外面 `opts.stop<Body | undefined | 'stopped'>(withDeadline(…, remaining, 'chat-people'), 'stopped')`（类型参数显式写，理由同 s27b 4.2）。`remaining` 是 `PEOPLE_READ_MS` 减去这一次 `load` 已用的时间（开始读时记一个起点，用 `Date.now()` 算；单元测试用假计时器），所以总时间是一份预算，不是每页各 5 秒。
- 循环的停止：`has_more` 不是 true → 读完，`complete: true`。`has_more` 为 true 时：已经读了 `PEOPLE_MAX_PAGES` 页、或剩余时间 ≤ 0、或没有 `page_token`、或 `page_token` 在本次读取中已经出现过（含跨页循环，防死循环）→ 停下，`complete: false`。不拿"这一页是不是满 100 个"当结束的依据，只看 `has_more`。
- 结果：`'stopped'` → undefined，不记失败；`undefined`（超时）→ 失败 `timeout`；`body.code !== 0` → 失败 `code=…`（照 `names.ts` 的 `contactNames`）；`body.data?.items` 不是数组 → 失败 `no-items`；否则逐项取 `member_id` 和 `name`，两个都是非空字符串的才留（**不填"…尾号"**：没名字的人匹配不到，也不该匹配到），各页按页序接起来，日志 `card chat-people { chatId: 尾号, people: n, pages: n, more?: true }`（`complete` 为 false 时带 `more`）。
- **不完整的记法**（product.md 3.4"只认群里的 bot 和名字只有一个人叫的真人"）：一份名单要读完才能知道一个名字是不是只有一个人叫。读不完的两种——`has_more` 到预算（页数、时间）还是 true；已经读到几页以后某一页失败（抛错、`code !== 0`、超时、`no-items`）——都记 `complete: false`，名单里是已读到的人。第一页就失败、又没有旧表的，`peek` 是 undefined，调用方同样当不完整。**不完整的名单不用来建立候选**，见 4.2。
- 失败：照 `bot-roster.ts` 的 `failed`：`scopeDenial(failure)` 有的话 `reportScopeDenied(deniedScopeName(denial.accepted) ?? MEMBERS_SCOPE, 'chat-info')`；日志 `card chat-people-failed { chatId: 尾号, reason }`；抛错的 `code` 用 `feishuError(err)?.code`，没有就 `errorDetail(err) ?? 'error'`。
- 缓存：和 `bot-roster.ts` 一样的 `entries` / `entryOf` / `start`：读完的（`complete: true`）缓存 `PEOPLE_TTL_MS`；失败和不完整的 `PEOPLE_RETRY_MS` 内不再读（一个永远读不完的大群，每分钟最多读 10 页，只在 agent 的回答要交接时才读）。失败或读不完时：有旧表，保留旧表的人（不用这次读到的残页盖掉，名字照样能用来写脚注），但 `complete` 改成 false；没有旧表，存这次读到的（可能是空）为 `complete: false`。**过期的完整表不再证明一个名字只有一个人叫**：旧表过期后的那次读取一失败或读不完，到下一次读完（`complete: true`）之前，`peek` 返回的都是 `complete: false`，`handOff` 因此真人和 bot 一个都不发。TTL 内复用读完的表照旧。`load` 有读取在飞就等它，过期才起新的。没有 `refresh`。
- 只有尾号和计数进日志，不写名字。

在 orchestrator 里，名册旁边（今天 :1176，s27a 后是 `const roster = …` 那一行下面）：


### 4.2 名字→id 的改动：`D/bot/bot-handoff.ts`

在 s27b 的文件上改，规则编号沿用 `s27b.md` 4.1。

类型和签名：

```ts
import type { ChatPerson } from './chat-people';

/** 一条交接文字最多 @ 几个，真人和 bot 合计（s27b2，product.md 3.4"bot 之间"）。 */
export const HANDOFF_MAX_ATS = 5;
/** 永不当收件人的名字（personName 后、ASCII 不分大小写比）：写成 @它们的都是文字（s27b2）。 */

  ambiguousPeople: string[];
  /** 第 6 个起的收件人，按出现先后；不发（s27b2） */
  over: Pick<Handoff, 'name' | 'person'>[];
  /** 名单不完整（peopleComplete 为 false）时，本来会发的收件人（bot 和已读到的真人，按出现先后）：一个都不发，卡上写一行（s27b2） */
  unverified: Pick<Handoff, 'name' | 'person'>[];
}
export function findHandoffs(text: string, bots: ReadonlyMap<string, RosterBot>, me: Me, people?: readonly ChatPerson[], peopleComplete = true): Found
```

第四个参数可选，第五个默认 `true`：不传名单（s27b 的单元测试、规则不涉及真人的调用）时没有真人候选，行为和 s27b 一样，只多了保留名字、引用块、5 个的上限和 id 格式这几条刹车。`handOff` 总是显式传第五个参数（4.3）。

**名单不完整（`peopleComplete === false`）**：成员名单没读完，一个名字是不是只有一个人叫就不知道，包括 bot 的名字（可能和没读到的成员重名）。所以走完上面和下面的全部规则（候选、保留名字、同名、去重、跳过的区间）以后，**本来会进 `handoffs` 和 `over` 的收件人，改记进 `unverified`，`handoffs` 和 `over` 为空**，句子不改（`@名字` 留作文字）。bot 之间同名、有真人的同名照常进 `ambiguous`、`ambiguousPeople`（那是已经知道的事实，卡上照写）。没匹配到候选的 `@名字`（不在名册、也不在已读到的名单里）是文字，不记：我们没有证据它是群里的人。

规则的改动：

- **规则 1 候选**：
  - bot：照 s27b（名册里除我以外、`personName` 非空的）。
  - 真人：`people` 里每一项，`personName(name)` 非空、`openId !== me.openId` 的，记 `person: true`。
  - **id 格式**（bot 和真人都过）：`/^ou_[^\s<>"'&]+$/u`。不合格的不是候选：`all`、`cli_…` 这类不是 open_id 的 id，和带引号、尖括号、空白的（它们要拼进 `<at user_id="…">`）。测试里的 `ou_审` 这种也合格。
  - **保留名字**：`personName(name)` 转成 ASCII 小写后在 `RESERVED_AT_NAMES`（同样转小写）里的，不是候选，bot 也一样。
  - **同名**：按 `personName` 后、ASCII 转小写的键分组，一组不止一个候选的是歧义名：组里全是 bot 的进 `ambiguous`（s27b 的脚注），组里有真人的进 `ambiguousPeople`（新脚注）。歧义名照常参加前缀匹配（它仍然挡住更短的名字），匹配到了不记交接。我自己在候选之前就排除了（s27b），不和别人算同名：成员里有人和我同名，`@小码` 认成那个人。
  - 候选按名字长度从长到短排，同长按 open_id 排（s27b）。
- **规则 2 跳过的区间**：`codeSpans(text)`（s27b）加上**引用行**：每一行第一个非空白字符是 `>` 的，从行首到行尾（不含换行）是一个区间。在 `bot-handoff.ts` 里写一个私有的 `quoteSpans(text): Span[]`（`Span` 从 `md-scan.ts` 引入类型；`/^[ \t]*>.*$/gmu` 逐个取区间）。两种区间里的 `@` 和 `<at` 都不认。代码块里的 `>` 行本来就在代码区间里，叠在一起没关系。
- **规则 3 `@名字`**：每个 `@` 处，**先看保留名字**，再找候选：
  - `text.slice(i + 1)` 以某个保留名字开头（ASCII 不分大小写），而且是 ASCII 的保留名字（`all`、`everyone`）时 s27b 的 ASCII 边界成立 → 这一处是文字，扫描位置跳过这个词，不再找候选。中文的保留名字不要求边界。
  - 为什么先看：中文名不要求边界，有人叫"所有"或"全体"时，`@所有人`、`@全体成员` 会按最长前缀认成他。`@allen`（有人叫 allen）：`all` 后面是字母，边界不成立，不算保留，照常认 allen。
  - 其余照 s27b。
- **规则 4 `<at>`**：id 在候选里（bot 或真人）才记；起点在跳过的区间里的不记。`<at user_id="all">` 的 id 不是 `ou_`，本来就不是候选。
- **规则 5 去重、排序、上限**：照 s27b 按 open_id 去重、按第一次出现排序，然后**前 `HANDOFF_MAX_ATS` 个**进 `handoffs`，其余按顺序进 `over`（`{ name, person? }`）。歧义名不算在 5 个里（本来就不发）。
- **规则 6 句子**：照 s27b，只算 `handoffs` 里的；`over` 的那几处 `@名字` 也要从句子里去掉（和"记录到的"一起去），不然句子里留着"@孙八"文字，读的人以为也 @ 了他。
- **规则 7**：不是候选的名字（没读到的真人、保留名字、不在群里的）当普通文字，不记，没有脚注。名单不完整时的收件人不走这条，走上面的 `unverified`。

`handoffText(handoffs)` 不改：真人的标签和 bot 一样是 `<at user_id="${openId}">${name}</at>`。

在 s27b 的 `handOff` 上：

- `note(why?)` 拼的行：没发出那一行（有的话，`handoffNote(found, why)`）→ bot 同名的每个一行（`ambiguousNote`）→ 有真人的同名每个一行（`ambiguousPersonNote`）→ 名单没读全的一行（`incompleteNote(unverified)`，有的话）→ 超过 5 个的一行（`overNote(over)`，有的话）。一行都没有就不再定稿（s27b）。`over` 非空时 `found` 一定有 5 个，所以"只有 `over`"走不到前面那个 `return`。

- 名册读不到（`!bots`）时，真人名单读到了也不发：分不出谁是 bot，就判不了真人和 bot 撞名；宁可少发一次（和 s27b 一样无脚注）。
- 真人名单不完整（`known` 为 undefined，或 `known.complete` 为 false：读不完、中途失败、一页都没读到）：**一个都不发，bot 名也不发**——它可能和没读到的成员重名，随便挑一个等于随便提醒一个。已匹配到的收件人在卡上写一行 `incompleteNote`，没匹配到的当文字。日志多 `incomplete: true`（一页都没读到时同时 `people: false`）。这代替 s27b 的"bot 照发"：s27b 只有名册，现在多了成员这个来源，认不准就不发。
- 发出后 `await note()` 照旧：有同名的、有超过 5 个的，发完再定稿写那几行。
- `me` 那个对象（`{ openId: channel.botIdentity?.openId, appId: channel.rawClient.appId }`）照 s27b，不改。
- 停机的两处检查、发送、超时、失败的处理都不改。
