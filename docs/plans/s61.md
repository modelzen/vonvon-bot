# s61：导入事务（上）：停 bridge、占锁、复制、回滚

## 1. 做什么

product 第 5 节"怎么迁"的第 3 到 5 步，以及失败时的回滚。daemon 里多一个导入事务：
- 停掉 bridge 的后台服务；
- 用 bridge 的锁格式给每个 bot 占住锁；
- 把 bridge 的数据换算后放进暂存目录，旧密钥解开以后用 v1 的密钥库重新加密；
- 任何一步失败，就按倒序回滚，并把 bridge 重新启动起来。

这一片没有界面，用户还看不到。界面在 s63，后半段（第 6 到 9 步和提交）在 s62。

依赖：
- 已合入：s58（#373）、s59（#463，`49c13c6`）。
- 要先合入：s60（任务 134 在做）。
- e08 和 Mac 测试用户：第 6 节的真机检查要用。写代码和定向测试不用等它们。

## 4. 怎么改

### 4.1 谁来跑事务、谁来持锁

事务跑在 daemon 的 host 进程里（`runSupervisor` 所在的进程，`!process.send`），由 host 自己持有 bridge 的锁。原因：
- e07 第 2 条：持有者要活过整个事务，而且要自己写锁。命令行进程跑完就退，锁跟着失效。
- s62 之后 host 一直持有这些锁（e07 第 7、9 条），交接不用换进程。

同一时间只有一个事务：host 本来就靠 `host` mutex 保证一份数据只有一个 host；进程内再加一个标志，第二次 `start` 直接回"已经在导入了"。

### 4.2 新文件 `D/import/bridge/transaction.ts`

```ts
export type ImportStep = 'checking' | 'stopping' | 'locking' | 'staging' | 'staged' | 'rolling-back' | 'rolled-back' | 'rollback-failed' | 'refused';
export interface ImportView {
  readonly txId: string;
  readonly step: ImportStep;
  readonly bots: readonly { appId: string; name: string }[];
  readonly notes: readonly ImportNote[];   // s60 的 notes，原样带上
  readonly error?: { code: string; message: string };   // 给人看的中文，不带密钥和完整 id
}
export interface BridgeImporter {
  start(): Promise<ImportView>;            // 立即返回，事务在后台跑
  rollback(): Promise<ImportView>;         // 只在 staged 时接受
  view(): ImportView | undefined;
  shutdown(): Promise<void>;               // host 退出前调，见 4.7
}
export function createBridgeImporter(deps: ImporterDeps): BridgeImporter;
/** host 启动时、读注册表之前调，见 4.10。 */
export function recoverBridgeImport(deps: ImporterDeps): Promise<void>;
```

`ImporterDeps` 是给测试换的接缝，生产用真的：
- 各个路径：bridge 目录 `join(homedir(), '.feishu-codex-bridge')`、plist 路径、`paths.appDir`；
- `uid`；
- `run(command, args)`：只给 `/bin/launchctl` 和 `/bin/ps` 用，和 s59 的 `command` 一样；
- 时钟、`sleep`；
- `convert`：s60 的入口；
- 密钥库三件：`setSecret`、`removeSecret`、`listSecretIds`；
- `fault`：见 4.9。

### 4.3 第 0 步：动手前全部查完，有一条不过就什么都不改

按顺序：
1. `process.platform === 'darwin'`，否则 `refused`："只有 macOS 能从 bridge 导入。"
2. `inspectBridgeSource` 返回 `inspected`。
   - `upgrade-required` 原样给 s59 的那句提示。
   - `not-found`、`invalid` 给对应的话。
3. 每个 bot 的 `secret`：
   - `decryptable`、`plaintext`、`external-reference` 可以导入。
   - `cannot-decrypt` 回"改过主机名，旧密钥解不开，先扫码刷新这个 bot"（product 第 5 节）。
   - 其余拒绝。
4. 区分 bridge 的两种运行方式：
   - 服务没装、也没在跑（`service` 为 `stopped`），但有 bot 的进程在跑：这是在终端里手动跑的 `run`。拒绝："bridge 正在终端里运行，不是后台服务。先在那个终端按 Ctrl+C 停掉它，再重试导入。"

5. 和 v1 已有的数据撞不撞：每个 `appId` 都不能已经在 `loadBots()` 里，不能已经有 `app-<appId>` 这个密钥，`botPaths(appId).dir` 也不能已经存在。撞了就拒绝："Vonvon 里已经有「<名字>」这个 bot。先在 Vonvon 里删掉它，再重试导入。"（Claude 2026-10-20 定）
6. 读一份快照（读法同 4.7 第 1 条），交给 s60 转换一遍。有任何一个 bot 报错，就整个拒绝，列出每个 bot 的错误。"一次导入全部 bot"（product 第 5 节）。
7. 记下现在的状态，写进日志：
   - plist 在不在；
   - `launchctl print` 的结果；
   - 每把 bridge 锁现在的持有者（`readSingleInstanceHolder(appId, bridgeLock)`）。

这一步只读。拒绝时状态是 `refused`，不写日志文件，也不建目录。

### 4.4 日志 `D/import/bridge/journal.ts`

- 位置：`<appDir>/import/bridge/journal.json`。同一时间只有一份。旧的结局（`rolled-back`、`rollback-failed`，以及 s62 的 `done`）留着给 s63 看，新事务开始时改名成 `journal-<旧 txId>.json`。
- 原则是"先记再做"：每个有副作用的动作前，先把"要做什么"写进日志，再动手；做完再记一笔"做完了"。
- 写法：临时文件、fsync、rename、fsync 目录，和 `config/bots.ts` 的 `publish` 一样。
- 读法：用 s59 的 `readLocalText`，限 1 MB，严格 JSON，zod 校验。
- 日志里记：
  - `txId`、`hostPid`、`startedAt`、`bridgeDir`、`uid`；
  - 第 0 步第 7 条的状态；
  - plist 的处理：`moved` 和备份路径；
  - 拿到了哪些锁（appId）；
  - 建了哪些密钥（id）；
  - 暂存目录；
  - 当前步骤、错误。

  不记密钥和明文配置。
- 暂存目录 `<appDir>/import/bridge/<txId>/`，0700，建好后 lstat 一下，确认是真目录、不是链接。

### 4.5 第 3 步：停 bridge

做的事和 bridge 自己的 `stop` 一样，但由 vonvon 自己用 launchctl 做，不去调 bridge 的命令行。原因：
- 回滚要用到原来的 plist，而 bridge 的 `stop` 会直接删掉它；
- plist 里记的 node 路径可能已经不在了；
- bridge 的 `start` 要先联网校验凭据，回滚时不能靠它。

product 第 5 节第 3 步的说法随这一片改（第 7 节）。

1. plist 在的话：
   1. 先在日志里记下"要搬 plist"；
   2. 把它 rename 进暂存目录，叫 `bridge.plist`；跨卷报 EXDEV 时，改成复制、fsync、再删原文件；
   3. 记下"已搬"。
2. 服务加载着的话：`launchctl bootout gui/<uid>/ai.feishu-codex-bridge.bot`，然后每 200 毫秒 `print` 一次，直到"找不到服务"，最多 30 秒。
3. 超时、bootout 报错：都按失败回滚。

### 4.6 第 4 步：占锁

在 `D/core/single-instance.ts` 加两个可选参数：

```ts
acquireSingleInstanceLock(appId, file, { createDir?: boolean; onExit?: boolean })
```

两个都默认 `true`，现有调用不变。
- 导入用 `createDir: false`：bridge 的 bot 目录必须已经在，不替它建。
- 导入也用 `onExit: false`：e07 第 9 条，退出时由导入器统一放锁，不每把锁挂一个回调。

导入器里放一个 `BridgeLocks`，管 `appId → release`，进程退出时只挂一个回调，挨个放。s62 也用它。

对每个 bot：
1. 每 100 毫秒试一次，直到拿到，最多 30 秒（e07 第 3 条；e08 量出 bridge 实际要多久退干净，再定这个数）。
2. 遇到 `BridgeAlreadyRunningError` 时，看持有者：
   - 和第 0 步记下的是同一个 pid：继续等。
   - 第 0 步没有持有者、现在有了，或者换了 pid：这段空档里有人手动起了 bridge。按失败回滚："导入时 bridge 又被启动了（PID x）。"
3. 每拿到一把就记进日志。
4. 全部拿到后，再 `print` 一次服务。又加载了（有人跑了 `start`），就按失败回滚。

### 4.7 第 5 步：读快照、换算、暂存、重新加密

1. **再读一份快照。** 现在 bridge 已经停了，用 `readLocalText` 读这些：
   - 顶层的 `bots.json`；
   - 每个 bot 的 `config.json`、`projects.json`、`sessions.json`、`comment-instructions.md`。

   不读 `processes.json`、`comments/`、`cli-bridge.sock`。读出来交给 s60（#436 评论 6282239350 写的形状），这次的结果就是要写的东西。和第 0 步的结果比，bot 的集合不一样，就按失败回滚："导入时 bridge 的 bot 变了，请重试。"
2. **暂存。** 每个 bot 的 `config`、`projects`、`sessions` 写到暂存目录的 `bots/<appId>/` 下，文件名和 v1 的一样，写法同日志。s60 给的 `copy` 清单按相对路径逐个复制：
   - 读的时候不跟随链接，按 s59 的路径检查确认不出 bot 目录；
   - 目录里的链接和特殊文件都不复制，记成 note；
   - 普通文件按字节复制，目标用 `wx` 打开。
3. **重新加密。**
   - `legacy-keystore` 和 `plaintext` 两种：先 `listSecretIds()` 确认 `app-<appId>` 还没有；再把这个 id 记进日志；然后在内存里解出明文，`setSecret` 写进去。
   - 解密用 s59 的 `loadLegacyKeystoreKey`。在 `legacy-keystore.ts` 里加一个 `decryptLegacySecret(key, envelope): Buffer`，和 `canDecryptLegacySecret` 用同一套格式。用完 `fill(0)` 清掉 key 和缓冲区。
   - 明文不进日志，不进错误信息，也不进暂存文件。
   - `external` 种类的不碰。
4. **停下。** 步骤改成 `staged`，等 `rollback`（s62 以后接着往下走）。

v1 的注册表、v1 的 bot 目录和正在跑的 bot，这一步都不碰。暂存目录和新写的密钥都还没被任何地方引用，跑着的 daemon 看不见它们。

### 4.8 回滚

触发：
- 第 3 到 5 步里任何一步失败；
- `staged` 时收到 `rollback`；
- 关机（4.9）；
- 启动时恢复（4.10）。

按下面的顺序做，每一步先记日志：
1. 放掉这次事务拿到的 bridge 锁。只放 `BridgeLocks` 里有的。release 会先核对锁里的 pid 是不是自己，和现在的写法一样。
2. 把 bridge 恢复到第 0 步时的样子：
   - 原来有 plist、现在那个位置没有：把暂存目录里的 `bridge.plist` 原样 rename 回去。
   - 现在那个位置已经有 plist（有人跑过 `start`）：用现在这份，不覆盖。
   - 原来服务是加载着的：`launchctl bootstrap gui/<uid> <plist>`。之后最多等 30 秒，直到 `print` 看到服务在跑。KeepAlive 拉起的 `run` 在放锁以后才连得上，e07 第 4 条。
   - 原来就没装服务：什么都不做。
3. 删掉这次建的密钥：日志里记了哪些就删哪些，用 `removeSecret`。
4. 删掉暂存目录。删之前确认三件事：它就是 `<appDir>/import/bridge/<txId>`；是真目录；`bridge.plist` 已经不在里面了。
5. 步骤改成 `rolled-back`，error 写原来那次失败的原因。

第 2 步 bootstrap 失败或者等不到：
- 步骤改成 `rollback-failed`，告诉用户："bridge 没能重新启动。请在终端运行 `feishu-codex-bridge start`。"
- 第 3、4 步照做。
- 不反复重试。

第 3、4 步失败：只记日志，不影响 bridge。下次启动时 `recoverBridgeImport` 再清一次。

### 4.9 关机

host 收到停止或重启的请求时（`ShutdownControl.requested`）：
- `shutdown()` 让事务在下一个步骤边界停下，然后回滚；`staged` 时直接回滚。
- host 的退出要等这次回滚做完。时间算在现有的关机宽限里，在 `runSupervisor` 的收尾、停子进程之前调。
- 宽限内没做完，就留着日志，下次启动时 `recoverBridgeImport` 接着做。

### 4.10 启动时恢复

在 `runHostRuntime` 里调 `recoverBridgeImport()`：只在 host 里（`!process.send`），拿到 pid 锁之后、进 `runRun` 之前。要在读注册表之前调，因为 s62 的回滚会改注册表。日志的步骤在 `stopping` 到 `staged` 之间（包括 `rolling-back`），就说明上一个 host 在事务中途死了，这时：
- 旧 pid 已经死了，它的锁 bridge 会当残留锁清掉（e07 第 3 条）。这里不去动锁文件。
- 照 4.8 的第 2 到 5 步做一遍，error 写"daemon 在导入中途退出了，已经回滚"。

恢复失败也不挡 daemon 启动，只记日志，把步骤改成 `rollback-failed`。

### 4.11 RPC 和隐藏命令

**RPC**
- `machineRequestSchema` 加 `z.object({ type: z.literal('bridgeImport'), action: z.enum(['start', 'rollback', 'status']) })`。
- `machineReplySchema` 加 `{ type: 'bridgeImport', view: ImportView | null }`。
- `machineRpc` 经 `MachineServiceContext` 拿到 `BridgeImporter`：
  - 没有导入器时（不是 host，或者不是 macOS）回 `unsupported()`；
  - `start` 是 mutation，其余是 read。

**隐藏命令**
- `program.command('__import-bridge <action>', { hidden: true })` 照 `bot list` 的写法连 daemon。
- 打印 `ImportView`：一行一个字段，notes 一行一条，带 `--json` 时输出 JSON。
- `start` 之后每秒查一次，直到步骤不再变化（`staged`、`rolled-back`、`rollback-failed`、`refused`）。
- 这是测试入口，不进 help，不写进 product.md。s63 的导入页用同一个 RPC。

### 4.12 故障注入

只给验收用：
- 环境变量 `VONVON_TEST_IMPORT_FAIL`，取值 `after-stop`、`after-lock`、`during-copy`、`after-copy`。
- 只有 host 进程读它，在对应的位置抛一个错，走正常的回滚。
- `during-copy`：写完第一个 bot 的暂存文件、写第二个之前抛。
- 照 `VONVON_TEST_CRASH` 的样子，host 每次启动只要看到这个值，就记一条 `test_seam`，并打到 stderr。
- 值不认识就忽略，也记一条。

5. 第 0 步没有持有者，占锁时冒出一个新的活持有者：回滚，error 带它的 pid。
6. 占完锁以后 `print` 又看到服务：回滚。

**故障和回滚**

7. 四个注入点各跑一次：都走到 `rolled-back`。
   - 锁文件不在了，或者不再是测试进程的 pid。
   - plist 原样回到原处（字节相同），`bootstrap` 调了一次。
   - 密钥和暂存目录都没了，`VONVON_HOME` 和开始前逐字节相同。
8. `staged` 时调 `rollback`：结果同第 7 条。
9. 回滚时 plist 那个位置已经有一份新的：不覆盖，照样 `bootstrap`。
10. `bootstrap` 失败：走到 `rollback-failed`，带那句提示；密钥和暂存目录照样清掉。
11. 原来没装服务：回滚时不碰 plist，也不 `bootstrap`。

**关机和恢复**

12. 关机：`staged` 时和 `staging` 中途各调一次 `shutdown()`。都等回滚做完才返回，结果同第 7 条。
13. 恢复：子进程在 `staged` 时被 SIGKILL，留下日志。调 `recoverBridgeImport()` 以后，走到 `rolled-back`，原因写"中途退出"。
14. 日志坏了（不是 JSON、校验不过）：`recoverBridgeImport` 不动任何东西，记成 `rollback-failed`，daemon 照常启动。

**并发**

15. 两次同时 `start`：只有一个开始，另一个回"已经在导入了"。
16. `staged` 时再 `start`：同上。

**密钥不外泄**

17. 所有 `ImportView`、日志文件、错误信息、`console` 输出里，都不出现测试用的明文密钥和完整 app id。

## 9. 风险和行数

估计（不含 lockfile）：

| 部分 | 行数 |
|---|---|
| 事务和日志 | 约 380 |
| launchctl 和锁 | 约 90 |
| RPC、命令、host 接线 | 约 80 |
| 测试 | 约 500 |
| 文档 | 约 40 |
| **合计** | **约 1,090** |

v1-plan 原来估的 650 没算测试。超过 1,500 就拆成两片：
- **s61a：** 第 0 步、日志、第 3、4 步、回滚、恢复、RPC 和命令。
- **s61b：** 第 5 步（快照、暂存、重新加密）。s61a 先停在占好锁的那一步。

**风险：**
- **launchd 的时间：** bootout 后 bridge 多久退干净、bootstrap 后多久重新连上，以 e08 实测为准。上限定得太短，就会误判失败、白白回滚。
- **sudo 进不去 gui 域：** 测试用户的 gui 域从 `sudo -u` 进不去的话，真机检查做不了，按 6.2 写"卡住了"，由 owner 定换别的办法。
- **钟跳：** 系统时钟往前跳 15 秒以上时，bridge 会把 vonvon 长期持有的锁误判成 pid 复用（e07"没测到的"）。s61 持锁的时间短，影响小。s62 长期持锁，会在那一片记下来。
- **跨卷：** plist 和数据目录不在同一个卷上，rename 会报 EXDEV。这时改成复制、fsync、再删原文件。
