# s61：导入事务（上）：停 bridge、占锁、复制、回滚

## 1. 做什么

product 第 5 节"怎么迁"的第 3 到 5 步，以及失败时的回滚。daemon 里多一个导入事务：
- 停掉 bridge 的后台服务；
- 用 bridge 的锁格式给每个 bot 占住锁；
- 把 bridge 的数据换算后放进暂存目录，旧密钥解开以后用 v1 的密钥库重新加密；
- 任何一步失败，就按倒序回滚，并把 bridge 重新启动起来。

这一片没有界面，用户还看不到。界面在 s63，后半段（第 6 到 9 步和提交）在 s62。

依赖：

- e08 和 Mac 测试用户：第 6 节的真机检查要用。写代码和定向测试不用等它们。

## 4. 怎么改

### 4.1 谁来跑事务、谁来持锁

事务跑在 daemon 的 host 进程里（`runSupervisor` 所在的进程，`!process.send`），由 host 自己持有 bridge 的锁。原因：
- e07 第 2 条：持有者要活过整个事务，而且要自己写锁。命令行进程跑完就退，锁跟着失效。
- s62 之后 host 一直持有这些锁（e07 第 7、9 条），交接不用换进程。

同一时间只有一个事务：host 本来就靠 `host` mutex 保证一份数据只有一个 host；进程内再加一个标志，第二次 `start` 直接回"已经在导入了"。

### 4.2 新文件 `D/import/bridge/transaction.ts`

```ts

export interface ImportView {
  readonly txId: string;
  readonly step: ImportStep;
  readonly bots: readonly { appId: string; name: string }[];
  readonly notes: readonly ImportNote[];   // s60 的 notes，原样带上

export interface BridgeImporter {

```

### 4.4a 预留：不让正常注册和导入抢同一个 bot

host 只有一个、导入同时只有一个，都挡不住同一个 host 里或者终端里的正常注册（`D/bot/register-bot.ts` 调 `registerBotEntry`，在 `bots` mutex 里写密钥、config 和注册表）。所以要预留：

1. 第 0 步都通过以后，拿 `bots` mutex（`acquireMutex(paths.appDir, 'bots')`），在 mutex 里：
   - 再查一遍第 0 步第 5 条；
   - 写下第一份日志，带上预留的 appId 列表。

   然后放开 mutex。查和预留在同一把锁里，中间插不进注册。
2. `registerBotEntry` 在 `ownBots` 里、动手写任何东西之前，读一下导入日志：这个 appId 被一个还没结束的事务预留着，就抛 `BridgeImportReservedError`，文字是"这个 Bot 正在从 bridge 导入，导入结束后再试"。
   - "还没结束"：步骤不是 `refused`、`rolled-back`、`rollback-failed`、`done`，或者 `cleanupPending` 为 `true`。
   - 日志读不了，也当成预留着：宁可让注册稍后重试，也不能两边一起写。
   - `register-bot.ts` 把这个错误显示成普通的注册失败。
3. 导入自己注册时（s62）带上 `txId`，`registerBotEntry` 认得出是本事务，就放行。
4. 开工时用 grep 找一遍：还有没有别的地方，会在注册之前为一个新的 appId 写 `botPaths(appId)` 或者 `app-<appId>`。有的话，也在第一笔写之前查预留，写进 PR。
5. 事务结束（`rolled-back`、`rollback-failed` 且清理做完，或者 `done`），预留就自然失效。

### 4.4b 安全搬文件

新函数 `moveFileSafely(src, dst, sha256)`，停 bridge 和回滚两个方向都用它。`sha256` 是这个文件应有的内容，取自意图。

**正常搬：**
1. 先 rename。
2. 报 EXDEV 时：
   1. 复制到 `dst` 同一个目录里的临时文件 `.<文件名>.vonvon-<txId>.tmp`，fsync；
   2. 再 rename 成 `dst`，fsync 目录；
   3. 最后才删 `src`。
3. 哪一步失败，`src` 都还在，`dst` 不留半截。

**可以重跑。** 中途被杀以后再调一次，按两边的实际状态收尾：

| `src` | `dst` | 做法 |
|---|---|---|
| 在 | 不在 | 照上面搬 |
| 不在 | 在，sha256 对得上 | 已经搬完，返回成功 |
| 在，sha256 对得上 | 在，sha256 对得上 | EXDEV 发布了 `dst`、还没删 `src` 时被杀。删 `src`，返回成功 |
| 在 | 在，sha256 不对 | 返回 `conflict`，两边都不动 |
| 不在 | 不在 | 返回 `missing` |

另外，`dst` 目录里本事务名字的临时文件（`.<文件名>.vonvon-<txId>.tmp`）一律删掉，只删这个确切的名字。

### 4.5 第 3 步：停 bridge

做的事和 bridge 自己的 `stop` 一样，但由 vonvon 自己用 launchctl 做，不去调 bridge 的命令行。原因：
- 回滚要用到原来的 plist，而 bridge 的 `stop` 会直接删掉它；
- plist 里记的 node 路径可能已经不在了；
- bridge 的 `start` 要先联网校验凭据，回滚时不能靠它。

product 第 5 节第 3 步的说法随这一片改（第 7 节）。

1. plist 在的话：
   1. 先记意图：从 plist 的位置搬到暂存目录的 `bridge.plist`，带上原内容的 sha256；
   2. 用 `moveFileSafely` 搬过去。
2. 服务加载着的话：`launchctl bootout gui/<uid>/ai.feishu-codex-bridge.bot`，然后每 200 毫秒 `print` 一次，直到"找不到服务"，最多 30 秒。
3. 超时、bootout 报错：都按失败回滚。

### 4.6 第 4 步：占锁

在 `D/core/single-instance.ts` 加两个可选参数：

```ts
acquireSingleInstanceLock(appId, file, { createDir?: boolean; onExit?: boolean })
```

两个都默认 `true`，现有调用不变。
- 导入用 `createDir: false`：bridge 的 bot 目录必须已经在，不替它建。
- 导入也用 `onExit: false`：e07 第 9 条，退出时由导入器统一放锁，不每把锁挂一个回调。

导入器里放一个 `BridgeLocks`，管 `appId → release`，进程退出时只挂一个回调，挨个放。s62 也用它。

对每个 bot：
1. 每 100 毫秒试一次，直到拿到，最多 30 秒（e07 第 3 条；e08 量出 bridge 实际要多久退干净，再定这个数）。
2. 遇到 `BridgeAlreadyRunningError` 时，看持有者：
   - 和第 0 步记下的是同一个 pid：继续等。
   - 第 0 步没有持有者、现在有了，或者换了 pid：这段空档里有人手动起了 bridge。按失败回滚："导入时 bridge 又被启动了（PID x）。"
3. 每拿到一把就记进日志。
4. 全部拿到后，再 `print` 一次服务。又加载了（有人跑了 `start`），就按失败回滚。

### 4.7 第 5 步：读快照、换算、暂存、重新加密

1. **再读一份快照。** 现在 bridge 已经停了，用 `readLocalText` 读这些：
   - 顶层的 `bots.json`；
   - 每个 bot 的 `config.json`、`projects.json`、`sessions.json`、`comment-instructions.md`；
   - 每个 bot 的 `outbound-files/` 在不在；
   - 根上的 `secrets.enc` 里，各个 bot 的配置引用到的那几条（只取密文，不解）。

   不读 `processes.json`、`comments/`、`cli-bridge.sock`。读出来交给 s60（#436 评论 6282239350 写的形状），这次的结果就是要写的东西。和第 0 步的结果比，bot 的集合不一样，就按失败回滚："导入时 bridge 的 bot 变了，请重试。"
2. **暂存。** 每个 bot 的 `config`、`projects`、`sessions` 写到暂存目录的 `bots/<appId>/` 下，文件名和 v1 的一样，写法同日志。s60 给的 `copy` 清单按相对路径逐个复制：
   - 读的时候不跟随链接，按 s59 的路径检查确认不出 bot 目录；
   - 目录里的链接和特殊文件都不复制，记成 note；
   - 普通文件按字节复制，目标用 `wx` 打开；
   - 最后在 `bots/<appId>/` 里放一个空文件 `.vonvon-import-<txId>`，s62 搬目录以后靠它认出这是本事务的目录。
3. **重新加密。**
   - `legacy-keystore` 和 `plaintext` 两种。`config/keystore.ts` 加两个函数，都在 keystore 自己的 mutex 里做：
     - `createSecret(id, plaintext, iv)`：这个 id 已经有了就报错，不覆盖；没有才写，用调用方给的 iv（12 字节随机数）。
     - `removeSecretIfIv(id, iv)`：这一条的 iv 还是给的那个才删，否则不动，返回"不是我们的"。
   - 做法：
     1. 生成 iv，把 id 和 iv 记进意图；
     2. 在内存里解出明文，调 `createSecret`；
     3. 报"已经有了"：说明预留之外还有别的写入者，按失败回滚，不删那一条。
   - 解密用 s59 已有的 `loadLegacyKeystoreKey` 和 `decryptLegacySecret`，它返回 `undefined` 时按"解不开"失败回滚。用完 `fill(0)` 清掉 key 和缓冲区。
   - 明文不进日志，不进错误信息，也不进暂存文件。
   - `external` 种类的不碰。
4. **停下。** 步骤改成 `staged`，等 `rollback`（s62 以后接着往下走）。

v1 的注册表、v1 的 bot 目录和正在跑的 bot，这一步都不碰。暂存目录和新写的密钥都还没被任何地方引用，跑着的 daemon 看不见它们。

### 4.8 回滚

触发：
- 第 3 到 5 步里任何一步失败；
- `staged` 时收到 `rollback`；
- 关机（4.9）；
- 启动时恢复（4.10）。

按下面的顺序做，每一步先记日志。进入回滚的那一笔日志，同时写步骤 `rolling-back` 和 `cleanupPending: true`。从这笔开始，不管在哪被杀，下次启动都会接着清。

1. 放掉这次事务拿到的 bridge 锁。只放 `BridgeLocks` 里有的。release 会先核对锁里的 pid 是不是自己，和现在的写法一样。
2. 把 bridge 恢复到第 0 步时的样子。原来有 plist 的，用 `moveFileSafely(暂存目录的 bridge.plist, 原位置, 原 sha256)` 搬回去，按它的结果走：
   - 成功：已经搬回去了，包括"两边各有一份一样的"那种中断。
   - `conflict`：原位置已经有一份不一样的 plist（有人跑过 `start`，它会重写 plist）。用现在这份，不覆盖。暂存目录里那份原件搬进 `<appDir>/import/bridge/backups/<txId>/bridge.plist`，这个目录回滚、清理都不删，回执里写出位置。
   - `missing`：两边都没有，记一条，按"原来就没装服务"往下走。
   - 原来服务是加载着的：`launchctl bootstrap gui/<uid> <plist>`。之后最多等 30 秒，直到 `print` 看到服务在跑。KeepAlive 拉起的 `run` 在放锁以后才连得上，e07 第 4 条。
   - 原来就没装服务：什么都不做。
3. 先把 `cleanupPending` 记成 `true`，再清理：
   1. 删掉这次建的密钥：意图里记了哪些就删哪些，用 `removeSecretIfIv`。不是我们的 iv（被别人改过）就不删，记一条。
   2. 删掉暂存目录。删之前确认三件事：它就是 `<appDir>/import/bridge/<txId>`；是真目录；`bridge.plist` 已经不在里面了（还在就说明没搬回去，这时不删暂存目录）。
4. 最后一笔日志同时写结局和 `cleanupPending`：
   - 结局：第 2 步 bootstrap 失败或者等不到，是 `rollback-failed`；否则是 `rolled-back`。error 写原来那次失败的原因。
   - `cleanupPending`：第 3 步都做完了是 `false`，否则留着 `true`。

第 2 步 bootstrap 失败或者等不到：
- 先只在日志里记一笔"bridge 没能重新启动"，步骤还是 `rolling-back`，第 3 步照做；
- 结局写成 `rollback-failed` 时，告诉用户："bridge 没能重新启动。请在终端运行 `feishu-codex-bridge start`。"
- 不反复重试。

第 3 步的清理失败：只记日志，不影响 bridge。`cleanupPending` 留着 `true`，下次启动时 `recoverBridgeImport` 再清一次。

### 4.9 关机

host 收到停止或重启的请求时（`ShutdownControl.requested`）：
- `shutdown()` 让事务在下一个步骤边界停下，然后回滚；`staged` 时直接回滚。
- host 的退出要等这次回滚做完。时间算在现有的关机宽限里，在 `runSupervisor` 的收尾、停子进程之前调。
- 宽限内没做完，就留着日志，下次启动时 `recoverBridgeImport` 接着做。

### 4.10 启动时恢复

在 `runHostRuntime` 里调 `recoverBridgeImport()`：只在 host 里（`!process.send`），拿到 pid 锁之后、进 `runRun` 之前。要在读注册表之前调，因为 s62 的回滚会改注册表。有两种情况要处理：

**步骤在 `stopping` 到 `staged` 之间（包括 `rolling-back`）。** 这说明上一个 host 在事务中途死了，这时：
- 旧 pid 已经死了，它的锁 bridge 会当残留锁清掉（e07 第 3 条）。这里不去动锁文件。
- 照 4.8 的第 2 到 5 步做一遍。每条意图都按 4.4 核对实际状态，不管有没有"做完了"那一笔。
- error 写"daemon 在导入中途退出了，已经回滚"。

**步骤已经是 `rolled-back` 或 `rollback-failed`，但 `cleanupPending` 还是 `true`。** 只把 4.8 的第 3 步再做一遍。全做完了，把 `cleanupPending` 改成 `false`，结局不变。

恢复失败也不挡 daemon 启动，只记日志，把步骤改成 `rollback-failed`，`cleanupPending` 不动。

### 4.11 RPC 和隐藏命令

**RPC**
- `machineRequestSchema` 加 `z.object({ type: z.literal('bridgeImport'), action: z.enum(['start', 'rollback', 'status']) })`。
- `machineReplySchema` 加 `{ type: 'bridgeImport', view: ImportView | null }`。
- `machineRpc` 经 `MachineServiceContext` 拿到 `BridgeImporter`：
  - 没有导入器时（不是 host，或者不是 macOS）回 `unsupported()`；
  - `start` 是 mutation，其余是 read。

**隐藏命令**
- `program.command('__import-bridge <action>', { hidden: true })` 照 `bot list` 的写法连 daemon。
- 打印 `ImportView`：一行一个字段，notes 一行一条，带 `--json` 时输出 JSON。
- `start` 之后每秒查一次，直到步骤不再变化（`staged`、`rolled-back`、`rollback-failed`、`refused`）。
- 这是测试入口，不进 help，不写进 product.md。s63 的导入页用同一个 RPC。

### 4.12 故障注入

只给验收用：
- 环境变量 `VONVON_TEST_IMPORT_FAIL`，取值 `after-stop`、`after-lock`、`during-copy`、`after-copy`。
- 只有 host 进程读它，在对应的位置抛一个错，走正常的回滚。
- `during-copy`：写完第一个 bot 的暂存文件、写第二个之前抛。
- 照 `VONVON_TEST_CRASH` 的样子，host 每次启动只要看到这个值，就记一条 `test_seam`，并打到 stderr。
- 值不认识就忽略，也记一条。

单测另有一个只经 `ImporterDeps.fault` 传进去的 `crash-after:<动作>`（第 5 节第 26 条），环境变量里认不到它，生产进程碰不到。
