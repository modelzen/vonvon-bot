# 切片的详细计划

2026-10-19 起，新切片由 Codex 照这里的计划写代码，Claude 写计划、审查、合入（`AGENTS.md`"2026-10-19 起"）。每片一份，文件名 `<片>.md`，例如 `s27a.md`。计划由 Claude 写，走纯文档 PR 合入；实现的 PR 里，Codex 不改计划，和计划不一样的地方写进 PR 描述。

计划要写到能直接动手：不用再读设计讨论，也不用回头问。行号以计划合入时的 `main` 为准，以后会漂，按函数名找。

## 每份计划的几节

1. **做什么**：一两句话，用户能看到什么变化。依赖哪些片，已合入的写 PR 号。
2. **范围**：这一片做什么、不做什么，不做的留给哪一片。
3. **现在的代码**：要改的文件、函数、类型和行号；相关的旧行为。
4. **怎么改**：按文件或按步骤写清楚。
   - 数据结构、函数签名和调用顺序；
   - 并发和出错时怎么办，停机时怎么收尾；
   - 产品行为引用 `docs/product.md` 的节号，不另写一套。
5. **测试**：要加的用例，每条写输入和期望。今天的 `main` 上会失败的，标"main 必败"。
6. **Codex 的自测**：先写这一片交给哪台机器上的 Codex（要桌面、macOS 的给 Mac，要 JP-VPS 测试环境的给 JP-VPS），再写：
   - 用哪个测试环境里的哪个 bot、哪个群：Mac 的见 #322 正文"Mac 的测试环境"，JP-VPS 的见 #422 正文第 4 节。计划写明自测用哪个群；没写的不发飞书消息；
   - lark-cli 的命令和期望看到的结果；
   - 界面上的步骤优先写成用 Codex 自带的网页控制在网页端做；只有桌面外壳自己的行为、托盘、菜单和系统弹窗这类网页端碰不到的，才用 Computer Use，单列；
   - 哪些步骤做不了，原因写进 PR。
7. **文档**：
   - 要改的 `docs/product.md` 的节；
   - `docs/v1-plan.md` 里这一片那一行要勾上，加"<片> 做法"。先不写 PR 号，Claude 合入前补；
   - 第 5 节要加的默认值。
8. **验收要点**：给审查者的清单，一条一条能核对。每份计划的验收要点里都有一条：diff 里没有真实 id、密钥、本机路径。
9. **风险和行数**：估计改多少行，不含 lockfile。超过 1,500 行就先拆，拆法写在这里。

## 计划和实现的关系

- 计划里定的产品行为，实现时不改。要改，Codex 停下，结果里写"卡住了"，由 Claude 问 owner，再改计划。
- 纯技术的取舍（函数怎么拆、测试怎么写）Codex 可以自己定，写进 PR 描述"和计划不一样的地方"。
- 实现合入以后，计划文件留着，作为这一片当时的设计依据，不跟着以后的代码更新。
