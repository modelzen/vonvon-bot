## 1. 做什么

智能群里，我的回答写了 `@名字`（这个群里的另一个 bot），回答卡定稿以后，我再回复这张卡发一条文字消息，里面是真正的 @ 加上含 @ 的那一句。对方收到后调一次判断，定回不回、回在哪（s27a）。这是 3.4 例子第 5 行"小P 在 T2 的回答里写了'@小审 帮我看下这个方案'，程序发成真 @"的发出那一半。

发送失败或没收到发送结果，回答卡最后一行灰字写明。@ 的名字在群里有两个同名的 bot 时不交接，卡上也写一行灰字。

被 bot 叫醒的回合：没有完成提醒（s27a 挡，任何提醒模式）。要不要 @ 回对方只看 agent 的回答，写了就是一条交接，所以一张卡最多一条 @ bot 的消息（3.4"bot 之间"、3.8"完成提醒"）。

bot 之间来回停不停得下来，不归本片管：没有来回次数的上限，对方靠自己的判断和每小时 60 次的判断上限停（3.4"bot 之间"），本片不数、不拦。

产品依据：`docs/product.md` 3.4"bot 之间"、交接段（"交接按实际消息状态显示接收者和已有消息、话题的位置。发送成功只说明已发出，观察到对方响应才说明对方已开始处理；失败或结果未知如实显示。不为交接另加私有信道、确认循环或新的 bot 身份"）、"一个例子"第 5 行，3.8"完成提醒"；`docs/v1-plan.md` M5 切片表 s27b 那一行（Claude 已在 #432 改好）、"s27 开工要点"三条。

### 4.1 名字→id：`D/bot/bot-handoff.ts`（新）

```ts
import type { RosterBot } from './bot-roster';
import { atTags, neutraliseAts } from '../card/at-guard';
import { codeSpans } from '../card/md-scan';
import { personName, sanitizeContext } from './context-weave';
import { stripFileTokens } from './media';

export const HANDOFF_TEXT_MAX = 200;
export const HANDOFF_SEND_MS = 10_000;
export const HANDOFF_FALLBACK = '请看上面的回答';

export interface Handoff { openId: string; name: string; /** 含这个 @ 的那一句，去掉 @ 以后；可能为空 */ sentence: string }
/** 我自己：名册里的 open_id（`channel.botIdentity?.openId`）和 app_id（`channel.rawClient.appId`），都可能没有。 */
export interface Me { openId?: string; appId?: string }
export interface Found { handoffs: Handoff[]; /** 回答里 @ 到、却对应不止一个候选 bot 的名字（personName 后），去重；这些不交接，卡上各写一行 `ambiguousNote` */ ambiguous: string[] }

/** 回答里 @ 到的这个群里的别的 bot，按第一次出现的顺序，每个一次。 */
export function findHandoffs(text: string, bots: ReadonlyMap<string, RosterBot>, me: Me): Found
```

规则，按这个顺序写进代码注释和测试：

1. **候选名单**：`bots` 里 `openId !== me.openId`、`appId !== me.appId`（`me.appId` 非空时才比；名册的 bots 桶里本来就有我自己，`botIdentity` 没解析出来时靠 app_id 排除）、`personName(name)` 非空的。名字按长度从长到短排，同长按 open_id 排，结果才稳定。
   - **同名**：`personName` 后相同（ASCII 不分大小写）的名字对应不止一个候选 bot 时，这个名字是"歧义名"：两个人的 bot 都叫"Vonvon Bot"，或者"小审(1)"和"小审1"去括号后撞名，都算。歧义名照常参加前缀匹配（它仍然挡住更短的名字），但匹配到了不记交接、不随便挑一个，名字进 `ambiguous`。卡上照其他没交接的情况写一行脚注（下面的 `ambiguousNote`：`→ 想 @ 小审（bot），没交接：群里不止一个叫 小审 的 bot`），不列 id；日志照记（4.2）。Claude 10-19 定，见第 9 节。
2. **代码跳过**：`codeSpans(text)` 的区间里的 `@` 和 `<at` 都不算（agent 贴代码、贴日志里的 @ 不是交接）。`feishu-card` 围栏不是代码，`codeSpans` 已经这样定。
3. **`@名字`**：扫每个 ASCII `@`（U+0040）。前一个字符是 ASCII 字母、数字或 `/` 的不算（`a@b.com`、`node_modules/@types`）。在它后面，取候选里第一个能作**前缀**的名字（已按长到短排，所以是最长的）：
   - 比较：`text.slice(i + 1, i + 1 + name.length)` 和 `name`，ASCII 字母不分大小写，其余字符精确比。名字里的空格照原样比（`@Vonvon Bot 8` 能中，`@VonvonBot8` 不中）。
   - **ASCII 边界**：名字最后一个字符是 ASCII 字母或数字时，看名字后面紧跟的字符 `c`：`c` 是 ASCII 字母或数字，边界不成立；`c` 是 `_`、`-`、`/`、`.` 之一且再后面一个字符是 ASCII 字母或数字，边界也不成立（`@types/node`、`@bot-8x`、`@Jojo.Wang` 都当文字）；其他情况（标点、空格、中文、行尾、`.` 后面是空格或行尾）边界成立。名册有"Bot 8"时，`@Bot 80` 不中，`@Bot 8，`、`@Bot 8 请审`、`@Bot 8.`、行尾都中。
   - **边界不成立就不退回更短的名字**：这一处 `@` 当文字，往后扫。名册有"Bot"和"Bot 8"时，`@Bot 80` 不中"Bot 8"，也**不**中"Bot"。
   - 中文名不要求边界：`@小审帮我看` 中；`@小码哥 你看下` 中"小码"，句子是"哥 你看下"。名册里没有真人的名字可比，分不出"小码哥"是不是另一个人；误交接一次，对方会自己判断要不要回，代价是对方多花一次判断，写进 v1-plan 第 5 节（第 7 节）。`@小审2` 和 `@小审` 同在名册时，最长前缀选 `小审2`。
   - `@Jojo Wang`（名册有"Jojo"）：中"Jojo"，句子"Wang"。真人全名和 bot 短名撞头的，同上，接受。
   - 中了就记一条（歧义名进 `ambiguous`，见规则 1），扫描位置跳到名字末尾。没中就是普通文字，往后扫。
4. **agent 自己写的 `<at …>`**：`atTags(text)`（从 at-guard 导出，见下）给出每个开标签的 id 和区间；id 在候选名单里的记一条，起点在代码区间里的不算。它在卡上已被 s27a0 变成文字；这里认的是回答原文。
5. **每个 bot 只记一次**：按 open_id 去重，留第一次出现的那条（它的句子）。顺序按第一次出现的位置。
6. **句子**：边界是 `。！？!?；;` 和换行。一条记录的句子 = 它所在位置前后两个边界之间的文字（含末尾标点），按这个顺序清理：
   1. 去掉其中所有记录到的 `@名字` 和 `<at …>…</at>`（含歧义名的那几处）；
   2. `neutraliseAts(s, undefined)`（at-guard.ts:42）：剩下的每个 `<at>` 都变成文字 `@名字`——`<at user_id="all">所有人</at>` 变"@所有人"，真人的 `<at user_id="ou_…">张三</at>` 变"@张三"。不这样做，这些 `<at>` 会原样进 text 消息，text 不经 at-guard（at-guard.ts:83-91），就会真的 @所有人、把真人再 @ 一次，绕过 s27a0 的出口规则；
   3. 去掉剩下的所有 `<` 和 `>`（句子是复述，不需要任何标签）；
   4. `stripFileTokens`，再 `sanitizeContext(s, HANDOFF_TEXT_MAX, true)`。
   去完没字就是空串。
7. 不是候选的名字（真人、`@所有人`、不在群里的 bot）当普通文字，不记，后面也没有脚注：我们不知道它是谁。

`atTags` 加在 `D/card/at-guard.ts`，紧挨 `neutraliseAts`：

```ts
/** Every opening `<at>` tag that names an id (s27b reads the answer text for a bot's own `<at>`). */
export function atTags(text: string): { id: string; start: number; end: number }[]
```

用 `text.matchAll(AT)` 扫（`matchAll` 自己复制一份正则，不和 `neutraliseAts` 的 `replace` 共用 `AT` 的 `lastIndex`；不用 `exec` 循环），每个匹配用 `AT_ID`（:38）取 id；`tag.length === 3`（只有 `<at`）和没 `=` 的（`<at least>`）跳过；`end` 是整个匹配（含 `</at>`）的末尾。不改这两个正则。

**交接文字**：

```ts
/** 一条 text 消息的正文：每个 bot 一个真 @，后面是含 @ 的那几句，一共不超过 200 字。 */
export function handoffText(handoffs: readonly Handoff[]): string
```

- `<at user_id="${openId}">${name}</at>`，每个 bot 一个，用一个空格连起来；name 去掉 `<`、`>`、`&`。正文里的 `<at` 只有这里拼出来的这几个：句子在规则 6 已把所有 `<`、`>` 去掉。
- 句子：按顺序取各条的 `sentence`，去重（同一句里 @ 了两个 bot 只留一句），用一个空格连成一行，再 `sanitizeContext(joined, HANDOFF_TEXT_MAX, true)`（超了截到 200 个码元并加"…"，所以最长 201 个码元）。
- 一个字都没有（agent 常把"@小审"单独写一行）→ `HANDOFF_FALLBACK`"请看上面的回答"。
- 返回 `${ats} ${sentences}`。发送时包成 `JSON.stringify({ text })`。

例：回答"方案在上面。\n@小审 请审一下。" → `<at user_id="ou_审">小审</at> 请审一下。`；回答"@小审 @小码 你们看看" → `<at …>小审</at> <at …>小码</at> 你们看看`。

**脚注**：

```ts
/** 没发出、没确认的原因。 */
export type HandoffMiss = 'failed' | 'timeout' | 'unknown';
/** 回答卡最后一行的灰字；只在没发出、没确认时有。 */
export function handoffNote(names: readonly string[], why: HandoffMiss): string
/** 同名没交接的那一行，一个歧义名一行。 */
export function ambiguousNote(name: string): string
```

- 开头固定 `→ 想 @ `，然后 `小审（bot）`（名字去掉 `<`、`>`），几个用"、"连；然后：
  - `failed`：`，没发出：发送失败`
  - `timeout`：`，没收到发送结果：超时，可能已发出`
  - `unknown`：`，没收到发送结果：可能已发出`（传输异常、缺 code 等无效业务响应，不称超时）
- `ambiguousNote`：同样的写法，`→ 想 @ 小审（bot），没交接：群里不止一个叫 小审 的 bot`（名字去掉 `<`、`>`）。先写结果，冒号后写原因。不列 id，不说是谁的 bot。
- 不写时间，不写"已 @"（发出去的那条文字本身就显示了交给谁、在哪个位置，3.4 交接段）。
- 原因的文字放在一个按 `HandoffMiss` 取的表里（`const MISS: Record<HandoffMiss, string>`），不写成 if 链。

### 4.2 什么时候发：`handOff`（新，orchestrator 里，放在 `sendCompletionReminder` 旁边）

在 `launchRun` 的 `if (!gone) try { … }` 里，围栏卡循环之后、`patchSession` 之前加一行：

```ts
await handOff(rc, stream, finalMsgId, answerText, terminalCardUpdated, opts);
```

```ts
async function handOff(rc: RunCardState, stream: RunCardStream, cardId: string, answerText: string, cardUpdated: boolean,
  opts: Pick<LaunchOpts, 'chatId' | 'flat' | 'smart'>): Promise<void> {
  // 顺序：0 只在智能群、正常结束、卡还在；1 定稿成功；2 只有同名的：不发、写同名脚注；3 发一条文字；
  // 4 失败或结果未知再定稿写脚注；5 发出了、另有同名的：再定稿写同名脚注。同名的几行跟在没发出那一行后面一起写。
  if (!opts.smart || rc.rs.terminal !== 'done') return;
  if (!answerText.includes('@') && !/<at\b/i.test(answerText)) return;   // 便宜的预判，不读名册
  const ref = cardId.slice(-6);
  const done = (fields: Record<string, unknown>): void => log.info('card', 'handoff', { ref, ...fields });
  if (shuttingDown) { done({ sent: false, why: 'shutdown' }); return; }
  await orStop(roster.load(opts.chatId), undefined);   // 过期才读，最多 3 秒；停机马上放手
  const bots = roster.peekForHandoff(opts.chatId);
  if (!bots) { done({ sent: false, why: 'no-roster' }); return; }   // 名册不可用或不完整：不交接，不加脚注
  const { handoffs: found, ambiguous } = findHandoffs(answerText, bots, { openId: channel.botIdentity?.openId, appId: channel.rawClient.appId });
  if (!found.length && !ambiguous.length) return;
  const to = found.map((h) => h.openId.slice(-6));
  // 脚注：没发出或没确认的一行（有的话）在前，同名的每个名字一行在后；一行都没有就不再定稿
  const note = async (why?: HandoffMiss): Promise<void> => {
    const lines = [...(why ? [handoffNote(found.map((h) => h.name), why)] : []), ...ambiguous.map(ambiguousNote)];
    if (!lines.length) return;
    rc.handoffNotes = lines;
    if (!(await stream.finalizeCard(channel, buildRunCard(rc)))) log.warn('card', 'handoff-note-failed', { ref, why: why ?? 'ambiguous' });
  };
  if (!cardUpdated) { done({ to, sent: false, why: 'finalize-failed' }); return; }   // 卡都没定稿，不发，也不再写卡
  if (!found.length) { done({ sent: false, why: 'ambiguous', names: ambiguous.length }); await note(); return; }   // 只有同名的：不发，写同名脚注
  // 读名册时开始停机：orStop 已放手，这里不能再把请求发出去（4.6"停机，还没开始发：不发"）
  if (shuttingDown) { done({ to, sent: false, why: 'shutdown' }); return; }
  const text = handoffText(found);
  const send: Promise<HandoffSendResult> = channel.rawClient.im.v1.message.reply({
    path: { message_id: cardId },
    data: { msg_type: 'text', content: JSON.stringify({ text }), reply_in_thread: !opts.flat },
  }).then(handoffSendResult, (err: unknown) => handoffSendResult(feishuError(err)));
  const r = await orStop<HandoffSendResult | undefined | 'stopped'>(withDeadline(send, HANDOFF_SEND_MS, 'handoff'), 'stopped');
  if (r === 'stopped') { done({ to, sent: 'unknown', why: 'shutdown' }); return; }   // 停机：不再写卡
  if (r === undefined) { done({ to, sent: 'unknown', why: 'timeout' }); await note('timeout'); return; }
  if (r.kind === 'unknown') { done({ to, sent: 'unknown', why: 'no-result' }); await note('unknown'); return; }
  if (r.kind === 'failed') { done({ to, sent: false, why: 'send-failed', code: r.code }); await note('failed'); return; }
  done({ to, sent: true, len: text.length, ...(ambiguous.length ? { ambiguous: ambiguous.length } : {}) });
  await note();   // 另有同名的：发出后再定稿，写同名那几行；没有就什么都不做
}
```

`orStop` 的类型参数要显式写（`bot-roster.ts:55` 也是这样写的）：`orStop<T>(p: Promise<T>, fallback: T)` 从第一个参数推 T 时，`'stopped'` 赋不进去，tsc 报 TS2345。

说明：
- **顺序**（写进代码注释）：定稿卡 → 围栏卡 → **交接文字** → `patchSession` → 完成提醒。交接放在完成提醒之前：提醒是这一轮给真人的最后一条，真人看到提醒时交接已经发了。
- **和完成提醒的关系**（3.8"完成提醒"，3.4"bot 之间"最后一条）：
  - 真人发起的回合：完成提醒今天照提醒设置发，@ 真人；交接 @ 回答里写到的 bot。@ 的不是同一个人，两条各发各的，不去重。s27b2 起智能群不按设置发提醒、只在出错或超时时发，那时正常结束的回合就只剩交接；本片不管。
  - 被 bot 叫醒的回合（`requesterKind === 'bot'`）：任何提醒模式都没有完成提醒，手动模式也不显示"完成后提醒我"，由 s27a 挡（`sendCompletionReminderReply` 和 `completionReminderView`），本片不加代码。要不要 @ 回叫醒我的那个 bot 只看 agent 的回答：写了 `@小P` 就是一条交接，没写就没有。所以一张卡最多一条 @ bot 的消息，对方不会被同一轮叫醒两次。
  - 插话不换发起人（s27a）：bot 的 @ 插进真人那一轮，提醒照真人的设置发给真人，交接照回答发；真人插进 bot 发起的那一轮，这一轮没有提醒，交接照回答发。
- `rc.rs.terminal !== 'done'`：⏹（`interrupted`）、出错、看门狗（`idle_timeout`）的回合不发、不加脚注。卡上可能留着半截"@小审 请审"，那是中断了的回答，不是交接；状态 note 已经写了"已被中断"等。日志里不单独记（没有 `@` 预判之前就返回了；要记的话加 `why: 'not-done'`，Codex 自定）。
- `dropSilentCard` 删了卡（`gone`）的根本不进这段。被 bot 叫醒的回合不走 `dropSilentCard` 的删卡（s27a 不给它设 `initiative`），空回答的卡留着，回答里没有 @ 就什么都不发。
- `!cardUpdated`（终态卡更新失败）：不发。卡上还是流式内容和 ⏹，这时发一条真 @ 等于把一张没定稿的卡交出去；完成提醒的"最终卡片更新失败"兜底照旧发（真人发起的回合）。也不再 `finalizeCard` 写脚注（刚失败过）。
- `roster.load`：过期才读。被 bot 叫醒的回合，s27a 的 `wakeSender` 查发信人时刚 `load` 过，这里不会再读；真人叫的回合最多等 3 秒，10 分钟一次。
- `peekForHandoff` 只返回完整名册：内部快照同时存 bots 和 complete，`has_more: true` 标为不完整；一旦观察到不完整，旧完整表不能用于交接，后续读失败也不能绕过，直到读到完整表才恢复。此片不补分页，不完整时连显式 at id 也不发。原 `peek` 继续供 at guard 读取旧表或部分表，保持它的中和用途。
- `!bots`：名册从来没读到过，或已知分页未完。卡上 agent 写的 `<at>` 已被 s27a0 全变文字，`@名字` 本来就是文字。不加脚注：我们不知道这个名字是不是 bot。日志 `no-roster`。
- `ambiguous`（4.1 规则 1 的同名）：匹配到的都是歧义名、一个都不发时，日志 `why: 'ambiguous'` 带个数，卡上写同名脚注；有能发的就照发，日志多一个 `ambiguous` 个数，发出后再定稿写同名脚注；能发的没发出（失败、超时），同名那几行跟在没发出那一行后面一起写。每个歧义名一行 `ambiguousNote`，不列 id。定稿失败（`!cardUpdated`）、停机的那几处照旧不写卡。
- 预判 `includes('@')`：大多数回答没有 @，不读名册、不扫。
- `shuttingDown` 查两次：读名册前一次，发送前一次。只查一次的话，读名册时开始停机，`orStop` 放手后代码继续往下走，`message.reply` 在套 `orStop` 之前就已经发出去了，日志却记 `sent: 'unknown'`，和 4.6 表"停机，还没开始发：不发"对不上。
- `handoffSendResult(reply: unknown): HandoffSendResult` 在边界用 zod 解析整数 code；联合类型为 `{ kind: 'sent' } | { kind: 'failed'; code: number } | { kind: 'unknown' }`。code 为 0 才成功；明确的非零业务 code 才失败。抛错先用 feishuError 取明确业务拒绝，没有业务结果的传输异常、缺 code、非整数 code 等均为 unknown，不重试，不声称没发出。
- `withDeadline` 第三个参数是日志名（s23f2 起要传）。超时不取消底层请求，那条文字可能已发出，所以脚注写"没收到发送结果"，`sent: 'unknown'`。
- 一张卡只发一条文字。`completionReminderSent` 那样的去重不需要：`handOff` 每张终态卡只走一次（在 `!gone` 分支里，每轮一次）。重试（🔁）是新的一轮、新的卡。
- **对方怎么处理这条文字**（s27a，3.4"bot 之间"）：它是我的 app 发的 `msg_type: text`、`mentions` 有对方。对方查发信人；我在它的响应成员名单上（或它没设名单），它就拿一次判断预算（算进它每小时 60 次）、调一次判断，三选一（话题里只判回不回）；判成开新话题的，话题开在这条文字自己下面。判断说不回、判断出错或超时、它这一小时 60 次判断用完了，它都不回，诊断页记一条。我不知道它判成什么，也不记（3.4 交接段"发送成功只说明已发出，观察到对方响应才说明对方已开始处理"）。来回停不停得下来靠它的判断和它的每小时上限，我这边不数。
- 不 `recent.addOwn` 这条文字：回答卡已经在 `recent` 里，这条只是其中一句的复述，判断不需要它。

### 4.3 和 s27a0 出口的关系

- s27a0 把卡片和 markdown 里 bot 的 `<at>` 变成 `@名字`，是因为卡片里的 @ 叫得醒、飞书的消息列表却看不到。本片不改它，也不绕它：交接走 `msg_type: 'text'` 的回复，text 的 @ 列表里看得到。`installAtGuard` 只包 `channel.send`（at-guard.ts:83-91），`rawClient.im.v1.message.reply` 不经它，不用加例外。
- 卡上"@小审"是文字，文字消息里 `<at user_id>小审</at>` 是真 @：读者在飞书里看到一张卡加一条回复它的 @，和"小P 发了卡，又 @ 了小审"一样。
- 脚注里的 `→ 想 @ 小审（bot）` 是纯文字，没有 `<at`，at-guard 不碰它。
- agent 写了 `<at id="ou_审">`（卡上已变文字）和写了 `@小审`，交接一样发。agent 写了 `<at id="ou_真人">`：卡上是真 @（s27a0 放行真人），本片不记（不在名册里；s27b2 才认真人）。
- 发送方不查对方开没开 `include_bot`、是不是规则模式：收不到的就是白 @，没有脚注（我们不知道也不该知道对方的模式，3.4"几个 bot 都会回的时候"）。

### 4.4 `LaunchOpts.smart`

- `LaunchOpts`（:5735）加 `/** The run's group was a smart one when it started (s27b): hands off the answer's @ to other bots. */ smart?: true;`，放在 `initiative`（:5744）旁边。

- `startTopicDirectly` 的 `launchOpts`（:3203）加同样一行。主区真人 @ 我、判断说开新话题的走这里；s27a 以后，bot 的 @ 判成开新话题的也走这里。

### 4.6 并发、出错、关闭

| 场景 | 结果 | 怎么保证 |
|---|---|---|
| 同一会话排了几轮 | 每轮定稿后各发各的，第 2 轮开始前第 1 轮的文字已发完 | `handOff` 在同一个循环里 `await` |
| 对方同一秒也在 @ 我 | 各发各的；各自收到后各判各的 | 不加本机状态 |
| 明确的非零业务 code（返回或异常体） | 不重试；再定稿一次写"没发出：发送失败"；`sent: false` | `note('failed')` |
| 传输异常、缺 code 等无效响应 | “没收到发送结果：可能已发出”；sent 为 unknown，不重试，不称超时 | note(unknown) |
| 发送 10 秒没回 | 脚注"没收到发送结果：超时，可能已发出"；`sent: 'unknown'` | `withDeadline`，不取消底层请求 |
| 发出去了，回答里另有同名的 bot | 发完再定稿一次，最后一行写同名脚注 | `note()`（4.2） |
| 再定稿也失败 | 日志 `handoff-note-failed`，没有别的 | 终态卡本来就可能更新失败，完成提醒兜底照旧 |
| 用户在定稿和发送之间删了卡 | 发送失败（回复的消息没了）→ 写脚注也失败 → 两条日志 | 同上 |
| 定稿卡更新失败 | 不发文字，不写脚注，`finalize-failed` | `!cardUpdated` |
| 名册没读到过或已知不完整 | 不发、无脚注、`no-roster` | `!bots` |
| 名册读到了、过期了 | 用过期的，后台已在刷新 | `load` 过期才读，最多 3 秒，`orStop` |
| `handOff` 自己抛错（不该发生） | 落到外层 `catch` `terminal-delivery`，发"⚠️ 本轮已结束，但结果同步失败" | 和围栏卡一样；`handOff` 里的发送已 `.then(ok, err)` 接住 |
| 发出去了，对方没回（对方规则模式、没开权限、不在它的响应成员名单上、判断说不回、判断出错或超时、它这一小时的判断用完了） | 群里看得到那条 @，对方没回；我不知道也不记 | 3.4 交接段："发送成功只说明已发出" |
| 两个 bot 来回交接停不下来 | 每一轮照回答发；停在对方判断说不回，或对方每小时 60 次判断用完 | 3.4"bot 之间"：没有来回次数的上限；本片不数 |
| 停机，还没开始发 | 不发、不写卡，`why: 'shutdown'` | `shuttingDown` |
| 停机，正在等名册 | `orStop` 马上放手，`peek` 多半有旧表，接着判同名，写不写脚注；发送前再查一次 `shuttingDown`，不发、不写卡，`why: 'shutdown'` | 两处 `shuttingDown` |
| 停机，正在等发送 | `sent: 'unknown', why: 'shutdown'`，不再写卡；那条文字在飞书那边自己完成或失败 | `orStop(…, 'stopped')` |

关闭顺序（`shutdown`，:7718）不改：`onStop` 全部放手时，`handOff` 的 `roster.load` 和发送都以兜底值返回，一个 tick 内结束，不等飞书；没回来的请求在自己的超时里结束。`handOff` 没有别的飞书读取。

### 4.8 日志

只有尾号、计数和固定的英文词，不写正文、名字和完整 id：
- `card handoff { ref, to: [尾号…], sent: true, len }`。
- `card handoff { ref, to?, sent: false, why }`，`why` 是 shutdown、no-roster、ambiguous（带 `names` 个数；卡上写同名脚注）、finalize-failed、send-failed（带 `code`）之一。
- 发出去了、另有歧义名没发的：`sent: true` 那行多一个 `ambiguous` 个数，卡上写同名脚注。
- `card handoff { ref, to, sent: 'unknown', why: 'timeout' | 'no-result' | 'shutdown' }`。
- `card handoff-note-failed { ref, why }`，`why` 是 failed、timeout、unknown、ambiguous 之一（只有同名那几行时是 ambiguous）。
- 发送异常不记录原始 Error 或正文，只记固定 why 和明确业务 code。
