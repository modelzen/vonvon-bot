# s62：导入事务（下）：Codex 兜底、hook、启动、回执

## 1. 做什么

接着 s61 的"已暂存"，做 product 第 5 节"怎么迁"的第 6 到 9 步，并把导入提交：
1. 找不到别的 codex 时，用 bridge 自带的那份；
2. 先备份，再卸掉 bridge 装进 Claude Code 和 Codex CLI 的 hook；
3. 把暂存的 bot 搬进 Vonvon；
4. 启动全部 bot，等长连接连上；
5. 再查一次 bridge 的后台服务；
6. 写迁移标记，给出回执。

导入以后，daemon 每次启动都会先占住 bridge 的锁。bridge 正在跑某个 bot 时，Vonvon 不启动这个 bot，并说明原因。

这一片没有界面，界面在 s63。

依赖：s61（以及它的依赖 s59、s60）。真机检查用 s61 准备好的 Mac 测试用户。

## 2. 范围

- 提交点、迁移标记、回执。
- 之后每次启动都占 bridge 的锁，bridge 在跑时的处理。

## 4. 怎么改

步骤接在 s61 的 `staged` 后面，去掉 s61 在那里的停顿。`ImportStep` 加上这几个值：`codex`、`hooks`、`moving`、`starting`、`finishing`、`done`。

每个动作都照 s61 4.4 的规矩：先记意图，意图里带着事后核对要用的东西；回滚和恢复按实际状态核对，不信"做完了"那一笔。预留（s61 4.4a）一直有效到 `done`，或者回滚的清理做完。

### 4.1 第 6 步：codex

1. `resolveCodexBin({ force: true })` 找得到：什么都不做。
2. 找不到，但 bridge 自带的 codex 在（预检的 `bundledCodex` 是 `present`）：引用 bridge 那份。
   - 做法：`locateBin` 的候选目录最后加一项 `<bridge>/codex-cli/node_modules/.bin`，只在导入完成的标记（4.6 的 `done.json`）在时才加。
   - 不另存设置，不复制文件。回滚时标记还没写，这一项自然不生效。
   - 回执里写"用的是 bridge 自带的 Codex"。
3. 两样都没有：不挡导入，回执里写"没找到 Codex，到「环境」页装一个"。

第 3 条改了 product 第 5 节第 6 步里的"或者装一份"（Claude 2026-10-20 定）。导入时装 Codex 要联网、要等，装不上还会让整个导入回滚；"环境"页本来就有装 Codex 的流程。

### 4.2 第 7 步：卸 hook

新文件 `D/import/bridge/hooks.ts`。

**认哪些 hook**
- 把 s59 `hookFor` 里认 bridge 命令的正则，抽成 `classifyHookCommand(command)`，预检和这里共用。返回三种：`bridge`、`vonvon-legacy`、`other`。
- `vonvon-legacy` 是 s02c2 留下的 Electron 时代的 vonvon hook：`"<…>" "<…/bin/vonvon.mjs>" hook …`。v1-plan 的 s02c2 写了归 s62 卸。
- 不认 `agent2lark-hook`，也不认别的命令。
- 所有 bot 的、带不带 `--bot` 的，都卸。整个 bridge 都不用了。

**删哪些**
- 两个文件：`~/.claude/settings.json` 和 `~/.codex/hooks.json`。
- 用 s59 的 `readLocalText` 读，限大小，严格 JSON。移植 #226 的形状检查，形状不对就失败回滚，error 写出是哪个文件。
- 删掉 `bridge`、`vonvon-legacy` 两种 hook。一组的 `hooks` 删空了，这一组也删掉；一个事件下的组删空了，这个事件也删掉。删法照 bridge 自己的 `removeHookGroups`。
- 其余的键和值原样留着。
- 文件不在、或者里面没有要删的：不写这个文件。

**备份放在哪：** `<appDir>/import/bridge/backups/<txId>/`，和 s61 留 plist 原件的是同一个目录。这个目录不在暂存目录里，回滚、清理、导入完成都不删它。

**怎么写**
1. 把原文件的字节写进备份目录的 `claude-settings.json`、`codex-hooks.json`，fsync。
2. 算好新内容：`JSON.stringify(value, null, 2) + '\n'`。
3. 先记意图：文件路径、原内容的 sha256、新内容的 sha256、备份路径。
4. 新内容写成同一个目录里的临时文件，权限和原文件一样，fsync。
5. rename 之前再读一次原文件，sha256 变了就失败回滚："Claude Code 的设置在导入时被改过，请重试。"
6. rename，fsync 目录。

**`config.toml` 不改。** bridge 自己的卸载会关掉 `features.hooks`，但这个开关可能是用户别的 hook 也在用的；hook 都删了以后，开着它也不起作用。和 bridge 的卸载在这一点上不一样，写进 PR。

**回滚和恢复**，按意图核对现在文件的 sha256：
- 等于新内容的：说明是我们写的，把备份原样写回去，写法同上。
- 等于原内容的：说明 rename 没做成，什么都不用做。
- 都不等（导入以后又被改过）：不动，回执和日志里写"hook 文件后来被改过，没有还原，备份在 <路径>"。这个路径在备份目录里，回滚清理完以后还在。

**备份留着。** 导入完成后备份也不删，回执里写出备份的位置（product"备份后卸掉"）。

### 4.3 第 7b 步：把 bot 搬进 Vonvon

s61 暂存每个 bot 目录时，已经在里面放了一个空文件 `.vonvon-import-<txId>`，用来认出这是本事务的目录。

对每个 bot：
1. **搬目录。**
   1. 再核对一次：`botPaths(appId).dir` 不存在，注册表里没有这个 `appId`。预留挡着正常注册，这里应该不会撞；撞了就失败回滚，不动那个目录。
   2. 先记意图：从暂存的 `bots/<appId>/` 搬到 `botPaths(appId).dir`。
   3. rename。暂存目录和 bot 目录都在 `<appDir>` 底下，同一个卷。
   4. 恢复时这样判断：目标那里有目录、里面有 `.vonvon-import-<txId>`，就是我们搬过去的；源那里还在，就是没搬。
2. **注册。** `registerBotEntry` 加一个导入用的选项 `{ txId, registrationId, onBeforePublish }`：
   - `registrationId` 由导入器事先生成，先记进意图，再调 `registerBotEntry`。函数里用它，不再自己生成。
   - 这个 `appId` 已经注册了：返回错误，不返回 `already-registered`，导入也不认领别人的条目。
   - 分配记录是这次新建的，就在发布之前调 `onBeforePublish(allocation)`。导入器在回调里把 handle 记进意图，记好了才往下发布。
   - `persistAccount` 只核对搬进来的 `config.json` 是完整的、`appId` 一致，不重写。
   - 参数用 s60 给的 `entry`：`appId`、`tenant`、`botName`；想用的名字给 `desiredName`；`initialPreferences` 取 config 里的 `preferences`。
3. **启用状态。** 按 s60 给的 `active` 调 `setBotActivation`。bridge 里没启用的 bot，导进来也不启用，回执里列出来。

`done` 以后，`.vonvon-import-<txId>` 这个空文件尽量删掉；删不掉留着也没关系，没有代码读它。

### 4.4 第 8 步：启动全部 bot，等它们连上

- 对每个 `active` 的 bot，走和网页上"启用 bot"同一条路（admin service 的启用：先 `setBotActivation`，再 `applyBotActivation(appId, true)`）。
- 然后每秒用 `status` IPC 查一次 `connection`，等到 `connected`，每个 bot 最多 60 秒，几个 bot 一起等。
- 有一个 bot 连不上，就失败回滚，error 写出是哪个 bot、最后看到的状态。
- 这时 bridge 的锁一直在 host 手里（s61 拿的），bridge 起不来。

### 4.5 第 9 步：再查一次 bridge，写标记，提交

1. **再查 bridge 的服务。** 用 `launchctl print`，再看 plist 的位置。有人在导入期间跑过 `start` 时：
   - 照 s61 4.5 的做法再停一次；
   - 这次挪走的 plist 叫 `bridge.plist.late`；
   - 回滚时只放回第一次挪走的那份。
2. **写 bridge 一侧的标记**，给 s64 读：
   - 位置：`<bridge>/vonvon-migration.json`，内容 `{ "version": 1, "migratedAt": <毫秒>, "bots": [<appId>…], "vonvonVersion": "<版本>" }`；
   - 先记意图，带上内容的 sha256，再按日志的写法写；
   - 回滚和恢复：文件的 sha256 和意图里的一样才删，不一样就不动。
3. **写 Vonvon 一侧的标记，这就是提交点。**
   - 位置：`<appDir>/import/bridge/done.json`，内容 `{ "version": 1, "txId", "at", "bridgeDir": <realpath>, "bots": [<appId>…] }`；
   - 日志的步骤随后改成 `done`；
   - 判断提交没提交，只看 `done.json` 在不在，不看日志的步骤。写完 `done.json`、日志还没改就被杀，恢复时看到 `done.json` 在，就把日志补成 `done`；
   - 从这里开始不再回滚。
4. **回执。** `ImportView` 的步骤是 `done`，`notes` 里放：
   - s60 给的差异；
   - 4.1 的 codex 那一行；
   - 4.2 的备份位置；
   - 没启用的 bot；
   - 最后一行固定是"旧目录不要删，空白项目还在里面"（product 第 5 节第 9 步）。

提交以后再出的错（比如回执发不出去）只记日志，不回滚。

### 4.6 之后每次启动都占 bridge 的锁

在 `runSupervisor` 里，起子进程之前：
1. 读 `done.json`：限大小，zod 校验。读不了，就照"锁读不了"处理：不启动标记里的 bot，提示，等着重试。
2. 对标记里、而且还在注册表里的每个 `appId`，用 host 的 `BridgeLocks` 拿锁（`createDir: false`，`onExit: false`）。

   有三种情况：
   - **拿到：** 照常起这个 bot 的子进程。
   - **bridge 的 `bots/<appId>/` 目录已经不在了**（用户删了旧目录）：bridge 跑不了这个 bot，不用占锁，照常起。
   - **`BridgeAlreadyRunningError`**（bridge 正在跑它，e07 第 7 条）：不起这个子进程。
     - 在 `Child` 上记 `bridgeHeld: { pid, since }`，每 `LOCK_SLOW_MS` 重试一次。拿到就起；一直拿不到就一直等，不加上限。
     - 提示接到现有的 `lockHeld` 上，加一个 `by: 'bridge'`。网页、桌面端和 `vonvon bot list` 显示："bridge 正在运行这个 Bot（PID x）。在终端运行 `feishu-codex-bridge stop` 停掉它，Vonvon 会自动接上。"
     - 持有者的 pid 变了才再记一条 `log.warn`。
   - **别的错误**（锁文件坏了、没权限）：同样不起这个 bot，提示里写"读不了 bridge 的锁文件"，每 `LOCK_SLOW_MS` 重试。不放行，免得两边抢同一个应用的卡片回调。
3. 什么时候放锁：
   - bot 被禁用：照样占着锁，导入以后的意思就是不让 bridge 跑它。
   - bot 从 Vonvon 里删掉（`removeBot` 那条路）：放掉它的锁。
   - host 退出：`BridgeLocks` 统一放。
4. **核对手里的锁。** host 每 `LOCK_SLOW_MS` 核对一次手里的每把锁，看锁文件里还是不是 host 的 pid：
   - 锁文件被删了：马上重新拿；
   - 被一个活着的 bridge 进程换掉了：先停掉这个 bot 的子进程，免得两边同时连着同一个应用，再走第 2 条的第三种情况，等它退出；
   - 锁文件坏了：同样停掉这个 bot，走第 2 条的第四种情况。

   最常见的原因是钟跳：系统时钟往前跳 15 秒以上时，bridge 会把这把长期持有的锁当成 pid 复用而抢走（e07"没测到的"）。核对有间隔，最多有一个 `LOCK_SLOW_MS` 的时间两边都连着，写进风险。

### 4.7 回滚

在 s61 的回滚前面加几步，按倒序做，每步先记日志。进入回滚的那一笔照 s61 4.8，同时写 `rolling-back` 和 `cleanupPending: true`，在下面第 1 步之前；结局和 `cleanupPending` 也照 s61 在最后一笔里一起写。

1. **删 bridge 一侧的标记：** 写过才删，删前核对内容。
2. **停掉这次启动的 bot：** 用 supervisor 的 `stopBot`，关机时也能用，不走 `applyBotActivation`。
3. **撤销注册：** 新加 `unregisterImportedBots(entries)`，在 `bots` mutex 里只发布一次。
   - 只删 `appId` 和意图里的 `registrationId` 都对得上的条目；
   - 分配记录只删意图里记了 handle、而且 handle 对得上的。
   - 分配时已经建好的空目录不删，在日志里记一条。
   - 不走 `removeBot`，它还会做别的事。
4. **把 bot 目录搬回暂存目录：** 用 rename。按 4.3 的判断，只搬里面有 `.vonvon-import-<txId>` 的目录。bot 跑的时候写的文件跟着一起走。
5. **还原 hook：** 照 4.2。
6. **接着做 s61 的回滚：** 放锁 → 放回 plist、重新加载 bridge → 删密钥 → 删暂存目录。

关机（s61 的 4.9）和启动时恢复（s61 的 4.10）都包括这几步：
- 没有 `done.json`、日志的步骤在 `codex` 到 `finishing` 之间，就整个回滚。每条意图都按实际状态核对。
- 恢复时还没有起任何子进程，第 2 步跳过。
- 恢复在读注册表之前，所以第 3 步撤销的条目，supervisor 根本看不到。

### 4.8 RPC 和命令

- `start` 一直走到 `done`，或者回滚完。
- `rollback` 这个 action 去掉：中间不再停顿。
- `status` 在 `done` 以后返回回执。
- `__import-bridge` 照旧是隐藏的。

故障注入点加上这几个：`after-hooks`、`after-move`、`during-start`（第一个 bot 已经启动以后）、`before-marker`、`after-bridge-marker`。

14. bridge 的 bot 目录不在：不占锁，照常起；也不替它建目录。
15. bot 被删掉：放掉它的锁。host 退出：只挂了一个 exit 回调，13 把锁时也没有 `MaxListenersExceededWarning`（main 必败）。

**恢复和关机**
16. 在 `moving`、`starting`、`finishing` 时被 SIGKILL：`recoverBridgeImport` 在读注册表之前整个回滚，supervisor 起来时看不到导入的 bot。
17. 在 `starting` 时关机：先停导入的 bot，再撤销注册，最后照 s61 的顺序做完。
18. 有了 `done.json` 以后被杀：恢复什么都不做，下次启动照常占锁、起 bot。

**密钥不外泄**

19. 照 s61 第 17 条：
    - 明文密钥哪里都不出现；
    - 日志、两个标记文件、本机的 `ImportView` 可以带完整 app id；
    - `console`、`log.*` 和错误信息只带 bot 的名字。

**崩溃空档**（用 s61 的 `crash-after:<动作>`）

20. 下面每个动作各跑一次，做完、"做完了"还没记上时被杀，然后跑 `recoverBridgeImport`：
    - 写 hook 文件的 rename；
    - 搬 bot 目录的 rename；

    - 写 bridge 一侧标记以后；
    - 写 `done.json` 以后。

    期望：前四个都整个回滚，结果同第 9 条；最后一个不回滚，日志补成 `done`。
21. hook 文件导入以后被用户改过，再在第 8 步失败：
    - 回滚不动那个文件；
    - 回滚清理做完以后，备份目录里的原文件还在，字节和导入前一样；
    - 回执里写的路径就是它。

**不认领别人的条目**

22. 导入注册时，这个 appId 已经注册了（测试绕过预留，直接写进注册表）：`registerBotEntry` 返回错误，导入失败回滚。那个条目、它的目录、config 和密钥都还在。

**核对手里的锁**

23. bot 在跑时，锁文件被换成一个活着的假 bridge 进程：
    - 一个 `LOCK_SLOW_MS` 以内，这个 bot 的子进程被停掉，`lockHeld.by` 是 `bridge`；

    锁文件被删：重新拿到，子进程不停（main 必败）。

## 9. 风险和行数

估计（不含 lockfile）：

| 部分 | 行数 |
|---|---|
| hook | 约 180 |
| 第 6 到 9 步、意图核对和回滚 | 约 260 |
| 之后每次启动占锁、定时核对（supervisor 和 lockHeld） | 约 110 |
| 导入注册的选项、撤销注册 | 约 60 |
| codex 兜底 | 约 15 |
| 测试 | 约 640 |
| 文档 | 约 40 |
| **合计** | **约 1,305** |

超过 1,500 就拆成两片：
- **s62a：** hook（4.2），带它的回滚和测试。
- **s62b：** 其余部分。

**风险：**
- **改 hook 文件会动到用户的格式。** 重新写出来是两空格缩进，用户原来的缩进和键的顺序以外的格式会变。只在里面有 bridge 的 hook 时才写，原文件有备份。
- **长期占锁会被钟跳抢走。** 见 4.6 第 4 条。host 定时核对，发现被抢就停掉这个 bot。从被抢到发现，最多有一个 `LOCK_SLOW_MS` 的时间两边都连着同一个应用，卡片回调可能落到 bridge 那边。抢走后表现为"bridge 正在运行这个 Bot"，用户停掉 bridge 就恢复了。
- **0.6.14 的 `start` 会把自启装回来**，被拉起的 `run` 一直被拒，日志会越来越大。这一片只在导入时再查一次；之后由 s64 让 bridge 看到标记就拒绝启动。
- **第 8 步受飞书影响。** 飞书那边慢或者出故障时，会整个回滚。回执的 error 写清是哪个 bot 没连上，用户可以重试。
- **撤销注册会留下空目录。** 分配时建好的空目录留着，以后再注册同一个 bot 会复用它。
