# Windows Provider 检测、模型缓存和安装包验收

## 做什么与范围

修复 0.8.1 运行中的群设置通过 supervisor 转发时超过 15 秒的问题。普通页面读取复用已成功的 Codex 环境和原生模型结果；用户重新检测时强刷，执行程序、账号、配置、自定义目录或 requirements 变化使对应缓存失效。保持 product.md 的原生 Provider、模型和权限语义，不用静态模型表冒充实时发现。

## 已确认原因

- #620 放宽了内部探测预算，未同步检查 supervisor → Bot IPC 的 15 秒期限。直接调用 settings owner 的验收没有覆盖实际转发链路。
- 模型读取强制执行版本和 Windows 沙箱体检；普通页面重开、焦点变化和 Provider 实例重建放大了重复工作。
- Windows holder 每次启动 PowerShell、编译 C#；原生命令本身和热模型缓存远快于这层开销。
- 正式包压力复验发现：进程树已确认退出后，输出管道仅有 500 ms 排空期限；调度延迟会把已读到的模型误判为清理失败。改为使用既有 10 秒关闭期限的剩余预算，仍等待管道真正关闭，并以 800 ms 延迟消费覆盖回归。
- 已安装 daemon 的字节与 0.8.1 源码按正式 staging 参数编译结果完全一致，安装目录关键文件也与更新安装包一致。

## 实现

1. Windows 的设置/Provider IPC 操作使用明确的冷启动预算，状态和无关操作保留短期限；真实挂死仍拒绝。
2. 模型元数据检查不启动沙箱探测。普通群设置复用同身份权限缓存；实际 start/resume 仍刷新并执行 fail-closed 验证；停止 Bot 的离线读取不启动 Provider。
3. Codex 原生目录使用进程内共享缓存及 single-flight；正常读取不因 TTL 启动新进程，过期的账号速度证据只移除速度选项。手动 refresh 不会被普通在途读取吞掉。自定义目录在所有异步步骤结束后复核指纹，旧身份结果不得覆盖新身份。
4. 环境、版本和 setup 复用版本证据；setup 接入首启 gate。成功的安装/账号结果按身份缓存，显式重新检测和安装/登录操作可更新。
5. 正式 Windows 包在 staging 时编译同一嵌入 C# 源码为独立 supervisor EXE，并把 SHA-256 嵌入 daemon。运行时校验字节后直接启动；缺失/变化拒绝。开发模式保留每 daemon 一次的 DLL 编译，认证 hello 绑定实际加载 digest。Job containment、控制管道、退出和清理回执保持原语义。
6. UI 区分普通读取和用户 refresh，不因窗口重新获得焦点重检。新状态取代旧请求时保留用户的强刷意图，避免旧结果盖回新状态。

## 检查与验收

- 缓存：普通/并发/跨实例读取、显式刷新、配置/账号/requirements/自定义文件变化、过期速度证据、刷新失败恢复和旧请求迟到。
- IPC：超过旧期限但正常结束、真实超时、子进程退场；实际 supervisor/Bot 设置链路在本机包中验收。
- 原生模型：同 executable、CODEX_HOME、cwd 的 model/list，比较顺序、ID、默认项、effort 和 hidden；静态 fallback 不得变成 ready。
- Windows：预编译 holder 的认证、孙进程清理、篡改拒绝、既有完整专项清单；真实 ARM64 包再验。
- 每个正式 Windows 包的 runtime smoke 使用该包的 EXE 和 daemon，通过原生协议 fixture 检查目录等价、缓存、手动刷新、失败恢复和配置失效。安装/覆盖/重装流程记录结果并绑定 source SHA 与安装包 SHA-256，不能沿用另一份产物的验收。
- 本机真实 Codex 验收证据保留在仓库外；不提交真实账号、群、密钥或本机路径。不向飞书发送验收消息。

## 合入和后续发布

最终提交通过独立审查、多角度审查、三平台 CI 及本机包验收后合入 dev。dev、main、公开发布分别报告。后续版本变更或重新构建必须运行最终候选自身的安装包验收；源码 SHA 和产物哈希绑定不得由“上次测过”代替。

## 风险

涉及进程启动、退出、异步缓存和构建流程，必须重点检查认证、并发刷新、取消及旧结果污染。缓存不代替真实会话权限验证。首次原生模型获取仍受 Codex 本身初始化和网络状态影响，不承诺任意机器固定耗时。
