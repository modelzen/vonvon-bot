# s31b0 计划：`vonvon secrets get` 在 Claude 沙箱里能用

行号按 `main` b57f5cd。路径缩写：`D/` = `packages/daemon/src/`，`T/` = `packages/daemon/test/`。

任务 94（s31b 开工前的实测 4.0 B，结果在 #422）停在这里：放开飞书凭据以后，Claude 沙箱里的 lark-cli 仍然用不了 bot 身份。原因有两处，和挡配置文件、限读无关，单独成片先修。s31b 依赖这一片，这一片合入后 s31b 重跑 4.0 B。

## 1. 做什么

- 对应 `docs/v1-plan.md` M6 的 s31b0 行。`docs/plans/s31b.md` 4.5 要靠它才做得到：owner 2026-10-19 选了 B，只读、读写档不挡飞书凭据，为的是 lark-cli 能以 bot 身份用。
- 依赖：代码上不依赖别的片。5.4 的真实测试用 s31（#443）的档。
- 用户能看到的变化：Claude 只读、读写档的会话里，lark-cli 经数据目录根上的 `secrets-getter` 能解出 App Secret。今天有两处挡着：
  1. 沙箱里，`vonvon secrets get` 先在 `D/cli/index.ts` 的 preAction 里进 `enterDataAccess`。Linux 上它要监听一个抽象 Unix socket，沙箱的 seccomp 不让，报 `listen EPERM`；它还要在数据目录里建 `.access/`、写租约，沙箱不让写。macOS 上还要建 `.locks/`、开带 `O_EXLOCK` 的锁文件，也是写。还没解密就以退出码 1 退出，stdout 没有 JSON。
  2. 沙箱外也不行。lark-cli 1.0.98 要求回复里有 `"protocolVersion": 1`，`secretsGet()` 只回 `values` 和 `errors`，lark-cli 报 `exec provider protocolVersion must be 1, got 0`。所以今天不管哪一档，包括终端里，经 getter 走 bot 身份的 lark-cli 都用不了。
- 不变：
  - 别的 `vonvon` 命令照旧拿准入锁、写租约。
  - 密钥库的写者照旧：`setSecret`、`removeSecret`、第一次建 `master.key`。
  - 决策模型的 key 照旧不交出。
  - 会话里调 `secrets list|set|remove` 照旧被拒（s23g）。

### 3.3 密钥库 `D/config/keystore.ts`

- 读者不拿锁。`getSecret`（`:99-110`）先 `readStore`（`:23-29`）：没有 `secrets.enc` 就返回 `undefined`，不读 `master.key`；有就 `keyForStore`（`:54-60`），再解密。daemon 自己就是这样读的：`resolveExecRef` 认出是自己的 getter 时直接调 `getSecret`（`D/config/secret-resolver.ts:87-94`），密钥页的 `keyStatus`（`D/admin/secrets.ts`）也一样。
- 写者用 `mutate`（`:113-122`）拿 `keystore` 互斥，最多等 30 秒；同一个进程里也排队。
  - `secrets.enc`：`writeStore`（`:80-90`）写临时文件、fsync、`rename`、fsync 目录。只有这里写它。
  - `master.key`：`keyForMutation`（`:62-78`）只在它不存在时建。做法是临时文件写 32 字节随机数、fsync，`link` 成 `master.key`（已经有了就用已有的，不覆盖），fsync 目录，再删临时文件。`setSecret`（`:124-132`）先建 key，后写 store。没有代码改写、删除 `master.key`，也没有往它上面 `rename` 的（全仓只有这里写它）。
- 每一项用 AES-256-GCM，`iv` 12 字节，`tag` 16 字节（`:9-15`、`:92-97`）。解密是 `update` 再 `final`，`final` 校验不过就抛 `KEYSTORE_DECRYPT`（`:105-109`）。
- `loadKey`（`:38-51`）：`lstat` 要求是普通文件、不是链接；用 `O_NOFOLLOW` 打开；要求 32 字节、权限 0600、本人所有。不看 `nlink`。
- `readStore` 用 `readFile` 读：跟着符号链接走，不看文件类型和大小。如果 `secrets.enc` 是 FIFO，会一直卡住。
- `getSecret` 用 `store.entries[id]` 取条目（`:103`）。`constructor` 这类 id 会取到原型上的东西，结果报解密错，而不是"没有"。
- 任务 94 在沙箱外用 strace 看过：getter 在数据目录里只碰 `secrets-getter`、`.access/<记录>.json`、`secrets.enc`、`master.key`。它不读 `.keystore.salt`；`paths.keystoreSaltFile` 没有代码用。

### 3.5 getter 和 lark-cli

- `ensureSecretsGetterWrapper`（`D/config/store.ts:70-86`）在数据目录根上写 `secrets-getter`（权限 0700），内容是 `VONVON_HOME=<数据目录>; exec <node> <入口> secrets get "$@"`。bot 配置里的 provider 指向它（`:55-60`）。
- lark-cli 1.0.98 的 exec provider：2026-10-19 写计划时在 JP-VPS 上用全假数据实测过。做法是写一份假的 OpenClaw 配置，跑 `lark-cli config bind --source openclaw`，它会经 provider 解一次 secret。结果：
  - 请求从 stdin 进：`{"protocolVersion":1,"provider":"bridge","ids":["app-<appId>"]}`。
  - 回复必须有 `"protocolVersion": 1`。没有这个键时报 `got 0`，值是 2 时报 `got 2`。
  - `values` 要有。`errors` 可以没有，`{}` 也行。末尾带换行没问题。
  - 某个 id 在 `errors` 里：lark-cli 报 `exec provider failed for id "<id>": <message>`，message 原样传给 agent。
  - id 在 `values` 和 `errors` 里都没有（比如只有 `errors._`）：报 `exec provider response missing id "<id>"`。
  - 退出码不是 0：lark-cli 不看 stdout，只报 `exec provider exited with error: exit status N`。
  - stdout 不是 JSON：报 `exec provider returned invalid JSON`。

## 4. 怎么改

### 4.0 开工前的实测（JP-VPS，几分钟）

用任务 94 的 preflight 脚本，在真实 Claude 沙箱的读写关网档里，用 Bash 跑两条（数据目录用任务 94 的假数据）：
- `node -e "const s=require('fs').statSync('<假数据目录>/master.key');console.log(s.uid===process.getuid(),(s.mode&0o777).toString(8))"`。期望打出 `true 600`。打出别的说明沙箱换了 uid，`loadKey` 的本人检查会不过，这时停下，结果写"卡住了：沙箱里 uid 对不上"。
- `node -e "require('net').createServer().listen({path:'\0s31b0'}).on('error',e=>console.log(e.code))"`。期望打出 `EPERM`，确认挡住的就是 socket。

结果写进 PR 描述"第 0 步"。

### 4.1 选哪种

| 方案 | 做法 | 结论 |
|---|---|---|
| A 共享文件锁 | 读者对一个预先建好的锁文件只读打开、加 `flock(LOCK_SH)`；写者加 `LOCK_EX` | 不选。Node 24 没有 `flock`，也没有 `fcntl` 锁的 API，Linux 上得带原生小程序，或者调外部的 `flock(1)`，macOS 上没有这个命令。data-access.ts 在 Linux 上用的也是抽象 socket，不是文件锁（`:55-60`）。锁文件沙箱建不了，得宿主先建，旧的数据目录还要补建。写者今天都是原子发布，加锁对读者的正确性没有帮助；读者卡住时还会让写者等满 30 秒。 |
| B 不拿锁的只读读者 | 读者不拿锁、不写文件，靠写者的原子发布和 AES-GCM 校验 | 选。daemon 自己读密钥库今天就是这样（3.3）。为什么对见 4.2。 |
| C 宿主拿着租约，另开只读通道 | daemon 经 socket 或本机端口发 secret | 不选。Linux 沙箱的 seccomp 不让开 Unix socket，关网档连本机地址也不让（s31）。终端里没起 daemon 时，lark-cli 也得能用。这样做等于给本机别的进程开了一个取密钥的口子，接近一个通用的管理能力。 |
| D 让准入在沙箱里也能跑 | 把租约挪到别处，或者吞掉 `EPERM` | 不选。沙箱不让写数据目录，也不让开 socket；吞掉 `EPERM` 等于不检查。而且租约今天没人读（3.2）。 |

### 4.2 读者和写者的约定

这一片只改读者。写者今天已经守着 R3 到 R5，这一片用测试把它们钉住，并写进 `keystore.ts` 文件头的注释。

- R1：读者不拿任何锁，不写任何文件，不建目录（数据目录本身也不建），不监听也不连接 socket。读者指 `vonvon secrets get`（沙箱里外一样）和 daemon 的 `getSecret`。
- R2：读者先读 `secrets.enc`，再读 `master.key`。`secrets.enc` 不在时，每个 id 都按"没有"回，不读 `master.key`。
- R3：写者先发布 `master.key`（临时文件、fsync、`link`、fsync 目录），后发布 `secrets.enc`（临时文件、fsync、`rename`、fsync 目录）。
- R4：`master.key` 只写一次，不覆盖、不删，也不往它上面 `rename`。以后要换主密钥的片，必须先另定读者协议（比如带代号的新文件名，新旧两把 key 并存一段时间），不能原地换。
- R5：`secrets.enc` 只用 `rename` 整个替换，不原地改，不截断。
- R6：读者每一项都要等 GCM 的 `final()` 校验过了才用。校验不过，这一项就报错，不给值，也不给半截明文。
- R7：`.access` 租约只表示"有别的 `vonvon` 命令在用数据目录"，不包括 `secrets get`。要独占数据目录的操作（搬家、删除、换主密钥）不能靠 `assertNoDataLeases` 挡住密钥库的读者。今天没有这种操作（3.2）。

为什么这样是对的：
- 读者打开 `secrets.enc` 时，拿到的是某一次 `rename` 发布出来的那个 inode（R5）。之后写者再换文件，也不影响已经打开的这个。所以读到的一定是一份完整的 store，不会半新半旧。
- 读到了 store，说明在它发布之前 `master.key` 已经在了（R3），而且以后不会变（R4）。所以接着读到的 key，正是加密这份 store 的那一把。读不到 store，就当作是在它发布之前读的，回"没有"。
- 如果有人手动换了 key、拷回了半个文件、或者改坏了字节，要么 GCM 校验不过，要么 JSON 不合法，读者报错、不给值（R6）。最坏的结果是一次报错，不会是一个错的值。
- 读者不拿锁，所以不会出现读者卡住写者，也不会出现读者死了锁没放。写者之间照旧用 `keystore` 互斥。
- 沙箱和宿主之间没有共享的锁。读者什么锁都不拿。写者只在宿主上跑：daemon，和终端里的 `secrets set|remove`；会话里的 `secrets set|remove` 已经被拒了（s23g）。

### 4.4 `D/cli/commands/secrets.ts`

```ts
/** lark-cli's exec provider (1.0.98, the same protocol as OpenClaw's). */
export const EXEC_PROTOCOL_VERSION = 1;
export interface ExecReply {
  protocolVersion: typeof EXEC_PROTOCOL_VERSION;
  values: Record<string, string>;
  errors: Record<string, { message: string }>;
}
export type ExecRequest = { ids: string[] } | { ids: string[]; problem: string };
export function parseExecRequest(input: string): ExecRequest;
export async function secretValues(ids: string[], read: typeof getSecret = getSecret): Promise<ExecReply>;
export async function secretsGet(io?: { input(): Promise<string>; write(text: string): void }): Promise<void>;
```

`parseExecRequest` 按下表从上往下判断，命中一行就停：

| stdin | 结果 |
|---|---|
| 不是 JSON，或者不是对象（包括 `null`、数组） | `{ ids: [], problem: 'invalid request JSON' }` |
| 有 `ids`，但不是数组，或者有一项不是字串 | `{ ids: [], problem: 'invalid request: ids must be an array of strings' }` |
| 有 `protocolVersion`，但不等于 1 | `{ ids: <去重后的 ids>, problem: 'unsupported protocolVersion: only 1' }` |
| 没有 `ids` | `{ ids: [] }` |
| 其余 | `{ ids: <去重后的 ids> }` |

- 没有 `protocolVersion` 的当作 1：本机的自测脚本和老的调用方有不带这个键的。`provider` 不看，和今天一样。
- 去重保留第一次出现的顺序。

`secretValues`：
- 对每个 id：
  - 决策模型的 key：`errors[id] = { message: 'not handed out: only the daemon reads this key' }`，不读文件；
  - `read(id)` 返回 `undefined`：`'not found'`；
  - 返回字串：放进 `values[id]`；
  - 抛错：`errors[id] = { message: keystoreMessage(error) }`。
- `keystoreMessage(error)` = `${problem}（${code}）`，`problem` 和 `code` 来自 `describeKeystoreError`（`D/admin/secrets.ts:41-46`）。消息里不带路径。
- `values` 和 `errors` 用 `Object.fromEntries` 建，这样 `__proto__` 这类 id 不会改到原型。
- 返回 `{ protocolVersion: 1, values, errors }`，键就按这个顺序。

`secretsGet(io = { input: readStdin, write: t => { process.stdout.write(t); } })`：

```ts
let ids: string[] = [];
let reply: ExecReply;
try {
  const request = parseExecRequest(await io.input());
  ids = request.ids;
  reply = 'problem' in request ? failAll(ids, request.problem) : await secretValues(ids);
} catch (error) {
  const { code } = describeKeystoreError(error);
  reply = failAll(ids, `secrets get 出错了（${code}）`);
}
io.write(`${JSON.stringify(reply)}\n`);
```

- `failAll(ids, message)`：`values` 是 `{}`。`ids` 不空时，每个 id 一条 `errors`；`ids` 为空时，只有一条 `errors._`。
- stdout 只写一次，只写这一行。不打日志，因为 info 级的日志可能写进 stdout。
- 退出码一律是 0：lark-cli 只在退出码为 0 时才读 `errors`，这样原因才能传到 agent 那里（3.5）。
- 有几种情况进程走不到 `secretsGet`：数据目录是符号链接（`paths` 加载时就抛了），模块加载失败，被 SIGKILL。这时 stdout 什么也不写，退出码不是 0，lark-cli 报 `exec provider exited with error`。这是失败就关，不算一条回复。5.3 第 6 条钉住"stdout 为空"。
- 写 stdout 的中途被杀（比如 lark-cli 超时 SIGKILL）时，stdout 可能只有半行 JSON。这一条保证不了完整，靠接收方失败就关：lark-cli 报 `exec provider returned invalid JSON` 或 `exited with error`，不会拿半截内容当 secret。

每条路的回复如下。假设 `app-cli_t` 存的值是 `v`：

| 情况 | stdout（一行） |
|---|---|
| 成功 | `{"protocolVersion":1,"values":{"app-cli_t":"v"},"errors":{}}` |
| 部分成功：ids 是 `["app-cli_t","app-cli_x","typesafe-api-key"]` | `{"protocolVersion":1,"values":{"app-cli_t":"v"},"errors":{"app-cli_x":{"message":"not found"},"typesafe-api-key":{"message":"not handed out: only the daemon reads this key"}}}` |
| 密钥库读不了：`master.key` 改成 0644 | `{"protocolVersion":1,"values":{},"errors":{"app-cli_t":{"message":"master.key 不对：要是本人所有、权限 0600、32 字节的普通文件（KEYSTORE_MASTER_KEY_MODE）"}}}` |
| 没有 `ids` | `{"protocolVersion":1,"values":{},"errors":{}}` |
| 不是 JSON | `{"protocolVersion":1,"values":{},"errors":{"_":{"message":"invalid request JSON"}}}` |
| `ids` 不对 | `{"protocolVersion":1,"values":{},"errors":{"_":{"message":"invalid request: ids must be an array of strings"}}}` |
| 版本不对：请求是 `{"protocolVersion":2,"ids":["app-cli_t"]}` | `{"protocolVersion":1,"values":{},"errors":{"app-cli_t":{"message":"unsupported protocolVersion: only 1"}}}` |
| 意外异常：读 stdin 时出错，`ids` 还是空的 | `{"protocolVersion":1,"values":{},"errors":{"_":{"message":"secrets get 出错了（UNKNOWN）"}}}` |

### 4.5 `D/config/keystore.ts`

```ts
/** The files under the data root that a keystore read opens, in this order (s31b0). s31b leaves them readable. */
export const KEYSTORE_READ_FILES = ['secrets.enc', 'master.key'] as const;
const READ_FLAGS = constants.O_RDONLY | (constants.O_NOFOLLOW ?? 0) | (constants.O_NONBLOCK ?? 0);
```

- 文件头加一段注释，写 4.2 的 R1 到 R7。按仓库注释的习惯用英文。
- `readStore`：
  - 用 `open(paths.secretsFile, READ_FLAGS)` 打开。`ENOENT` 返回 `undefined`。`ELOOP` 或 `EMLINK`（说明是符号链接）抛 `KEYSTORE_STORE_FORMAT`。
  - `handle.stat()` 不是普通文件，抛 `KEYSTORE_STORE_FORMAT`。
  - 用同一个 handle `readFile('utf8')`，`finally` 里关掉 handle。
  - **不加大小上限**（#452 审查）：写者没有上限，正常的 `set --raw` 写一个 800,000 字节的值，发布出来的库就超过 1 MiB。读者加上限会让这种合法的库连 get、set、remove 都做不了，删掉大条目也恢复不了。要限大小，得读写共用一个标准、发布前拒绝，这不是本片的事。
  - 之后照旧 `JSON.parse`，再过 schema。
  - FIFO 带着 `O_NONBLOCK` 打开时不会卡住，`stat` 认出来就报错。
- `loadKey`：`open` 的 flags 加上 `O_NONBLOCK`，这样 `lstat` 和 `open` 之间文件被换成 FIFO 也不会卡住。别的不变。
- `getSecret`：先 `if (!Object.hasOwn(store.entries, id)) return undefined;`，再取 `store.entries[id]`。
- 不加 `nlink` 检查，有两个原因：
  - 硬链接改变不了内容从哪来，内容靠 GCM 校验（R6）；
  - 第一次建 key 时，如果进程在 `link` 之后、删临时文件之前被杀，`master.key` 会一直是 `nlink 2`（3.3）。加了检查，这种数据目录就永远读不了。
- 写者（`keyForMutation`、`writeStore`、`mutate`）不改。不过 `readStore` 变严对写者也生效：`secrets.enc` 是链接或 FIFO 时，`setSecret`、`removeSecret` 也报错、不写。以前会跟着链接写，或者卡住。
- 密钥页对 `KEYSTORE_STORE_FORMAT` 的说法是"secrets.enc 的格式不对"（`D/admin/secrets.ts:30`），不另加说法。

### 4.7 并发、出错和停机

| 场景 | 读者看到什么 | 靠什么保证 |
|---|---|---|
| 写者正在换这一项的值 | 旧值或新值。同一个读者先后读，值不会往回退 | R5，`rename` 是原子的 |
| 写者在删这一项 | 值，或者"没有" | 同上 |
| 第一次 `setSecret`，还没有 key 和 store | 先是"没有"，之后是值。不会报 `KEYSTORE_MASTER_KEY_MISSING` | R2、R3 |
| 写者拿着 `keystore` 互斥，停在 `rename` 之前 | 马上回旧值，不等锁 | R1 |
| 写者在 `rename` 或 `link` 之前被 SIGKILL | 之前的状态。留下的 `*.tmp` 读者不碰 | R3、R5；读者只开 `KEYSTORE_READ_FILES` |
| 别的命令拿着 `admission` 互斥 | 照常回 | R1 |
| 读者被 lark-cli 超时 SIGKILL，或者 stdout 被关掉 | 什么也不留下。今天会留下一个 `.access` 记录 | R1 |
| daemon 停机或重启 | 不相干 | 两边没有共享状态 |
| 有人拷回旧的 store 和 key，或者手动改了文件 | 解得开，就是那时的值；拷到一半时报错 | GCM 和 schema（R6）。退回旧备份认不出来，但能写数据目录根的人本来就能读密钥 |
| 数据目录被搬走或删掉（今天没有代码这样做） | "没有"，或者 `KEYSTORE_MASTER_KEY_MISSING`，不会拼出一个错的值 | R2、R6；以后做这种操作的片要守 R7 |
| `.access/`、`.locks/` 里有坏记录 | 不相干 | 读者不读它们 |
| 网络文件系统（NFS 等） | 不在范围内 | 和今天的写者一样，按本地文件系统的 `rename`、`link` 语义算 |

### 4.8 出错时 lark-cli 怎么说

| 原因 | 回复里的 message | lark-cli 给 agent 的话 |
|---|---|---|
| 没填 | `not found` | `exec provider failed for id "app-…": not found` |
| 决策模型的 key | `not handed out: …` | 同上的格式 |
| `master.key` 没了 | `master.key 不在了，…（KEYSTORE_MASTER_KEY_MISSING）` | 同上的格式 |

### 6.3 规矩（原样照做）

- 临时目录只用 `T=$(mktemp -d)` 建，只用 `rm -rf -- "${T:?}"` 删，或者删刚在 `/tmp/` 下建的字面路径。
- 不对 `$HOME`、`~`、`$PWD`、`$VONVON_HOME` 或任何可能为空、未设置、指向真实 home 的变量拼出来的路径用 `rm`、`find -delete`、`find -exec rm` 或 `xargs rm`。
- 不在 shell 里给 `HOME`、`VONVON_HOME` 赋值或 export，只写在单条命令前面，例如 `HOME=$T/home VONVON_HOME=$T/vh npx vitest run`。
- 每次调用工具都是新的 shell，`T` 不会留下来。建完以后把 `mktemp -d` 打出的路径记下来，后面的命令在同一条命令里写 `T=<那个字面路径>`，再用 `$T`。
- 假的数据目录只建在 `$T` 下。这一片不碰验收 daemon 和 `accept-home2`：不读、不改，也不拿 `/tmp/accept-user.d`。真要用的话，照 #422 第 4 节拿锁。
- 不读 `local-secrets`（#422 第 4 节"密钥"）。不打印真实的密钥、app secret、chat id。这一片只用假值，假值也只在内存里比，PR 里只写 true/false。
- 本机已有的 lark-cli 配置不碰（profile jojo、`~/.local/share/lark-cli`）。lark-cli 的命令一律在前面写临时的 `HOME` 和 `LARKSUITE_CLI_CONFIG_DIR`。
- 真实的 `~/.claude/settings.json` 不改。Claude 的登录文件不拷、不打印。
- Mac 上不碰 owner 的 `~/.vonvon-bot`、`com.vonvon.bot.daemon`、bridge 和 `/Applications/Vonvon Bot.app`。
