# 配方不携带记忆

2026-11-15 owner 决定：发布的配方不带记忆。本章覆盖早期设计中“可选 Bot 记忆”和配方“记忆”页签的规则。产品规则已确定，联合实现和真实流程验收仍在进行。

## 创作者与使用者看到的内容

创作者只能选择角色、规则、沟通设置、可移植技能与文件、任务模板和公开介绍。来源枚举不读取 Bot、私聊、项目或群记忆，也不提供记忆开关。setup 仍是普通技能。

配方详情、创作中内容和发布预览共用五个页签：概览、模型与权限、能力、沟通方式、任务。群设置自己的记忆功能继续保留。安装和更新不会读取、复制或覆盖目标群的原生记忆。

历史开发草稿可能含记忆。继续编辑时，系统将“排除旧配方中的记忆”列入本次改动，作者确认后才产生新修订。该操作只清理配方快照，不删除源群或 Bot 的记忆。未确认前保留原草稿。

## 新写入与历史读取

通用 rich-v2 解码、规范序列化、历史版本校验和完整性检查继续识别旧字段。历史 canonical 字节、哈希、对象和已提交回执保持原样。

`validateWritableRichRecipeContent` 只用于新写入，要求 `memories` 为空。新的来源快照、编辑结果、元信息修改和发布均遵守此约束。单纯隐藏客户端字段不能代替服务端检查。

编辑协议增加一个 `removeLegacyMemories` 操作。它清理所有旧记忆，并删除因此失去引用的附件；被其他条目共同引用的附件仍保留。它占用现有的一个编辑名额，不提高单次十六项上限。十六项普通修改再加清理时，整批拒绝并保留原稿，提示先确认清理再重新提交修改，不创建后台续写任务。

新的复制或来源恢复请求不能引入 memory，即使后续另一个操作又把它清除。元信息写入既检查结果，也检查锁定的旧草稿；旧稿仍含记忆时不能借元信息入口绕过已审阅清理。

数据库以新的前向迁移替换四个现有写函数，不编辑已应用的迁移或重写历史业务数据。精确匹配的旧 accept、metadata 和 publish 回执先返回原结果，新写入随后才执行记忆策略。其他账号、摘要或修订不能借重放取得旧回执。

## 本地安装与恢复

安装比较中的作者基线、本地配方覆盖项和新版投影均排除记忆。模型上下文不再注入历史配方覆盖层中的记忆，原生记忆仍按原有规则装配。

Main 在准备、开始签发和提交三个写请求中带 `memoryPolicy: 'exclude'`。旧目标的严格解析器会在执行前拒绝这些请求，客户端提示更新目标设备，不去掉字段重试。新 daemon 即使收到省略字段的旧客户端请求，也执行同一排除策略。读取状态、取消、对账和已完成回执不增加这个字段。

恢复旧私聊卡时，清理本地选择并不足以证明远端 CardKit 实体已清理。旧实体在重新发送前必须先完成内容更新，更新结果不明时不重发。操作仍沿用原卡与原发送身份。

旧直接更新操作的批准摘要可能包含记忆。新的准备和签发不能沿用与当前策略不符的未发行计划。已经发行的操作在实际应用前核对已批准摘要；投影改变时按既有拒绝与完成回执路径结束，不悄悄替换批准内容。已完成的安装回执仍可读取。

## 验收证据

联合验收需同时观察这些结果：

- 来源记忆中放入哨兵，生成与修改配方的候选、IM 实际发送体和新云快照均不含哨兵。
- 旧草稿经确认清理后只推进一次修订，保留共用附件，旧回执仍能精确重放。
- 数据库服务角色不能用干净输出直接覆盖含记忆的旧草稿。
- 恢复旧卡遇到发送或更新回执丢失时，不能再次发送旧记忆正文。
- 安装和更新后的有效配置、冲突列表和模型上下文不含配方记忆；真实 MemoryStore 字节保持不变。
- 新客户端连接旧目标时在写入前拒绝，不能出现看不见的零冲突记忆安装。
- 私聊编辑与最终发布可以完成，App 和社区都使用相同的五页详情结构。

单元、隔离数据库或旧源码探针只证明对应边界。签名 App、真实 Bot 和 staging 的联合流程通过后，才交给 owner 验收。
