## 结论

1. **只读档限读**：macOS 上，Bash 的 `denyRead` 挡住其他群、公共记忆、bot 自身文件；嵌套 `allowRead` 放开本群记忆、技能和 cwd。`allowWrite` 让本群记忆可写，其他群记忆和 `SOUL.md` 不可写。两个符号链接建成，但沿链接读不到禁止的内容。Read 工具读 cwd 外走回调，连放开的本群记忆也如此。五个根凭据的批量读取因 shell 变量先走回调、被实验策略拒绝，不能称为逐项实测；递归搜索也无法遍历被拒目录。
2. **完全访问下的 ask 规则**：`bypassPermissions` 下，项目层 `Bash(echo e03b-ask:*)` 命中并走回调，Bash deny 规则直接拒绝且不走回调，普通 Bash 不走回调。Write `ask-me.txt` 走回调且写成，但设置的是 `Edit(./ask-me.txt)`，所以不能单凭它证明该 Edit ask 规则匹配。AskUserQuestion 也走回调。
3. **用户层权限规则**：owner 用户设置的 allow、deny、ask 均为空，未设 sandbox。本任务按要求只记录结构，加载与不加载用户设置的受控对比由同 PR 的 e03（上）完成。四轮都加载 `['user','project']`；若用户设置含 sandbox，会与会话配置合并生效。
4. **配置文件**：Claude 自带沙箱已挡住 Bash 直接改写 `.mcp.json`、`.claude/settings.json`，还挡住新建 `.claude/skills`、settings 硬链接及搬走整个 `.claude`。附加保护进一步挡住 Write `.mcp.json`、Edit settings、Write `.claude/skills/y/SKILL.md` 和 Bash 新建 `.codex/config.toml`；基线的 `.codex/config.toml` 写成。符号链接 Write 在基线被工具拒绝。硬链接没建成，之后 Write 创建的是独立普通文件，无法判定真正的硬链接写能否绕过。

## 对 s31、s39、s39b、s40 的含义

- s31：Bash 的 `denyRead` 加子目录 `allowRead` 在这次 macOS 实测有效；Read 工具还需处理 cwd 外的权限回调。shell 变量会让静态检查转为回调，回调策略是边界的一部分。本群记忆的 `allowWrite` 有效。
- s39、s39b、s40：现有 SDK 沙箱保护了若干 Claude 配置路径，但基线没挡住 `.codex/config.toml`。本实验的附加保护挡住该 Bash 创建步骤。硬链接创建失败，无法给出实际硬链接写的结论；其余配置根未逐一覆盖。产品承诺和对策待 owner 定。

## 没测的

- Bash 的 `rm`、`rmdir` 有一个叫 `dangerousRemoval` 的检查。目标是系统的关键目录，是工作目录、附加的工作目录或它们的上级目录，以可能为空的变量开头、以根下一级的目录名结尾，或者路径静态解析不了时，它返回 `behavior: 'ask'`，`decisionReason.type` 是 `safetyCheck`，提示里写"不能被权限规则自动放行"。权限模式表里它标了 `bypassImmune: true`，也就是 `bypassPermissions` 下也照样要问。SDK 下"要问"的调用，挂了 `canUseTool` 时会走到回调（推断，没实测）。这是读 SDK 0.3.296 所带 Claude Code 2.1.296 代码的结论，**没有做删除实测**。
- 条件性 `denyread-b` 未跑。根上五文件在第 9 步未执行读取。真正的硬链接写没跑成；基线 Edit 被 settings schema 自身拒绝。`.claude/settings.local.json`、`.claude/commands/`、`.claude/agents/`、`.agents/skills/` 未逐项探测。上述格子不能作为沙箱效果证据。
