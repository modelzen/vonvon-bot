# e03：Claude 的权限回调和 macOS 沙箱

2026-10-19 在 owner 的 Mac 上由 Mac 任务 43 实测。代码引用按 `main` 的 `84162db`。对应 `docs/product.md` 第 9 节第 11、12 项中需要沙箱的部分、`docs/v1-plan.md` 4.1 的 e03，以及 e02 没测完的用户层设置。结果影响 3.8、s31、s39。

## 结论

1. s31 候选只读档和读写档下，`Read` 读 cwd 外都走回调、被拒；`Bash cat` 读 cwd 外都没走回调、读成了。`Write` 写 cwd 外走回调、被拒；`Bash` 写 cwd 外没走回调、被沙箱以 `operation not permitted` 挡住。只读档写 cwd 内的 `Write` 走回调、被拒，`Bash` 写 cwd 内没走回调、被沙箱挡住。读写档写 cwd 内的两种工具都没走回调、做成了。
2. 候选关网档的两个 `Bash curl` 都走到了 `canUseTool`，回调工具名是 `SandboxNetworkAccess`，参数是 `{"host":"example.com"}` 或 `{"host":"www.iana.org"}`，不是 `Bash` 命令。回调拒绝后，`curl` 收到 CONNECT 403 和 `deny network-outbound`，没有连成。今天的两个关网档没有回调，却各自得到两个 HTTP 200。
3. 候选开网但不给域名名单时，两个主机都走 `SandboxNetworkAccess` 回调，放行后各得 HTTP 200。名单只有 `example.com` 时，它没走回调、直接得到 200；`www.iana.org` 仍走回调，放行后得到 200。
4. 今天的两个关网档在 init 工具列表里没有 `WebFetch`、`WebSearch`，模型也跳过了第 10、11 步。候选两种关网档有两个工具，两步都走回调并被拒，因而无法判断拒绝后工具本身能否联网。候选两种开网档有两个工具；设置裸 `allowedTools: ['WebFetch', 'WebSearch']` 的两轮，两步都没走回调且成功；保存的日志不能独立证明内部放行顺序。未跑开网但不设这条允许规则的对照，不能据此断言那个配置下两工具一定走回调。
5. 今天的只读关网档：`Bash curl` 得到 200；`Bash` 写 cwd、cwd 外和 `/tmp` 都被沙箱挡住。今天的读写关网档：`Bash curl` 也得到 200；`Bash` 写 cwd 成功，写 cwd 外和 `/tmp` 被挡；`Write` 写 cwd 外却成功。文件工具和沙箱里的 Bash 有不同边界。
6. owner 用户设置的权限规则结构里，`allow`、`deny`、`ask` 都是空数组；但认证来源在用户设置的 `env` 中。只用 `['project']` 的对照轮收到 `Not logged in · Please run /login`，没有调用任何工具，因此不能逐步比较用户层规则对回调的影响。这只代表带 owner 设置的本机环境，不代表一般用户。

## 关网和域名名单

候选关网档的 Bash 命令本身没有以 `Bash` 名义进回调。真正触发回调的是网络目的主机，工具名 `SandboxNetworkAccess`。回调拒绝后，tool_result 含 `curl: (56) CONNECT tunnel failed, response 403` 和 `deny network-outbound example.com:443 (user denied)`。开网无名单时两个目的主机都进回调；名单内的 example.com 没进回调，名单外的 www.iana.org 仍进回调。这说明域名名单在本次 macOS 沙箱中改变了是否请求回调（各跑一次）。

今天的两个关网配置没有回调。两个目的主机的 `curl` 都返回 200。这里只证明本机本轮的 HTTP 请求成功；没有检查网络路径或换一台机器重测。`curl` 的 403 错误显示了 CONNECT 隧道。e04b 证实了原因：沙箱给 Bash 注入了 HTTP 代理变量，今天的关网档经这个代理出去，所以 `curl` 能返回 200。没有读取代理凭据。

## WebFetch 和 WebSearch

候选关网轮次中两个工具都存在，且分别以自己的工具名走回调，实验策略一律拒绝。执行者在 `rounds.sh` 的终端输出中观察到 Node 的 `CLAUDE_SDK_CAN_USE_TOOL_SHADOWED` 警告，但没有保存进七份 JSONL，核实代理未能独立确认警告原文或内部放行顺序。两轮的 WebFetch 都返回页面标题“Example Domain”，WebSearch 都返回结果列表，且没有对应回调。这里只确认这组允许规则配置下两工具无回调且成功；开网而不加允许规则的效果未测。

## 今天的只读、读写档

今天的两档用 `bypassPermissions`，没有回调。只读档没有 Write、Edit；模型强行调用 Write 收到 `No such tool available: Write`。Bash 读 cwd 外成功，写 cwd 内、cwd 外和 /tmp 均由沙箱拒绝。读写档的 Write 在 cwd 内和 cwd 外都成功；Bash 只在 cwd 内写成功，cwd 外和 /tmp 被沙箱拒绝。该差异不能用“沙箱挡住了所有 cwd 外写”概括。

## 用户层设置

`cand-write-off` 的 `['user','project']` 轮次完成 12 步。`cand-write-off-nouser` 的 `['project']` 轮次只发出 init，随后文本是 `Not logged in · Please run /login`，result 虽为 `success`，却没有任何 tool_use。按提示词要求未尝试补入认证。因而问题 6 的逐步回调对比没有数据。结构检查显示 owner 用户层没有 allow、deny、ask 规则，无法把本轮任何免回调归因于一条用户权限规则；用户层的认证 env 名称与未登录结果相符，但未读其值。

## 对 s31、s39 的含义

- s31 的候选只读档在本次实验中阻止了 Bash 写 cwd 内外及 /tmp；候选读写档阻止 Bash 写 cwd 外及 /tmp。cwd 外的 `Bash cat` 仍直接成功，cwd 外的 `Read` 则经过回调。如何定义“只读”和“工作区外访问”，待 owner 定。
- s31 若要让每次 WebFetch、WebSearch 都经回调，需另验允许规则的交互：本实验设置裸允许规则的两轮都没有回调。内部放行原因不能只靠这组保存日志确认。产品行为待 owner 定。
- s39 的“关网”在今天的 `bypassPermissions` 配置下没有挡住本次两个 curl；候选档拒绝 `SandboxNetworkAccess` 后挡住了。是否采用候选档、是否给域名名单，待 owner 定。
- 今天读写档的 Write 能写 cwd 外，而 Bash 沙箱会挡同一个目录。文件工具的边界应单独核对；行为变更待 owner 定。

## 没测的

- `cand-write-off-strict` 未跑：触发条件是 `cand-write-off` 的第 8 或 9 步得到 HTTP 状态码；本轮两步均是 CONNECT 403 和 `000`，未连成。
- `cand-write-off-nouser` 未登录，1–12 步都未运行；用户设置有无对回调的逐步影响未测成。
- 开网但不设 `allowedTools` 的 WebFetch、WebSearch 未测。候选关网档回调一律拒绝，拒绝后两工具能否用无法从该轮判断。
- today 两档没有第 10、11 步的工具，模型跳过了；没有把模型跳过当作执行失败。其他有效轮次按编号逐步各调用一次。没有一轮超时。
- 仅在 owner 这台 Mac、这组用户设置和代理路径上各跑一次；没有验证其他用户、其他网络或代理设置。
