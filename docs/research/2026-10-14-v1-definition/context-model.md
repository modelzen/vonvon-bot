## 1. 一句话结论

每个飞书对话（一个话题、一个"连续"的群主区、主人的私聊）对每个 bot 就是一条原生 Codex 线程或 Claude 会话；bot 回复时看到自己这条会话的历史，再加上"上次回复以后这里的新消息"（带真名，含别的 bot 的最终回答），更早的历史由 bot 用一个只限本群的工具自己查；子 agent 挂在父运行卡里看进度、单独停，不另开会话；压缩用原生自动压缩，加一个 `/compact` 命令。

## 2. 会话在哪里

### 事实
- 旧产品有两种群。多会话群一个话题一条会话，键是话题 id；单会话群整群一条，键是群 id（`D/project/registry.ts:23-25`；`D/bot/handle-message.ts:544-548`）。
- 映射存在每个 bot 的 `sessions.json`。重启后用存的 id 接上（`D/bot/session-store.ts:42-73`；`handle-message.ts:1697-1729`）。接不上就新建，只有话题会重新带上最近的消息（`handle-message.ts:1617-1634`）。
- 飞书本身就按话题切。每条消息带群 id、类型（单聊或群）、话题 id（FS `message_events_receive.md:55-80`）。飞书的"话题群"里所有消息都是话题（`飞书文档副本/im-v1_message_thread-introduction.md:65-75`）。
- 管理员和访客档位不同时，旧产品把同一个话题拆成两条会话（`D/project/registry.ts:107-126`）。用户说上下文对不上（群#953）。
- 私聊今天不跑 agent，只弹管理菜单，非管理员被拒（`D/bot/dm-console.ts:9-22`）。用户问过"不支持私聊吗"（群#582、#605）。没人说过想在私聊里写代码（〔飞〕4.1）。
- 别家：OpenClaw 在飞书上可以一个话题一个会话，不在话题里就落回群会话（docs.openclaw.ai/channels/feishu/advanced-configuration）。Slack 的 AI 应用、Cursor、Grok Team Bots 都是一个线程一个会话（docs.slack.dev/ai/developing-ai-apps；cursor.com/docs/slack；docs.x.ai/grok-bot/team-bots）。
- 两家原生都能做到一对一。Codex 有线程 id 和 `thread/resume`，Claude 有会话 id 和 `resume`（〔码〕2.3）。

### 建议：不再分"两种群"，改成"每个对话一条会话"

| 飞书里的地方 | 一条会话是什么 | 什么时候建 |
|---|---|---|
| 任何群里的一个话题 | 每个 bot 在这个话题里一条 | 这个 bot 第一次在这个话题里被叫到时 |
| 群主区，设成"连续" | 每个 bot 在主区一条，一直接着聊 | 第一次被叫到时；`/new` 以后换一条 |
| 群主区，设成"开话题" | 主区不留会话。@ bot 时，bot 用话题回复，开出一个新话题，就是第一行 | — |
| 主人和 bot 的私聊 | 每个 bot 一条，一直接着聊 | 同"连续" |

- 旧的单会话群 = 主区"连续"。旧的多会话群 = 主区"开话题"。两者只是主区的一个设置。话题的规则在两种群里一样。
- "连续"的群里，有人在某条消息下开了话题，这个话题就是一条新会话，不并进主区那条。开场带什么见第 3 节。
- 一条会话里不管是谁在说话。权限档位按群定一个，不再按管理员和访客拆会话。谁能叫动 bot，仍由群白名单管。
- 重启后按存的 id 接上。接不上就新建一条，用飞书历史重新带上开场。话题、主区、私聊都这样做。
- 保持原生形式：这条会话就是一条普通的 Codex 线程或 Claude 会话。用户在 Codex 应用里或用 `claude --resume` 打开，看到的和 bot 看到的一样（推断，要 Mac 实测；CXR `app-server/src/main.rs:50-55`；code.claude.com/docs/en/agent-sdk/sessions）。
  - 为此不用 Codex 的 `thread/inject_items`。它塞进去的内容模型看得到，应用里却不显示（CXR `app-server-protocol/src/protocol/thread_history.rs:478-501`）。
  - 同一条会话一边在应用里续写、一边在群里续写，会有两个写入方，可能乱序（推断）。v1 建议应用里只看，不续写。

### 私聊：建议 v1 做，但只给 bot 主人
- 主人私聊：一条连续会话，用 bot 的主工作区。管理功能（建群、诊断、用量）留在同一个私聊里，用卡片按钮进，和对话分开。
- 其他人私聊：不跑 agent。回一张卡片，写"在群里 @ 我"，列出他所在的、有这个 bot 的群。
- 理由：
  1. 私聊会话跑在主人的 Mac 上。bot 可用范围里谁都能私聊它（FS `message_create.md:5-9`）。放开就等于让同事在主人电脑上随便跑 agent。
  2. 记忆设计里只有主人私聊有自己的记忆（`owner.md`，〔记〕7(b)）。放开给别人，就要每人再加一份私人记忆。
  3. 实现简单。私聊会话和"连续"主区是同一种会话，只换了工作区和权限来源。
- 飞书私聊里能不能开话题：未知（〔飞〕1.5）。能的话，私聊里的话题也按第一行算。

## 3. 上下文怎么算

### 事实
- 今天是"触发时去拉"。只有话题里才补拉没触发的消息：按水位只拉上次之后的，一页 50 条，最多留 20 条，每条 280 字（`D/bot/context-weave.ts:38-45`、`:103-141`）。单会话群没有补拉（〔码〕1.6）。
- 引用的消息按 id 取回，最多 800 字（`context-weave.ts:36`、`:77-92`）。附件下载到本地，给路径清单（`handle-message.ts:1272-1295`）。
- 人名没进去。触发人的名字恒为"某用户"，因为建通道时没传 `resolveSenderName`（`D/bot/bridge.ts:59-81`）。飞书拉历史的接口不返回名字（FS `message_list.md:61-66`）。
- bot 的消息全被过滤。没申请收 bot 消息的权限（`D/config/scopes.ts:23-24`；FS `message_events_receive.md:12-22`），拉上文时也只留人发的（`context-weave.ts:125`）。所以今天 B 看不到 A。
- Codex 和 Claude 的用户消息都没有"发言人"字段。多人只能写进文字里（CXG `v2/UserInput.ts`；SDK `:6311-6320`）。
- 飞书拉历史：群主区能按时间过滤，话题不能（FS `message_list.md:32-33`）。
- 别家：OpenClaw 在要 @ 才回的群里，没 @ 的消息先存着，被 @ 时一起交给 agent（docs.openclaw.ai/channels/groups）。Cursor 被叫到时读整个线程（cursor.com/docs/slack）。OpenClaw 在 Discord 上，bot 自己的输出不放进自动历史（docs.openclaw.ai/channels/discord/threads-and-sessions）。

### 建议：bot 回复时看到这些

| 内容 | 放不放 | 说明 |
|---|---|---|
| 人设和记忆 | 放，在会话开始或恢复时 | 见第 6 节 |
| 自己这条会话的历史 | 放（原生的） | 压缩过的部分是摘要 |
| 上次回复以后，这里的新消息 | 放，按字数预算 | "这里"指本话题，或"连续"主区。包括人发的，和别的 bot 的最终回答（第 8 节问题 3） |
| 触发消息 | 放，排在最后 | 带名字和 open_id，方便 bot @ 回去 |
| 引用的那条消息 | 放 | 太长就截断 |
| 文件和图片 | 触发消息和引用消息里的，下载到本地给路径 | 别人消息里的文件只写文件名 |
| 语音 | 放转写的文字 | 今天已有 |
| 别的话题、别的群、主人私聊 | 不放 | 要查本群更早的，用查历史工具（第 5 节） |
| 别的 bot 的过程、工具步骤、子 agent | 不放 | 只放它的最终回答 |
| 自己以前的回复 | 不重复放 | 已经在自己的会话里 |

新会话的开场多带一点：
- 新话题：话题的第一条消息，加话题里已有的消息。
- 从主区开出来的话题（两种主区都一样）：再加主区在第一条消息之前的最近几条。
- 不复制主区会话的历史。要更早的，bot 自己查。
- "从主区会话整个分叉出去"（Codex `thread/fork`，Claude `forkSession`）v1 不做。它把整段主区历史复制过去，很费 token（〔码〕3.2）。以后需要可以加 `/fork`。

新消息合成一个"对话记录块"，按时间排，最后一行是触发消息。样子如下：

```
[飞书 · 群「支付组」· 话题「订单接口 500」]
10:01 张三：订单接口今天一直报 500
10:03 小审（bot）：第 88 行改对了，但金额为 0 时还会出错……
10:05 王五（ou_…a1b2）→ @小码：小审说的那个情况你改一下
[/飞书]
```

- 用真名。触发人靠 SDK 的 `resolveSenderName`；其他人用群成员接口换名字，记在缓存里。要哪个权限：未知，候选是 `im:chat.members:read` 或 `contact:user.base:readonly`（〔码〕3.3）。查不到就写 open_id 尾号。
- 预算按字数，不按条数。超了就留最近的，开头加一行"更早还有 N 条没放进来，可以用查历史工具"。具体数字实现时定。
- 每条压成一行，防止有人在消息里伪造记录块（今天已有，`context-weave.ts:375-384`）。
- 记录块要写得像给人读的，因为用户在 Codex 或 Claude 里打开会话时会看到它。

### 三种回复模式下的区别

| 模式 | 什么时候开一轮 | 这一轮带进去的新消息 |
|---|---|---|
| 仅 @ 时回复 | 有人 @ 它 | 上次回复以后的全部新消息，加这条 @ |
| 全部回复 | 每条消息。@ 了别人（包括别的 bot）的不算（今天的规则，`handle-message.ts:1199`） | 通常只有这一条。它正忙时来的几条，插进当前这一轮，或合成下一轮，都带名字 |
| 智能回复 | 小模型判"该回"的消息 | 和仅 @ 一样。判"不回"的消息不进会话，下次开轮时作为新消息一起带上 |

- 智能回复的小模型自己看最近几条来判断。它读到的东西不写进 bot 的会话，不会弄脏会话（推断：用一次性调用，`D/provider/engines/engine.ts:64-65` 的 `oneShot`）。
- 三种模式共用一条规则：原生会话里只有 bot 真正开轮时读到的东西。不做"每条消息都实时塞进会话"。理由是：每个群都要常驻进程；Codex 塞进去的在应用里看不到；闲聊越多，压缩越频繁（〔码〕3.4）。
- "开话题"的主区，三种模式都要 @ 才开新话题，旧产品就是这样（`handle-message.ts:1197-1205`）。
- 话题里：bot 开的话题、或者它被 @ 过的话题，按它的回复模式走；别的话题要 @ 才回。comma 和 Grok 也是"参与过的线程里不用再 @"（`references/comma/systems/apps/salix_im/lib/salix_im/provider_http.ex:3595-3620`；docs.x.ai/grok-bot/team-bots）。

### 多个人
- 一条会话大家共用。每条消息带名字，触发人多带一个 open_id。
- 权限按群定，不按人拆会话（第 2 节）。

### 多个 bot
- 每个 bot 在同一个话题或主区里各有一条会话（owner 已认可）。
- 建议 B 看得到 A 的最终回答，标成"A（bot）"，截到几百字。看不到 A 的过程和子 agent。这样能做"A 写，B 审"。
- 拿到 A 的回答有两条路（推断）：
  - A 和 B 在同一台 Mac 的 vonvon 里，daemon 自己就有 A 的回答。
  - A 在别人的机器上，就要从飞书拉。拉的时候要让飞书返回卡片原文（FS `message_list.md:37` 的 `card_msg_content_type`）。拉历史会不会返回别的 bot 的消息、要不要多申请 `include_bot` 权限：未知。
- B 不会因为 A 说了话就开一轮。只有 A 明确 @ B 才算，而且来回次数有上限。防循环、几个 bot 抢答同一条，按 v1 回复模式那部分的规则（`owner-updates.md` 更新 1）。

## 3b. 子 Agent

### 事实
- 两家的子 agent 都是原生的。每个子 agent 有自己的上下文，父会话只拿到最终结果（Codex：CXG `v2/ThreadItem.ts:64-101`、`SubAgentSource.ts`；Claude：code.claude.com/docs/en/sub-agents）。
- Claude 的子 agent 默认从空白开始，只拿到父 agent 给的任务；"分叉"的子 agent 例外，带上全部对话（code.claude.com/docs/en/sub-agents）。Codex 旧工具默认不带父历史，新版 `multi_agent_v2` 默认带全部（CXR `core/src/tools/handlers/multi_agents_spec.rs:627-632`、`:665-669`）。0.156.1 的默认值：未知。
- Claude 的子 agent 默认在后台跑，结果在之后的回合送回来（code.claude.com/docs/en/sub-agents）。bridge 用户碰到过："开 5 个子进程，一个完成会话就结束了"，"他不回显处理细节吗"（群#681-693）。
- 能单独停。Claude 用 `stopTask`（SDK `:3235-3238`），Codex 对子线程发 `turn/interrupt`（`docs/native-capabilities.md:150`）。Claude 还能给一句"现在在做什么"（SDK `:2078-2087`）。
- 上限：Codex 默认最多 6 个、1 层（CXR `core/src/config/mod.rs:255`、`:265`）；Claude 最多嵌套 3 层、同时 20 个（code.claude.com/docs/en/agent-sdk/subagents）。
- 今天：Codex 子线程的事件全被丢掉（`D/agent/codex-appserver/backend.ts:333-337`）。Claude 子 agent 的步骤混在主过程里（`D/agent/claude-agent/event-map.ts:92-123`）。
- 别家都是"挂在父任务下面"：
  - Codex 桌面版有子 agent 面板，分进行中和已完成（learn.chatgpt.com/docs/agent-configuration/subagents）。
  - Claude Code 在输入框下面有子 agent 面板，能选中、能停（code.claude.com/docs/en/sub-agents）。
  - OpenClaw 说"要开子 agent 不等于要新会话"。在飞书上它不支持子 agent 自己开线程（docs.openclaw.ai/tools/subagents；docs.openclaw.ai/tools/subagents/thread-bound-sessions）。
- 飞书的限制：
  - 一个群里所有 bot 共用每秒 5 条的发送额度（FS `message_create.md:13`）。
  - 一张卡片每秒最多改 10 次；流式更新开启 10 分钟后自动关（`飞书文档副本/uAjLw4CM_ukzMukzMukzM_feishu-cards_streaming-updates-openapi-overview.md:25`、`:244`）。
  - 一张卡片最多 200 个组件、30 KB（〔飞〕1.6）。
- 已有设计：运行卡第 6 区叫"子 agent"。最多 6 行运行中、3 行已完成，再写"另有 N 个已完成"。每行有状态、任务、步数、用时、当前步骤；展开看最近 5 步和结果；有"查看完整过程"和"停止"（`docs/providers.md:775`、`:783`）。但同一份设计写着"后台子 agent 随运行结束"（`docs/providers.md:617`），和 Claude 默认后台跑冲突。

### 建议：怎么显示
- 子 agent 只显示在父运行卡里，用已经设计好的子 agent 区。不每个发一张卡，也不开话题。
  - 理由：5 个子 agent 各发一张卡，很容易撞上群里共用的每秒 5 条；话题里不能再套话题（推断）；Codex 和 Claude 原生也是挂在父会话下面。
- 一行一个子 agent：状态、名字或类型、在做什么、几步、用了多久。Claude 的"一句话进度"放在"在做什么"。嵌套的子 agent 缩进，排在它的父行下面。
- 点开一行，看最近 5 步和结果。"查看完整过程"在运行卡同一处另发一张卡（话题里就发在话题里）。
- 卡片头部的上下文仪表只算父会话。子 agent 自己的用量写在它那一行。
- 主回答发出时还有子 agent 在跑：卡片不写"完成"，写"已回复，还有 N 个子 agent 在跑"，这一区继续更新。全部跑完以后，bot 在同一处接着回复，标"子 agent 完成后继续"。这要改 `docs/providers.md:617`，见第 8 节问题 4。
- 跑过 10 分钟，飞书的流式更新会自动关。之后卡片改成隔一会刷新一次（推断，频率实现时定）。

### 用户能做什么
- 看进度：看运行卡里的子 agent 区。
- 停一个：点那一行的"停止"。父 agent 继续，拿到"已停止"的结果。
- 全停：点运行卡的 ⏹，主任务和它的所有子 agent 一起停。
  - Claude 要先声明 `perTaskStopAffordance` 才能单独停；声明以后，停主回合不会顺带停后台子 agent（SDK `:1796-1813`）。所以全停时 daemon 要逐个停。
- v1 不能直接跟某个子 agent 说话。群里的新消息只给父 agent。原生能不能对子 agent 单独开一轮：未知（〔飞〕3b）。

### 子 agent 的上下文和父会话的关系
- 子 agent 没有自己的飞书对话。它的上下文是父 agent 交给它的任务，加它自己的指令；分叉的子 agent 再带上父会话的历史。
- 群里的新消息、对话记录块、人设和记忆，都只进父会话。Claude 原生的自动记忆本来也不传给子 agent（code.claude.com/docs/en/memory）。
- 子 agent 不占父会话的窗口。父会话只多了每个子 agent 的最终结果。子 agent 的窗口满了，自己压缩（code.claude.com/docs/en/sub-agents）。
- 子 agent 的记录跟着父会话存。在 Codex 应用或 Claude 里打开父会话，能看到它们（推断：Codex 子线程带 `parent_thread_id`，Claude 存在会话的 `subagents/` 目录下，〔码〕2b）。

## 4. 压缩

### 事实
- 两家都有原生的自动压缩和手动压缩。
  - Codex 手动用 `thread/compact/start`，不能带说明（CXG `v2/ThreadCompactStartParams.ts`）。
  - Claude 手动发 `/compact`。压缩时有 `compact_boundary` 事件，带压缩前后的 token 数（SDK `:3776-3784`）。
- 今天每个群有个"关闭自动压缩"开关，只接了 Codex（`D/project/registry.ts:51-55`；`D/agent/codex-appserver/backend.ts:55-71`）。新版 Codex 会把阈值封顶在窗口的 90%，这个关法可能已经失效（推断，CXR `protocol/src/openai_models.rs:529-540`）。关掉以后窗口满了，卡片只能报"上下文已满"（`docs/providers.md:801`）。
- 今天 `/compact` 只能在空闲时用，压缩中来的消息要用户重发（`D/bot/handle-message.ts:2101-2106`）。`/clear` 只在单会话群、只限管理员，旧会话能 `/resume` 回来（`:2110-2190`）。`/context` 的用量只存在内存，重启后显示 0（`:853-855`）。
- 压缩会丢早期细节。Claude 官方建议长期规则写进指令文件，不要只留在对话里（code.claude.com/docs/en/agent-sdk/agent-loop）。
- 别家：OpenClaw 默认自动压缩，`/compact` 可以带重点；默认不定期重置会话（docs.openclaw.ai/concepts/compaction；docs.openclaw.ai/concepts/session）。
- bridge 用户说"上下文太长会压缩吧，不需要 new，群聊最主要的是可以持久保持上下文"（群#46）。也有人要单会话群能清空重开（群#578、#598）。

### 建议：自动为主，保留命令
- 自动压缩：两家都用原生的，一直开。去掉"关闭自动压缩"开关。
- `/compact`：保留。话题、"连续"主区、主人私聊都能用。
  - v1 不带说明，因为 Codex 不支持。
  - bot 正在跑时发 `/compact`，等这一轮结束再压。
  - 压缩时来的消息排队，压完接着处理，不让用户重发。
- 用户看到的：
  - 运行卡头部一直有上下文仪表（今天已有）。
  - 压缩时，过程区多一行"上下文已自动压缩"或"上下文已手动压缩"，带"85% → 20%"（`docs/providers.md:774` 已有这一行）。
  - 用量过某个线（比如 80%）时，卡片底部提示"可以 /compact，或开个新话题"。线在哪里实现时定。
  - `/context` 随时能查。用量要存盘，重启后还在。
- 从头开始：
  - 话题里不清空。开个新话题，就是新会话。
  - "连续"主区和主人私聊用 `/new`（旧的 `/clear` 继续能用）。旧会话停放，能 `/resume` 回来。"连续"主区里只有管理员能 `/new`，因为这条会话是大家共用的。
- 压缩后忘掉的细节，原文还在飞书里，bot 可以用查历史工具回查。长期的事放进记忆和人设，不靠会话撑着。
- 压缩前不自动写记忆。记忆设计 v1 只做"用户说记住"和"agent 自己判断要记"两种，而且都要在卡片上显示（〔记〕结论 3）。OpenClaw 那种压缩前悄悄写记忆，v1 不做。

## 5. 查历史

### 事实
- 飞书接口 `GET /im/v1/messages` 按群或按话题取，一页最多 50 条；群主区能按时间过滤，话题不能（FS `message_list.md:30-35`）。
- bot 不在群里，返回 230002（FS `message_list.md:126`）。开了保密模式的群拉不到（`:132`）。
- 进群前的消息能不能拉，看群设置"新成员可查看历史消息"（FS `message_list.md:130`）。这个设置的默认值：未知。
- 用应用身份读群消息，文档要求的权限 v2 今天没申请全（FS `message_list.md:18`；`D/config/scopes.ts:18-38`）。今天的话题补拉到底能不能成功：未知，要看 Mac 上的日志。
- lark-cli 有只读命令 `im +chat-messages-list` 和 `im +threads-messages-list`，可以选用户身份或 bot 身份（`lark-cli im +chat-messages-list --help`，标着 `Risk: read`）。
- 实测：本机 lark-cli 用用户身份，能从一个社区群的第一条消息读起，而那个群里的 bot 不是 lark-cli 用的应用；换 bot 身份读同一个群，返回 230002（〔飞〕2.3）。也就是说，用户身份看得到"这个人在飞书里能看到的一切"。
- 消息搜索接口按文档只收用户身份（open.larkoffice.com/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/message/search）。
- lark-cli 同一个程序也能发消息。它的 `config strict-mode` 只锁身份，不锁读写（`lark-cli config strict-mode --help`）。
- comma 的飞书接入给 agent 两个窄工具：拉群历史、拉话题回复，读到的内容打上来源标签（`references/comma/systems/apps/salix_im/lib/salix_im/provider/feishu.ex:133-137`；`…/salix_im/ifc/read_labels.ex:1-30`）。

### 建议
- 平时不用查。每轮都自动带上"上次以后的新消息"（第 3 节）。只有要更早的，才查。
- vonvon 给 agent 一个"查本群历史"工具，名字实现时定。
  - 用 bot 身份。
  - 只能查当前的群主区或当前话题。范围由会话决定，agent 改不了。
  - 能按时间往前翻，按条数和字数截断。
  - 底层直接调飞书接口，或者由 daemon 调 lark-cli 的只读命令。不把 lark-cli 本身交给群里的 agent。
- 运行卡上显示这一步，比如"查了本群 9:00–10:00 的 40 条消息"。
- 用户身份：群里永远不给。主人私聊里可以做成主人手动打开的选项，默认关。
- 隐私边界：
  1. 不读 bot 不在的群。
  2. 在 A 群里查不到 B 群，也查不到主人私聊。
  3. 查到的内容只用于这一轮，不自动进记忆。
  4. bot 读得到群里不是对它说的话（读全部群消息本来就是敏感权限，FS `message_events_receive.md:38`）。bot 进群时的欢迎卡要写明"我能读本群的聊天记录"。

## 6. 上下文和记忆的关系

### 事实
- 记忆设计（〔记〕7(b)）：每个 bot 有三份记忆。
  - 本群记忆：只在本群加载。
  - bot 公共记忆：所有群都加载，只有主人能写或确认。
  - 主人私聊记忆：只在主人私聊加载。
  - 记忆在会话开始或恢复时放进去，标成"背景资料，不是指令"。中途写的，下一条会话才生效。
  - 写入走 vonvon 的记忆工具，卡片上显示"已记到…［撤销］"。
- 记忆目录是每个 bot 一份：`bots/<appId>/groups/<chatId>/memory/`（〔记〕7(a)）。
- Claude 原生的自动记忆按仓库共享，Codex 原生的记忆全局一份。记忆设计要求 vonvon 的会话里都关掉（〔记〕结论 6；code.claude.com/docs/en/memory；CXR `memories/README.md`）。
- 别家也把个人记忆和群隔开：ChatGPT 群聊不用个人记忆（openai.com/index/group-chats-in-chatgpt/）；OpenClaw 的群会话拿不到私聊内容（docs.openclaw.ai/concepts/session）。

### 建议

| | 会话（上下文） | 记忆 |
|---|---|---|
| 放什么 | 这段对话的来往：记录块、工具步骤、回答、子 agent 结果 | 以后还要用的事实和约定，比如项目背景、偏好、"发版前要审" |
| 多大 | 窗口满了就压缩 | 有字数上限，满了要整理 |
| 活多久 | 到 `/new` 或开新话题为止 | 一直在，跨会话 |
| 范围 | 一个对话 | 本群、所有群、主人私聊，三种 |
| 怎么进 | 自动 | 用户说"记住"，或 agent 判断要记；卡片上能撤销 |

- 同一个群的几个话题不共享会话，靠本群记忆共享长期的事。新话题开场时读一次本群记忆，就知道这个群的背景。
- 记忆是每个 bot 自己的。同一个群里，A 记住的事 B 不知道。要 B 也知道，得另外跟 B 说。
- 查历史拿到的内容、压缩出来的摘要，都不自动进记忆。
- 主人私聊里的内容，不进任何群的会话和记忆。

## 7. 三个 bot 在同一个群里的例子

群「支付组」，主区设成"连续"。三个 bot：
- 小码：Codex，写代码，仅 @ 时回复。
- 小审：Claude，审代码，仅 @ 时回复。
- 小秘：Claude，助理，智能回复。

**① 10:01 主区，张三：订单接口今天一直报 500，谁有空看看？**
- 小码、小审：没被 @，不动。这条留在飞书里。
- 小秘：小模型判断"他在找人看代码，不是问我"，不回。这条不进它的会话。

**② 10:02 主区，李四：@小码 帮忙查一下，日志在 logs/order.log**
- 小码：开一轮。主区会话里加一个记录块：①张三那句，加②这条（带李四的 open_id）。
  - 它派了两个子 agent，一个看日志，一个看最近的提交。运行卡的子 agent 区出现两行。
  - 看提交的那个跑偏了，李四点了那一行的"停止"。另一个继续。
  - 小码回答："空指针在 OrderService 第 88 行，已改。"
- 小审、小秘：这条 @ 了小码，不动。

**③ 10:20 王五在小码那条回答下开了话题：@小审 帮看下这个改动有没有风险**
- 这是新话题 T。小审在 T 里建一条新会话。开场有：话题第一条（小码的最终回答，标"小码（bot）"）、主区在它之前的①②、王五这条。
- 小审看不到小码的过程和子 agent。它回答："第 88 行改对了，但金额为 0 时还会出错。"
- 小码：在 T 里没被 @，不动。它主区那条会话没变。
- 小秘：这条 @ 了别人，不动。

**④ 10:25 话题 T，王五：@小码 小审说金额为 0 的情况没处理，你改一下**
- 小码：在 T 里建自己的新会话，和它主区那条是两条。开场有：话题第一条（它自己在主区的回答）、小审的回答、王五这条。它改完回复。
- 小审：这条没 @ 它，不动。下次在 T 里被 @，④和小码的新回答会作为新消息带进去。

**⑤ 10:40 主区，张三：下午三点发版。以后发版前都要小审过一遍，记一下**
- 小秘：小模型判"该回"。它的主区会话带进来的新消息有：①、②、小码在主区的最终回答、⑤。话题 T 里的消息不在里面，因为那是另一个对话。
  - 它把"发版前要小审审查"记进它自己的本群记忆。卡片显示"已记到本群记忆［撤销］"。
- 小码、小审：没被 @，不动。这条记忆是小秘的，它们看不到（第 6 节）。

## 8. 需要你拍板的问题

**问题 1：群主区怎么接**
- A. 只留"开话题"：主区 @ 一次，开一个话题。
- B. 只留"连续"：主区一条会话，话题另算。
- C. 两种都留，每个群选一种，随时能切，切了以后从新会话开始。默认"开话题"。
- 推荐 C。干活的群用"开话题"，一件事一条会话，互不干扰（群#41）。一个人用、想一直接着聊的群用"连续"（群#46）。默认"开话题"，是因为人多的群里，一条会话不会越滚越长。

**问题 2：私聊做不做**
- A. 不做。私聊只是管理菜单，和今天一样。
- B. 只给 bot 主人做对话。其他人看到一张"去群里 @ 我"的卡片。
- C. 主人再加一份名单。名单里的人也能私聊对话，每人一份私人记忆。
- D. 谁都能私聊对话。
- 推荐 B。不让别人在主人电脑上随便跑 agent，记忆也不用按人再分。C 可以以后再加。

**问题 3：同一个群里，bot 能不能看到别的 bot 的回答**
- A. 能看到最终回答，看不到过程和子 agent。
- B. 完全看不到，和今天一样。
- 推荐 A。能做"小码写、小审审"；用户说"看看小码的方案"时，小审不会一头雾水。代价：要在 Mac 上确认飞书会不会把别的 bot 的消息给我们，要不要多申请权限。防循环的规则在回复模式那部分定。

**问题 4：主回答发出了，后台子 agent 还在跑，怎么办**
- A. 继续跑。卡片写"已回复，还有 N 个在跑"，继续更新。跑完以后 bot 在同一处接着回复。
- B. 主回答一结束，没跑完的子 agent 一起停。
- 推荐 A。这是 Claude 的原生做法，也正是 bridge 用户抱怨"一个完成就结束了"的地方（群#681-693）。B 做起来简单，但子 agent 白跑，用户也看不到结果。
