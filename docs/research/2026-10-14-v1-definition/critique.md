## 1. 需求还原度

**1.1 高：管理员和访客两档被悄悄合并，迁移后权限会变宽或变窄**
- 现状：草案 3.7 写"权限档按群定一个，不再按管理员和访客拆成两条会话"。第 4 节只把它列为"会感到的变化"，没说迁移时取哪一档。今天如果群里设了不同的访客档，访客按自己的档跑，会话也拆开（`D/project/registry.ts` 的 `turnTier`）。
- 后果：合并后取管理员档，访客就拿到 full；取访客档，管理员就干不了活。
- 依据：草案引的群#953，用户要的是"同一会话按发信人切权限"，不是取消分档。按轮切档没有验证过：Codex 的 `turn/start` 有 `sandboxPolicy`，但 v2 用的是 thread 级的 `permissions` 配置。
- 改法：v1 保持今天的行为，只有设了不同访客档的群才拆会话。把这条从"会感到的变化"里删掉，"同一会话按人切档"放进 v1 之后。或者做成拍板问题，见 4.3 的问题 A。

**1.2 高：工作区和代码仓库没有区别**

  - 工作区是 bot 产出文件的地方，可写。
  - 代码仓库是一个 git 目录，可以填本机路径，也可以填 git 地址（由 vonvon clone 到 `~/Vonvon/<bot>/repos/`）。界面显示分支。bot 的指令里写"先读该仓库的 AGENTS.md"。仓库可写，但要提醒：在 Codex 下 `.git` 默认只读。
  - 要不要支持 git 地址，放进静默决定列表，或者问 owner。

## 2. 可行性

**2.1 高：拉历史和查引用消息要一个今天没申请的权限**
- 飞书文档的说法：用应用身份读群消息，除了 `im:message.group_msg`，还要再开 `im:message`、`im:message:readonly`、`im:message.history:readonly` 三个里的一个（`飞书文档副本/server-docs_im-v1_message_list.md:18`、`server-docs_im-v1_message_get.md:17`）。
- v2 现状：`config/scopes.ts` 的 `REQUIRED_SCOPES` 和一键授权用的 `GRANT_SCOPES` 里，这三个都没有（grep 无结果）。今天话题补拉失败时，代码只写一条 `thread-context-failed` 警告，然后返回空（`D/bot/context-weave.ts:103-140`）。所以补拉可能一直在悄悄失败。
- 草案的问题：3.6 的权限表说拉历史只要 `group_msg`，"迁移 bot 都有"。这个说法不成立。依赖拉历史的东西有五样：
  - 对话记录块；
  - 查本群历史工具；
  - 底线 2（看话题里最近说话的是哪个 bot）；
  - 底线 1（按 `parent_id` 查引用的是谁）；
  - 跨机器发出前的复查。
- 改法：
  - 权限表加一行 `im:message:readonly`，标为新增。所有 bot 都要，包括迁移过来的；企业租户要管理员审核。
  - M1 的第一件事：在 Mac 日志里搜 `thread-context-failed`，确认现状。
  - 写明缺这项权限时怎么降级：bot 只看触发消息，以及 daemon 在本机记下的消息。

**2.2 高："新安装时 group_msg 改为可选"和上下文设计冲突**
- 现状：静默决定的列表里有这一条，3.6 说缺了"只能用仅 @"。
- 冲突：3.7 里仅 @ 档也要带"上次以后的全部新消息"，查历史也要读群消息，两样都靠这项权限。缺了以后，仅 @ 档也只剩触发消息本身。
- 改法：从静默列表里拿掉。要么保持必需；要么写清"缺了只能仅 @，而且 bot 看不到群里的其他消息"。

**2.3 高：Claude 后端的登录政策会卡住发布，草案只写成"待定风险"**
- 我核实了 code.claude.com/docs/en/agent-sdk/overview 的原文："Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK. Use the API key authentication methods…"。v1 是发给别人用的闭源产品，而 Claude bot 复用的正是用户本机的 claude.ai 登录。
- 同一页的品牌规定：产品里不许把功能叫"Claude Code"或"Claude Code Agent"。草案第 1 节和 v2 catalog 的说明文字都写着"Claude Code"。
- 3.5 末尾"影响所有 Claude bot，不只是 v1"读不通。调研原文是"不只是智能回复"。
- 改法：升为拍板问题，见 4.3 的问题 B。界面文案统一改成"Claude"。

**2.4 高：Codex 的几个关键字段是实验性的，用户的 Codex 版本又没人管**
- 实验字段：`runtimeWorkspaceRoots`（`codex-rs/app-server-protocol/src/protocol/v2/thread.rs:82-85`，标了 `#[experimental]`）、`skills/extraRoots/set`、`dynamicTools`。vonvon 按 0.156.1 生成的类型里没有这几个，只有打开 `experimentalApi` 时才能用。
- 版本没人管：v2 用的是用户自己的 codex，来源可能是 `CODEX_BIN`、PATH、Codex.app 自带的，或者 managed-tools（`D/agent/codex-appserver/locate.ts:25-60`）。代码只读出版本号用来显示，没有最低版本检查（`backend.ts:540-552`）。
- 后果：Codex.app 会自己升级。实验字段改了名或被删掉时，多工作区和 skill 隔离会悄悄失效。
- 改法：
  - 3.5 里把这几个字段标成"实验 API"。
  - v1 定一个最低版本和一个验证过的版本，首次运行和诊断页都检查。
  - 调用实验字段失败时直接报错，不要悄悄退回单目录。
  - 可以考虑默认用 vonvon 自己管的 Codex（managed-tools）。

**2.5 中：Claude SDK 下载时不锁版本**
- 现状：`D/agent/catalog.ts:98-116` 里按需下载的包名是 `@anthropic-ai/claude-agent-sdk`，不带版本号，installer 直接执行 `npm install <pkg>`。开发机上装的是 0.3.296，`docs/providers.md` 计划用 0.3.246。
- 后果：草案依赖的 `plugins`、`skills` 白名单、`settings.autoMemoryDirectory`、`snapshot:false`，都会跟着下载那天的最新版走。
- 改法：v1 锁一个验证过的 SDK 版本，和 `package.json` 保持一致，下载时带上版本号。

**2.6 中：记事本和查历史两个工具，要一条现在两家都没接的工具通道**
- 现状：v2 今天不给 agent 注入任何 vonvon 自己的工具。Claude 那边传的是 `mcpServers: {}`，grep 也没找到别的注入。可草案把记忆写入、查本群历史、个性修改建议、提议写公共记忆，都写成"vonvon 给的工具"，没说怎么接进去。
- 可选的接法：
  - Claude：用 SDK 的进程内 MCP（`createSdkMcpServer`）。
  - Codex：用实验字段 `thread/start.dynamicTools`（`codex-rs/.../v2/thread.rs:145-151`），或者在 config 里配一个 MCP server。
- 未知：resume 以后动态工具还在不在；在 qa 只读沙箱里能不能调。
- 改法：
  - 3.4 和 3.5 各加一行"工具通道"，写进 Mac 探针清单，在 M2 之前先做。
  - 写明降级：通道不可用时，记忆只能由用户在桌面端编辑。

**2.7 中：迁移以后可能找不到 Codex**
- 现状：bridge 有一份自己装的 codex，放在 `~/.feishu-codex-bridge/codex-cli`（bridge `src/agent/codex-appserver/locate.ts:19`）。launchd 下的 PATH 很短，很多老用户可能就靠这一份。v2 只在自己的数据根下找 `codex-cli` 和 managed-tools，不找 bridge 的那份。`bridge-inventory.md` 第 2 节还把 `codex-cli/` 列成了"不迁"。
- 另外，首次运行清单（第 2 节第 4 条）里没有"Codex 或 Claude 能用"这一步。
- 改法：
  - 预检时检测 bridge 自己装的 codex，导入时引用它的路径，或者用 managed-tools 装一份。
  - 首次运行清单加一步："检测 Codex 或 Claude 已安装、已登录、版本够用"。

**2.8 中：几个 bot 都开"全部回复"时到底几个回，前后说法不一致**
- 现状：3.6 只写了界面提示"几个 bot 都开会抢着回"；可 M3 要验的是"两个 bot 都开全部回复……实际只有一个回"。只放一个 bot 回，靠的是 daemon 仲裁（`group-response.md` 6.6：优先最近说过话的，都没说过就选最早绑定的），草案里没写这条规则。
- 改法：
  - 3.6 写明：同一台机器上，daemon 只放行一个 bot，按上面的规则选；不同机器上的 bot 可能都回，靠界面提示。
  - 提示文案改成"不同电脑上的 bot 可能抢着回"。

**2.9 中：三条底线漏了两种情况**
- 话题里还没有 bot 说过话。两种来源：普通群里真人自己开的话题；飞书话题群里，每条新帖本身就是一个话题。bridge 今天开了免 @ 的 bot 在任何话题里都回（`D/bot/handle-message.ts:1196-1203` 的 `Boolean(msg.threadId)`）。草案的底线 2 只管"有 bot 说过话"的话题。单 bot 群的迁移用户在这里会感到变化。
- 引用的规则有三种说法：
  - 底线 1 写"回复（引用）了谁，就只有谁回"。
  - `group-response.md` 6.2 有一个例外："仅 @ 档里，引用我的消息不算点名"，草案没带上。
  - 第 4 节又写"全部回复档里，引用 bot 的消息就算点名它"。
- 改法：
  - 补一条："话题里还没有 bot 说过话时，开了全部回复的 bot 回（单 bot 群和今天一样）；几个 bot 都开了，按 2.8 仲裁。"
  - 底线 1 补上仅 @ 档的例外。

**2.10 中：智能回复判断模型的两条建议互相冲突**

**2.11 中："主回答发出后子 agent 继续跑、跑完接着回"没验证过**

**2.13 低：登录自启的选项少了一个中间方案**

## 3. 范围

**3.1 可以砍掉、让 v1 早点发的（按省下的工作量排）**
- skill 的"git 地址加子路径、钉 commit、更新时看差异"这一种来源。v1 只留三种：内置、本机文件夹、从 `~/.claude/skills` 等目录导入。迁移用户用最后一种就够了。
- 在聊天里改配置，一共三种：说"以后这个群说话活泼点"后弹修改建议卡；说"给小码加上 X"；bot 提议写公共记忆后弹确认卡。v1 里个性、skill、公共记忆只在桌面端改，保留"记住"写本群记忆。这和"不做聊天建 bot"一致，还能少三种确认卡。
- 智能回复的跨机器复查（"晚的那个发出前再查一次"）。v1 接受偶尔两台机器都回。
- 子 agent 的"查看完整过程另发一张卡"。
- 诊断页只留连接状态和"没回的消息和原因"。判断次数放进用量页，或者以后再做。
- 问题 3 可以考虑选 b：能看到别的 bot 的最终回答，但不能互相 @。这样省掉一个要企业管理员审核的新权限，也省掉 bot 回合计数和循环提示。这是砍范围的候选；草案推荐 a 也说得通，交给 owner 定。

**3.2 迁移用户一定会要、草案没写的**

- Intel Mac。#257 只出过 arm64 包，`electron-builder.yml` 里没写架构。老用户里有多少人用 Intel Mac 不知道。要么出 universal 包，要么写进第 4 节"失去"一栏。见 4.3 的问题 C。

- 云文档评论的会话用哪个工作区、带不带个性和公共记忆，草案没定义。建议：沿用今天"每篇文档一个目录"，带 bot 个性和公共记忆，不带任何群的记忆。
- 首次运行清单少了"Codex 或 Claude 能用"这一步，见 2.7。

**3.3 迁移放到 M4 太晚**
