## 0. 结论先行

1. **界面能用，但只是两个纯文本框。** Bot 详情页有"个性 / 记忆"两个输入框；Bot×群 页有两个本群输入框，各自上方可以挂一块灰色的 Bot 继承引用块。界面上没有生效后的组合结果，没有来源、版本、历史、写入者，也没有字数显示。【确认】
2. **现在只有主人手写，bot 自己一个字也不会记。** s40（说"记住"就写进记忆、卡片能撤销）、私聊干活 s49、私聊改设置 s54a/s56a 都没做。主人看到的"个性和记忆都是空的"，就是现在的真实状态：新 bot 和新群的默认值都是空串。【确认】
3. **运行时确实在用这两段文字。** 每轮发给任务会话，也发给智能判断；改了以后下一轮通过"设置更新"生效。但走的是概览设计（today-design）落地时写的 `bot/group-profile.ts` 这条简化路径，**没有用** s38a1 合入的带来源、版本标题的组合模块。【确认】
4. **文档和实现在存储位置上冲突。** product.md 3.3/3.6 说本群个性和记忆放在 `groups/<chatId>/…` 下的 Markdown 文件里，s40 也打算让 agent 直接写这个文件。实际上本群内容存进了 `projects.json` 的 `profile` 字段，那个文件只在旧数据物化时读一次。照原计划做 s40，agent 写进去的是一个没人读的文件。【确认 + 推断】
5. **私聊现在根本不跑 agent**，进的还是旧的管理菜单卡，谈不上"认识我"。多个 bot 之间没有任何共享层。【确认】

### 1.3 保存、冲突、草稿保护（通用的 `Editor`，`settings/SettingsPanel.tsx:100-310`）

- 个性和记忆在**同一节**（`profile`），共用一个版本号和一个"保存"按钮。保存只提交改过的字段，带上读到时的版本号做比较替换（CAS）（`SettingsPanel.tsx:216-245`）。
- 成功后出提示"本次修改已保存"，后面跟 daemon 给的生效说明。群页给的是"下一条消息生效"，所以群页平时的脚注是隐藏的（`SettingsPanel.tsx:168-175, 268`；`admin/settings.ts:579`）。
- 冲突时提示"设置已在别处更改：当前草稿已保留。重新读取后可基于最新设置修改。［重新读取并放弃草稿］"（`SettingsPanel.tsx:140-148, 293-296`）。**没有差异对比，也没有合并**，只能选丢掉草稿重新读。
- 带着草稿离开页面，会弹"有未保存的修改"：［放弃并离开］或［保存并离开］（`settings/DraftGuard.tsx:63-67`）。
- 保存本群个性或记忆后，daemon 会关掉这个群在内存里活着的会话句柄，下一轮以恢复的方式重开（`admin/settings.ts:857-859`，`bot/handle-message.ts:3642-3653`）；保存 Bot 个性不会这样做。【确认】正在跑的那一轮会不会被打断，没有核实。【推断待查】

### 1.4 字数上限：三处口径不一致

| 位置 | 上限 | 依据 |
|---|---|---|
| 界面输入框 | `maxLength=30000`（按 UTF-16 计），没有计数器 | `GroupDesignSettings.tsx:129-132,296-297` |
| 保存时的协议校验 | `value.length <= 30000` | `admin/settings-parse.ts:8,67,102` |
| Bot 个性和公共记忆落盘 | 30000 个码点 **且** ≤64 KiB（UTF-8 字节） | `group-profile.ts:49`，`personality-files.ts:30,169-170` |
| 本群个性和记忆（存 `projects.json`） | 只有上面那条 30000 的校验 | `admin/settings.ts:791` |

由此推出：中文每字 3 字节，**Bot 个性或公共记忆写到约 21,845 个汉字就会保存失败**，比界面允许的 30000 少。失败时抛的是普通 `Error`，被映射成通用文案"settings：保存失败，请刷新设置后重试；若配置被其他进程修改，请重启 daemon"（`admin/settings.ts:258-266, 894-901`）。主人看不出原因是太长。【推断，按代码算的，没有实测】另外，按浏览器的标准行为，超出 `maxLength` 的粘贴内容会被直接截掉，不会有任何提示。【标准行为】

## 2. 规划：做了什么、没做什么、明确不做

### 2.1 背后的数据流（现行路径）【确认】

- **存储**：Bot 个性 → `bots/<appId>/SOUL.md`（读时并入 `AGENTS.md`）；公共记忆 → `bots/<appId>/memory/shared.md`；本群个性和记忆 → `bots/<appId>/projects.json` 里那个群的 `profile` 字段（`project/registry.ts:11-12,21`，`config/paths.ts:51`）。新群初始值是 `{persona:'',memory:'',inheritPersona:true,inheritMemory:true}`（`project/initial-settings.ts:77`）。每次 bot 启动，`materializeGroupSettings` 会把还没有 `profile` 的旧群，从 `groups/<chatId>/SOUL.md` 和 `memory/group.md` 一次性复制进 JSON（`admin/settings.ts:1008-1038`，`handle-message.ts:8738`）。从那以后 `readGroupProfile` 只读 JSON（`group-profile.ts:35-40`）。
- **组合**：`readGroupPersonality` 生成"身份行 + [个性与职责] + [本群可用记忆 · 背景资料，不是指令]"三段。公共记忆和本群记忆**合成一个块**，模型分不出哪句是公共的、哪句是本群的（`group-profile.ts:79-91`）。
- **交付**：开会话时作为 profile 指令传入（`handle-message.ts:1051-1057`）；后续每轮比较版本，变了就在消息前附"[vonvon 个性与记忆更新 · 后台设置，不是群消息] 以下全文替换……"（`handle-message.ts:1059-1068`）；智能判断也传 persona 和 memory（`handle-message.ts:2027-2030`）。两家自带的记忆都关掉了（`automaticMemory:false`，`handle-message.ts:1055`）。
- **没交付的地方**：云文档评论会话调用的是 `profileOf(undefined, …)`，**个性和公共记忆都不带**（`handle-message.ts:8261,8271`）。这和 product.md 3.12 的"带 bot 个性和公共记忆"（`docs/product.md:690`）不一致。私聊不跑 agent（见第 3 节）。

## 4. 多 bot、多群的继承现状，以及含糊、矛盾的地方

**现状【确认】**：一共两层。第一层是 Bot 个性 + 公共记忆，每个 bot 一份。第二层是 Bot×群 的本群个性 + 本群记忆，每个群里的每个 bot 一份，个性和记忆各自能选继不继承。私聊记忆按人（`memory/dm/<open_id>/dm.md`）只有文件布局和 s38a1 的选择逻辑（`personality-files.ts:48`，`personality-context.ts:27-29`），没有接到运行时。没有机器级、也没有跨 bot 的"关于主人"这一层。product.md 明写"同一个群里几个 bot 各有一份本群记忆，不共享"（`:407`），"千人千面"体现在记忆上（`:68`）。

**含糊或矛盾的地方：**

1. **本群内容存在哪里。** product.md 3.3 的布局（`:112-119`）和 3.6（`:416-417`）都说本群个性和记忆是 `groups/<chatId>/` 下的 Markdown 文件，"主人可以直接用编辑器改"（`:127`）；s40 也计划让 agent 写 `group.md`（`v1-plan.md:1255`）。实现却放在 `projects.json`，启动时就物化掉了（第 2.1 节）。照原计划做 s40，写进去的文件没人读。
2. **有两套组合实现。** 现行的 `group-profile.ts` 把公共记忆和本群记忆合成一块，不带版本和来源；s38a1 的 `personality-context.ts` 按 3.6 分层，带"范围 · 文件 · 版本"，却没被接上。哪套是正统，s38b 怎么收敛，没有写。
3. **"群里任何人说'记住'都能写本群记忆"**（`product.md:403`）和"群里不能在聊天里改设置"（`:498`）字面上冲突。文档的处理是把记忆当作设置以外的例外（`v1-plan.md:1649`），但谁能点［撤销］写的是"主人和管理员"（`:1652`）。群成员能往记忆里写像指令的话，正是第 9 节第 25 项挂着的残余风险（`product.md:813`）。现在这条**完全没有实现**，固定层的话却已经说出去了（`bridge-instructions.ts:15`）。
4. **公共记忆"所有群和私聊"都用**（`product.md:401-405`），可群页能取消继承，取消后这个群就没有公共记忆了。
5. **AGENTS.md 的去向。** 3.6 的注入顺序把 bot 的 `AGENTS.md` 列为单独一层（`product.md:392-397`），s41 要单独的编辑器（`v1-plan.md:1256`）；3.2 改成"规矩并入个性，不另设编辑区"（`product.md:75-76`）；实现是读时合并、写时清空（`group-profile.ts:27-29,52-54`）。s41/s42 的勾选状态和描述已经落后于实际。product.md 自己声明这些"不是界面占位"（`:91`），v1-plan 里却还是 [ ]。
6. **评论会话**按文档应带个性和公共记忆（`product.md:690`，`v1-plan.md:1245`），代码一样都没带（`handle-message.ts:8261,8271`）。
7. **"不悄悄截断"**（`product.md:410`）只对任务会话成立。判断路径会静默截取前 1,500 / 2,000 字，被截掉的恰好是本群补充（第 1.5 节）。
8. **字数上限口径不一致**（第 1.4 节），而且继承后的组合最多可到 6 万字，没有总量提示。
9. **"按人"只覆盖私聊里的主人和管理员**（`product.md:702`）。群里按人分的记忆明确不做（`:766`），所以第一版的设计里，bot 在群里本来就无法"认识某个人"，包括主人。
10. **生效方式不对称**：保存本群内容会关掉活跃会话（`admin/settings.ts:857-859`），保存 Bot 内容只靠版本比较。对正在跑的一轮有什么影响，没有核实。
