# Rakazo runtime/state comparison

Research baseline: Rakazo `e55263f5fdfee9b2c48680a78e4487d37b4c04a8`; Vonvon `bbb329b9a9eef0dd809ee9468e0b6d1b9bf4a769`. Source exploration only. No upstream code, tests, services, dependencies, provider calls or user data executed/read. “Implements” below means the checked-in code implements that path; it does not assert a successful live run. Licensing/third-party exceptions are a separate root check. All recommendations remain proposals.

## Main judgment

Rakazo is relevant because it treats an agent conversation as durable product state, not merely a streamed model reply. Its strongest reusable ideas are explicit execution identity, durable outcome uncertainty, exact-history retrieval evidence, and bounded context assembled from scoped inputs. **Its architecture is not a drop-in backend for Vonvon.** Rakazo owns the model/tool loop through Pi and coordinates work through Postgres/Graphile; Vonvon delegates that loop and native history to subscription-backed Codex/Claude sessions. Importing Rakazo's runtime would change product authentication, isolation, permission and recovery contracts rather than simply improve them. Rakazo does support OAuth-related model configuration; the mismatch is ownership of runtime/native sessions, not a claim that Pi is API-key-only.

Vonvon already has important analogous protections: backend-neutral run events; synchronous ask ownership release; uncertain-steer non-retry; native-session writer ownership; and explicit restart-drop notification. The next step should strengthen those seams with small invariants/tests, not create a second executor beside the native one.

## Components and actual end-to-end flow

### Rakazo

1. **Intake and ownership.** API `sendThreadMessage` accepts text/artifacts/mentions/quote/clientNonce, checks a replay before writing, and commits the message plus associated run/steering/event inside a retrying transaction. Existing conversational runs receive durable steering rows; some background triggers instead leave input pending for a subsequent run. Waiting input can be answered rather than blindly starting another turn. After commit, realtime failure is logged and jobs are enqueued; persistence is authoritative, notifications are wakeups. See [thread-target.ts:612–648,700–805,1016–1037][r-intake]. Nonce replay is an explicit request identity, not a hash of natural-language text.
2. **Worker dispatch.** Worker wiring constructs PostgreSQL events, Graphile job publisher/host, sandbox, memory and Pi runtime; `AGENT_RUNTIME=scripted` is a separate test/development path. Background job `run.continue` dispatches into the executor. This is not an in-browser agent or a CLI-only wrapper. [worker/index.ts:69–114][r-worker], [background-job-handlers.ts:45–65][r-jobs].
3. **Run admission.** `continueRun` reads the run, rejects terminal work, conditionally claims queued/waiting or expired leased/running state with a new fence and five-minute lease, and conditionally advances to running. A separate computer execution lease mediates shared/dedicated computer ownership. Heartbeats renew both leases and abort on lost ownership. Immediately before opening a model stream, it rechecks status/owner/fence. [executor.ts:3432–3559,6891–6911][r-executor]. These are SQL distributed-worker ownership guarantees; a timestamp alone is not the mechanism.
4. **Context and capabilities.** Executor selects current bot/configuration, history and summary, scoped memory, connections and offered tools; it constructs the request to `runtime.run`. Pi creates an Agent with the resolved model, instructions, tool host and history. Its per-model-call context policy handles retrieval projections/tool-output limits; screenshot/page-state pruning is an additional transform. Optional authenticated Pi JSONL recording is diagnostic and best-effort, not the primary durable message authority. [executor.ts:3708–3840,6931–7045][r-executor], [pi-runtime.ts:280–330,401–450][r-pi], [runtime-context.ts:63–101,157–168][r-context].
5. **Tool execution and approvals.** Pi tool wrappers call the executor's dispatcher. Executor resolves the concrete route/resource, evaluates approval policy, records/claims an external effect, performs the tool, then stores the result. Persisted approved requests are replayed in order using their exact bound arguments; an unclaimed/uncertain execution is not automatically repeated. Connector read-only hints do not bypass all approval/replay checks. [executor.ts:4390–4467,4525–4566,4850–4893,8786–8941][r-executor], [approval-effect.ts:16–79][r-approval]. This is materially different from Vonvon s32 declining Codex permission requests.
6. **Steering and cancellation.** Pi claims steering at startup and before subsequent model turns, using already-seen IDs; steering is not necessarily immediate preemption of an ongoing tool. Stop flips all active thread runs to cancelled and persists terminal events in the same transaction, capturing teardown coordinates before releasing computer state. Worker event consumption rechecks status/lease at approximately one-second intervals **when events arrive**; heartbeat is a separate slower liveness backstop. The stop endpoint also performs scoped sandbox cleanup. [pi-runtime.ts:275,430–456][r-pi], [thread-target.ts:1090–1234][r-stop], [executor.ts:3539–3559,7120–7148][r-executor]. Do not interpret a database cancelled row as proof the remote side effect never happened.
7. **Stream teardown.** Pi returns a custom async iterator whose `return()` aborts synchronously before awaiting the underlying generator, so a pending `next()` can wake. Executor's `withRuntimeCleanup` similarly aborts tool work before closing an interrupted iterator. These solve different levels of the same pending-read ordering hazard. [pi-runtime.ts:187–224][r-pi], [runtime-stream.ts:3–27][r-stream].
8. **Final response and replay.** Pi distinguishes tool-turn narration from a final answer and may request continuation after a tool result; it can fail a tool-bearing turn without a final response rather than report generic success. Executor assembles final blocks and calls `finalizeRun`; the DB transaction conditionally transitions the owned running attempt, writes final product state and may create a continuation. Thread events have monotonically allocated sequence numbers; reconnect reads `seq > cursor`. Realtime delivery is advisory, with durable catch-up. [pi-runtime.ts:512–523,586–645][r-pi], [executor.ts:7550–7583][r-executor], [db/events.ts:1220–1280,1506–1580][r-events]. Finalization atomicity is within its database, not exactly-once external-service behavior.
9. **Restart recovery.** Reconciler finds queued and expired leased/running records, enqueues continuation and separately repairs other unfinished work/delivery. Effects record intended/executing/completed state; unknown earlier outcomes require verification instead of a blind action repeat. [job-reconciler.ts:123–137,185–205,332–355][r-reconcile], [executor.ts:8786–8941][r-executor]. Reclaiming a model run is not identical to replaying every tool safely.

### Vonvon's actual boundary

`handle-message.ts` reserves an active session, prepares Feishu context, chooses steering versus queued input, resolves/resumes a native `AgentThread`, calls `runStreamed` or native `runGoal`, consumes neutral events, and updates Feishu cards/session metadata. `ActiveState.queue` is an in-process collection, not Rakazo's durable steering table. Session metadata persists native backend/session identity and seen/compaction marks; native history remains in the backend. Restart-drop records support notifying users about lost work instead of pretending all queued actions can resume exactly once. [handle-message.ts:583–630,2036–2080,5548,6352][v-handle], [session-store.ts:11–65,113–163][v-session], [restart-dropped.ts:74–121][v-dropped].

The `AgentThread` API exposes streamed runs, native goals, steer(expectedTurnId), abort, compact, native-history checks and close; `AgentRun` exposes events, turn identity and raw last activity. It deliberately does **not** own the native tool loop. `AskCoordinator` settles/releases its local continuation before presentation/network effects, preventing a failed card update from keeping the provider waiting. [agent/types.ts:246–319][v-types], [ask-coordinator.ts:156–175][v-ask].

A steer timeout is explicitly uncertain delivery. Vonvon marks the input seen before dispatch and only requeues when it can establish an explicit unsent/stale-target refusal. That is already the same essential uncertainty discipline as Rakazo's effects ledger, at the boundary Vonvon can actually control. [steer-delivery.ts:5–31][v-steer], [handle-message.ts:2046–2078][v-handle]. Do not regress it by applying a generic retry decorator.

## Context, memory, agents and isolation

**History strategy.** Rakazo defaults to retrieval but retains a fallback when exact-history tools are unavailable. It offers navigation snapshots, distinguishes exact read/search outputs from ordinary shorten-able tool output, and scopes cache observations by user/space/bot/thread/provider/credential hash. Local compaction only replaces old history when following sequence numbers are contiguous; recalled/compacted material is labelled untrusted history. [runtime-context.ts:23–28,63–120,157–168][r-context], [history-compaction.ts:22–125][r-compact], [adapter-kit/types.ts:444][r-types]. Vonvon currently bounds Feishu opening/backfill/quote context and persists seen marks, while compaction is native. s48 proposes same-bot/same-group/permission-limited access to other native conversations. Copying Rakazo's history authority would duplicate native sessions. [context-weave.ts:10–79][v-weave], [types.ts:273–310][v-types], [v1-plan.md:879][v-plan].

**Important qualification limit.** Upstream `docs/agent-verification.md:262–276,338–351` reports historical candidate successes followed by a later53/54 qualification, explicitly leaves a live gate failed, and states the failed outgoing payload was not captured. These are upstream historical reports for their identified revisions—not our test result, not proof pinned HEAD fails, and not validated cost/savings figures. Their useful lesson is the separation of deterministic actual-wire checks from paid end-to-end quality qualification. [verification doc][r-verification]. No reported monetary totals are adopted here.

**Memory/profile.** `MarkdownMemoryStore` is DB-backed despite its portable-Markdown name: document replacement and revision append occur in a serializable transaction, optionally checking expected revision, retaining source run/thread provenance. Memory context combines bot/user scope, orders recency/revision, and caps32KiB. [memory/index.ts:16–44,72–118][r-memory], [memory-context.ts:3–63][r-memory-context]. Vonvon s38–40 are still planned, with stronger product-specific group separation and agent-written local-file capture/merge/undo semantics. SQL expectedRevision does not solve concurrent native agents directly editing a shared file. Adopt provenance/budget ideas, not that storage API as the full solution. [v1-plan.md:840–843,1022–1024][v-plan]; current concrete owners are `config/store.ts` and `project/registry.ts`, not an implemented memory ledger.

**Subagents versus lasting bots.** Pi helpers have maximum parallelism4 and depth1, no further delegation tools, separate namespace and empty initial history for child context. Parent abort propagates to nested agents. Lasting `spawn_bot` is a different product operation: a regular bot with its own chat/computer/memory. Peer `message_bot` selects targets within user+space, excludes self, limits hop chains and uses a delivery key. [pi-runtime.ts:101,242–268,453–456,1336–1434][r-pi], [executor.ts:6429–6452,6597–6620,8273–8276][r-executor], [bot-messages.ts:65–138][r-peers]. Vonvon's native child events/stop UI belong to M6 s34/s35; automatic lasting peer creation is a separate product-scope proposal, not an implementation shortcut for those slices. [types.ts:174–224][v-types], [v1-plan.md:800–801][v-plan].

**Permission and computer boundaries.** Rakazo executor owns explicit approval/replay and multiple computer providers. Its desktop provider's file operations include containment machinery, but command execution ultimately uses host `spawn` with cwd/environment and `shell:false`; that is not by itself OS read/write/network confinement. Docker/computer isolation is a different deployment boundary. Never import the desktop adapter as proof of Vonvon's permission tiers. [desktop-sandbox.ts:67–85,705–723][r-desktop], [executor.ts:4525–4566][r-executor]. Vonvon explicitly fails closed before starting Codex qa/write on platforms lacking required read confinement, and uses native permission configuration on macOS; s31/s39 have real symlink/hardlink/config-protection acceptance cases. [codex backend.ts:39–76][v-codex], [v1-plan.md:799,842][v-plan]. Its native connector exposure is an explicit product decision; Rakazo's tool filtering cannot be assumed to control tools hidden inside native Codex/Claude.

## Patterns not to copy

- **The giant executor.** `executor.ts` combines policy, shell lifecycle parsing, approvals, tools, memory, media, peer bots and completion across roughly9k lines. Do not recreate that monolith inside Vonvon's already-large handle-message. Put each new invariant at its actual owner: backend adapter, ask coordinator, context reader or storage writer.
- **Database fences as filesystem locks.** SQL leaseFence guards SQL transitions. They do not stop a stale OS process writing files or undo an external action. Vonvon kernel mutex/strict child ownership and cooperative path admission remain necessary.
- **Approval semantics as permission equivalence.** Rakazo's “approve then replay exact tool” is not Vonvon's “deny out-of-tier native access” and could broaden access contrary to product decisions.
- **Retrieval savings as established performance.** Neither historical cost figures nor cache predictions establish current quality or savings; default strategies and model wiring can change the outcome.
- **Persistent peer bots as native subagents.** Different lifecycle, credentials, storage and user-visible scope. Keep this v1-after unless product explicitly accepts it.
- **Remote computer/cloud dependency by default.** Postgres/Graphile, Pi-owned model credentials (including OAuth-capable configurations), Docker/cloud computers and hosted semantic-memory providers are deployment commitments, not free utility libraries.

## Boundaries, evidence limits and open questions

The source boundary is API durable transaction → job delivery → conditional execution lease → Pi model/tool runtime → effect ledger → final DB transaction → cursor-based UI catch-up. Computer operations and external services remain outside the DB atomic boundary. Pi JSONL diagnostics are optional and cannot substitute for outgoing-wire evidence. Vonvon's boundary is Feishu/session intake → native provider run → local coordination/card state, with native session persistence rather than a product-owned model transcript.

Not fully audited: every connector route, sandbox provider, Postgres isolation/index definition, all reconcile categories, provider fallback/caching implementation and token-accounting accuracy. No security certification or exactly-once guarantee is inferred. Root subsequently reports8 safe direct-Node source probes passed, including canonical argument order, occurrence distinction and invalid-JSON rejection; I did not execute or inspect those probes here. This is narrow helper evidence, not Pi/service/UI qualification. The wider no-provider checks above remain proposals; existing upstream test files are source intent only. No conclusion depends on reading credentials, private conversation logs or upstream service data.

核实记录（2026-10-17）：独立 gpt-6-astra 抽查了条件认领、fence/租约、取消与 iterator 清理、效果身份、数据库记忆实现及 desktop spawn 边界；报告区分静默流与事件到达时的检查，也保留外部效果结果未知的限制。历史 53/54 为上游旧提交记录，并非本轮复现。八项独立 helper 探针通过不代表数据库、模型或 UI 已验收。
