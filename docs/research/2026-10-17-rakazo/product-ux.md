# Rakazo product/chat UX explorer — 2026-10-17

## Scope and conclusion

Source-only investigation, not a live product evaluation. Rakazo is pinned to `e55263f5fdfee9b2c48680a78e4487d37b4c04a8`; Vonvon to `bbb329b9a9eef0dd809ee9468e0b6d1b9bf4a769`. No dependencies, applications, tests, providers or external integrations were run. Repository screenshots are illustrative assets, not proof of current rendered behavior. “Implemented” below means an actual source path exists, not that it passed a live acceptance test.

Rakazo's strongest applicable lesson is **a durable teammate whose changes and work products remain inspectable in the conversation**. It makes setup choices, instruction edits, memory documents, delegation and recurring work into persistent objects rather than promises in assistant prose. Vonvon already chose much of that direction in M7–M9, but has not delivered those milestones. The immediate opportunity is to make their acceptance criteria precise, not add a second web-chat application or replace Feishu session boundaries.

“Grok-like” is a product resemblance, not a verified comparison with Grok's implementation. Rakazo's [README lines 10–22](https://github.com/elie222/rakazo/blob/e55263f5fdfee9b2c48680a78e4487d37b4c04a8/README.md#L10-L22) explicitly markets persistent teammates and chat-based setup as a Grok Bot alternative. Actual code supports chat choices, self-instruction changes, memory, bot-to-bot delivery and routines. That substantiates the resemblance. It does not establish feature parity, usability superiority, reliability or security relative to Grok.

## Components and actual flows

### 1. Setup and configuration become conversation objects

A fresh bot chat initially stays empty. `startOnboarding` does not emit a greeting despite an older module description suggesting one. `promptFocus` later posts a deterministic choice asking what the bot should focus on; its transaction locks the thread, refuses to duplicate an existing choice and skips users who already sent a message. The client schedules the first bot immediately and later bots after ten seconds, with cancellation checks. This is real non-model onboarding logic, not merely a system prompt. Sources: [onboarding.ts 99–161](https://github.com/elie222/rakazo/blob/e55263f5fdfee9b2c48680a78e4487d37b4c04a8/apps/api/src/onboarding.ts#L99-L161), [focus-prompt.ts 1–27](https://github.com/elie222/rakazo/blob/e55263f5fdfee9b2c48680a78e4487d37b4c04a8/apps/web/src/lib/focus-prompt.ts#L1-L27).

The important design is “offer a concrete first action, then get out of the way when the person starts.” Do not copy the day/inbox/research options without checking Vonvon capabilities. Vonvon's actual onboarding is infrastructure readiness: `packages/ui/src/setup/SetupChecklist.tsx:39–92` reads live status and routes registration, setup, login and service actions. That remains necessary for local providers and Feishu. A chat greeting cannot replace those checks.

Rakazo's self-instruction update is a real mutation: after approval and effect checks, it locks the thread/run, verifies the active run, writes against the previous instructions, handles conflicts, and persists an answered card containing before/after, reason and an undo version. Source: [executor.ts 6361–6412](https://github.com/elie222/rakazo/blob/e55263f5fdfee9b2c48680a78e4487d37b4c04a8/packages/adapters/src/executor.ts#L6361-L6412). The tool contract requests approval: [builtin-tools.ts 1038 onward](https://github.com/elie222/rakazo/blob/e55263f5fdfee9b2c48680a78e4487d37b4c04a8/packages/adapters/src/builtin-tools.ts#L1038).

Vonvon's finalized contract differs deliberately: settings are changed in owner/admin DM, daemon validates session and triggering actor, changes produce a receipt with undo, and group chat cannot mutate settings (`docs/product.md:429–450`). No universal settings approval should be imported. Existing UI settings operations already return applied/refused states (`packages/ui/src/management/ConversationPanel.tsx:68–89`), and the legacy DM handler has revision-conflict handling (`packages/daemon/src/bot/handle-message.ts:5006`). The new natural-language DM settings route is still planned in s46/s47/s49/s54–56, not delivered by those old controls.

### 2. Persona persists beyond conversation; memory is inspectable

The `remember` execution writes durable memory with source run and thread IDs. Shared memory mutation uses an expected revision and returns a committed revision or conflict. This is more credible than replying “I'll remember” without storage evidence. Source: [executor.ts 5513–5552](https://github.com/elie222/rakazo/blob/e55263f5fdfee9b2c48680a78e4487d37b4c04a8/packages/adapters/src/executor.ts#L5513-L5552).

Memory context loads bot and user documents, sorts them, marks them as possibly outdated background data rather than instructions, and caps injected bytes with UTF-8-safe truncation. Source: [memory-context.ts 1–77](https://github.com/elie222/rakazo/blob/e55263f5fdfee9b2c48680a78e4487d37b4c04a8/packages/adapters/src/memory-context.ts#L1-L77). The web Knowledge section lists documents and revisions, opens editable text, saves via RPC, and exports a freshly reloaded Markdown snapshot: [KnowledgeSection.tsx 98–205](https://github.com/elie222/rakazo/blob/e55263f5fdfee9b2c48680a78e4487d37b4c04a8/apps/web/src/pages/KnowledgeSection.tsx#L98-L205). Readability and correction matter more here than having a vector database.

Clearing a Rakazo thread deliberately leaves durable memory; summary purge is best-effort, so the source does not justify an absolute “all historical recall erased” claim. Source: [router.ts 2227–2272](https://github.com/elie222/rakazo/blob/e55263f5fdfee9b2c48680a78e4487d37b4c04a8/apps/api/src/router.ts#L2227-L2272).

Vonvon plans a finer privacy topology: public, per-group and per-person DM memory; next-turn changes; native memory disabled; scoped file writes, concurrent merges and undo (`docs/product.md:334–427`; `docs/v1-plan.md:840–845`, s37–42). Importing Rakazo's bot-plus-user shared-memory selection into a Feishu group would lose required isolation. M7's merged defaults/directory/ownership foundations do not mean personality or memory now works. In particular, s38/s40/s41/s42 remain unchecked.

### 3. Peer delegation is distinct from ephemeral subagents

`message_bot` resolves the target inside the same space/user, rejects self-send and archived/nonexistent recipients, requires a target thread, applies a hop budget, deduplicates by delivery key, and constructs a visible sent-message block. It locks affected threads in sorted order before committing delivery. Source: [bot-messages.ts 65–175](https://github.com/elie222/rakazo/blob/e55263f5fdfee9b2c48680a78e4487d37b4c04a8/packages/adapters/src/bot-messages.ts#L65-L175). This is an actual asynchronous handoff, not just a model writing another bot's name.

Room handoff is a separate path: active run and group membership are checked; replay is tied to the originating run; handing back immediately to the sender is guarded. Source: [group-handoff.ts 20–110](https://github.com/elie222/rakazo/blob/e55263f5fdfee9b2c48680a78e4487d37b4c04a8/packages/adapters/src/group-handoff.ts#L20-L110). Group contexts remove private `message_bot` and expose room handoff, preserving visible collaboration: [schedule-tools.ts 18–33](https://github.com/elie222/rakazo/blob/e55263f5fdfee9b2c48680a78e4487d37b4c04a8/packages/adapters/src/schedule-tools.ts#L18-L33).

Tool contracts explicitly distinguish ephemeral `run_subagent` from persistent `spawn_bot`; their descriptions are not proof that every execution backend implements those capabilities equivalently. Source: [builtin-tools.ts 1012–1153](https://github.com/elie222/rakazo/blob/e55263f5fdfee9b2c48680a78e4487d37b4c04a8/packages/adapters/src/builtin-tools.ts#L1012-L1153). This report does not infer a complete subagent runtime from descriptions alone.

Vonvon needs the same conceptual distinction but different mechanics: s27 is Feishu bot mentions, final answers only, capped at three rounds without human input (`docs/v1-plan.md:724`); s34/s35 are provider subagent events, recent steps and individual stop (`:800–801`). These are pending. Creating Rakazo teammates programmatically cannot be equated with creating Feishu application identities: Vonvon forbids chat creation of new bots and changing other bots (`docs/product.md:439–441`), and Feishu name/avatar remain platform-owned (`:54–57`).

### 4. Tasks, routines and proactive behavior have explicit ownership

A routine stores bot, owner and originating thread, validates one-shot versus recurring timing, queues its next execution, and rolls back or deactivates if scheduling fails. Notification failure after durable scheduling is not reported as creation failure. Its return contains the authoritative routine ID and next execution time. Source: [schedule-tools.ts 60 onward, 202–275](https://github.com/elie222/rakazo/blob/e55263f5fdfee9b2c48680a78e4487d37b4c04a8/packages/adapters/src/schedule-tools.ts#L202-L275).

When due, execution claims the still-eligible routine transactionally, creates a task and run with the same thread, and pins the selected model. Retry checks paused/archived state, later runs and target thread membership before making a retry task. Sources: [executor.ts 3150–3210](https://github.com/elie222/rakazo/blob/e55263f5fdfee9b2c48680a78e4487d37b4c04a8/packages/adapters/src/executor.ts#L3150-L3210), [3315–3395](https://github.com/elie222/rakazo/blob/e55263f5fdfee9b2c48680a78e4487d37b4c04a8/packages/adapters/src/executor.ts#L3315-L3395). These are genuine durable scheduled-work structures. They do not by themselves prove every job is delivered on time or a general task-board UX is complete.

Proactive group participation is separately conservative: the team-chat judge limits context, treats messages as untrusted, has no tools, defaults invalid/no-model outcomes to silence and uses a timeout. Source: [team-chat-judge.ts 25–190](https://github.com/elie222/rakazo/blob/e55263f5fdfee9b2c48680a78e4487d37b4c04a8/apps/api/src/team-chat-judge.ts#L25-L190). Vonvon already has a delivered judgment foundation, but actual smart inbound activation remains s25, cross-bot coordination s26 and peer mentions s27 (`docs/v1-plan.md:719–724`). Do not call those user-visible features delivered.

Timed tasks are explicitly excluded from Vonvon v1 (`docs/product.md:672`, owner decision `:754`). Current autonomous goals and completion reminders already appear in the actual management UI (`packages/ui/src/management/ConversationPanel.tsx:103–106`); neither is a scheduler. Routines belong to v1-after unless owner changes scope.

### 5. Progress is quiet; results are durable and named

The web tool disclosure shows six recent live steps, an omitted count, counts/duration, and terminal folding. Tool-only narration uses a muted line instead of a full assistant bubble. Filtering helpers omit tool activity when disabled while retaining meaningful message blocks. Sources: [ToolActivityDisclosure.tsx 1–135](https://github.com/elie222/rakazo/blob/e55263f5fdfee9b2c48680a78e4487d37b4c04a8/apps/web/src/components/ToolActivityDisclosure.tsx#L1-L135), [tool-activity-view.ts 1–67](https://github.com/elie222/rakazo/blob/e55263f5fdfee9b2c48680a78e4487d37b4c04a8/apps/web/src/lib/tool-activity-view.ts#L1-L67).

Vonvon already separates process into collapsible panels and preserves ordered text/tool blocks: `packages/daemon/src/card/process-panel.ts:3–26`, `run-process.ts:25–99`. Its card budget path currently retains the earliest fitting units and reports omitted later items (`run-process.ts:39–46`), unlike Rakazo's recent live window. That is a specific improvement candidate, not evidence that Vonvon lacks progressive disclosure. s35 already specifies the latest five steps per subagent, so use that approved number instead of importing six globally.

`attach_file` reads actual bytes from the bot workspace, checks size and MIME, writes through artifact storage, publishes the resulting block, and only then returns an artifact ID. Source: [executor.ts 5252–5295](https://github.com/elie222/rakazo/blob/e55263f5fdfee9b2c48680a78e4487d37b4c04a8/packages/adapters/src/executor.ts#L5252-L5295). Its contract describes name-based versions; the gallery component shows name, description, version count, author bot and age: [builtin-tools.ts 310–321](https://github.com/elie222/rakazo/blob/e55263f5fdfee9b2c48680a78e4487d37b4c04a8/packages/adapters/src/builtin-tools.ts#L310-L321), [Artifacts.tsx 640–687](https://github.com/elie222/rakazo/blob/e55263f5fdfee9b2c48680a78e4487d37b4c04a8/apps/web/src/pages/Artifacts.tsx#L640-L687). These support an authored-result concept; attachment success alone does not prove an HTML page renders correctly or the result is factually correct.

Vonvon already detects local output references and renders inline delivery controls, including tables; tokens avoid exposing paths in callback data (`packages/daemon/src/card/file-refs.ts:15–69`, `inline-files.ts:5–15,26–99`). Adopt clear title/summary and verified-delivery receipts where those fit existing output. A searchable versioned artifact gallery is a separate v1-after product addition, not a missing s40 memory feature.

HTML reuse has a concrete boundary: Rakazo's CSP helper blocks network and is explicitly only a second layer; iframe sandboxing without same-origin or isolated native WebView remains necessary. Source: [artifact-sandbox.ts 1–24](https://github.com/elie222/rakazo/blob/e55263f5fdfee9b2c48680a78e4487d37b4c04a8/packages/core/src/artifact-sandbox.ts#L1-L24). Do not paste its HTML wrapper into unrestricted Electron content and call that safe preview support.

### 6. Interrupt, steer and retry honor uncertain acceptance

Sending coordinates uploads, target bot/group, references and a client nonce; stopping calls the server and clears local state only after the stop is accepted. Sources: [Shell.tsx 2150–2295](https://github.com/elie222/rakazo/blob/e55263f5fdfee9b2c48680a78e4487d37b4c04a8/apps/web/src/pages/Shell.tsx#L2150-L2295), [2308–2338](https://github.com/elie222/rakazo/blob/e55263f5fdfee9b2c48680a78e4487d37b4c04a8/apps/web/src/pages/Shell.tsx#L2308-L2338). Composer submission preserves a nonce for a known-failed unchanged draft, does not overwrite a newly edited draft, and avoids restoring a possibly accepted send after an unknown exception: [5822–5850](https://github.com/elie222/rakazo/blob/e55263f5fdfee9b2c48680a78e4487d37b4c04a8/apps/web/src/pages/Shell.tsx#L5822-L5850). This avoids duplicates but can leave the user uncertain; a visible “delivery uncertain; check conversation” status would be a proposal, not a feature established by this excerpt.

Vonvon already implements the corresponding harder native-provider case. It rechecks ownership after image/context preparation; rejects input during autonomous goals with an explicit reply; rejects stale retries; and, when steer ACK is uncertain, informs the user and does not automatically replay. Only an explicit rejected steer can be queued again (`packages/daemon/src/bot/handle-message.ts:1979–2082`). Its management UI binds stop to run ID and exposes applied/refused/error notices (`packages/ui/src/management/ConversationPanel.tsx:98–118`). Do not regress this into “retry every network error.” Rakazo's web composer is not a drop-in Feishu message input.

## Boundaries, non-obvious facts, and remaining questions

- **Chat-first does not mean chat-only.** Rakazo has editable Knowledge and artifact screens; Vonvon's local settings UI and CLI remain valuable recovery surfaces when providers/Feishu fail.
- **One persistent teammate is not one universal session.** Keep Vonvon bot × group × topic/DM boundaries (`docs/product.md:186–333`), including memory scope. Clear conversation and erase durable memory must remain different actions.
- **Approval is not universal product quality.** Rakazo's instruction proposal fits its product; Vonvon explicitly rejected permission escalation cards (`docs/product.md:452–463`). Receipts and undo are the transferable parts.
- **Marketing, prompts and effects have different evidence strength.** README supports positioning; tool descriptions support intended affordances; handlers support persistence paths. None establishes production success rates. Screenshots and unexecuted tests are not live UX evidence.
- **Durable artifacts are not automatically verified artifacts.** The traced attach path verifies readability/storage publication, not rendering or content accuracy. Any stronger “inspects its own output before claiming completion” claim needs the exact prompt/tool/runtime path and an executed proof.
- **Shared memory requires a threat-model translation.** Rakazo user/space ownership is not equivalent to several humans in one Feishu group. Never reuse its selection query as Vonvon's privacy policy.
- **Native provider mismatches remain.** Claude steering differs from Codex; parent/child event delivery and completion need native acceptance, not a Rakazo-shaped UI mock. M5/M6/M7 status must retain pending acceptance gates.
- **Useful later checks, not performed here:** isolated pure tests for duration filtering, bounded UTF-8 memory rendering, unchanged-draft nonce reuse and idempotent prompt scheduling; a sandboxed artifact preview smoke check only if that feature is approved; native/Feishu acceptance for actual receipts and subagent stop. No need to boot Rakazo's cloud stack just to compare these functions.

## Product reconsideration: sequencing the teammate experience

The current M ordering is technically defensible but **delays the experience that makes Rakazo attractive**: users first meet a configurable Feishu execution bridge, while conversational DM work, a stable persona and self-service configuration arrive only after substantial infrastructure. If the owner's intended product is now closer to a Grok-style personal teammate, that is a reason to reconsider sequencing explicitly. The finalized scope constrains implementation today; it does not make the product order optimal by definition.

The source contrast is concrete. Rakazo combines the focus choice, persistent bot thread, instruction mutations, inspectable memory and ordinary sending in one surface (sources above). Vonvon currently shows readiness checks and a conversation-management panel whose main actions are context/clear/goal/stop/history, while actual interaction opens Feishu (`SetupChecklist.tsx:39–92`; `ConversationPanel.tsx:98–114`). The spec promises natural DM work in s49 only after s37/s36/s38/s40, and chat settings in s54 after s47/s49/s43/s44 (`docs/v1-plan.md:897–905`). A new user can therefore complete considerable setup before experiencing “this is my teammate.” This is a sequencing diagnosis, not an assertion that those dependencies can be deleted.

### Strategic recommendation A: prioritize one vertical “meet your bot” experience

Highest product leverage: after the necessary M7 directory/profile foundations, consider a deliberately split **basic admin DM + persona + first useful result** slice earlier than the full M9 bundle. Example target: an already-authorized owner opens bot DM, asks for a small real task, sees one concise result with a usable file if relevant, stops or steers it, and returns later to the same persona. Preserve ordinary Feishu groups and location-specific sessions. No new hosted service is needed.

This should not be labeled “move all of s49 earlier” without design. The existing s49 couples DM execution with per-person memory writable under every permission tier and depends on s40. Options worth comparing are: (1) deliver the relevant s37/s38/s40 foundations first and then extract s49 ahead of unrelated M8 UI; or (2) explicitly amend scope for basic DM execution without durable personal memory initially, clearly showing that limitation, then add memory. The second is faster to demonstrate but creates a temporary behavior and migration obligation; if continuity is the point, the first may be the better product. Persona without memory must never imply factual recall.

Required dependencies stay real: authenticated owner/admin boundary, correct bot defaults, independent DM session identity, provider permissions, stop/queue behavior, and no reuse of another person's or group's context. Proof should be a first-run narrative with both native backends and actual Feishu: setup → first DM task → interrupted task → return visit → edit persona → next-turn behavior. Completion should be measured by task success and comprehensibility, not merely a green checklist. Cost is medium-to-high planning/integration, but mostly reorders existing commitments rather than adding a new product. Scope and slice dependencies need owner acceptance before implementation.

### Strategic recommendation B: narrow conversational self-configuration before the whole settings catalog

Rakazo's instruction receipt suggests a smaller satisfying interaction than “complete all setting types, then expose chat.” After the authorization/token path exists, consider persona/rules plus receipt/undo as the first DM settings capability, before skills/MCP installation and group creation. The present s54 bundles persona, memories, skills and MCP and inherits all library dependencies. Splitting it could show the core teammate benefit sooner without pretending that every capability is ready.

Counterargument: a piecemeal settings skill can produce confusing “I can change X but not Y yet” conversations, and rewriting it twice adds work. Make the available operations authoritative, expose only working commands, and keep the desktop editor as recovery. Never shortcut daemon actor/session checks to accelerate the demo. This is a potential reorder/split of M8 s46/s47 and M9 s54/s56, not approval to bypass M7 protections or introduce universal confirmation cards.

### Strategic recommendation C: evaluate a small optional local chat surface, not a replacement for Feishu

A local web/desktop chat could reduce time to first value when Feishu registration is the onboarding bottleneck, offer a private test conversation before group installation, and put result previews beside the conversation. Rakazo's web shell makes this benefit tangible. This is the strongest reason to revisit Vonvon's console-only desktop posture. It does not require hosted inference, abandoning subscription providers, or stopping Feishu work.

However, this is a genuine product expansion: one must define local identity/authorization, memory scope, history placement, attachments, reconnect/replay and how a local conversation relates to a Feishu DM. Reusing a Feishu user's private memory merely because the same person owns the machine would require an explicit identity policy. A second input surface also doubles important interaction acceptance (stop/steer/asks/files). Rakazo's Shell is not a shortcut through those decisions.

Recommendation: first validate whether the frustration is “I cannot experience the bot until Feishu is configured” or “I need a second daily chat client.” The former can justify a bounded local first-task sandbox; the latter needs a full product decision. Compare a simple local-chat prototype with an improved Feishu-first onboarding narrative before committing. No prototype is requested or built in this research. Rank this below the earlier DM/persona vertical slice because Vonvon's distinguishing collaboration surface is already Feishu.

### Strategic recommendation D: routines are a meaningful future choice, not a trivial checkbox

If proactive teammate behavior is central to the revised vision, re-open the excluded-routines decision explicitly rather than saying the old scope settles the question forever. Rakazo demonstrates why “report to me every morning in this same place” is compelling. For Vonvon, begin with one recurring informational task, clear ownership, next-run receipt and pause/cancel, not an autonomous task board. The hard difference is local availability: the Mac may sleep, Linux may be persistent, and native provider sessions have budgets and failures. Decide missed-run behavior and execution machine before any scheduling UI. This remains lower priority than making ordinary DM work and memory trustworthy; it is a significant new scope choice.

Recommended product order to debate: **retain required foundations → earlier complete persona/basic-DM vertical slice → narrow authorized settings with receipts → broader libraries/settings → optional local chat or routines only after a concrete need is demonstrated**. This is an evidence-backed alternative to the current milestone order, not a claim that research has changed the approved plan. The highest-value borrowing from Rakazo is the short route from “new bot” to “recognizable teammate who did something useful,” not the number of tools in its catalog.

Dependency precision for any sequencing proposal: existing s49 requires **s37, s36, s38, s40 and e10**; existing s54 requires **s47, s49, s43 and s44**; existing s56 requires **s54 and s55** (`docs/v1-plan.md:897,903,905`). None can simply become the next implementation task. An earlier experience requires prioritizing its complete prerequisite chain or approving a newly defined thinner preview with explicit omissions, contracts and acceptance. Splitting receipts earlier also requires separating their operation set from s55, not silently declaring s56 dependency-free.
