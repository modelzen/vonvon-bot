## 1. 一句话

Vonvon Bot 是一个 macOS 桌面应用；Linux 上可以只装后台服务，用命令行和网页管理（3.10）。主人在自己的 Mac 上养几个飞书机器人，每个 bot 有自己的个性、记忆、工作区、代码仓库、skill 和 MCP，能进不同的群，在每个群里表现不同。干活用主人本机已经登录的 Codex 或 Claude。

和 feishu-codex-bridge 最大的区别：bridge 的行为大多靠规则设定，Vonvon Bot 主推**智能模式**。bot 自己判断要不要接话、要不要开新话题、要不要和别的 bot 搭话。主人可以直接跟 bot 聊天来改它的设置、让它建群（在私聊里，3.7）。bridge 原来的规则保留为**规则模式**。

给谁用：
1. 正在用 feishu-codex-bridge 的 Mac 用户。迁过来后，群、话题、卡片、命令和旧会话都保留。
2. 有 Codex 或 Claude 订阅、想在飞书群里有一个"像同事"的 bot 的个人和小团队。他们不一定用 GitHub，也不一定会装 Node。

不给谁用：Windows 用户；想在 Linux 上用桌面应用的人，Linux 只有命令行版；没有 Codex 或 Claude 订阅的人；想要云端托管、不开电脑也能用的人。

## 2. 叫法

| 叫法 | 意思 |
|---|---|
| bot | 一个飞书机器人（一个飞书应用）。名字、头像、简介以飞书为准 |
| 主人、管理员 | 能管这个 bot 的人，见第 6 节。两者能做的事一样 |
| 群主区 | 群里不在任何话题里的地方 |
| 话题 | 飞书话题，包括话题群里的帖子 |
| 会话 | 后台的一条 Codex 线程或 Claude 会话。bot 记得的对话内容都在这里 |
| 子 agent | 一个会话临时分出去、并行干活的帮手，干完就结束 |
| 智能模式 | 群设置。bot 自己判断接不接话、开不开话题、和不和别的 bot 搭话 |
| 规则模式 | 群设置。bridge 原来的规则：仅 @ 或全部回复；主区"开话题"或"连续" |
| 会话方式 | 群设置，绑定群时三选一：多会话（@ 我开新会话）、单会话（整群一条会话）、智能。前两种是规则模式，后一种是智能模式，见 3.4 |
| 工作区 | bot 产出文件的目录，可写。主工作区是会话的工作目录 |
| 代码仓库 | 本机的一个 git 目录。和工作区一样传给 agent，区别在界面和指令 |
| skill、MCP | 给 agent 用的技能包和工具服务。本机各有一个库，bot 和群各有名单 |

产品文案里叫"Claude"，不叫"Claude Code"，这是 Anthropic 的品牌规定（code.claude.com/docs/en/agent-sdk/overview）。

## 3. 第一版做什么

### 3.1 桌面端

1. 桌面应用就是控制台，不再引导用户开网页。同一套页面也能用本机浏览器打开，但只在本机：daemon 只监听 `127.0.0.1`（`D/server/http.ts:184`），第一版不开放局域网和远程访问。
2. 签名加公证的 dmg，带更新源。现在更新源是空的（`packages/desktop/src/updates.ts:46`）。出 universal 包，Intel Mac 也能装。
3. 后台服务：bot 跑在后台服务里，登录电脑后自动启动。Mac 设成自动登录时，就等于开机启动。后台服务由 daemon 自己装，不依赖桌面应用，崩溃后自动重启，见 3.10。
4. 首次运行是一张清单，每一步都实时检测：扫码建飞书应用（建好的 bot 默认启用，马上连上飞书）→ 一键开权限 → 检测事件订阅 → 检测应用已发布 → 检测 Codex 或 Claude 已安装、已登录、版本够用 → 登录电脑时自动运行 bot（推荐，3.10）→ 可选从 bridge 导入。v2 里还没有人从头扫码成功过（`docs/research/2026-10-14-strategy/runnable.md` 第 1 节），这一条第一版必须走通。
5. 建新 bot 只走上面的向导，不在聊天里做。Mac 上在桌面端，Linux 上在网页或终端里（3.10）。
6. Bot 页：个性、规矩、工作区、代码仓库、skill、MCP、记忆、智能提示词、所在的群。
7. 群详情页：这个 bot 在这个群里的会话方式（3.4）和各项覆盖，见 3.2。被拉进来、还没设置好的群也列在这里，能在这里设置。
8. 状态与诊断页：每个 bot 的连接状态，Codex 和 Claude 的版本检查，最近没回的消息和原因（包括智能模式判断"不回"的原因）。用量页显示判断调用的次数。
9. 没有 Windows，也没有 Linux 桌面。Linux 上只装后台服务，见 3.10。

### 3.2 bot 模型

一个 bot 有三层：
1. **飞书身份**：名字、头像、简介，来自飞书应用，vonvon 不改。飞书能不能让同一个机器人在不同的群里显示不同的名字：没查到，所以"千人千面"体现在说话方式、工作区、仓库、skill 和记忆上，外观不变。
2. **bot 默认**：个性、规矩、工作区、仓库、skill、MCP、公共记忆、智能提示词。
3. **群内覆盖**：这个 bot 在某个群里另外的设置，以及这个群自己的记忆。没设的项继承 bot 默认。

| 项 | bot 默认 | 群内 | 规则 |
|---|---|---|---|
| 名字、头像 | 来自飞书 | 不能改 | — |
| 个性 `SOUL.md` | 有 | 可补充 | 群的默认加在 bot 后面，也可以选择整段替换 |
| 规矩 `AGENTS.md` | 有，可选 | 不能改 | 只在 bot 层 |
| 工作区 | n 个，1 个主的 | 可覆盖 | 群没设时，在默认位置给这个群建一个目录，见 3.3 |
| 代码仓库 | 0 到 n 个 | 可覆盖 | 只接本机已有的 git 目录，不接 git 地址 |
| skill | 启用名单 | 可增、可减 | 实际生效 =（bot 启用 ∪ 群增加）− 群移除 |
| MCP | 启用名单 | 可增、可减 | 同 skill |
| 记忆 | 公共记忆，所有群都看 | 本群记忆，只在本群看 | 见 3.6 |
| 智能提示词 | 有，带内置默认值 | 可覆盖 | 只在智能模式下用 |
| 会话方式（智能或规则模式） | 无 | 多会话、单会话或智能 | 只在群层，绑定群时选，见 3.4 |
| 权限档 | 默认值 | 可覆盖 | 见 3.8 |
| 运行中来了消息：插话或排队 | 默认值 | 可覆盖 | 见 3.5。今天只有 bot 级的设置（`D/config/schema.ts:236-238`），要加群内覆盖 |
| 聊天改设置：私聊里装不装 vonvon 设置 skill、能不能用设置命令 | 开，可以关 | 没有这一项：群里不装设置 skill，不能用设置命令 | 只对私聊，见 3.7 |
| 网络、后端、模型 | 默认值 | 可覆盖 | 和今天一样 |

### 3.3 磁盘上的位置

```
~/.vonvon-bot/
  skills/                       本机 skill 库
  mcp/                          本机 MCP 库
  projects/<bot 名>/            bot 主工作区的默认位置
    groups/<群名>/              群没设工作区时的默认目录
  bots/<appId>/
    config.json                 bot 设置，含工作区、仓库
    projects.json               每个群一条，含群的覆盖
    SOUL.md                     bot 个性
    AGENTS.md                   规矩，可选
    SMART.md                    智能提示词，不存在时用内置默认值
    skills.json  mcp.json       启用名单
    memory/shared.md            公共记忆
    memory/dm/<open_id>.md      每个主人或管理员的私聊记忆
    groups/<chatId>/
      SOUL.md                   本群个性补充
      SMART.md                  本群智能提示词覆盖
      skills.json  mcp.json     {"add": [...], "remove": [...]}
      memory/group.md           本群记忆
```

- 工作区默认放在隐藏目录 `~/.vonvon-bot/projects/` 下，和今天一样（`D/config/paths.ts:115`），可以在桌面端改到别处。比今天多一层 `<bot 名>/`：今天所有 bot 共用这个目录，两个 bot 的同名项目会落进同一个目录（推断，`docs/research/2026-10-14-v1-definition/v2-fit.md` 第 8 节第 6 条）。
- 每个群默认有自己的目录。共用一个目录的话，B 群的会话能看到 A 群产生的文件，和"每个群的记忆分开"矛盾。
- 目录名按建立时的名字取，之后不跟着改名，重名时加一个短后缀，"/"等字符替换掉。
- 定义文件都是 markdown 和 json，主人可以直接用编辑器改。它们不进用户的代码仓库。仓库里的 `AGENTS.md`、`CLAUDE.md` 照旧由 agent 自己读。

### 3.4 群：智能模式和规则模式

每个群对每个 bot 有一个开关：智能模式或规则模式。

**智能模式**一起管三件事：
1. 要不要接话。
2. 群主区来了一件新事，要不要开一个新话题来回。
3. 要不要和别的 bot 搭话。

**规则模式**就是 bridge 原来的设置：回复方式选"仅 @"或"全部回复"，群主区选"开话题"或"连续"。规则模式下 bot 之间互相看不到，和今天一样。

**会话方式。** 界面上不分"智能模式""规则模式"和"主区方式"，绑定群时只选一项会话方式。按下表的顺序列，每项一个主标题、一行副标题（owner 2026-10-16）：

| 顺序 | 叫法 | 主标题 | 副标题 | 等于 |
|---|---|---|---|---|
| 1 | 多会话 | @ 我开新会话 | 在主区 @ 我就开一个话题，一个话题一条会话，几件事各聊各的 | 规则模式，主区"开话题" |
| 2 | 单会话 | 整群一条会话 | 主区里跟我说的话都进同一条会话，上下文一直连着 | 规则模式，主区"连续" |
| 3 | 智能 | 智能开话题 | 主区一条会话，不用 @ 我也会看情况接话；聊到新的事，我自己开话题、起新会话 | 智能模式 |

- 选了多会话或单会话，再多一项回复方式。默认沿用 bridge：多会话是"话题里不用 @ 也回"（主区照旧要 @ 才开话题），单会话是"要 @ 才回"（`D/project/registry.ts:83-85`）。
- 话题群和话题形式群没有主区，三种的会话都一样，一个帖子一条会话。卡上不列这三项，只问回不回：智能（看情况接话）、要 @ 才回、帖子里都回。
- 不预选任何一项，也不标"推荐"：产品上主推智能，界面里不替人选。命令行绑定群和建群时必须带会话方式。
- 三种方式下，有人开的话题都另算一条会话（3.5），副标题说的"一条会话"指主区。
- 上面的主标题、副标题，回复方式那一项和话题群的问法，是 Claude 按 owner 的意思定的（`docs/v1-plan.md` 第 5 节）。

**被拉进已有的群时。** owner 2026-10-16 定了绑定时选工作区和会话方式；卡上还有哪几项、发给谁、设置好之前怎么回，是 Claude 定的（`docs/v1-plan.md` 第 5 节）。bot 被拉进来，先不在群里干活，私聊发一张设置卡：拉它进群的人是主人或管理员，就发给这个人；不是，就发给主人，写明谁把它拉进了哪个群。卡上有：
1. 会话方式，按上表；选了前两种时多一项回复方式。
2. 工作区：默认按 3.3 给这个群建目录，也能填本机已有的目录。
3. 后端：默认用 bot 的。
4. 权限档和网络：显示默认的只读、关网（3.8），设置好以后在群详情页或私聊里改。

选好会话方式、点［绑定］才算设置好。设置好之前，有人在这个群里 @ bot，bot 只回一句"主人还没设置好这个群，设置好就能用"，同一个群 10 分钟最多回一次；不 @ 的消息不读。卡不过期，也能在桌面端或网页里设置（今天网页上已有待绑定的提示和绑定对话框）。这张卡是第 4 节拿掉私聊控制台以后，私聊里唯一留下的设置卡。

**默认值：**
- 新进的群没有默认的会话方式：被拉进已有的群时在设置卡上选（见上面），bot 在私聊里建群时，主人没说就先问（3.7）。选了智能，bot 在群里说一句"我会读群消息，合适时接话"。
- 从 bridge 迁来的群用规则模式，沿用各群原来的回复方式和主区方式，不换算：多话题群就是多会话，单会话群就是单会话。bridge 今天的默认是免 @ 开，只有被拉进来的"连续"群默认关（`D/project/registry.ts:83-85`）。
- 设置好以后，会话方式能在群详情页或私聊里改（3.7）。在多会话和单会话之间切换，回复方式不自动变，界面提示一句。

**三条底线**，两种模式共用。先回答"这条消息是对谁说的"，再轮到模式：
1. **点名**：@ 了谁、引用了谁的消息，就只有谁回。@ 了别人、@所有人、引用别人的消息，其他 bot 都不回。@ 两个 bot 就两个都回。例外：规则模式的"仅 @"里，引用我的消息不算点名，和 bridge 一致。话题里飞书只给话题第一条的 id（`root_id`、`parent_id` 都是它），分不出引用的是哪一条，所以话题里的点名只看 @（要实测）。
2. **接着聊**：话题里没点名的消息，归最近在这个话题里说过话的 bot。别的 bot 开的话题，我不插嘴。
3. **bot 消息**：别的 bot 发的消息，只有 @ 我才算。

这三条顺带修掉今天多 bot 群里的三个毛病：开了免 @ 的 bot 会进别的 bot 的话题；主区不带 @ 的 `/help` 每个 bot 都回；连续群里每个免 @ 的 bot 都回每条（推断，`docs/research/2026-10-14-v1-definition/group-response.md` 结论 3）。

**智能模式怎么判断。** 底线定不下来时，调一次判断模型，结果三选一：不回、在主区接着聊、开新话题回。在话题里只判断回不回，不再拆话题。
- 判断用这个 bot 那家订阅里的小模型，比如 Codex 的 GPT-6-Luna（走 Codex 订阅的普通调用，不是 Decisions API），关掉思考，一次不带工具的调用。专门做判断的模型（OpenAI 的 Decisions API、TypeSafe 的 Jev，要主人填 OpenAI、TypeSafe 或 OpenRouter 的 key）第一版不做，见第 10 节。资料见 `docs/research/2026-10-14-decision-models/decision-models.md`。
- 判断出错或超时就不回。被 @ 的消息一定回：在话题里直接回；在主区要调一次判断，只决定回在主区还是开新话题，出错或超时就在主区回（3.5）。
- 只回"回"或"不回"，不做"只回一个表情"。"不回"的原因只记在本机诊断页，不发到群里。
- 判断用的提示词就是智能提示词：内置默认值，主人可以在 bot 层改，群里可以覆盖。
- 控制成本：只对允许使用 bot 的真人消息调；同一台机器上一条消息只调一次，本机几个智能 bot 合成一次"选谁回"；话题里只有一个真人在和我聊时直接回；每个群每小时有上限。延迟和每次占多少额度要在 Mac 上量。

**bot 之间。** 智能模式下，别的 bot @ 我时我能收到（要新开一个可选权限，见 3.11），这样能做"小码写、小审查"。B 看到的 A 的消息只有 A 的最终回答，标成"A（bot）"，截到几百字。没有真人插话时，bot 之间最多来回 3 轮，到了就停下并提示一次；真人说一句就清零。不收别的 bot 的全部消息。

**几个 bot 都会回的时候。** 同一台机器上，daemon 只放行一个：优先最近在这里说过话的 bot，都没说过就选最早进群的。不同机器上的 bot 没法协调，可能都回，第一版接受。界面提示："不同电脑上的 bot 可能抢着回。"

**一个例子。** 真人张三、李四。三个 bot 在同一台 Mac 上：小码（Codex，规则模式，全部回复，主区"开话题"），小P（Claude，智能模式，管产品），小审（Claude，智能模式，管审查）。

| # | 消息 | 小码 | 小P | 小审 | 判断调用 |
|---|---|---|---|---|---|
| 1 | 张三在主区："@小码 登录接口为什么 500？" | 回，开话题 T1 | 不回，点名了别人 | 不回，点名了别人 | 0 |
| 2 | 李四在 T1，没 @："是不是昨天改了 token？" | 回，T1 归它 | 不回 | 不回 | 0 |
| 3 | 张三在主区，没 @："下周发布要不要先砍掉导出功能？" | 不回，"开话题"的主区要 @ | 判断：开新话题回，开 T2 | 判断：不回 | 1（两个智能 bot 合成一次） |
| 4 | 李四在主区："今天食堂的红烧肉不错" | 不回 | 判断：不回 | 判断：不回 | 1 |
| 5 | 小P 在 T2："@小审 帮我看下这个方案" | — | — | 回（bot 互 @）；bot 回合 +1 | 0 |
| 6 | "@所有人 明天十点开会" | 不回 | 不回 | 不回 | 0 |
| 7 | 李四在 T2 引用小P 的回答："优先级再排一下" | 不回 | 回，引用就是点名 | 不回 | 0 |

第 5 行要两个 bot 都在智能模式。小P 要是 @ 小码，小码收不到，和今天一样。

### 3.5 会话和上下文

owner 说这一块很关键：飞书里的位置怎么对应 agent 的会话，上下文是什么关系，哪些要存进会话历史。下面依次回答，再用一个群的时间线走一遍。今天的代码和这里不一样的地方，列在本节末尾。调研见 `docs/research/2026-10-14-session-approval-service/session-map.md`。

**一个飞书位置对应一条会话。** 每个 bot 各有各的会话。下表说的是一个 bot 在一个位置上。群里只有主区和话题两种位置；私聊不在群里，是主人或管理员和 bot 一对一的聊天窗口。

| 飞书里的位置 | 智能 | 单会话（规则模式"连续"） | 多会话（规则模式"开话题"） | 什么时候建 |
|---|---|---|---|---|
| 群主区 | 一条会话，一直接着聊 | 一条会话 | 不留会话，@ bot 就开一个话题 | 这个 bot 第一次在主区回复时 |
| 话题，不管是谁开的，包括话题群里的帖子 | 一条会话 | 一条会话 | 一条会话 | 这个 bot 第一次在这个话题里回复时 |
| 私聊（不在群里，一对一） | 一个私聊窗口一条会话：主人一条，每个管理员各一条 | 同左 | 同左 | 第一次私聊时 |
| 私聊里的话题 | 单独一条会话，和群里一样。用户开的和 bot 开的私聊话题，事件里都带 `thread_id`（e10） | 同左 | 同左 | 第一次在这个话题里回复时 |
| 云文档评论 | 每篇文档一条，和今天一样 | 同左 | 同左 | 和今天一样 |

- 会话就是一条普通的 Codex 线程或 Claude 会话。主人在 Codex 应用里或用 `claude --resume` 打开它，看到的和 bot 看到的一样（e14 在终端里实测过）。主人可以在终端或 Codex 应用里接着 bot 的会话聊：bot 每一轮开口前看一眼这条会话，别人写过（聊了几轮、压缩过）就重新接上，从最新的地方接着说；Codex 那边 bot 每一轮结束就放开线程，终端随时打得开。bot 正在回答的那一轮里终端也在写，两边会分叉，不处理（owner 2026-10-16 定，D6 选 A；s15b 改）。今天 bot 在最后一轮之后还占着会话 45 到 50 分钟：这期间 Claude 那边终端里写的轮次和 `/compact` bot 看不到，下一轮接着自己的历史写，两边分叉；Codex 那边终端打开会被拒（e14）。
- 不在同一个位置里悄悄换会话。只有 `/new`、`/clear`、`/resume` 会换，见下面的"命令"。
- 话题群和话题形式群里没有主区对话，每个帖子就是一个话题，也就是一条会话，不判断要不要开话题。
- 子 agent 代替不了新会话：它的结果会回到父会话里，干完就结束，事后没法接着问它。它的用途是把一件事拆开并行做。
- 一个群只有一个权限档，群里谁说话都用这一档、进同一条会话（owner 2026-10-16 去掉了访客档，见 3.8）。今天群里设了不同的访客档时，访客跑在另一条会话上（`D/project/registry.ts:115` 的 `turnTier`），主区和每个话题都可能有两条会话；s15c 改成一条。

**主区和话题是什么关系。**
- 主区会话和话题会话互不复制历史。
- 话题开出来时，不管是用户开的，还是 bot 判断后开的，主区会话里只留一行引用，指向这个话题的会话：谁、几点、在哪条消息下开了话题、话题的标题、话题 id，以及话题会话的 id（Codex 的线程 id 或 Claude 的会话 id）。话题会话里也记着主区会话的 id。两边靠这两个 id 互相找到。
- 引用行由 daemon 生成，不带话题里的内容，用户也伪造不出来。
- 会话在 bot 第一次回复时才建。所以 bot 还没在某个话题里说过话时，这个话题还没有会话，引用里只有话题 id；主区会话还没建时，话题的回指里也没有主区会话的 id。这两种情况下用话题 id 或群也能找到对方现在的会话。主区 `/new` 以后，旧话题的回指仍然指向开话题时的那条主区会话。
- 引用行在主区会话下一次开口时，和别的新消息按时间一起写进对话记录块。不在话题一开就单独写进主区会话：Codex 那种写法（`thread/inject_items`）在 Codex 应用里看不到，Claude 那种写法（`shouldQuery: false`）Codex 没有，而且为了一行字要拉起一个会话进程。主区会话在开口之前也用不着知道。
- 不在群主区另发一条带链接的消息。飞书新版客户端会把话题回复直接显示在那条消息下面，主区的人本来就看得到。
- 话题会话开场带四样：一行回指（"这个话题开在主区 10:01 张三的消息下，主区会话 id 是……，主区更早的内容用 vonvon 飞书 skill 查"）、主区在话题第一条消息之前的最近 10 条、话题第一条消息、话题里已有的消息。
- 之后两边要看对方的内容，都用 vonvon 飞书 skill 去查（见下面的"查飞书上下文"）：按会话 id 读对方会话里说过什么，或者按话题 id、时间读飞书消息。查到的内容作为工具结果进 bot 自己的会话。
- 主区会话压缩以后，引用行可能被摘要掉。所以压缩后主区下一次开口时，附一张"本群最近 5 个活跃话题"的短表；skill 也能列出本群所有话题。不管是谁压缩的都附：vonvon 发起的、Claude 空闲时自己压的、主人在终端或 Codex 应用里压的。bot 每次开口前看一眼原生会话，有新的压缩就附（owner 2026-10-16 定，D4 选 B；s15b 改）。今天只在 vonvon 自己看到的压缩之后附（e14）。

**哪些存进会话历史。** 只存 bot 真正开始回复时读到的东西，一共四类：
1. 会话开始时的个性和记忆。
2. 每次回复前，这个位置自上次以来的新消息，合成一个对话记录块。真人的话带真名，包括智能模式判了"不回"的消息；别的 bot 只放最终回答，标成"某某（bot）"，截到几百字。主区的记录块里还有新开话题的引用行。
3. 触发这次回复的消息、它引用的消息、附件路径、语音转写。
4. bot 自己的回答、工具步骤和子 agent 的结果，由 Codex 和 Claude 原生记录。

不存的：
- 别的话题、别的群、私聊的内容。
- 主区会话里不放话题里的回复，包括这个 bot 自己在话题里说的话。
- 话题会话里不放话题开出来以后主区的消息。话题第一条只在开场放一次，之后每轮不再重复。
- 别的 bot 的过程和子 agent。
- 自己以前的回复，已经在会话里了。

消息不是一到就塞进会话，而是等 bot 开口时一起带进去。daemon 给每条会话记一个水位，表示它已经读到哪条消息。每送进一条就推进，包括触发、插话、排队和记录块里的消息。

对话记录块每条带真名、压成一行，防止有人伪造记录块（今天已有，`D/bot/context-weave.ts:375-384`）。触发这次回复的消息不进记录块，放在块下面，照旧是发信人一行、引用、正文和附件清单：压成一行会毁掉多行文字和代码，也会丢掉引用、附件路径和语音转写。主区会话的一个记录块和它下面的触发消息：

**主区里被 @ 时回在哪里（智能模式）。** 调一次判断，只决定回在主区还是开新话题（3.4）。回在主区，就进主区会话；开新话题，就用 `reply_in_thread` 回这条消息，开一条话题会话。

**bot 正在跑的时候又来了消息。** 按这个群的"运行中来了消息"设置：插话，就插进正在跑的这一轮；排队，就等这一轮结束再跑。每个群都能设，没设时用 bot 默认（3.2）。Claude 不支持插话，总是排队（`D/agent/claude-agent/thread.ts:534-538`）。主区正忙不另加规则。智能模式下主区的 @ 消息照样按上一段判断回在哪里，这个判断和主区忙不忙无关；判断回在主区、主区又正在跑，才按插话或排队的设置处理。

群里有几个 bot 时，每个 bot 各有自己的一套会话、水位和引用行。A 开的话题，B 的主区会话也会看到一行"A（bot）开了话题"；B 只有在这个话题里被 @，才建自己的话题会话，开场里 A 的发言只放最终回答。B 要认得出这个话题才有这一行：同一台电脑上的 vonvon bot 开的都认得出（登记表），开在 B 自己回复下的也认得出（s14c）。别的电脑上的 bot 和别家的 bot 开的，有两种情况 B 没有这一行：话题开在 B 早就读过的旧消息下；B 读过那条消息以后，A 才在它下面开话题。owner 2026-10-16 接受（D5 选 A）。

**查飞书上下文。** 每个会话预装一个 vonvon 飞书 skill，背后是 `vonvon` 命令行（见 3.7）。bot 用它查自己能看到的飞书内容：主区要看某个话题里说了什么，话题里要看主区更早的消息，都通过它查；它也能列出本群的话题。
- 按会话 id 读另一条会话：返回那条会话里用户的消息和 bot 的最终回答，不含工具步骤。背后是 Codex 的 `thread/turns/list`（带 `itemsView: "summary"`）和 Claude Agent SDK 的 `getSessionMessages`（0.3.296 的 `sdk.d.ts:906`）。Claude 一半实测过：能读别的工作目录下的会话。传那条会话原来的工作目录最快；不传也能读，但要扫所有项目；传错了读到 0 条，不报错。读出来含工具步骤，vonvon 自己滤掉（e02 第 5 节）。Codex 一半也实测过：用 daemon 常驻的辅助进程读，不用加载那条会话，也不起回合（所以不花额度，推断）；summary 视图只返回用户的消息和最终回答。只做过 `thread/start`、还没跑过回合的会话读不到，报 `thread not loaded`，和 id 不存在时一样，vonvon 按空会话返回。正在跑的那一轮读出来只有用户的消息，和被打断的一样，所以哪条会话正在跑，daemon 按自己的记录写成"这一轮还在进行"（e11）。不用 `thread/read`：0.162.1 上用它读全部历史已经标成过时。
- 只能读同一个 bot、同一个群里的会话。私聊的会话在群里读不到。owner 说过这个 skill 可以以后再做；Claude 把它放进了第一版，因为主区只留话题的引用，没有它就查不到话题里说了什么。
- 用机器人身份查，只能查这个 bot 所在的群；在群里只能查当前这个群。卡片上显示"查了本群 9:00 到 10:00 的 40 条"。
- 不把用户身份的 lark-cli 交给 agent：它能读到主人所在的所有群，包括机器人不在的群（实测，`docs/research/2026-10-14-v1-definition/context-feishu-products.md` 2.3）。

**压缩。** 两家都用原生的自动压缩，一直开，去掉"关闭自动压缩"开关：它只接了 Codex，而且新版 Codex 会把阈值封顶在窗口的 90%，推断已经关不掉。运行卡头部一直有上下文仪表；压缩时过程区显示"已压缩 85% → 20%"。

**daemon 在本机记什么。**
- 每条会话的绑定和水位，和今天的 `sessions.json` 在一起（`D/bot/session-store.ts:13-39`）。
- 每个群一份话题登记表：话题 id、第一条消息的 id、谁开的、几点、标题（第一条消息的开头几个字）、这个 bot 在里面有没有会话。用来生成引用行，给 skill 列话题。话题常常开在一条旧消息下，按时间拉主区拉不到这件事，所以要单独记。
- 判断用的最近消息只放在内存里，每个群几十条，重启就清空。除了话题标题，群里的聊天内容不存到本机磁盘；回复时从飞书拉。
- 这些都在 daemon 里，只用 node 的文件读写，不依赖 Electron。

### 3.7 在聊天里改设置

主人和管理员可以在私聊里直接跟 bot 说，比如"以后在支付组说话活泼点"、"给支付组加上 X skill"、"建一个发布群，把张三拉进来"。第一版只在私聊里能说，群里不能在聊天里改设置。

**做法**：
1. 扩展已有的 `vonvon` 命令行（`packages/daemon/package.json` 的 `bin`，现在注册了 `daemon`、`open`、`service` 等子命令，`D/cli/index.ts:20-55`），加上设置和飞书两组子命令。设置命令是所有会改东西的命令，包括建群和拉人进群；飞书命令只查不改。命令行也能在终端里直接用。
2. vonvon 设置 skill 告诉 agent 怎么用这些命令。只有私聊的会话装它、能用设置命令。

**能改什么**：只限这个 bot 自己的事。

| 能改 | 不能改 |
|---|---|
| 个性、规矩、智能提示词；记忆；skill 和 MCP 的启用名单；仓库和工作区；会话方式和回复方式；权限档和网络；建群、拉人进群 | 建新 bot、改别的 bot；填 API key（只在桌面端或网页里填，聊天里不收 key）；vonvon 的全局设置 |

- 群里不能在聊天里改设置。某个群自己的设置、bot 的默认设置和别的群的设置，都在私聊里改，说清是哪个群。
- 谁能改由 daemon 判断，不由 agent 判断。daemon 知道这一轮是谁的消息触发的，只有主人和管理员触发的那一轮能改设置，别人的命令直接被拒。私聊本来只有主人和管理员能用，daemon 照样再查一遍。
- daemon 靠每条会话自己的令牌认出命令来自哪条会话：会话启动时 vonvon 给它一个令牌，命令行调用时带上。没有令牌、令牌对不上，或者不是私聊会话的设置命令，一律拒绝。能不能在沙箱里带上，见第 9 节第 2 项。
- 改完在卡片上显示改了什么，带［撤销］。
- 私聊有一个"聊天改设置"开关，默认开着。关掉以后，私聊的会话也不装设置 skill，daemon 也拒绝它的设置命令。开关只在桌面端或网页里改，聊天里不改，因为关掉以后聊天里就打不开了。群里没有这个开关，第一版群里不装设置 skill、不能用设置命令；给群加开关放进第 10 节。这是 owner 第 29 题和之后的补充定的。
- 会话中途改了开关：设置命令的拒绝马上生效，因为是 daemon 判断的；skill 装不装，要等私聊的下一条会话，除非两家能中途换 skill 列表（第 9 节第 3 项：Codex 从 0.148.0 起能，Claude 没测）。
- 群里不能用的只是设置 skill 和设置命令。飞书 skill 和它用的只读查询命令不受影响，每个会话都能用，因为主区和话题要靠它互相查（3.5）。这一条是 Claude 定的，和 owner 说的"禁止使用 vonvon-bot 的 CLI"字面上不同，见第 11 节第 26 条。
- 建群和拉人：bot 可以自己建一个新群，再把人拉进来。建群要定会话方式（3.4），主人没说，agent 先问。对已有的群，bot 不自己进，要群里有人拉它，所以 bot 把拉它进群的步骤发给你。飞书其实允许机器人自己进公开群，私有群不行（e10）；owner 2026-10-15 定第一版不用这个，都要人拉。

### 3.8 卡片和权限

owner 的话："确认卡、选项卡、授权卡这些需要用户交互、用户确认的体验，要和 Agent 里面的一种授权一致……它也可以设置成完全访问，也就是用户不需要确认任何事情。"问到越权时要不要发卡请人批准，owner 答："超出权限就直接拒绝啊，为什么还要授权呢？""无越权的授权，不授权。"

所以第一版的权限只靠权限档，不发卡请人批准越权：
- 权限档三档：只读、读写、完全访问，名字沿用 bridge。有 bot 默认，群里可以覆盖，私聊用 bot 默认（3.2）。新群的默认档和今天一样：bot 自己建的群是完全访问，被拉进的已有群是只读、关网（`D/project/lifecycle.ts:138`、`:206`、`:221`）。从 bridge 迁来的群沿用原来的档。一个群只有一档，群里谁触发都用这一档：bridge 的访客档（普通成员用另一档、跑另一条会话）去掉了，owner 2026-10-16 的话："反正管理员问的信息，其他成员也都看得到，还是只保持一个权限就好了"（s15c 改）。只限主人和管理员的事照旧，比如主区的 `/new`、`/clear`、私聊、点 Claude 自己要问的卡（3.5、第 4 节、下面的表）。
- 只读和读写：agent 要做超出这一档的事，比如写工作区以外的文件、关网时联网，直接拒绝。agent 收到拒绝的原因，自己换个办法，或者停下来说明。和今天一样。
- 完全访问：从不问权限。
- agent 向人提问、请人确认方案时，照样发卡，因为那是在问人的意见，不是要权限。
- 完全访问下，Claude 自己仍会停下来问的少数几类照样发卡（第 25 题 a，见下面"完全访问下还会问什么"）。那是 Claude 自己的行为，不是 vonvon 的越权授权。

调研见 `docs/research/2026-10-14-session-approval-service/approval-ux.md`。调研推荐过一个"超出权限时：问我 / 直接拒绝"的开关，owner 没要。

今天两边都不问。Codex 写死了 `approvalPolicy: 'never'`（`D/agent/codex-appserver/backend.ts:30`），Codex 发来的请求一律回报错（`D/provider/transport/jsonrpc.ts:197-206`），连它在计划模式下的提问都收不到。Claude 三档都用 `bypassPermissions`，没有 `canUseTool`（`D/agent/claude-agent/permission.ts:56`、`:73`），今天只读、读写两档的会话里根本没有提问这个工具，计划模式的两个工具也没有，Claude 只能用文字问（实测，`docs/research/2026-10-14-v1-spikes/e02-claude-permissions-sessions.md` 第 1 节）。推断原因是没有 `canUseTool` 时 SDK 不给 CLI 留提问的通道，完全访问档也一样。第一版要把提问接上。

换成两家的设置（Claude 一列不带沙箱的部分在 JP-VPS 上实测过，见 `docs/research/2026-10-14-v1-spikes/e02-claude-permissions-sessions.md`；沙箱的部分和 Codex 一列还是推断，要实测，第 9 节）：

| 权限档 | Codex | Claude |
|---|---|---|
| 只读 | `never` + 今天的只读沙箱，就是今天的行为 | `default` 模式 + 今天的只读沙箱。`canUseTool` 对要权限的请求一律拒绝并说明原因，对提问发选项卡 |
| 读写 | `never` + 今天的读写沙箱，就是今天的行为 | `acceptEdits` + 今天的读写沙箱，`canUseTool` 同上 |
| 完全访问 | `never` + `danger-full-access`，就是今天的行为 | `bypassPermissions`，就是今天的行为。`canUseTool` 只处理提问和 Claude 自己仍要问的几类，见下 |

- Claude 的只读、读写两档不再用 `bypassPermissions`。今天用它，推断有两个缺口：关网时 Bash 可能仍能连外网，Edit 和 Write 可能写到工作区以外（`approval-ux.md` 3.3）。不带沙箱时这两个缺口都在：今天的只读档下 Bash 能写工作区内外的文件、能 curl 出去，`bypassPermissions` 下工作区以外的 Write 也直接放行；带上今天的沙箱还在不在，第 9 节第 12 项在 Mac 上测。换成上表以后，只读档下写文件的 Bash、联网的 Bash、工作区以外的读写都会先到 `canUseTool`；读写档下工作区里的写直接放行，其余同样先到回调（实测，e02 第 1 节）。只读档可以对这些一律拒绝；读写档关网时，回调分不出哪条 Bash 在联网，要看命令文字或者靠沙箱，在 Mac 上测（e03）。代价是今天这两档下能用的 WebFetch、往工作区以外写文件会被拒；开网时给 WebFetch、WebSearch 加允许规则。
- Codex 三档都保留 `never`：模型知道不能申请，就不会白白尝试。`never` 下没有标成只读的 MCP 工具会被拒（`approval-ux.md` 1.5），vonvon 自己的 MCP 要配 `approve`（第 9 节第 2 项）。
- 中途改档不用重开会话：Codex 每一轮的 `turn/start` 能带新的设置，Claude 运行中能 `setPermissionMode`，升档降档都是下一轮生效（实测，e02 第 3 节）。升到完全访问要求会话启动时带 `allowDangerouslySkipPermissions`，所以每条会话启动时都带上；resume 不恢复上次的档（`settingSources` 为空时测的），每次都明确传。Codex 一半还是推断。
- Linux 上 Codex 的只读、读写档今天直接拒绝启动（`D/agent/codex-appserver/backend.ts` 的 `sandboxParams`），所以 Linux 上的 Codex 只能用完全访问，界面写明。被拉进的已有群默认只读，在 Linux 上用 Codex 时起不来：bot 回一句说明，等主人在设置里明确改成完全访问，不自动放开。（s20b 已改）

**完全访问下还会问什么。** 不问权限。Claude 自己在任何模式下都会停下来问的少数几类，照样发卡问，和 Claude 自己的行为一致，比如用户在自己的 Claude 设置里写了"这类操作必须问"、删除关键目录（`approval-ux.md` 2.2）。这种卡只有主人和管理员能点，15 分钟没人点按拒绝。只读、读写两档下，这几类直接拒绝。实测里 `bypassPermissions` 下只有 AskUserQuestion 走到回调，写 `.claude/` 下的文件也直接放行；ask 规则和删除关键目录还没测，测试时 `settingSources` 为空，用户层的 ask 规则也没测到（e02 第 1 节，第 9 节第 11 项）。测出来走不到回调的几类，按 `docs/v1-plan.md` 4.2 第 3 条问 owner。

**卡片。** 所有要人点的卡片一个样：同样的版面、同样的状态、同样的"谁能点"规则。所有会话默认就有，不只在私聊。
- **运行卡**：流式输出、⏹ 停止、工具折叠、上下文仪表、子 agent 区（见 3.9）。等人回答时显示"⏸ 等 张三 回答（见下方卡片）"。
- **选项卡**：agent 问一个带选项的问题时（Claude 的 AskUserQuestion，Codex 的提问；Codex 只在计划模式下会问）。空提交时提示"至少选一项"。
- **确认卡**：只要"是 / 否"的确认，比如 Claude 的计划（ExitPlanMode）。按钮是［按这个方案做］［不行，我来说］。
- 完全访问下 Claude 自己仍要问的那几类，用同样的版面，按钮是［允许这一次］［拒绝］。

- 卡片写清后果：选了会怎样，不选会怎样。今天咖啡一下的卡片，社区群里有人看不懂按钮是干什么的（`approval-ux.md` 第 5 节）。
- 回复这张卡片，等于用你的话回答。能回答的人在同一个位置直接发新消息，也算回答。运行卡上的 ⏹，等于不回答并停止这一轮。
- 答完以后按钮去掉，换成一行结果，比如"张三 选了：方案 B 10:03"、"⏱ 15 分钟没人回答"、"⏹ 已停止"、"已失效（后台服务重启过）"。每种结局都改卡，不让按钮一直挂着。bridge 里咖啡一下的卡超时后按钮还在。
- 每张卡单独发一条消息，回复触发这一轮的那条消息，在话题里就发在话题里；卡片里 @ 能回答的人。不把按钮放进运行卡，因为运行卡在流式更新，按钮会和输出抢。卡片里的 @ 会不会提醒人要实测，不会就另发一条带 @ 的文字。

**谁能点。** 由 daemon 按点击人的 open_id 判断，不由 agent 判断。daemon 还要核对这张卡属于这个群和这条会话，转发出去的卡点了无效。

| 卡片 | 能点的人 |
|---|---|
| 选项卡、确认卡 | 发起这一轮的人，管理员也能代答 |
| 完全访问下 Claude 自己要问的 | 主人和管理员 |
| bot 触发的那一轮（bot 之间对话） | 主人和管理员 |
| 云文档评论的会话 | 没地方放卡片：提问按"没人回答"处理，Claude 自己要问的直接拒绝 |

- 点的人不对时，回贴一条去重的小注，比如"只有发起人或管理员能回答"，和今天 ⏹ 的做法一样（`D/bot/handle-message.ts:2384-2397`）。第一次有效的点击生效。

**等待和超时。**
- 15 分钟没人回答：选项卡告诉 agent"用户没有回答"；确认卡和 Claude 自己要问的按拒绝处理。
- 等人回答时，空闲看门狗暂停，不然这一轮会被当成"没输出"杀掉。
- 同一条会话同时只显示一张待回答的卡，其余排队。
- 后台服务重启后，挂着的请求就没了。点到旧卡时，卡片自愈成"已失效（后台服务重启过）"，和今天的 `healDeadRunCard` 一样（`D/bot/handle-message.ts:2398`）。
- 子 agent 发起的卡片，发在父运行卡所在的位置，卡上写"子 agent X 问……"。
- 要填密码这类敏感信息的问题，不在群里显示输入框，请用户去私聊回答。

**在聊天里改设置。** 不发授权卡，也不按权限档拒绝。owner 第 29 题定了：改 vonvon 设置都走设置 skill 和 `vonvon` 命令行，只有私聊的会话有，群里没有（3.7）。私聊的开关开着时，主人和管理员触发的那一轮改了就直接生效，带撤销。

留下的风险：agent 读到的文档或网页里可能藏着"去装这个 MCP"之类的指令，诱导主人或管理员触发的那一轮去装 MCP、装含脚本的 skill、加目录、升档或开网。daemon 按触发人判断，挡不住这一种，只读、读写档的会话也能这样给自己升档。第 29 题问的时候写了这个风险，owner 选了按位置装不装设置 skill 来管，所以私聊里有这个风险，群里没有。缓解：这几种扩大能力的改动，改完的卡片上单独标出来，带［撤销］（Claude 加的，第 11 节第 29 条）。

### 3.9 子 agent

- 子 agent 显示在父运行卡的"子 agent 区"，一行一个：状态、名字、在做什么、几步、用了多久，嵌套的缩进。点开看最近 5 步和结果。每行有"停止"，运行卡的 ⏹ 全停。不给每个子 agent 发一张卡：飞书对群里所有 bot 有每秒 5 条的共用限额。
- **一张运行卡包含这一轮的所有子 agent，子 agent 都跑完了，这张卡才算结束。**
  - Codex：本来就是这样。文档原文是"Codex waits until all requested results are available, then returns a consolidated response"（learn.chatgpt.com/docs/agent-configuration/subagents）。
  - Claude：不一样。Claude Code 的子 agent 默认在后台跑，经 Agent SDK 用时也是；主回合可以先结束，子 agent 跑完再通知 Claude 起新的一轮（code.claude.com/docs/en/sub-agents）。实测里一条消息出了 4 到 6 个结果。设置 `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` 后，子 agent 一律在前台跑，主回合等它们都结束，一条消息只有一个结果，几个子 agent 之间仍然并行（实测，`docs/research/2026-10-14-v1-spikes/e01-background-tasks.md`）。代价是它同时关掉后台 Bash 等所有后台任务，比如 bot 不能在后台起一个开发服务器再结束这一轮；模型要在后台跑命令时会先报错一次，再改成前台跑。第一版在 bot 的 Claude 会话里打开这个开关，两家行为就一致了。这是 Claude 的决定。前台子 agent 跑着时按 ⏹ 多久能停下还没测，s35 开工时补测（e01）；停不下来的话，回头再定。
- 子 agent 跑的时候，群里的新消息按今天的规则插话或排队，只给父 agent。第一版不能直接跟某个子 agent 说话。
- 今天 Codex 的子线程事件全丢了，Claude 子 agent 的步骤混进了主过程（`D/agent/codex-appserver/backend.ts:333-337`；`D/agent/claude-agent/event-map.ts:92-123`），第一版要修。

### 3.10 后台服务和崩溃

owner 的话："后台服务不要依赖 Electron，因为 Linux 上没有桌面端，它可能就装一个 Daemon 后台服务。"调研见 `docs/research/2026-10-14-session-approval-service/service.md`。

**后台服务由 daemon 自己装。**
- 用 `vonvon service install`、`uninstall`、`status` 注册、卸载和查看。桌面端只调用打包在里面的同一个命令行。不用 Electron 的 `agentService`，也不用 SMAppService：这两种都要求服务登记在 .app 名下，Linux 上没有对应的东西。
- macOS：用户级 LaunchAgent `com.vonvon.bot.daemon`，plist 写在 `~/Library/LaunchAgents/`（`D/service/identity.ts:33`）。用户登录后启动，能用钥匙串里的 Claude 登录和 Codex 的登录（推断，要实测）。Mac 设成自动登录时，就等于开机启动。
- Linux：systemd 用户服务 `vonvon-bot.service`。安装时检查 linger：没开就问一句，同意后执行 `loginctl enable-linger`。这样开机就启动，退出 SSH 以后 bot 也还在跑。
- 从 dmg 装的，服务用 app 里的 Electron 程序以 Node 模式运行（`ELECTRON_RUN_AS_NODE=1`），不用另带一份 Node；从 npm 装的，用用户自己的 `node`。这只是借 Electron 的 Node 来用，服务的生死由 launchd 管，桌面窗口开不开都一样。代价是 app 被删或挪走以后，服务就起不来了，所以桌面端提供"关闭登录时启动"，文档写清卸载步骤。
- 注册以后，系统的服务管理器是唯一拉起 daemon 的。`vonvon daemon start` 和桌面端都请它去启动，不自己再起一个。停止走 `vonvon daemon stop`：先排空，再正常退出，管理器就不会再拉起它。
- 退出桌面端不停 bot。首次运行清单里加一步"登录电脑时自动运行 bot（推荐）"。跳过的话，就像今天一样起一个分离的 daemon，并提示"这样崩溃后不会自动重启"。
- 这些代码大部分已经在 main 上，只是没接线：launchd 和 systemd 的安装事务（#271、#274）、服务定义（#246）、退出码（#276）。今天 `vonvon service install` 直接报错（`D/cli/commands/service.ts:5`）。

**崩溃了自动重启。** 服务管理器在 daemon 异常退出后重启它（plist 的 `KeepAlive`、unit 的 `Restart=on-failure`，`D/service/definitions.ts:81`、`:85`）。两边都不会在连环崩溃时自己停下来，所以上限由 daemon 自己判断：
- daemon 和每个 bot 的子进程都加全局的异常兜底：崩溃前在 `~/.vonvon-bot/crash/` 写一条记录（版本、哪个 bot、错误的第一行、运行了多久），再退出。被系统强制结束、没留下记录的，下次启动时补一条"被系统强制结束"。今天没有任何崩溃记录（`D/cli-bridge/ipc.ts:24-25`）。
- 10 分钟内崩溃 3 次，daemon 进入暂停：网页和桌面端照常能打开，显示原因；bot 不连飞书，不跑 agent。不自动恢复，等主人点"恢复运行"，或执行 `vonvon daemon restart`。下次登录或开机时重新计数。
- 某一个 bot 的子进程 10 分钟内崩溃 3 次，只暂停这一个 bot，别的照常。今天子进程会无限重试（`D/bot/supervisor.ts:115-131`）。

owner 说过"崩溃报错就好了"，让 Claude 斟酌。自动重启是 Claude 加的：后台服务崩了，群里的人只会看到 bot 不回，主人不一定在电脑前。

**怎么告诉主人。**
- 崩了一次、已经自动恢复：桌面端的诊断页记一条；bot 给它的主人发一条私聊"刚才崩溃过一次，已自动恢复。原因：……"。
- 连环崩溃、已经暂停：诊断页顶上一条红条，带"恢复运行"按钮；私聊"10 分钟内崩溃 3 次，已停止自动重启"。
- daemon 主进程崩溃时所有 bot 一起下线，只由最早加入的 bot 发这条私聊，列出受影响的 bot。每个 bot 每 10 分钟最多发一条。
- 私聊只写一行原因，不放调用栈和本机路径。第一版不上传崩溃信息。
- 私聊直接调发消息的接口，不靠长连接，所以暂停时也能发。机器人能不能给没开过会话的主人发私聊，要实测。
- Linux 上用 `vonvon daemon status` 看服务状态和最近的崩溃。

**Linux 上只装后台服务。** Linux 没有桌面端，第一版做一个命令行版：
1. `npm i -g vonvon-bot`，或者装下载的安装包。
2. 在终端里登录 Codex 或 Claude：`codex login --device-auth`，或者在 `claude` 里 `/login`。

5. 连 SSH 转发都用不了时，终端里也能扫码建 bot。

## 4. 私聊

- 只有主人和管理员能私聊对话。别人私聊时 bot 不跑 agent，回一张卡片"在群里 @ 我"，列出这个人所在的、有这个 bot 的群。私聊会话跑在主人的 Mac 上，放开了等于让别人在主人的电脑上跑 agent。
- 私聊里的 bot 和群里的 bot 原理一样：有工作区、skill、MCP。它有一套默认的私聊设置，主人把飞书机器人加进 vonvon 以后，私聊马上就能用：
  - 工作区用 bot 的主工作区；
  - skill 和 MCP 用 bot 的名单，加上两个内置的 vonvon skill；
  - 权限档用 bot 的默认档。
- 主人可以在桌面端或网页里改这套私聊设置。
- 默认就是正常对话，能写代码、处理文件；额外能改设置（3.7）。
- 主人和每个管理员各有一条私聊会话、一份私聊记忆，能做的事一样。

## 5. 迁移

**保留**：
- 所有 bot，同一个飞书应用。
- 群绑定和它们的设置：群类型、免 @、权限、网络、白名单、后端、模型，换算成规则模式。设了访客档、和管理员档不同的群，取两档里更严的那一档，迁移结果里列出这些群。
- 旧会话：Codex 线程和 Claude 会话都能续上，前提是不换 `CODEX_HOME`、不动旧目录（推断）。
- bridge 本机的管理员名单，见第 6 节。
- 评论提示词、已发文件的记录。

bot 的个性、记忆、skill 导入后为空，行为和今天一样。

**会感到的变化**（写进迁移说明）：
- 原来的"群 = 仓库目录"，变成"这个群的主工作区覆盖"，目录本身不动。
- 多 bot 群里，bot 不再进别的 bot 的话题，主区命令要 @。
- "全部回复"里，引用 bot 的消息就算点名它。
- 关了自动压缩的群变成自动压缩。
- 网页控制台和 `feishu-codex-bridge` 命令由桌面端替代。
- 私聊控制台没了。
- 要补一项新权限 `im:message:readonly`。

**失去**：Windows、WSL 上的用法（bridge issue #1、#23、#42 的用户，占比不知道，bridge 没有遥测）。owner 说原来没有 Linux 用户，所以不做 Linux 上的导入。还会失去日志、缓存、已下载的 Claude SDK（重新下载约 265 MB）和 Codex Fast。咖啡一下也没了（3.12）：迁移时卸掉 bridge 装进 Claude Code 和 Codex CLI 的 hook，之后这两处的审批照常在终端里问。

**怎么迁**（只做 macOS）：
1. 桌面端首次运行发现 `~/.feishu-codex-bridge`，就显示导入页。
2. 只读预检：每个 bot 的群数、目录是否还在、密钥能否解开、hook 是否装了、bridge 是否在跑、bridge 自己装的 codex 在不在。
3. 调 bridge 自己的 `stop`，它会删 plist、去掉自启。
4. 用 bridge 的锁格式给每个 bot 占住它的 `bots/<appId>/processes.json`，防止有人手动 `run`。锁挡不住 `start`：`start` 不看锁，会把自启装回来，launchd 拉起的 `run` 再一遍遍被锁拒掉（e07：锁在函数层面实测过，`run` 和 `start` 的表现是读代码，真机在 e08）。
5. 复制数据，用新密钥重新加密。
6. 找不到别的 codex 时，引用 bridge 那份，或者装一份。
7. 备份后卸掉 bridge 装的 hook。
8. 启动全部 bot，等长连接连上。
9. 再查一次 bridge 的 plist 和 launchd 任务，还在就再 `stop` 一次；然后写迁移标记，显示回执"旧目录不要删，空白项目还在里面"。

任何一步失败就回滚：先放掉 bridge 的锁，再 `start` bridge，不然被拉起的 `run` 会被这把锁拒掉。

- 一次导入全部 bot，因为 bridge 是一个服务带全部 bot。
- 密钥用主机名加用户名派生，改过主机名就解不开，这时让主人扫码刷新。
- 空白项目目录不搬，原地引用。搬了 Claude 会话会找不到。
- 复用草稿 #226（V8 的 bridge 导入事务）里的预检、密钥解密和 hook 改写代码（用来卸掉 hook），约 640 行。不采用它的"准入互斥锁"：那个锁在已发布的 0.6.14 里不存在，会拒绝所有现有用户。
- bridge 出最后一版：从 0.6.14（`6698118`）开分支，只加三样东西：通知所有人，看到迁移标记就拒绝启动，`stop` 和 `status` 时提示。Mac 用户拿到下载地址；其他平台的用户只收到通知，继续用 0.6.14。

## 6. 主人和管理员

- 沿用飞书应用自己的角色。主人是飞书应用的所有者；管理员是飞书应用的管理员和开发者，运营不算。开发者也算，是按 owner 第 10 题的回答：扫码把应用加进 vonvon 的人，飞书在扫码时会确认是管理员或开发者（owner 的说法，没有实测）。

- 开了可选权限"管理应用自身资源"（`application:application:self_manage`）后，vonvon 会读飞书应用的所有者和协作者名单，主人在飞书里另外加的管理员和开发者也能管这个 bot。查询方法见 `docs/research/2026-10-14-feishu-app-roles/roles.md`。
