状态：待 owner 认可。owner 在这份文档的 PR 里认可后即为定稿，第一版的范围以它为准（`AGENTS.md`"范围和资料"）。定稿后的新想法写进第 10 节"v1 之后"，发布前不实现。

来源：2026-10-14 的调研（`docs/research/2026-10-14-v1-definition/`，以其中的 `final.md` 为底稿），加上 owner 在 2026-10-14 三组问答里的回答。第 11 节逐条列出回答和它改了底稿的哪些地方。和底稿冲突时以本文为准。

本文的"主人"指 bot 的主人，也就是用户；"owner"只在说本项目的流程时出现。出处写成 `文件:行`，`D/` 指 `packages/daemon/src/`。"推断"是没实测的判断，"要实测"的项列在第 9 节。

## 1. 一句话

Vonvon Bot 是一个 macOS 桌面应用。主人在自己的 Mac 上养几个飞书机器人，每个 bot 有自己的个性、记忆、工作区、代码仓库、skill 和 MCP，能进不同的群，在每个群里表现不同。干活用主人本机已经登录的 Codex 或 Claude。

和 feishu-codex-bridge 最大的区别：bridge 的行为大多靠规则设定，Vonvon Bot 主推**智能模式**。bot 自己判断要不要接话、要不要开新话题、要不要和别的 bot 搭话。主人可以直接跟 bot 聊天来改它的设置、让它建群。bridge 原来的规则保留为**规则模式**。

给谁用：
1. 正在用 feishu-codex-bridge 的 Mac 用户。迁过来后，群、话题、卡片、命令和旧会话都保留。
2. 有 Codex 或 Claude 订阅、想在飞书群里有一个"像同事"的 bot 的个人和小团队。他们不一定用 GitHub，也不一定会装 Node。

不给谁用：Windows 和 Linux 用户；没有 Codex 或 Claude 订阅的人；想要云端托管、不开电脑也能用的人。

## 2. 叫法

| 叫法 | 意思 |
|---|---|
| bot | 一个飞书机器人（一个飞书应用）。名字、头像、简介以飞书为准 |
| 主人、管理员 | 能管这个 bot 的人，见第 6 节。两者能做的事一样 |
| 群主区 | 群里不在任何话题里的地方 |
| 话题 | 飞书话题，包括话题群里的帖子 |
| 会话 | 后台的一条 Codex 线程或 Claude 会话。bot 记得的对话内容都在这里 |
| 子 agent | 一个会话临时分出去、并行干活的帮手，干完就结束 |
| 智能模式 | 群设置。bot 自己判断接不接话、开不开话题、和不和别的 bot 搭话 |
| 规则模式 | 群设置。bridge 原来的规则：仅 @ 或全部回复；主区"开话题"或"连续" |
| 工作区 | bot 产出文件的目录，可写。主工作区是会话的工作目录 |
| 代码仓库 | 本机的一个 git 目录。和工作区一样传给 agent，区别在界面和指令 |
| skill、MCP | 给 agent 用的技能包和工具服务。本机各有一个库，bot 和群各有名单 |

产品文案里叫"Claude"，不叫"Claude Code"，这是 Anthropic 的品牌规定（code.claude.com/docs/en/agent-sdk/overview）。

## 3. 第一版做什么

### 3.1 桌面端

1. 桌面应用就是控制台，不再引导用户开网页。同一套页面也能用本机浏览器打开，但只在本机：daemon 只监听 `127.0.0.1`（`D/server/http.ts:184`），第一版不开放局域网和远程访问。
2. 签名加公证的 dmg，带更新源。现在更新源是空的（`packages/desktop/src/updates.ts:46`）。出 universal 包，Intel Mac 也能装。
3. 后台服务：bot 跑在后台服务里，登录电脑后自动启动。Mac 设成自动登录时，就等于开机启动。崩溃后自动重启，见 3.10。
4. 首次运行是一张清单，每一步都实时检测：扫码建飞书应用 → 一键开权限 → 检测事件订阅 → 检测应用已发布 → 检测 Codex 或 Claude 已安装、已登录、版本够用 → 可选从 bridge 导入。v2 里还没有人从头扫码成功过（`docs/research/2026-10-14-strategy/runnable.md` 第 1 节），这一条第一版必须走通。
5. 建新 bot 只在桌面端做，走上面的向导，不在聊天里做。
6. Bot 页：个性、规矩、工作区、代码仓库、skill、MCP、记忆、智能提示词、所在的群。
7. 群详情页：这个 bot 在这个群里的模式（智能或规则）和各项覆盖，见 3.2。
8. 状态与诊断页：每个 bot 的连接状态，Codex 和 Claude 的版本检查，最近没回的消息和原因（包括智能模式判断"不回"的原因）。用量页显示判断调用的次数。
9. 没有 Windows，也没有 Linux 桌面。

### 3.2 bot 模型

一个 bot 有三层：
1. **飞书身份**：名字、头像、简介，来自飞书应用，vonvon 不改。飞书能不能让同一个机器人在不同的群里显示不同的名字：没查到，所以"千人千面"体现在说话方式、工作区、仓库、skill 和记忆上，外观不变。
2. **bot 默认**：个性、规矩、工作区、仓库、skill、MCP、公共记忆、智能提示词。
3. **群内覆盖**：这个 bot 在某个群里另外的设置，以及这个群自己的记忆。没设的项继承 bot 默认。

| 项 | bot 默认 | 群内 | 规则 |
|---|---|---|---|
| 名字、头像 | 来自飞书 | 不能改 | — |
| 个性 `SOUL.md` | 有 | 可补充 | 群的默认加在 bot 后面，也可以选择整段替换 |
| 规矩 `AGENTS.md` | 有，可选 | 不能改 | 只在 bot 层 |
| 工作区 | n 个，1 个主的 | 可覆盖 | 群没设时，在默认位置给这个群建一个目录，见 3.3 |
| 代码仓库 | 0 到 n 个 | 可覆盖 | 只接本机已有的 git 目录，不接 git 地址 |
| skill | 启用名单 | 可增、可减 | 实际生效 =（bot 启用 ∪ 群增加）− 群移除 |
| MCP | 启用名单 | 可增、可减 | 同 skill |
| 记忆 | 公共记忆，所有群都看 | 本群记忆，只在本群看 | 见 3.6 |
| 智能提示词 | 有，带内置默认值 | 可覆盖 | 只在智能模式下用 |
| 模式 | 无 | 智能或规则 | 只在群层，见 3.4 |
| 权限档、网络、访客档、后端、模型 | 默认值 | 可覆盖 | 和今天一样 |

### 3.3 磁盘上的位置

```
~/.vonvon-bot/
  skills/                       本机 skill 库
  mcp/                          本机 MCP 库
  projects/<bot 名>/            bot 主工作区的默认位置
    groups/<群名>/              群没设工作区时的默认目录
  bots/<appId>/
    config.json                 bot 设置，含工作区、仓库
    projects.json               每个群一条，含群的覆盖
    SOUL.md                     bot 个性
    AGENTS.md                   规矩，可选
    SMART.md                    智能提示词，不存在时用内置默认值
    skills.json  mcp.json       启用名单
    memory/shared.md            公共记忆
    memory/dm/<open_id>.md      每个主人或管理员的私聊记忆
    groups/<chatId>/
      SOUL.md                   本群个性补充
      SMART.md                  本群智能提示词覆盖
      skills.json  mcp.json     {"add": [...], "remove": [...]}
      memory/group.md           本群记忆
```

- 工作区默认放在隐藏目录 `~/.vonvon-bot/projects/` 下，和今天一样（`D/config/paths.ts:115`），可以在桌面端改到别处。比今天多一层 `<bot 名>/`：今天所有 bot 共用这个目录，两个 bot 的同名项目会落进同一个目录（推断，`docs/research/2026-10-14-v1-definition/v2-fit.md` 第 8 节第 6 条）。
- 每个群默认有自己的目录。共用一个目录的话，B 群的会话能看到 A 群产生的文件，和"每个群的记忆分开"矛盾。
- 目录名按建立时的名字取，之后不跟着改名，重名时加一个短后缀，"/"等字符替换掉。
- 定义文件都是 markdown 和 json，主人可以直接用编辑器改。它们不进用户的代码仓库。仓库里的 `AGENTS.md`、`CLAUDE.md` 照旧由 agent 自己读。

### 3.4 群：智能模式和规则模式

每个群对每个 bot 有一个开关：智能模式或规则模式。

**智能模式**一起管三件事：
1. 要不要接话。
2. 群主区来了一件新事，要不要开一个新话题来回。
3. 要不要和别的 bot 搭话。

**规则模式**就是 bridge 原来的设置：回复方式选"仅 @"或"全部回复"，群主区选"开话题"或"连续"。规则模式下 bot 之间互相看不到，和今天一样。

**默认值：**
- 新建的 bot、新进的群默认智能模式。bot 进群时在群里说一句"我会读群消息，合适时接话"。
- 从 bridge 迁来的群用规则模式，沿用各群原来的回复方式和主区方式，不换算。bridge 今天的默认是免 @ 开，只有被拉进来的"连续"群默认关（`D/project/registry.ts:83-85`）。
- 主区方式切换后，回复方式不自动变，界面提示一句。

**三条底线**，两种模式共用。先回答"这条消息是对谁说的"，再轮到模式：
1. **点名**：@ 了谁、引用了谁的消息，就只有谁回。@ 了别人、@所有人、引用别人的消息，其他 bot 都不回。@ 两个 bot 就两个都回。例外：规则模式的"仅 @"里，引用我的消息不算点名，和 bridge 一致。
2. **接着聊**：话题里没点名的消息，归最近在这个话题里说过话的 bot。别的 bot 开的话题，我不插嘴。
3. **bot 消息**：别的 bot 发的消息，只有 @ 我才算。

这三条顺带修掉今天多 bot 群里的三个毛病：开了免 @ 的 bot 会进别的 bot 的话题；主区不带 @ 的 `/help` 每个 bot 都回；连续群里每个免 @ 的 bot 都回每条（推断，`docs/research/2026-10-14-v1-definition/group-response.md` 结论 3）。

**智能模式怎么判断。** 底线定不下来时，调一次判断模型，结果三选一：不回、在主区接着聊、开新话题回。在话题里只判断回不回，不再拆话题。
- 判断模型自动选。主人在桌面端填了 OpenAI（Decisions API）、TypeSafe（Jev）或 OpenRouter 的 key，就用它；没填，就用这个 bot 那家订阅里的小模型，关掉思考，一次不带工具的调用。资料见 `docs/research/2026-10-14-decision-models/decision-models.md`。
- 判断出错或超时就不回。被 @ 的消息不调判断，一定回。
- 只回"回"或"不回"，不做"只回一个表情"。"不回"的原因只记在本机诊断页，不发到群里。
- 判断用的提示词就是智能提示词：内置默认值，主人可以在 bot 层改，群里可以覆盖。
- 控制成本：只对允许使用 bot 的真人消息调；同一台机器上一条消息只调一次，本机几个智能 bot 合成一次"选谁回"；话题里只有一个真人在和我聊时直接回；每个群每小时有上限。延迟和每次占多少额度要在 Mac 上量。

**bot 之间。** 智能模式下，别的 bot @ 我时我能收到（要新开一个可选权限，见 3.11），这样能做"小码写、小审查"。B 看到的 A 的消息只有 A 的最终回答，标成"A（bot）"，截到几百字。没有真人插话时，bot 之间最多来回 3 轮，到了就停下并提示一次；真人说一句就清零。不收别的 bot 的全部消息。

**几个 bot 都会回的时候。** 同一台机器上，daemon 只放行一个：优先最近在这里说过话的 bot，都没说过就选最早进群的。不同机器上的 bot 没法协调，可能都回，第一版接受。界面提示："不同电脑上的 bot 可能抢着回。"

**一个例子。** 真人张三、李四。三个 bot 在同一台 Mac 上：小码（Codex，规则模式，全部回复，主区"开话题"），小P（Claude，智能模式，管产品），小审（Claude，智能模式，管审查）。

| # | 消息 | 小码 | 小P | 小审 | 判断调用 |
|---|---|---|---|---|---|
| 1 | 张三在主区："@小码 登录接口为什么 500？" | 回，开话题 T1 | 不回，点名了别人 | 不回，点名了别人 | 0 |
| 2 | 李四在 T1，没 @："是不是昨天改了 token？" | 回，T1 归它 | 不回 | 不回 | 0 |
| 3 | 张三在主区，没 @："下周发布要不要先砍掉导出功能？" | 不回，"开话题"的主区要 @ | 判断：开新话题回，开 T2 | 判断：不回 | 1（两个智能 bot 合成一次） |
| 4 | 李四在主区："今天食堂的红烧肉不错" | 不回 | 判断：不回 | 判断：不回 | 1 |
| 5 | 小P 在 T2："@小审 帮我看下这个方案" | — | — | 回（bot 互 @）；bot 回合 +1 | 0 |
| 6 | "@所有人 明天十点开会" | 不回 | 不回 | 不回 | 0 |
| 7 | 李四在 T2 引用小P 的回答："优先级再排一下" | 不回 | 回，引用就是点名 | 不回 | 0 |

第 5 行要两个 bot 都在智能模式。小P 要是 @ 小码，小码收不到，和今天一样。

### 3.5 会话和上下文

**一个飞书位置对应一条会话。** 每个 bot 各有各的会话。

| 飞书里的位置 | 智能模式 | 规则模式 |
|---|---|---|
| 群主区 | 一条会话，一直接着聊 | "连续"：一条会话；"开话题"：主区不留会话，@ bot 就开一个话题 |
| 话题，不管是谁开的 | 一条会话 | 一条会话 |
| 私聊 | 每个人一条会话 | 同左 |

- 智能模式下，主区的会话和 bridge 的单会话群一样：`/new` 或 `/clear` 换一条新会话，`/compact` 主动压缩，`/resume` 换回以前的会话。不用命令时，上下文快满了自动压缩。
- 话题开出来时，不管是用户开的，还是智能模式判断后开的，主区的会话里只留一条指向这个话题的引用，作为主区的上下文。话题里是一条新会话。从主区开出来的话题，开场带话题第一条消息，加主区在那之前的最近几条。
- 子 agent 代替不了新会话：它的结果会回到父会话里，干完就结束，事后没法接着问它。它的用途是把一件事拆开并行做。
- 不在同一个位置里悄悄换会话。主人在 Codex 应用里或用 `claude --resume` 打开这条会话，看到的和 bot 看到的一样（推断，要实测）。
- 权限档和今天一样：群里设了不同的访客档时，访客跑在另一条会话上（`D/project/registry.ts:115` 的 `turnTier`）。

**bot 回复时看到什么。**

| 放不放 | 内容 |
|---|---|
| 放 | 个性和记忆（会话开始时）；自己这条会话的历史；上次回复以后这里的新消息，带真名，含别的 bot 的最终回答；触发消息和它引用的消息；附件路径；语音转写 |
| 不放 | 别的话题、别的群、私聊的内容；别的 bot 的过程和子 agent；自己以前的回复（已经在会话里） |

新消息合成一个"对话记录块"，每条带真名、压成一行，防止有人伪造记录块（今天已有，`D/bot/context-weave.ts:375-384`）：

```
[飞书 · 群「支付组」· 话题「订单接口 500」]
10:01 张三：订单接口今天一直报 500
10:03 小审（bot）：第 88 行改对了，但金额为 0 时还会出错
10:05 王五 → @小码：小审说的那个情况你改一下
[/飞书]
```

- 真名用 `contact:user.base:readonly` 换，查不到写 open_id 尾号。今天触发人以外的名字都是"某用户"（`D/bot/bridge.ts:59-81` 没传 `resolveSenderName`）。
- 字数超预算就留最近的，并写"更早还有 N 条，可以查"。
- 会话里只有 bot 真正开始回复时读到的东西，不做"每条消息实时塞进会话"。智能模式判"不回"的消息，下次回复时一起带上。
- 一条会话大家共用，每条带名字。

**查飞书上下文。** 每个会话预装一个 vonvon 飞书 skill，背后是 `vonvon` 命令行（见 3.7）。bot 用它查自己能看到的飞书内容：主区要看某个话题里说了什么，话题里要看主区更早的消息，都通过它查。owner 说过这个 skill 可以以后再做；Claude 把它放进了第一版，因为主区只留话题的引用，没有它就查不到话题里说了什么。
- 用机器人身份查，只能查这个 bot 所在的群；在群里只能查当前这个群。卡片上显示"查了本群 9:00 到 10:00 的 40 条"。
- 不把用户身份的 lark-cli 交给 agent：它能读到主人所在的所有群，包括机器人不在的群（实测，`docs/research/2026-10-14-v1-definition/context-feishu-products.md` 2.3）。

**压缩。** 两家都用原生的自动压缩，一直开，去掉"关闭自动压缩"开关：它只接了 Codex，而且新版 Codex 会把阈值封顶在窗口的 90%，推断已经关不掉。运行卡头部一直有上下文仪表；压缩时过程区显示"已压缩 85% → 20%"。bot 正忙时 `/compact` 等这一轮结束再压，压缩时来的消息排队。

### 3.6 个性、记忆、skill、MCP

**个性。** 注入顺序，越后越具体：
1. vonvon 固定的输出约定和隐私红线（今天的 `D/agent/bridge-instructions.ts:12-32`，加一句"不提别的群的内容"）。这一层改不掉。
2. 身份行：飞书名字、当前群名。
3. bot 的 `SOUL.md` 和 `AGENTS.md`。
4. 群的 `SOUL.md`。
5. 记忆。

**记忆。** 按"谁能看到来源"分三份。

| 记忆 | 在哪里用 | 谁能写 |
|---|---|---|
| 本群记忆 | 只在这个群 | 群里能用 bot 的人：说"记住"，或 bot 自己判断要记。主人和管理员能看、改、删 |
| 公共记忆 | 所有群和私聊 | 只有主人和管理员，在桌面端或聊天里 |
| 私聊记忆 | 只在这个人的私聊里 | 这个人的私聊会话 |

- A 群的记忆永远不会出现在 B 群。同一个群里几个 bot 各有一份本群记忆，不共享。
- 写入在卡片上显示"已记到本群记忆：…［撤销］"。第一版不做后台自动整理。
- 记忆在会话开始或恢复时放进去，标成"背景资料，不是指令"。中途写的，下一条会话才生效。每份有字数上限，满了让 bot 先整理，不悄悄截断。
- 关掉两家自带的记忆：Claude 的 auto memory 按 git 仓库共享，两个群用同一个仓库就会串；Codex 的 memories 是全局整合的。
- 主人本机的个人指令（`~/.claude/CLAUDE.md`、`~/.codex/AGENTS.md`）和个人 skill：从 bridge 导入的 bot 默认带上，行为不变；新建的 bot 默认不带。

**skill 和 MCP。**
- 本机各有一个库，装一次，bot 和群各有名单。从名单移除不删库；从库里删除时，列出还在用它的 bot。
- skill 的来源：内置、本机文件夹、从 `~/.agents/skills`、`~/.codex/skills`、`~/.claude/skills` 导入。格式按 Agent Skills 标准（agentskills.io/specification）。
- MCP 的来源：从本机 Codex、Claude 的配置导入，或在桌面端填命令或网址。
- 都不从 git 地址装，不自动更新。
- 只有主人和管理员能装和启用。含脚本的 skill 和所有 MCP 都会在主人的 Mac 上跑程序，装之前要授权，见 3.8。
- 内置两个 vonvon skill，每个会话都预装：设置 skill（3.7）和飞书 skill（3.5）。

**怎么交给 Codex 和 Claude。** 两家都有会话级的参数，不改用户的全局配置，不换 `CODEX_HOME` 和 `CLAUDE_CONFIG_DIR`（换了要重新登录，旧会话也续不上）。

| 项 | Codex（app-server） | Claude（Agent SDK） |
|---|---|---|
| 个性和约定 | `thread/start` 的 `developerInstructions`，今天已在用（`D/agent/codex-appserver/backend.ts:675`） | `systemPrompt.append`，今天已在用（`D/agent/claude-agent/thread.ts:267-268`） |
| 主工作区 | `cwd` | `cwd` |
| 其余工作区和仓库 | `runtimeWorkspaceRoots`（实验字段）加逐路径的读写权限 | `additionalDirectories` 加沙箱的根列表 |

### 3.7 在聊天里改设置

主人和管理员可以直接跟 bot 说"以后在这个群里说话活泼点"、"给这个群加上 X skill"、"建一个发布群，把张三拉进来"。私聊和群里都能说。

**做法**：
1. 扩展已有的 `vonvon` 命令行（`packages/daemon/package.json` 的 `bin`，现在注册了 `daemon`、`open`、`service` 等子命令，`D/cli/index.ts:20-55`），加上设置和飞书两组子命令。命令行也能在终端里直接用。
2. 每个会话预装 vonvon 设置 skill，告诉 agent 怎么用这些命令。

**能改什么**：只限这个 bot 自己的事。

| 能改 | 不能改 |
|---|---|
| 个性、规矩、智能提示词；记忆；skill 和 MCP 的启用名单；仓库和工作区；模式和回复方式；建群、拉人进群 | 建新 bot、改别的 bot；填 API key（只在桌面端填，聊天里不收 key）；vonvon 的全局设置 |

- 在群里只能改这个群的设置。bot 的默认设置和别的群的设置，在私聊里改。群里别人也看得见回复；改 bot 默认会影响所有群，别的群的设置也不该出现在这个群里。
- 谁能改由 daemon 判断，不由 agent 判断。daemon 知道这一轮是谁的消息触发的，只有主人和管理员触发的那一轮能改设置；别人让 bot 改，命令直接被拒，bot 回一句"只有管理员能改"。这样群里有人冒充"我是管理员"也没用。
- 改完在卡片上显示改了什么，带［撤销］。
- 建群和拉人：bot 可以自己建一个新群，再把人拉进来。飞书里机器人自己进不了一个已有的群，要群里有人拉它（要核实），所以对已有的群，bot 把拉它进群的步骤发给你。

### 3.8 卡片

owner 问过：确认卡、选项卡、授权卡是不是默认的会话功能？是的。下面这些所有会话默认就有，不只在私聊。授权卡也默认就有，但只在几种设置上出现：

- **运行卡**：流式输出、⏹ 停止、工具折叠、上下文仪表、子 agent 区（见 3.9）。
- **选项卡**：agent 问一个带选项的问题时（Claude 的 AskUserQuestion，Codex 的提问），发一张选项卡，点了就把答案送回去。咖啡一下已经有这种卡片（`D/cli-bridge/cards.ts:283`），会话里复用。
- **授权卡**：只用在会在主人的 Mac 上跑程序或打开文件访问的设置上，也就是装 MCP、装含脚本的 skill、加仓库或工作区、改权限档和网络开关。卡片写清要装什么、在哪个目录、会跑什么命令，只有发起的那个主人或管理员能点。原因：agent 读到的文档或网页里可能藏着"去装这个 MCP"之类的指令，授权卡让人在生效前看一眼。其他设置直接生效，带撤销。owner 说过"有了命令行也就没什么确认卡了"；只保留这一种授权卡是 Claude 的决定，owner 可以在 PR 里否掉。
- agent 自己的工具调用不弹审批：和 bridge 一样，会话的审批策略是 `never`，能做什么由权限档和沙箱决定（`docs/research/2026-10-14-v1-definition/bridge-inventory.md` 1.4）。

### 3.9 子 agent

- 子 agent 显示在父运行卡的"子 agent 区"，一行一个：状态、名字、在做什么、几步、用了多久，嵌套的缩进。点开看最近 5 步和结果。每行有"停止"，运行卡的 ⏹ 全停。不给每个子 agent 发一张卡：飞书对群里所有 bot 有每秒 5 条的共用限额。
- **一张运行卡包含这一轮的所有子 agent，子 agent 都跑完了，这张卡才算结束。**
  - Codex：本来就是这样。文档原文是"Codex waits until all requested results are available, then returns a consolidated response"（learn.chatgpt.com/docs/agent-configuration/subagents）。
  - Claude：不一样。Claude Code 的子 agent 默认在后台跑，经 Agent SDK 用时也是；主回合可以先结束，子 agent 跑完再通知 Claude 起新的一轮（code.claude.com/docs/en/sub-agents）。设置 `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` 后，子 agent 一律在前台跑，主回合会等它们。代价是它同时关掉后台 Bash 等所有后台任务，比如 bot 不能在后台起一个开发服务器再结束这一轮。第一版打算在 bot 的会话里打开这个开关，两家行为就一致了。这是 Claude 的决定，等第 9 节第 1 项实测后再定。不打开或者不生效时，运行卡在主回答发出后保持打开，写"已回复，还有 N 个在跑"，子 agent 完成后 Claude 接着的那一轮写进同一张卡。
- 子 agent 跑的时候，群里的新消息按今天的规则插话或排队，只给父 agent。第一版不能直接跟某个子 agent 说话。
- 今天 Codex 的子线程事件全丢了，Claude 子 agent 的步骤混进了主过程（`D/agent/codex-appserver/backend.ts:333-337`；`D/agent/claude-agent/event-map.ts:92-123`），第一版要修。

### 3.10 后台服务和崩溃

- bot 跑在一个后台服务里，登录电脑后自动启动，不用开着桌面应用。
- 崩溃了自动重启。重启以后，桌面端和主人的私聊里各说一次"刚才崩溃过一次，原因是……"。短时间内连续崩溃（比如 10 分钟内 3 次）就不再重启，只在桌面端显示错误和诊断信息，免得不停重启刷屏。owner 说过"崩溃报错就好了"，让 Claude 斟酌；自动重启是 Claude 加的：后台服务崩了，群里的人只会看到 bot 不回，主人不一定在电脑前；如果 `agentService` 能带 KeepAlive，自动重启几乎不用多写代码。
- 实现先试 Electron 自带的方式：macOS 13 以上用 `app.setLoginItemSettings` 的 `type: 'agentService'`，注册应用里自带的 LaunchAgent，带 KeepAlive。用户要在"系统设置 → 通用 → 登录项"里允许一次。这条要在 Mac 上核实，不行再改用 V5 的 launchd 服务线（#285 那条启动路由）。

1. dmg 签名并公证，更新源可用。要 Apple 开发者的公证凭据，以及一个公开的下载和更新地址。
2. Claude 的登录：第一版复用用户本机的 Claude 登录。Agent SDK 的文档写着"Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products"（code.claude.com/docs/en/agent-sdk/overview）；另一份帮助文档又说 Agent SDK 和第三方应用照样可以用订阅额度（`docs/research/2026-10-14-strategy/agent-integrations.md:119`）。两份说法不一致，所以公开发布前向 Anthropic 要书面确认。拿不到确认，公开版里 Claude 改成只支持 API key。开发和自用不受影响。问答第 17 题问的就是这件事，不是测试时用什么账号。
3. daemon 的 `package.json` 写着 MIT，发布前改掉。安装包带上 bridge（MIT）和 Paseo（Apache-2.0，NOTICE）的许可声明。第一版闭源。
4. bridge 的最后一版发出（第 5 节）。
5. 在一台没有 bridge 的 Mac 上，从零安装、扫码、开权限，第一次对话走通。
