## 1. 一句话

Vonvon Bot 是一个 macOS 桌面应用；Linux 上可以只装后台服务，用命令行和网页管理（3.10）。主人在自己的 Mac 上养几个飞书机器人，每个 bot 有自己的个性、记忆、工作区、代码仓库、skill 和 MCP，能进不同的群，在每个群里表现不同。干活用主人本机已经登录的 Codex 或 Claude。

和 feishu-codex-bridge 最大的区别：bridge 的行为大多靠规则设定，Vonvon Bot 主推**智能模式**。bot 自己判断要不要接话、要不要开新话题、要不要和别的 bot 搭话。主人可以直接跟 bot 聊天来改它的设置、让它建群。bridge 原来的规则保留为**规则模式**。

给谁用：
1. 正在用 feishu-codex-bridge 的 Mac 用户。迁过来后，群、话题、卡片、命令和旧会话都保留。
2. 有 Codex 或 Claude 订阅、想在飞书群里有一个"像同事"的 bot 的个人和小团队。他们不一定用 GitHub，也不一定会装 Node。

不给谁用：Windows 用户；想在 Linux 上用桌面应用的人，Linux 只有命令行版；没有 Codex 或 Claude 订阅的人；想要云端托管、不开电脑也能用的人。

## 2. 叫法

| 叫法 | 意思 |
|---|---|
| bot | 一个飞书机器人（一个飞书应用）。名字、头像、简介以飞书为准 |
| 主人、管理员 | 能管这个 bot 的人，见第 6 节。两者能做的事一样 |
| 群主区 | 群里不在任何话题里的地方 |
| 话题 | 飞书话题，包括话题群里的帖子 |
| 会话 | 后台的一条 Codex 线程或 Claude 会话。bot 记得的对话内容都在这里 |
| 子 agent | 一个会话临时分出去、并行干活的帮手，干完就结束 |
| 智能模式 | 群设置。bot 自己判断接不接话、开不开话题、和不和别的 bot 搭话 |
| 规则模式 | 群设置。bridge 原来的规则：仅 @ 或全部回复；主区"开话题"或"连续" |
| 工作区 | bot 产出文件的目录，可写。主工作区是会话的工作目录 |
| 代码仓库 | 本机的一个 git 目录。和工作区一样传给 agent，区别在界面和指令 |
| skill、MCP | 给 agent 用的技能包和工具服务。本机各有一个库，bot 和群各有名单 |

产品文案里叫"Claude"，不叫"Claude Code"，这是 Anthropic 的品牌规定（code.claude.com/docs/en/agent-sdk/overview）。

## 3. 第一版做什么

### 3.1 桌面端

1. 桌面应用就是控制台，不再引导用户开网页。同一套页面也能用本机浏览器打开，但只在本机：daemon 只监听 `127.0.0.1`（`D/server/http.ts:184`），第一版不开放局域网和远程访问。
2. 签名加公证的 dmg，带更新源。现在更新源是空的（`packages/desktop/src/updates.ts:46`）。出 universal 包，Intel Mac 也能装。
3. 后台服务：bot 跑在后台服务里，登录电脑后自动启动。Mac 设成自动登录时，就等于开机启动。后台服务由 daemon 自己装，不依赖桌面应用，崩溃后自动重启，见 3.10。
4. 首次运行是一张清单，每一步都实时检测：扫码建飞书应用 → 一键开权限 → 检测事件订阅 → 检测应用已发布 → 检测 Codex 或 Claude 已安装、已登录、版本够用 → 登录电脑时自动运行 bot（推荐，3.10）→ 可选从 bridge 导入。v2 里还没有人从头扫码成功过（`docs/research/2026-10-14-strategy/runnable.md` 第 1 节），这一条第一版必须走通。
5. 建新 bot 只在桌面端做，走上面的向导，不在聊天里做。
6. Bot 页：个性、规矩、工作区、代码仓库、skill、MCP、记忆、智能提示词、所在的群。
7. 群详情页：这个 bot 在这个群里的模式（智能或规则）和各项覆盖，见 3.2。
8. 状态与诊断页：每个 bot 的连接状态，Codex 和 Claude 的版本检查，最近没回的消息和原因（包括智能模式判断"不回"的原因）。用量页显示判断调用的次数。
9. 没有 Windows，也没有 Linux 桌面。Linux 上只装后台服务，见 3.10。

### 3.2 bot 模型

一个 bot 有三层：
1. **飞书身份**：名字、头像、简介，来自飞书应用，vonvon 不改。飞书能不能让同一个机器人在不同的群里显示不同的名字：没查到，所以"千人千面"体现在说话方式、工作区、仓库、skill 和记忆上，外观不变。
2. **bot 默认**：个性、规矩、工作区、仓库、skill、MCP、公共记忆、智能提示词。
3. **群内覆盖**：这个 bot 在某个群里另外的设置，以及这个群自己的记忆。没设的项继承 bot 默认。

| 项 | bot 默认 | 群内 | 规则 |
|---|---|---|---|
| 名字、头像 | 来自飞书 | 不能改 | — |
| 个性 `SOUL.md` | 有 | 可补充 | 群的默认加在 bot 后面，也可以选择整段替换 |
| 规矩 `AGENTS.md` | 有，可选 | 不能改 | 只在 bot 层 |
| 工作区 | n 个，1 个主的 | 可覆盖 | 群没设时，在默认位置给这个群建一个目录，见 3.3 |
| 代码仓库 | 0 到 n 个 | 可覆盖 | 只接本机已有的 git 目录，不接 git 地址 |
| skill | 启用名单 | 可增、可减 | 实际生效 =（bot 启用 ∪ 群增加）− 群移除 |
| MCP | 启用名单 | 可增、可减 | 同 skill |
| 记忆 | 公共记忆，所有群都看 | 本群记忆，只在本群看 | 见 3.6 |
| 智能提示词 | 有，带内置默认值 | 可覆盖 | 只在智能模式下用 |
| 模式 | 无 | 智能或规则 | 只在群层，见 3.4 |
| 权限档、超出权限时、访客档 | 默认值 | 可覆盖 | 见 3.8 |
| 网络、后端、模型 | 默认值 | 可覆盖 | 和今天一样 |

### 3.3 磁盘上的位置

```
~/.vonvon-bot/
  skills/                       本机 skill 库
  mcp/                          本机 MCP 库
  projects/<bot 名>/            bot 主工作区的默认位置
    groups/<群名>/              群没设工作区时的默认目录
  bots/<appId>/
    config.json                 bot 设置，含工作区、仓库
    projects.json               每个群一条，含群的覆盖
    SOUL.md                     bot 个性
    AGENTS.md                   规矩，可选
    SMART.md                    智能提示词，不存在时用内置默认值
    skills.json  mcp.json       启用名单
    memory/shared.md            公共记忆
    memory/dm/<open_id>.md      每个主人或管理员的私聊记忆
    groups/<chatId>/
      SOUL.md                   本群个性补充
      SMART.md                  本群智能提示词覆盖
      skills.json  mcp.json     {"add": [...], "remove": [...]}
      memory/group.md           本群记忆
```

- 工作区默认放在隐藏目录 `~/.vonvon-bot/projects/` 下，和今天一样（`D/config/paths.ts:115`），可以在桌面端改到别处。比今天多一层 `<bot 名>/`：今天所有 bot 共用这个目录，两个 bot 的同名项目会落进同一个目录（推断，`docs/research/2026-10-14-v1-definition/v2-fit.md` 第 8 节第 6 条）。
- 每个群默认有自己的目录。共用一个目录的话，B 群的会话能看到 A 群产生的文件，和"每个群的记忆分开"矛盾。
- 目录名按建立时的名字取，之后不跟着改名，重名时加一个短后缀，"/"等字符替换掉。
- 定义文件都是 markdown 和 json，主人可以直接用编辑器改。它们不进用户的代码仓库。仓库里的 `AGENTS.md`、`CLAUDE.md` 照旧由 agent 自己读。

### 3.4 群：智能模式和规则模式

每个群对每个 bot 有一个开关：智能模式或规则模式。

**智能模式**一起管三件事：
1. 要不要接话。
2. 群主区来了一件新事，要不要开一个新话题来回。
3. 要不要和别的 bot 搭话。

**规则模式**就是 bridge 原来的设置：回复方式选"仅 @"或"全部回复"，群主区选"开话题"或"连续"。规则模式下 bot 之间互相看不到，和今天一样。

**默认值：**
- 新建的 bot、新进的群默认智能模式。bot 进群时在群里说一句"我会读群消息，合适时接话"。
- 从 bridge 迁来的群用规则模式，沿用各群原来的回复方式和主区方式，不换算。bridge 今天的默认是免 @ 开，只有被拉进来的"连续"群默认关（`D/project/registry.ts:83-85`）。
- 主区方式切换后，回复方式不自动变，界面提示一句。

**三条底线**，两种模式共用。先回答"这条消息是对谁说的"，再轮到模式：
1. **点名**：@ 了谁、引用了谁的消息，就只有谁回。@ 了别人、@所有人、引用别人的消息，其他 bot 都不回。@ 两个 bot 就两个都回。例外：规则模式的"仅 @"里，引用我的消息不算点名，和 bridge 一致。话题里飞书只给话题第一条的 id（`root_id`、`parent_id` 都是它），分不出引用的是哪一条，所以话题里的点名只看 @（要实测）。
2. **接着聊**：话题里没点名的消息，归最近在这个话题里说过话的 bot。别的 bot 开的话题，我不插嘴。
3. **bot 消息**：别的 bot 发的消息，只有 @ 我才算。

这三条顺带修掉今天多 bot 群里的三个毛病：开了免 @ 的 bot 会进别的 bot 的话题；主区不带 @ 的 `/help` 每个 bot 都回；连续群里每个免 @ 的 bot 都回每条（推断，`docs/research/2026-10-14-v1-definition/group-response.md` 结论 3）。

**智能模式怎么判断。** 底线定不下来时，调一次判断模型，结果三选一：不回、在主区接着聊、开新话题回。在话题里只判断回不回，不再拆话题。
- 判断模型自动选。主人在桌面端填了 OpenAI（Decisions API）、TypeSafe（Jev）或 OpenRouter 的 key，就用它；没填，就用这个 bot 那家订阅里的小模型，关掉思考，一次不带工具的调用。资料见 `docs/research/2026-10-14-decision-models/decision-models.md`。
- 判断出错或超时就不回。被 @ 的消息一定回：在话题里直接回；在主区要调一次判断，只决定回在主区还是开新话题，出错或超时就在主区回（3.5）。
- 只回"回"或"不回"，不做"只回一个表情"。"不回"的原因只记在本机诊断页，不发到群里。
- 判断用的提示词就是智能提示词：内置默认值，主人可以在 bot 层改，群里可以覆盖。
- 控制成本：只对允许使用 bot 的真人消息调；同一台机器上一条消息只调一次，本机几个智能 bot 合成一次"选谁回"；话题里只有一个真人在和我聊时直接回；每个群每小时有上限。延迟和每次占多少额度要在 Mac 上量。

**bot 之间。** 智能模式下，别的 bot @ 我时我能收到（要新开一个可选权限，见 3.11），这样能做"小码写、小审查"。B 看到的 A 的消息只有 A 的最终回答，标成"A（bot）"，截到几百字。没有真人插话时，bot 之间最多来回 3 轮，到了就停下并提示一次；真人说一句就清零。不收别的 bot 的全部消息。

**几个 bot 都会回的时候。** 同一台机器上，daemon 只放行一个：优先最近在这里说过话的 bot，都没说过就选最早进群的。不同机器上的 bot 没法协调，可能都回，第一版接受。界面提示："不同电脑上的 bot 可能抢着回。"

**一个例子。** 真人张三、李四。三个 bot 在同一台 Mac 上：小码（Codex，规则模式，全部回复，主区"开话题"），小P（Claude，智能模式，管产品），小审（Claude，智能模式，管审查）。

| # | 消息 | 小码 | 小P | 小审 | 判断调用 |
|---|---|---|---|---|---|
| 1 | 张三在主区："@小码 登录接口为什么 500？" | 回，开话题 T1 | 不回，点名了别人 | 不回，点名了别人 | 0 |
| 2 | 李四在 T1，没 @："是不是昨天改了 token？" | 回，T1 归它 | 不回 | 不回 | 0 |
| 3 | 张三在主区，没 @："下周发布要不要先砍掉导出功能？" | 不回，"开话题"的主区要 @ | 判断：开新话题回，开 T2 | 判断：不回 | 1（两个智能 bot 合成一次） |
| 4 | 李四在主区："今天食堂的红烧肉不错" | 不回 | 判断：不回 | 判断：不回 | 1 |
| 5 | 小P 在 T2："@小审 帮我看下这个方案" | — | — | 回（bot 互 @）；bot 回合 +1 | 0 |
| 6 | "@所有人 明天十点开会" | 不回 | 不回 | 不回 | 0 |
| 7 | 李四在 T2 引用小P 的回答："优先级再排一下" | 不回 | 回，引用就是点名 | 不回 | 0 |

第 5 行要两个 bot 都在智能模式。小P 要是 @ 小码，小码收不到，和今天一样。

### 3.5 会话和上下文

owner 说这一块很关键：飞书里的位置怎么对应 agent 的会话，上下文是什么关系，哪些要存进会话历史。下面依次回答，再用一个群的时间线走一遍。今天的代码和这里不一样的地方，列在本节末尾。调研见 `docs/research/2026-10-14-session-approval-service/session-map.md`。

**一个飞书位置对应一条会话。** 每个 bot 各有各的会话。下表说的是一个 bot 在一个位置上。

| 飞书里的位置 | 智能模式 | 规则模式"连续" | 规则模式"开话题" | 什么时候建 |
|---|---|---|---|---|
| 群主区 | 一条会话，一直接着聊 | 一条会话 | 不留会话，@ bot 就开一个话题 | 这个 bot 第一次在主区回复时 |
| 话题，不管是谁开的，包括话题群里的帖子 | 一条会话 | 一条会话 | 一条会话 | 这个 bot 第一次在这个话题里回复时 |
| 私聊 | 每个人一条会话 | 同左 | 同左 | 第一次私聊时 |
| 私聊里的话题 | 单独一条会话，和群里一样（要实测） | 同左 | 同左 | 第一次在这个话题里回复时 |
| 云文档评论 | 每篇文档一条，和今天一样 | 同左 | 同左 | 和今天一样 |

- 会话就是一条普通的 Codex 线程或 Claude 会话。主人在 Codex 应用里或用 `claude --resume` 打开它，看到的和 bot 看到的一样（推断，要实测）。
- 不在同一个位置里悄悄换会话。只有 `/new`、`/clear`、`/resume` 会换，见下面的"命令"。
- 话题群和话题形式群里没有主区对话，每个帖子就是一个话题，也就是一条会话，不判断要不要开话题。
- 子 agent 代替不了新会话：它的结果会回到父会话里，干完就结束，事后没法接着问它。它的用途是把一件事拆开并行做。
- 权限档和今天一样：群里设了不同的访客档时，访客跑在另一条会话上（`D/project/registry.ts:115` 的 `turnTier`）。这样主区和每个话题都可能有两条会话，水位、引用行各算各的。

**主区和话题是什么关系。**
- 主区会话和话题会话互不复制历史。
- 话题开出来时，不管是用户开的，还是 bot 判断后开的，主区会话里只留一行引用：谁、几点、在哪条消息下开了话题、话题的标题、话题 id。引用行由 daemon 生成，不带话题里的内容，用户也伪造不出来。
- 引用行在主区会话下一次开口时，和别的新消息按时间一起写进对话记录块。不在话题一开就单独写进主区会话：Codex 那种写法（`thread/inject_items`）在 Codex 应用里看不到，Claude 那种写法（`shouldQuery: false`）Codex 没有，而且为了一行字要拉起一个会话进程。主区会话在开口之前也用不着知道。
- 不在群主区另发一条带链接的消息。飞书新版客户端会把话题回复直接显示在那条消息下面，主区的人本来就看得到。
- 话题会话开场带四样：一行回指（"这个话题开在主区 10:01 张三的消息下，主区更早的内容用 vonvon 飞书 skill 查"）、主区在话题第一条消息之前的最近 10 条、话题第一条消息、话题里已有的消息。
- 之后两边要看对方的内容，都用 vonvon 飞书 skill 去查（见下面的"查飞书上下文"）。查到的内容作为工具结果进 bot 自己的会话。
- 主区会话压缩以后，引用行可能被摘要掉。所以压缩后主区下一次开口时，附一张"本群最近 5 个活跃话题"的短表；skill 也能列出本群所有话题。

**哪些存进会话历史。** 只存 bot 真正开始回复时读到的东西，一共四类：
1. 会话开始时的个性和记忆。
2. 每次回复前，这个位置自上次以来的新消息，合成一个对话记录块。真人的话带真名，包括智能模式判了"不回"的消息；别的 bot 只放最终回答，标成"某某（bot）"，截到几百字。主区的记录块里还有新开话题的引用行。
3. 触发这次回复的消息、它引用的消息、附件路径、语音转写。
4. bot 自己的回答、工具步骤和子 agent 的结果，由 Codex 和 Claude 原生记录。

不存的：
- 别的话题、别的群、私聊的内容。
- 主区会话里不放话题里的回复，包括这个 bot 自己在话题里说的话。
- 话题会话里不放话题开出来以后主区的消息。话题第一条只在开场放一次，之后每轮不再重复。
- 别的 bot 的过程和子 agent。

**个性。** 注入顺序，越后越具体：

2. 身份行：飞书名字、当前群名。
3. bot 的 `SOUL.md` 和 `AGENTS.md`。
4. 群的 `SOUL.md`。
5. 记忆。

**记忆。** 按"谁能看到来源"分三份。

| 记忆 | 在哪里用 | 谁能写 |

| 本群记忆 | 只在这个群 | 群里能用 bot 的人：说"记住"，或 bot 自己判断要记。主人和管理员能看、改、删 |

- A 群的记忆永远不会出现在 B 群。同一个群里几个 bot 各有一份本群记忆，不共享。

### 3.7 在聊天里改设置

主人和管理员可以直接跟 bot 说"以后在这个群里说话活泼点"、"给这个群加上 X skill"、"建一个发布群，把张三拉进来"。私聊和群里都能说。

**做法**：
1. 扩展已有的 `vonvon` 命令行（`packages/daemon/package.json` 的 `bin`，现在注册了 `daemon`、`open`、`service` 等子命令，`D/cli/index.ts:20-55`），加上设置和飞书两组子命令。命令行也能在终端里直接用。
2. 每个会话预装 vonvon 设置 skill，告诉 agent 怎么用这些命令。

**能改什么**：只限这个 bot 自己的事。

| 能改 | 不能改 |
|---|---|
| 个性、规矩、智能提示词；记忆；skill 和 MCP 的启用名单；仓库和工作区；模式和回复方式；建群、拉人进群 | 建新 bot、改别的 bot；填 API key（只在桌面端填，聊天里不收 key）；vonvon 的全局设置 |

- 在群里只能改这个群的设置。bot 的默认设置和别的群的设置，在私聊里改。群里别人也看得见回复；改 bot 默认会影响所有群，别的群的设置也不该出现在这个群里。

- 改完在卡片上显示改了什么，带［撤销］。
- 建群和拉人：bot 可以自己建一个新群，再把人拉进来。飞书里机器人自己进不了一个已有的群，要群里有人拉它（要核实），所以对已有的群，bot 把拉它进群的步骤发给你。

### 3.8 卡片和授权

owner 的话："确认卡、选项卡、授权卡这些需要用户交互、用户确认的体验，要和 Agent 里面的一种授权一致，就是那种需要用户确认的授权体验。这种用户应该也可以设置吧？它也可以设置成完全访问，也就是用户不需要确认任何事情。"

所以授权跟着 agent 自己的审批走。用户选一个权限档，vonvon 把它换成 Codex 和 Claude 原生的审批设置。什么时候问由 agent 自己决定，vonvon 不加自己的规则，也不替 agent 少问。vonvon 只把 agent 的"问"变成飞书卡片，再把点击送回去。完全访问就是从不问。调研见 `docs/research/2026-10-14-session-approval-service/approval-ux.md`。

今天两边都不问。Codex 写死了 `approvalPolicy: 'never'`（`D/agent/codex-appserver/backend.ts:30`），Codex 发来的请求一律回报错（`D/provider/transport/jsonrpc.ts:197-206`），连它在计划模式下的提问都收不到。Claude 三档都用 `bypassPermissions`，没有 `canUseTool`（`D/agent/claude-agent/permission.ts:56`、`:73`），所以 Claude 的 AskUserQuestion 今天会被拒（推断）。

- 超出权限时：问我（发授权卡）/ 直接拒绝。只在只读和读写下有。

| 只读 · 问我 | `on-request` + 今天的只读沙箱 | `default` 模式 + 今天的只读沙箱，`canUseTool` 发卡 |
| 只读 · 直接拒绝 | `never` + 只读沙箱，就是今天的行为 | `default` 模式 + 同样的沙箱，`canUseTool` 一律拒绝并说明原因 |
| 读写 · 问我 | `on-request` + 今天的读写沙箱，约等于 Codex 的默认预设 | `acceptEdits` + 今天的读写沙箱，`canUseTool` 发卡 |
| 读写 · 直接拒绝 | `never` + 读写沙箱，就是今天的行为 | `acceptEdits` + 同样的沙箱，`canUseTool` 一律拒绝 |
| 完全访问 | `never` + `danger-full-access`，就是今天的行为 | `bypassPermissions`，就是今天的行为 |

- Claude 的"直接拒绝"不再用 `bypassPermissions`。今天只读、读写两档用它，推断有两个缺口：关网时 Bash 可能仍能连外网，Edit 和 Write 可能写到工作目录外（`approval-ux.md` 3.3）。换成上表正好补上，要实测。
- 中途改档不用重开会话：Codex 每一轮的 `turn/start` 能带新的审批设置，Claude 运行中能 `setPermissionMode`（推断）。
- Linux 上 Codex 的只读、读写档今天直接拒绝启动（`D/agent/codex-appserver/backend.ts:78-82`），所以 Linux 上的 Codex 只能用完全访问，界面写明。

**完全访问下还会问什么。** 授权卡一张都不发。但 agent 问你问题时，选项卡照样发，因为那是在问你的意见，不是要权限。Claude 自己在完全访问下也会停下来问的少数几类，比如用户在自己的 Claude 设置里写了"这类操作必须问"、删除关键目录，照样发卡，和 Claude 自己的行为一致（`approval-ux.md` 2.2）。

**卡片。** 所有要人点的卡片一个样：同样的版面、同样的状态、同样的"谁能点"规则。所有会话默认就有，不只在私聊。
- **运行卡**：流式输出、⏹ 停止、工具折叠、上下文仪表、子 agent 区（见 3.9）。等人确认时显示"⏸ 等待 李四 确认（见下方卡片）"。
- **授权卡**：agent 要越出权限档时，比如跑命令、改文件、联网、用 MCP 工具、申请更多权限；以及下面"设置类授权"里的几种设置。
- **选项卡**：agent 问一个带选项的问题时（Claude 的 AskUserQuestion，Codex 的提问，简单的 MCP 表单）。咖啡一下已经有这种卡片（`D/cli-bridge/cards.ts:283`），会话里复用；空提交时提示"至少选一项"。
- **确认卡**：只要"是 / 否"的确认，比如 Claude 的计划（ExitPlanMode）。按钮是［按这个方案做］［不行，我来说］。

授权卡的样子：

```
需要确认：运行命令                          [读写 · 问我]
张三 的这一轮，等 @李四 或其他管理员确认
命令      npm publish --tag next
目录      ~/work/app（工作区内）
原因      Codex：发布需要联网
如果拒绝  这条命令不会运行，agent 会换个办法或停下来问你
不处理    15 分钟后按拒绝处理

[允许这一次]  [本会话不再问这条命令]  [拒绝]
回复这张卡片 = 拒绝，并把你的话告诉 agent
```

- 卡片写清后果：点允许会怎样，点拒绝会怎样，不点会怎样。今天咖啡一下的卡片，社区群里有人看不懂按钮是干什么的（`approval-ux.md` 第 5 节）。
- 三个按钮：允许这一次、本会话不再问、拒绝。"本会话不再问"后面写清是哪一类：这条命令、这个主机、这些文件。"本会话"就是这个飞书位置的这条会话，`/new` 以后重算，每个话题各算各的。不给"以后都允许"，因为它会改写用户自己的 Codex 规则或 Claude 设置。
- 回复这张卡片，等于拒绝并附上说明。能点的人在同一个位置直接发新消息，也算拒绝并附上这句话。运行卡上的 ⏹，等于拒绝并停止这一轮。
- 点完以后按钮去掉，换成一行结果，比如"✅ 李四 允许了（仅这一次）10:03"、"⛔ 李四 拒绝了"、"⏱ 超时未确认，已按拒绝处理"、"⏹ 已停止"、"已失效（后台服务重启过）"。每种结局都改卡，不让按钮一直挂着。今天咖啡一下超时后按钮还在（`D/cli-bridge/service.ts:391-399`）。
- 每张卡单独发一条消息，回复触发这一轮的那条消息，在话题里就发在话题里；卡片里 @ 能点的人。不把按钮放进运行卡，因为运行卡在流式更新，按钮会和输出抢。卡片里的 @ 会不会提醒人要实测，不会就另发一条带 @ 的文字。

**谁能点。** 由 daemon 按点击人的 open_id 判断，不由 agent 判断。daemon 还要核对这张卡属于这个群和这条会话，转发出去的卡点了无效。

| 卡片 | 能点的人 |
|---|---|
| 越权的授权卡 | 主人和管理员。发起人不是管理员时，卡片 @ 主人和群里的管理员 |
| 设置类授权卡 | 发起的那个主人或管理员 |
| 选项卡、确认卡 | 发起人，管理员也能代答 |
| 访客那一轮的越权 | 默认没人，直接拒绝；访客档设成"问我"时，主人和管理员 |
| bot 触发的那一轮（bot 之间对话） | 主人和管理员 |
| 云文档评论的会话 | 没地方放卡片，超出权限一律拒绝 |

- 普通成员的越权也只有主人和管理员能批：权限档是主人给群里成员定的上限，越过上限只有主人和管理员能决定。
- 点的人不对时，回贴一条去重的小注"只有管理员能确认这一步"，和今天 ⏹ 的做法一样（`D/bot/handle-message.ts:2384-2397`）。第一次有效的点击生效。

**等待和超时。**
- 没人点，15 分钟后按拒绝处理。两家 agent 自己都没有等待上限，所以由 vonvon 定。选项卡超时，就告诉 agent"用户没有回答"。
- 等人确认时，空闲看门狗暂停，不然这一轮会被当成"没输出"杀掉。
- 同一条会话同时只显示一张待确认的卡。Codex 并行跑工具时可能一次来几个，其余排队，卡上写"后面还有 2 个"。
- 后台服务重启后，挂着的请求就没了。点到旧卡时，卡片自愈成"已失效（后台服务重启过）"，和今天的 `healDeadRunCard` 一样（`D/bot/handle-message.ts:2398`）。
- 子 agent 发起的审批，发在父运行卡所在的位置，卡上写"子 agent X 想运行……"。
- 要填密码这类敏感信息的问题，不在群里显示输入框，请用户去私聊回答。

**设置类授权。** 在聊天里改这几种设置时发授权卡：装 MCP、装含脚本的 skill、加仓库或工作区、改权限档和网络开关、改"超出权限时"。卡片写清要装什么、在哪个目录、会跑什么命令。原因是 agent 读到的文档或网页里可能藏着"去装这个 MCP"之类的指令，授权卡让人在生效前看一眼。
- 这类授权跟着权限档走：完全访问下不发，直接生效，带撤销，因为这一档 agent 本来就能跑任何命令。
- "直接拒绝"只管 agent 的工具调用，不管设置类授权，不然这一档里就没法在聊天里装 MCP。
- 降档不用卡片，比如从读写改成只读、关掉网络。
- 其他设置直接生效，带撤销。

### 3.9 子 agent

- 子 agent 显示在父运行卡的"子 agent 区"，一行一个：状态、名字、在做什么、几步、用了多久，嵌套的缩进。点开看最近 5 步和结果。每行有"停止"，运行卡的 ⏹ 全停。不给每个子 agent 发一张卡：飞书对群里所有 bot 有每秒 5 条的共用限额。
- **一张运行卡包含这一轮的所有子 agent，子 agent 都跑完了，这张卡才算结束。**
  - Codex：本来就是这样。文档原文是"Codex waits until all requested results are available, then returns a consolidated response"（learn.chatgpt.com/docs/agent-configuration/subagents）。
  - Claude：不一样。Claude Code 的子 agent 默认在后台跑，经 Agent SDK 用时也是；主回合可以先结束，子 agent 跑完再通知 Claude 起新的一轮（code.claude.com/docs/en/sub-agents）。设置 `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` 后，子 agent 一律在前台跑，主回合会等它们。代价是它同时关掉后台 Bash 等所有后台任务，比如 bot 不能在后台起一个开发服务器再结束这一轮。第一版打算在 bot 的会话里打开这个开关，两家行为就一致了。这是 Claude 的决定，等第 9 节第 1 项实测后再定。不打开或者不生效时，运行卡在主回答发出后保持打开，写"已回复，还有 N 个在跑"，子 agent 完成后 Claude 接着的那一轮写进同一张卡。
- 子 agent 跑的时候，群里的新消息按今天的规则插话或排队，只给父 agent。第一版不能直接跟某个子 agent 说话。
- 今天 Codex 的子线程事件全丢了，Claude 子 agent 的步骤混进了主过程（`D/agent/codex-appserver/backend.ts:333-337`；`D/agent/claude-agent/event-map.ts:92-123`），第一版要修。

### 3.10 后台服务和崩溃

owner 的话："后台服务不要依赖 Electron，因为 Linux 上没有桌面端，它可能就装一个 Daemon 后台服务。"调研见 `docs/research/2026-10-14-session-approval-service/service.md`。

**后台服务由 daemon 自己装。**
- 用 `vonvon service install`、`uninstall`、`status` 注册、卸载和查看。桌面端只调用打包在里面的同一个命令行。不用 Electron 的 `agentService`，也不用 SMAppService：这两种都要求服务登记在 .app 名下，Linux 上没有对应的东西。
- macOS：用户级 LaunchAgent `com.vonvon.bot.daemon`，plist 写在 `~/Library/LaunchAgents/`（`D/service/identity.ts:33`）。用户登录后启动，能用钥匙串里的 Claude 登录和 Codex 的登录（推断，要实测）。Mac 设成自动登录时，就等于开机启动。
- Linux：systemd 用户服务 `vonvon-bot.service`。安装时检查 linger：没开就问一句，同意后执行 `loginctl enable-linger`。这样开机就启动，退出 SSH 以后 bot 也还在跑。
- 从 dmg 装的，服务用 app 里的 Electron 程序以 Node 模式运行（`ELECTRON_RUN_AS_NODE=1`），不用另带一份 Node；从 npm 装的，用用户自己的 `node`。这只是借 Electron 的 Node 来用，服务的生死由 launchd 管，桌面窗口开不开都一样。代价是 app 被删或挪走以后，服务就起不来了，所以桌面端提供"关闭登录时启动"，文档写清卸载步骤。
- 注册以后，系统的服务管理器是唯一拉起 daemon 的。`vonvon daemon start` 和桌面端都请它去启动，不自己再起一个。停止走 `vonvon daemon stop`：先排空，再正常退出，管理器就不会再拉起它。
- 退出桌面端不停 bot。首次运行清单里加一步"登录电脑时自动运行 bot（推荐）"。跳过的话，就像今天一样起一个分离的 daemon，并提示"这样崩溃后不会自动重启"。
- 这些代码大部分已经在 main 上，只是没接线：launchd 和 systemd 的安装事务（#271、#274）、服务定义（#246）、退出码（#276）。今天 `vonvon service install` 直接报错（`D/cli/commands/service.ts:5`）。

**崩溃了自动重启。** 服务管理器在 daemon 异常退出后重启它（plist 的 `KeepAlive`、unit 的 `Restart=on-failure`，`D/service/definitions.ts:81`、`:85`）。两边都不会在连环崩溃时自己停下来，所以上限由 daemon 自己判断：
- daemon 和每个 bot 的子进程都加全局的异常兜底：崩溃前在 `~/.vonvon-bot/crash/` 写一条记录（版本、哪个 bot、错误的第一行、运行了多久），再退出。被系统强制结束、没留下记录的，下次启动时补一条"被系统强制结束"。今天没有任何崩溃记录（`D/cli-bridge/ipc.ts:24-25`）。
- 10 分钟内崩溃 3 次，daemon 进入暂停：网页和桌面端照常能打开，显示原因；bot 不连飞书，不跑 agent。不自动恢复，等主人点"恢复运行"，或执行 `vonvon daemon restart`。下次登录或开机时重新计数。
- 某一个 bot 的子进程 10 分钟内崩溃 3 次，只暂停这一个 bot，别的照常。今天子进程会无限重试（`D/bot/supervisor.ts:115-131`）。

owner 说过"崩溃报错就好了"，让 Claude 斟酌。自动重启是 Claude 加的：后台服务崩了，群里的人只会看到 bot 不回，主人不一定在电脑前。

**怎么告诉主人。**
- 崩了一次、已经自动恢复：桌面端的诊断页记一条；bot 给它的主人发一条私聊"刚才崩溃过一次，已自动恢复。原因：……"。
- 连环崩溃、已经暂停：诊断页顶上一条红条，带"恢复运行"按钮；私聊"10 分钟内崩溃 3 次，已停止自动重启"。
- daemon 主进程崩溃时所有 bot 一起下线，只由最早加入的 bot 发这条私聊，列出受影响的 bot。每个 bot 每 10 分钟最多发一条。
- 私聊只写一行原因，不放调用栈和本机路径。第一版不上传崩溃信息。
- 私聊直接调发消息的接口，不靠长连接，所以暂停时也能发。机器人能不能给没开过会话的主人发私聊，要实测。
- Linux 上用 `vonvon daemon status` 看服务状态和最近的崩溃。

**Linux 上只装后台服务。** Linux 没有桌面端，第一版做一个命令行版：
1. `npm i -g vonvon-bot`，或者装下载的安装包。
2. 在终端里登录 Codex 或 Claude：`codex login --device-auth`，或者在 `claude` 里 `/login`。
3. 执行 `vonvon service install`。它装 systemd 用户服务，处理 linger，最后打印打开网页的办法。
4. 在自己的电脑上执行打印出来的 `ssh -L …`，打开网页，走首次运行清单。网页和桌面端是同一套页面，daemon 仍然只监听 `127.0.0.1`。
5. 连 SSH 转发都用不了时，终端里也能扫码建 bot。

要补的：
- `vonvon open --print`：打印链接、端口和一行 `ssh -L` 示例，并提醒链接里带着凭据，别贴给别人。今天没有图形界面时 `vonvon open` 会失败（`D/cli/commands/open.ts:24`）。
- 界面在 Linux 上会显示成"这台 Windows 电脑"（`D/server/snapshot.ts:29`、`packages/ui/src/App.tsx:861-865`），要改。

## 4. 私聊

- 只有主人和管理员能私聊对话。别人私聊时 bot 不跑 agent，回一张卡片"在群里 @ 我"，列出这个人所在的、有这个 bot 的群。私聊会话跑在主人的 Mac 上，放开了等于让别人在主人的电脑上跑 agent。
- 私聊里的 bot 和群里的 bot 原理一样：有工作区、skill、MCP。它有一套默认的私聊设置，主人把飞书机器人加进 vonvon 以后，私聊马上就能用：
  - 工作区用 bot 的主工作区；
  - skill 和 MCP 用 bot 的名单，加上两个内置的 vonvon skill；
  - 权限档用 bot 的默认档。
- 主人可以在桌面端改这套私聊设置。
- 默认就是正常对话，能写代码、处理文件；额外能改设置（3.7）。
- 主人和每个管理员各有一条私聊会话、一份私聊记忆，能做的事一样。
- 私聊不再弹管理菜单。今天的私聊控制台（`D/bot/dm-console.ts`）拿掉，设置在桌面端改，或者直接跟 bot 说。

## 5. 迁移

**保留**：
- 所有 bot，同一个飞书应用。
- 群绑定和它们的设置：群类型、免 @、权限、访客档、网络、白名单、后端、模型，换算成规则模式。"超出权限时"用"直接拒绝"，和今天一样（3.8）。
- 旧会话：Codex 线程和 Claude 会话都能续上，前提是不换 `CODEX_HOME`、不动旧目录（推断）。
- bridge 本机的管理员名单，见第 6 节。
- 咖啡一下的 hook（重装）、评论提示词、已发文件的记录。

bot 的个性、记忆、skill 导入后为空，行为和今天一样。

**会感到的变化**（写进迁移说明）：
- 原来的"群 = 仓库目录"，变成"这个群的主工作区覆盖"，目录本身不动。
- 多 bot 群里，bot 不再进别的 bot 的话题，主区命令要 @。
- "全部回复"里，引用 bot 的消息就算点名它。
- 关了自动压缩的群变成自动压缩。
- 网页控制台和 `feishu-codex-bridge` 命令由桌面端替代。
- 私聊控制台没了。
- 要补一项新权限 `im:message:readonly`。
- 现在可以把"超出权限时"改成"问我"，让 bot 越权前先发授权卡。只在迁移回执和桌面端里说明，不在群里发消息。

**失去**：Windows、WSL 上的用法；Linux 上可以装命令行版重新开始，但不自动导入（bridge issue #1、#23、#42 的用户，占比不知道，bridge 没有遥测）；日志、缓存、已下载的 Claude SDK（重新下载约 265 MB）；Codex Fast。

**怎么迁**（只做 macOS）：
1. 桌面端首次运行发现 `~/.feishu-codex-bridge`，就显示导入页。
2. 只读预检：每个 bot 的群数、目录是否还在、密钥能否解开、hook 是否装了、bridge 是否在跑、bridge 自己装的 codex 在不在。
3. 调 bridge 自己的 `stop`，它会删 plist、去掉自启。
4. 用 bridge 的锁格式占住 `processes.json`，防止有人手动 `run`（推断，要实测）。
5. 复制数据，用新密钥重新加密。
6. 找不到别的 codex 时，引用 bridge 那份，或者装一份。
7. 重装 hook。
8. 启动全部 bot，等长连接连上。
9. 写迁移标记，显示回执"旧目录不要删，空白项目还在里面"。

任何一步失败就回滚，再 `start` bridge。

- 一次导入全部 bot，因为 bridge 是一个服务带全部 bot。
- 密钥用主机名加用户名派生，改过主机名就解不开，这时让主人扫码刷新。
- 空白项目目录不搬，原地引用。搬了 Claude 会话会找不到。
- 复用草稿 #226（V8 的 bridge 导入事务）里的预检、密钥解密和 hook 改写代码，约 640 行。不采用它的"准入互斥锁"：那个锁在已发布的 0.6.14 里不存在，会拒绝所有现有用户。
- 先修一处：打包版写进 hook 的命令指向 Electron 本体而不是 Node（`D/cli-bridge/hooks.ts:40-42`），改成桌面端注册的 `vonvon` 命令。
- bridge 出最后一版：从 0.6.14（`6698118`）开分支，只加三样东西：通知所有人，看到迁移标记就拒绝启动，`stop` 和 `status` 时提示。Mac 用户拿到下载地址；其他平台的用户只收到通知，继续用 0.6.14。

## 6. 主人和管理员

- 沿用飞书应用自己的角色。主人是飞书应用的所有者；管理员是飞书应用的管理员和开发者，运营不算。开发者也算，是按 owner 第 10 题的回答：扫码把应用加进 vonvon 的人，飞书在扫码时会确认是管理员或开发者（owner 的说法，没有实测）。
- 所以扫码的人一定能管这个 bot。今天的代码就是这样认主人的（`creds.operatorOpenId`，`D/bot/wizard.ts:81`），不需要新权限。
- 开了可选权限"管理应用自身资源"（`application:application:self_manage`）后，vonvon 会读飞书应用的所有者和协作者名单，主人在飞书里另外加的管理员和开发者也能管这个 bot。查询方法见 `docs/research/2026-10-14-feishu-app-roles/roles.md`。
  - 协作者接口每分钟只能调 10 次，所以本地缓存 10 分钟。在飞书里去掉一个管理员，最多 10 分钟后这个人就不能私聊、不能改设置了，除非这个人也在下面的本机名单里。
- 桌面端还可以另外加管理员，权限和飞书里的管理员一样，页面上标出每个人是从飞书来的还是本机加的。从 bridge 迁来的本机管理员名单（`preferences.access.admins`）放在这里：bridge 用它决定谁能用管理员档，谁能用 `/resume`、`/settings`、`/clear` 这类管理命令（`D/project/registry.ts:115` 的 `turnTier`；`D/bot/handle-message.ts:1206`）。不放的话，迁移后这些人会掉到访客档。本机名单是 Claude 加的，owner 只说了沿用飞书。
