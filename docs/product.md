## 1. 一句话

Vonvon Bot 是一个 macOS 桌面应用；Linux 上可以只装后台服务，用命令行和网页管理（3.10，0.7.0 先不发 Linux 命令行版）。主人在自己的 Mac 上养几个飞书机器人，每个 bot 有自己的个性、记忆、工作区、代码仓库、skill 和 MCP，能进不同的群，在每个群里表现不同。干活用主人本机已经登录的 Codex 或 Claude。

和 feishu-codex-bridge 最大的区别：bridge 的行为大多靠规则设定，Vonvon Bot 主推**智能模式**。bot 自己判断要不要接话、要不要开新话题、要不要和别的 bot 搭话。主人可以直接跟 bot 聊天来改它的设置、让它建群（在私聊里，3.7）。bridge 原来的规则保留为**规则模式**。

给谁用：
1. 正在用 feishu-codex-bridge 的 Mac 用户。迁过来后，群、话题、卡片、命令和旧会话都保留。
2. 有 Codex 或 Claude 订阅、想在飞书群里有一个"像同事"的 bot 的个人和小团队。他们不一定用 GitHub，也不一定会装 Node。

不给谁用：Windows 用户（Windows 和 Linux 的 bridge 用户照常用 bridge，不要求迁移）；想在 Linux 上用桌面应用的人，Linux 只有命令行版；本机尚未配置可用 Codex 或 Claude 的人；想要云端托管、不开电脑也能用的人。

## 2. 叫法

| 叫法 | 意思 |
|---|---|
| bot | 一个飞书机器人（一个飞书应用）。名字、头像、简介以飞书为准 |
| 主人、管理员 | 能管这个 bot 的人，见第 6 节。两者能做的事一样 |
| 群主区 | 群里不在任何话题里的地方 |
| 话题 | 飞书话题，包括话题群里的帖子 |
| 会话 | 后台的一条 Codex 线程或 Claude 会话。bot 记得的对话内容都在这里 |
| 后端 | 跑会话的那一家：Codex 或 Claude。见 3.11 |
| daemon、后台服务 | daemon 是本机跑着各个 bot 的进程；后台服务是登录电脑后拉起 daemon、崩溃后重启它的系统服务，见 3.1 第 3 条和 3.10 |
| 子 agent | 一个会话临时分出去、并行干活的帮手，干完就结束 |
| 智能模式 | 群设置。bot 自己判断接不接话、开不开话题、和不和别的 bot 搭话 |
| 规则模式 | 群设置。bridge 原来的规则：仅 @ 或全部回复；主区"开话题"或"连续" |
| 会话方式 | 群设置，绑定群时三选一：多会话（@ 我开新会话）、单会话（整群一条会话）、智能。只管群的结构和背后会话的关系，不管要不要 @；前两种是规则模式，后一种是智能模式，见 3.4 |
| 决策模型 | 界面统一称“决策模型”，决定智能模式何时回复、何时创建新话题；可用已准备好的 Provider 小模型，也可用 TypeSafe 的 Jev。旧文档与内部类型中的“判断模型”仍指这项用途，见 3.4 |
| 项目 | 一份工作区加一份项目记忆。可以被几个群、几个 bot 加入，解绑不删。界面上写成“小支 在 支付组群”，不写“绑定”（`docs/plans/memory-projects.md`） |
| 角色设定 | bot 自己的“身份与职责”“其他说明”两段（`SOUL.md`）。只有主人、管理员能改，bot 不能改自己的。没有单独的“规矩” |
| 本群角色 | 某个 Bot 在这个群里负责什么，原称“补充职责”。在记忆导图中点击节点编辑；和全局角色设定冲突时以它为准 |
| Bot 记忆 | 跨项目的合作方式，每个 bot 各一份。只有主人、管理员亲手说的话能进 |
| 项目记忆 | 项目的稳定决定、约定、事实。加入这个项目的群和 bot 共用，项目之间不通 |
| 分支 | 一份记忆里的分组，界面画成思维导图。有固定的几支，bot 可以新开，每份最多 12 支 |
| 可信、待确认 | 记忆条目的信任级。主人、管理员亲手写的是可信；群友说的、bot 自己记的是待确认，主人可以点成可信 |
| 项目的目录（工作区） | 项目里 bot 产出文件的目录，可写。主目录是会话的工作目录 |
| 代码仓库 | 本机的一个 git 目录。和工作区一样传给 agent，区别在界面和指令 |
| Skill、MCP | Skill 从工作区、个人和 Provider 原生来源发现，在 Bot × 群的能力页查看和开关；MCP 使用 Provider 原生配置，集中在设置的“工具与连接”管理 |

产品文案里叫"Claude"，不叫"Claude Code"，这是 Anthropic 的品牌规定（code.claude.com/docs/en/agent-sdk/overview）。界面上 bot 写成"Bot"；界面上每个概念怎么写，见 `docs/v1-plan.md` 第 5 节的叫法表。

## 3. 第一版做什么

### 3.1 桌面端

2026-10-28 Provider 配置约定（owner）：Vonvon 不发起 Codex 或 Claude 的登录认证。用户先在 Codex App、Codex CLI 或 Claude Code 中完成登录或自定义 API、模型配置，并确认可用，再回到 Vonvon 检测、复用本机配置。两个 Provider 的可用模型都使用带数量、可折叠的两列列表；无法启动的 Claude Code 与不完整的 Agent SDK 安装分别提示处理方法。

2026-10-26 组件细节：Bot 详情和群设置标签复用主导航的 Gooey 浅色滑块，按实际标签宽度定位，保留原路由与草稿保护。任务运行及注册 / Provider 连接的长等待采用 20px Thinking Orbs，等待超过两秒才显示，完成即移除；等待用户扫码或输入授权码时保持静态。全局搜索只在输入区底部加淡色静态内光，匹配和跳转保持即时；不以循环扫光暗示后台搜索。参数与验收见 [详情组件优化](plans/detail-component-polish.md)。

沟通方式保留一根细轴与三个档位，使用小尺寸浅色滑钮和蓝紫色反馈，轨道略微伸出两端；拖动连续跟手、松开按最近档位提交，原生键盘与取消语义保留。保存中保持所选位置与焦点，设置刷新不卸载已有内容，失败回到已保存档位并说明原因。工具安装进度在真实运行超过两秒后显示同款状态球，保留耗时、取消和后台继续。密钥验证维持原样，见 [单轴与安装提示](plans/communication-axis-polish.md)。

主导航为“此刻、Bot、群组”，使用 owner 已验收的 Gooey 浅色滑块及原预览的拖尾、回弹、字重和尺寸；鼠标切换播放短动效，键盘与减少动态效果模式直接切换，窄窗口优先保证导航空间，记忆计数超过 99 显示“99+”。工具栏保留搜索和设置。全局搜索采用紧凑列表：页面入口单行显示，Bot、群和项目使用不同图标，设置结果保留所属对象与分类。选中需要操作说明的结果时，在列表下方显示具体说明；搜索匹配、排序、别名和跳转目标保持不变。此刻页展示 Bot 的真实行动、群关注、群动态与 Provider 用量，保留“添加 Bot”。Bot 行可展开群列表；智能群以四段横向刻度和短状态展示关注，间隔及解释在悬停、点击或键盘焦点提示中显示，状态文字无下划线；非智能群显示实际沟通方式，无关注刻度。Bot 行动只取明确运行阶段与安全工具类别，不展示消息、思考正文、命令或路径；停用和离线停止活动效果。群动态展示最近模型判断的四种结果及触发事实，不编造自然语言理由，正向判断不等同于发送成功。用量按已配置 Provider 切换，复用设置用量页的查询、额度、每日 Token 热力图与活动统计组件；桌面左侧展示每日活动、累计 Token 与连续活跃，右侧展示额度；详情跳转设置用量页。Jev 在同一切换项中仅展示该来源的每日日期与次数，记录区最多约五行高，更多日期内部滚动，不重复显示套餐、记录标题或汇总说明；API 接入、未知账户和缺失统计明确区分。动态与活动保存在后台进程内存，重启后从新事件累积。导航、页面标题、辅助标签和搜索入口统一使用“此刻”，搜索“首页”或旧称“概览”也可到达。当前页面中，正常连接不重复写“已连接”，异常状态仍可见。Bot 行紧凑展示名称、行动、群关注概况与异常状态；“最近对话”不再占用首页，对话记录仍可从群设置进入。设置集中放 Provider、工具与连接、决策模型、用量、飞书连接、导入 Bridge、应用与启动、状态与诊断；不增加应用登录。采用紧凑的 macOS 风格分组、简洁文案和明确的操作反馈，默认窗口 1000 × 800，可调整大小，不强制窄窗口。

1. 桌面应用就是控制台，不再引导用户开网页。同一套页面也能用本机浏览器打开，但只在本机：daemon 只监听 `127.0.0.1`（`D/server/http.ts:184`），第一版不开放局域网和远程访问。
2. 签名的 dmg（Developer ID、hardened runtime），带更新源。Apple 芯片和 Intel 分别提供安装包，不发布通用版；不支持按架构更新的旧版从官网手动升级（owner 2026-10-28）。公证由 owner 自己做（owner 2026-10-26），仓库里的打包配置不放公证凭据。安装包和更新清单放在 https://dl.vonvon.cc，更新源地址在构建时写进包里（`packages/desktop/DISTRIBUTION.md`），之后不能改、不能做跳转。更新器只在打包版配好并通过签名校验的更新源时启用：启动约 60 秒后查一次，之后每 24 小时（加最多 1 小时随机延迟）查一次，查到更高版本时在设置按钮、设置首页的“应用与启动”和菜单栏的菜单里标出“有新版本”（菜单栏图标本身不变，菜单里多一项，点它打开窗口），下载和安装仍要用户点。“上次安装尚未生效”不会永久拦住检查，也不藏在设置深处：当前版本已经到了预期版本就清掉记录；没到时，同样三处标出“上次更新没装上”，设置里给“重试”和官网下载页 https://vonvon.cc/get/，自动检查照常联网，清单里有比预期更高的版本就按“有新版本”提示。更新失败、启动失败的提示都是中文，写明原因（没联网、更新服务器出错等）。更新清单含 `version`（x.y.z）、同源 https 的 `feedURL` 和 `feedURLs.arm64`、`feedURLs.x64`；新版根据运行架构选择对应 feed。旧版不支持按架构选择，需从官网手动升级。“发布说明”打开 https://vonvon.cc/changelog/。
3. 后台服务：bot 跑在后台服务里，登录电脑后自动启动。Mac 设成自动登录时，就等于开机启动。后台服务由 daemon 自己装，不依赖桌面应用，崩溃后自动重启，见 3.10。
4. 首次使用以引导卡片分三步：先准备 Provider（安装、登录、版本与可用性检查）→ 扫码创建飞书 Bot 并完成权限、事件和发布 → 连接群聊。检测到旧 Feishu Codex Bridge 时先提供导入入口和预检，保留执行、失败回滚与独立设置入口；不要求旧用户先重新建 Bot。至少一个 Provider 准备好才继续；未准备好的 Provider 不能作为建群或群模型选择。群绑定成功后进入该 Bot 的本群设置。注册弹窗用“扫码注册 → 开通权限”两步展示进度；完整扫码链接和缺少的权限 ID 按需展开。二维码过期、注册失败或取消后可在原弹窗重新获取；先取消旧任务，再核对最新任务、Bot 列表和本次流程开始时的基线，已注册则继续配置，结果不明时不重复创建。刷新凭据的重试始终使用原 Bot。权限阶段保留缺项、可选加群权限警告和检测失败提示，失败可重新检测，最新检测失败不能沿用旧成功结果显示就绪；开权限后提示创建版本并发布。页脚统一提供“稍后配置”和“检查连接”，权限未完成也可检查连接，全部处理后再突出“检查连接”。后台自动运行放在“应用与启动”（3.10）。 飞书连接通过应用信息接口只读检查卡片回调订阅和接收方式：订阅 `card.action.trigger` 且使用长连接时显示“已配置 · 长连接”，无需等待一次点击。只有接口明确返回缺失或使用请求地址时才提示修正；字段缺失、权限不足或网络异常显示无法确认，不视为未配置。真实回调接收证据和手动确认独立保留，不能覆盖明确的远端配置缺项。完成进度放在配置检查标题旁。配置正常时不显示操作按钮；存在缺项、可选配置警告或检测异常时，将相关操作放在对应状态右侧。凭据失效时先重新扫码，下游项目等待凭据恢复。`application.bot.menu_v6` 不列入订阅检查或配置要求。
5. 建新 bot 只走上面的向导，不在聊天里做。Mac 上在桌面端，Linux 上在网页或终端里（3.10）。
6. Bot 详情分为“群聊、记忆、管理 Bot”。导图以 bot 为中心：角色设定、Bot 记忆的分支、所在的项目。管理员、连接、并发、评论任务和生命周期等原有管理功能保留。Provider 页集中安装、登录、更新，并在列表中直接展示实时读取的可用模型；读取失败给出重试，不把内置备用目录当作已验证可用。
7. 群组页保留“群 → Bot”的树，点 Bot 行进入这个 Bot 的本群设置，按“模型与权限、能力、沟通方式、记忆”排列，默认模型与权限；旧权限搜索入口仍进入合并后的页面。群名、当前 Bot 和启用开关采用紧凑页头；不再常驻展示项目名、项目页和切换项目入口。聊天方式用三档滑轨选择“独立话题、连续交谈、智能”，对应原多会话、单会话、智能；悬停或键盘聚焦每档可看简介，拖动松手才提交，新群保存创建时设置中的默认决策模型、Provider 和思考强度，群聊可独立修改，后续不随全局默认更新。“记忆”直接展示本群所用的项目记忆导图，也展示当前 Bot 带来的角色设定和 Bot 记忆（只读）；项目页按各 Bot 分别显示继承内容，只能修改项目自己的记忆。“本群角色”也在导图中，点击节点才打开编辑；记忆页不再另放常驻角色表单和说明区。“对话记录”和“使用说明”常驻群设置标题栏右侧；点击群名及外链箭头在飞书打开此群，更多菜单保留解除群绑定。窄窗口将“对话记录”和“使用说明”收回更多菜单，保留群名跳转。对话记录弹窗以群和 Bot 为副标题，当前会话标题、上下文统计和清空/压缩操作集中展示，此处不提供任务目标设置入口；已知上下文窗口时显示占用进度。历史列表突出标题、时间、Provider 和状态，原始会话 ID、后端与目录展开查看，搜索和筛选集中排列。清空和压缩完成后，在对应群主区或话题发送轻量回执；恢复会话发送带历史摘要的恢复卡片，绑定成功后才显示恢复成功。操作生效与飞书回执送达分开处理：回执未确认时 App 显示警告，不重做操作。运行中任务、子任务停止、提醒、恢复及原有禁用条件保持不变。项目管理从次级入口进入，项目页保留“记忆、工作区”，导图按 D7 包含记忆分支和群与 Bot；日常界面不显示“模型看到什么”。支持搜索项目、群或 Bot。“在这个群中使用 Bot”控制是否处理群消息；解除群与 Bot 的关联保留目录、文件、项目及其记忆。
8. 状态与诊断页：标题、后台版本、最近读取时间和刷新按钮固定在上方；本机信息保留 Provider 与决策模型密钥，数据目录和崩溃历史收在“运行详情”。“后台日志”在同一卡片内点击整行就地展开，刷新与自动刷新放在日志上方，收起后停止日志自动刷新。Bot 默认展示名称、连接状态、待查看原因和中性的未回复记录数，点击展开完整诊断；停用 Bot 名称置灰，崩溃暂停红条始终可见。搜索会自动展开对应诊断区域。每个 bot 的连接状态，Codex 和 Claude 的版本检查，最近没回的消息和原因（包括智能模式判断"不回"的原因；用决策模型判断的，写选项和把握度）。选了决策模型、本机却没填它的 key 的 bot 和群，单独列一行。目录放错了位置的旧群（3.3）也单独列一行，写明到哪里换目录。用量页按天显示判断调用的次数：发起了调用的才算一次（连不上也算），见 `docs/v1-plan.md` 第 5 节。
9. “决策模型”设置页：集中管理模型服务及其密钥（沿用 owner 2026-10-18 确认的集中管理范围）。整台机器一份，所有 bot 共用，不按 bot 分。页面通过一个按 Provider 分组的模型选择器设置默认模型，并使用统一的思考强度组件；Codex 推荐 GPT-6-Luna，Claude 推荐 Haiku，Jev 不提供 Effort。Jev 密钥在下方集中管理，未配置或无法读取密钥时，下拉框内直接引导配置，不能选用 Jev。添加或连接群聊不再重复选择决策模型，而在创建时保存一份默认配置；群设置复用同一模型与思考强度组件，独立修改，不显示跟随全局或恢复默认选项。群设置不编辑密钥，只引导前往全局设置。默认服务不可用时明确提示配置问题，不自动切换其他服务；已有群的显式选择和历史继承保持兼容。Codex 和 Claude 用本机自己的登录（包括它们自己的 API key 登录），vonvon 不经手它们的 key；以后 provider 要 vonvon 来存 key 时（比如第 8 节第 2 条说的 Claude 改成只支持 API key，或者以后加的后端），也放在这里。
   - 每一项能填、能换、能删。页面只显示填没填和末四位，不回显全文；换的时候整串重填。填完马上试一次能不能用（TypeSafe 是调它列模型的接口，不发群消息），显示"能用""key 不对"或"连不上"。删之前列出哪些 bot 和群选了这家的决策模型，删了以后这些群照 3.4 出错的规矩走：要判断的消息，被 @ 的照常回，没 @ 的不回。
   - key 存在本机，和 bot 的 App Secret 同一个加密库（`~/.vonvon-bot/secrets.enc`，AES-256-GCM，主密钥是同目录下只有本人能读的 `master.key`），不进 `config.json`、快照和日志。bot 的 App Secret 由扫码写入和刷新，不在这页列。
   - 终端里用 `vonvon secrets`：`list` 看状态，`set <名字>` 从标准输入读 key（TypeSafe 的名字是 `typesafe-api-key`；key 不写在命令参数里，免得进 shell 的历史），`remove <名字>` 删。聊天里不收、不显示 key（3.7）。
10. 没有 Windows，也没有 Linux 桌面。Linux 上只装后台服务，见 3.10。

添加或连接群聊不展示项目选择和复用项目选项。工作目录可自动创建，或在同一个网页弹窗中按名称、`~/` 和绝对路径搜索 daemon 所在主机的目录，支持进入子目录和键盘选择；桌面与远程网页均使用此流程，不打开系统文件选择器。

### 3.2 bot 模型

一个 bot 有三层，外加它加入的项目：
1. **Bot**：飞书身份（名字、头像、简介，来自飞书应用，vonvon 不改。飞书能不能让同一个机器人在不同的群里显示不同的名字：没查到，所以"千人千面"体现在说话方式、工作区、仓库、skill 和记忆上，外观不变）、角色设定和 Bot 记忆。
2. **项目**：工作区（主目录、其余目录、代码仓库）和项目记忆。项目独立于群：新绑定默认新建一个项目，同一个群的第二个 bot 默认加入已有项目，别的群加入时提示会间接看到项目记忆、工作区文件和可恢复的会话；解绑不删项目和项目记忆，最后一个群也解绑了，项目留着、标“没有群”，主人可以手动删。
3. **群设置**（某个 bot 在某个群，界面写成“小支 在 支付组群”）：本群角色、模型、能力、沟通方式、权限分别保存，模型与权限在同一页。旧群未物化的字段仍按兼容规则读取，保存后使用群自己的值。

| 项 | bot 默认 | 群内 | 规则 |
|---|---|---|---|
| 名字、头像 | 来自飞书 | 不能改 | 在飞书开发者后台改。改名后，Bot 下次启动或在「状态与诊断」里检查连接时，Vonvon 里显示的名字跟着变；句柄和数据目录不变 |
| 角色设定 | 身份与职责（≤500 字）、其他说明，编辑器两个框 | 没有 | 只有主人、管理员能改，bot 不能改自己的。读取既有 `SOUL.md`，不丢旧内容 |
| 补充职责 | 没有 | 一个输入区（≤5,000 字） | 这个 bot 在这个项目里多做什么、少做什么，和角色设定冲突时以它为准，智能判断优先看它。不是记忆 |
| 项目的目录 | 保留新群目录默认位置 | 在项目页改，群设置页没有。多目录，其中一个为主目录（全局唯一） | 不分“工作区 / 附加目录”；桌面用原生多选，网页浏览 daemon 所在主机目录，见 3.3 |
| 代码仓库 | 保留旧数据兼容 | 多个，不分主次 | 只接本机已有的 git 目录，不接 git 地址 |
| Skill | 不新增 Bot 级技能库 | 查看已发现技能及来源，可开关 | 不提供添加技能入口或专用私聊创建流程；不显示推测的“工具待安装 / 待授权”状态 |
| MCP / CLI | 机器与 Provider 原生配置 | 可跳转集中管理 | CLI 安装与授权、MCP 添加与移除在“工具与连接”；不提供群级 CLI 开关 |
| 记忆 | Bot 记忆：条目，按分支分组（固定分支加 bot 新开的，每份最多 12 支），≤50 条 | 项目记忆：条目，按分支分组，≤100 条，加入这个项目的群和 bot 共用；没有继承开关 | 每条标来源和信任级，bot 判断后直接写，不事前审批；不记任务进度和密钥；见 3.6 |
| 智能提示词 | 保留旧 `SMART.md` 兼容 | 一个完整的判断规则编辑框，预填默认正文 | 只在智能模式下用，不增加合成提示词预览 |
| 决策模型 | 旧 Bot 默认保留兼容 | 群保存独立的 Provider、模型与 Effort | 新建或连接群聊时复制当时的全局默认值，后续全局更新不影响已有群。智能创建前校验所需登录与密钥，不重复选择模型；群设置可单独修改，Jev 无 Effort且密钥只在全局管理 |
| 可用模型 | 不设新的 Bot 级名单 | 一个 Provider，模型与 Effort 分别多选 | 沿用原版紧凑行布局，模型与思考强度使用相同尺寸的“已选择 N 个”按钮，点击就地展开多选菜单，选项右侧显示勾号；模型支持搜索，思考强度使用中文名称（Max、Ultra 保留原名）。勾选时保持菜单展开并直接更新页面草稿，点击外部或 Escape 收起，页面保存时一起提交并校验组合，放弃修改恢复已保存值。Provider 保留同尺寸分段选择并显示图标，选项较多或名称较长时自动使用带图标的下拉列表；新增 Provider 使用通用图标兜底。Provider 或目录不可用时保留已存值并允许只读查看；菜单始终使用当前页面草稿，切换 Provider 时关闭旧菜单。群内切换只允许选中的范围；具体组合仍校验模型是否支持该 Effort |
| 沟通方式（智能或规则模式） | 无 | 独立话题、连续交谈或智能 | 只在群层，绑定群时选，见 3.4 |
| 权限（预设或自定义） | 默认档，给私聊用；云文档评论没单独设时也用它（3.12） | 群在建立时写定自己的档，之后可以选择预设或自定义 | 群设置默认显示当前档位与实际访问范围，点击修改后在三个预设与自定义中选择；自定义原生字段放在同一权限弹窗，统一保存，取消不改，失败保留选择。页面不另设高级设置入口；Provider 原生字段若只重复三个预设，则不展示自定义入口。改 bot 默认不影响已有的群。bot 自己建的群是完全访问，被拉进的已有群是只读；旧数据没写档的按完全访问。联网由档决定，不单独设（2026-10-23）。见 3.8 |
| 运行中来了消息：插话或排队 | 默认值 | 可覆盖 | 见 3.5。群里没设就继承 bot 的；Claude 不支持插话，照样排队（s21） |
| 聊天改设置：私聊里装不装 vonvon 设置 skill、能不能用设置命令 | 开，可以关 | 没有这一项：群里不装设置 skill，不能用设置命令 | 只对私聊，见 3.7 |
| 后端、模型 | 默认值，给私聊用；云文档评论没单独设时也用它（3.12） | 群在建立时写定后端，模型可以覆盖 | 和今天一样，改 bot 默认不影响群：后端在建群和绑定时选（3.11）；旧数据没写后端的群用 Codex。群没设模型时，bot 的默认模型只在后端相同时生效。网络 2026-10-23 起并进权限的档，见 3.8 |

角色设定和记忆由 `bot/role-files.ts`、`bot/memory-store.ts` 读写，`bot/context-assembly.ts` 组装后送进任务和智能判断，取代原来的 `bot/group-profile.ts`。每一片的完成状态以 `docs/v1-plan.md` 的切片为准，设计依据是 `docs/plans/memory-projects.md`。

### 3.3 磁盘上的位置

下列布局及后续历史实现说明继续用于旧数据与切片追溯；当前 UI 的字段范围、入口和继承方式以 3.1、3.2 为准，不依据旧名单文件重新增加 Bot 级 Skill / MCP 管理页。

```
~/.vonvon-bot/
  skills/                       本机 skill 库
  mcp/                          本机 MCP 库
  library/
    projects.json               项目表：名字、工作区、记忆上限
    seen.json                   各页主人上次打开的时间，给“新”标记用
    integrity.json              各项目记忆写完后的哈希，对不上就告警
    <projectId>/
      memory.json               项目记忆的条目和分支
      events.jsonl              改动记录，先写它再写 memory.json
      usage.json                哪条被用过，尽力写
      sessions.json             这个项目里各 bot 的会话属于哪个群（/resume 用）
  projects/<bot 名>/            bot 主工作区的默认位置
    groups/<群名>/              群没设工作区时的默认目录
  bots/<appId>/
    config.json                 bot 设置，含工作区、仓库
    projects.json               每个群一条，含群的覆盖
    judge-usage.json            智能模式每天判断了几次，留 30 天
    SOUL.md                     角色设定：身份与职责、其他说明
    SMART.md                    智能提示词，不存在时用内置默认值
    skills.json  mcp.json       启用名单
    skills/                     这个 bot 自己的 skill，只给它用
    memory/bot.json             Bot 记忆的条目和分支
    memory/events.jsonl         Bot 记忆的改动记录，先写它再写 bot.json
    memory/usage.json           哪条被用过，尽力写
    memory/integrity.json       bot.json 和 SOUL.md 写完后的哈希，对不上就告警
    memory/originals/           迁移时备份的旧 SOUL.md、AGENTS.md
    memory/dm/<open_id>.json    每个主人或管理员的私聊记忆（s49 以后）
    groups/<chatId>/
      SMART.md                  本群智能提示词覆盖
      skills.json  mcp.json     {"add": [...], "remove": [...]}
```

- 工作区默认放在隐藏目录 `~/.vonvon-bot/projects/` 下，和今天一样（`D/config/paths.ts:108`），可以在桌面端改到别处。比今天多一层 `<bot 名>/`：今天所有 bot 共用这个目录，两个 bot 的同名项目会落进同一个目录（推断，`docs/research/2026-10-14-v1-definition/v2-fit.md` 第 8 节第 6 条）。
- 每个群默认有自己的目录。Claude 的只读、工作区可写档从 s31b 起按读名单隔开；完全访问档、Codex 和数据目录外的其他项目工作区不受这份读名单限制。Linux 上别的群目录名仍看得到，会话中新建的群、项目、bot 目录到这个话题下次起会话才挡住 Bash；Read 立即按粗名单拒绝。
- 目录名按建立时的名字取，之后不跟着改名，重名时加一个短后缀，"/"等字符替换掉。
- vonvon 建的这些目录（bot 的主工作区、`groups/` 和群的默认目录）被删了，下次用到时建一个空的。projects 根也不在了，只在它所在的文件夹还在、而且和它原来在同一块盘上时建回来；外接盘没接上（projects 根在盘里，或者它就是盘的挂载点）时不建，提示接上后重试。整机迁移、从备份恢复或整份复制回来以后，目录还在原来的路径，但已经不是 vonvon 记下的那一个，绑定和注册会停下来，提示主人确认目录没问题后在终端运行 `vonvon bot repair-dir <bot 名>`，按现在的位置重新记录。这类提示和工作区被拒的原因都是中文，不带完整路径，因为群里的卡片也会显示它们。
- 群解绑后再用默认目录绑回来，回到原来的目录，包括早期版本建在 `projects/<群名>/` 下的旧群。早期版本把一些群的目录放错了位置（某个 bot 自己的目录、projects 根本身、数据目录里 `projects/` 以外的地方，或数据目录的上级），这些群不回去，在状态与诊断页列出来（3.1 第 8 条），由主人到群详情页里换目录；vonvon 不搬文件。
- 定义文件都是 markdown 和 json，不进用户的代码仓库。只有角色设定（`SOUL.md`）主人可以直接用编辑器改；记忆条目库和项目表由 vonvon 读写，在桌面端改。主工作区（会话的 cwd）里的 `AGENTS.md`、`CLAUDE.md` 照旧由 agent 自己读；Claude 默认只在 cwd 和上级目录都没有 `CLAUDE.md` 时才读 `AGENTS.md`，按会话的开关能让它两份都读（Claude Code 2.1.296 实测，`docs/research/2026-10-16-bot-home/multi-workspace.md` 4.2、4.4）。其余工作区和代码仓库里的，两家默认都不读，vonvon 在指令里让 agent 先读（3.6）。
- vonvon 不往工作区写任何文件。角色设定、名单和 bot 自己的 skill 都只在 `bots/<appId>/` 下，项目和项目记忆在 `library/` 下，都由 vonvon 交给会话（3.6）。所以工作区里已有的文件不会被覆盖，工作区只读也不影响 bot 记东西。
- 会话照旧从工作区起，不从 bot 自己的目录起（owner 2026-10-16 定）。这样主工作区里的 `CLAUDE.md`、`AGENTS.md`、skill 和 MCP 由两家原生加载，Codex 一侧还要看 vonvon 传的信任设置（3.6）。原生加载只限主工作区：其余工作区和代码仓库在哪种做法下都是附加目录，那里的 MCP 和 `AGENTS.md` 两家都不加载，Claude 默认也不读那里的 `CLAUDE.md`，只加载 `.claude/skills`，Codex 连 skill 也不读（Claude Code 2.1.296、Codex 0.163.0 实测）。新群的主工作区默认是 vonvon 建的空目录，代码仓库作为附加目录接上（3.2，`docs/v1-plan.md` s36），所以默认情况下仓库自己的 `CLAUDE.md`、MCP 和 Codex 的 skill 都不会原生加载。从 bot 的目录起的话，连主工作区也成了附加目录；今天的代码里，只读档、能发哪些文件也只按会话目录判断。调研见 `docs/research/2026-10-16-bot-home/`。

### 3.4 群：智能模式和规则模式

每个群对每个 bot 有一个开关：智能模式或规则模式。

**智能模式**一起管三件事：
1. 要不要接话。
2. 群主区来了一件新事，要不要开一个新话题来回。
3. 要不要和别的 bot 搭话。

**规则模式**就是 bridge 原来的设置：回复方式选"仅 @"或"全部回复"（界面上叫免 @：关是仅 @，开是全部回复），群主区选"开话题"或"连续"。规则模式下 bot 之间互相看不到，和今天一样。

**会话方式。** 界面上不分"智能模式""规则模式"和"主区方式"，绑定群时只选一项会话方式。它只管群的结构和背后会话的关系，不管要不要 @ 才回：要不要 @ 是另一项"免 @"设置，也就是规则模式的回复方式（owner 2026-10-16）。按下表的顺序列，每项一个主标题、一行副标题：

| 顺序 | 叫法 | 主标题 | 副标题 | 等于 |
|---|---|---|---|---|
| 1 | 多会话 | @ 我开新会话 | 在主区 @ 我就开一个话题，一个话题一条会话，几件事各聊各的 | 规则模式，主区"开话题" |
| 2 | 单会话 | 整群一条会话 | 主区一条会话，上下文一直连着；想另起一件事，开个话题和我聊 | 规则模式，主区"连续" |
| 3 | 智能 | 智能开话题 | 主区一条会话，不用 @ 我也会看情况接话；聊到新的事，我自己开话题、起新会话 | 智能模式 |

- 不管哪种方式，一个飞书话题就是一条新会话（3.5）。三种的区别在主区：多会话的主区不留会话，@ bot 就自动开一个话题；单会话的主区是一条会话，要开新会话就由人开话题、在话题里和 bot 说；智能和单会话一样，只是 bot 自己判断每句话回不回、要不要开新话题，开了新话题也是一条新会话。
- 多会话和单会话再有一项免 @，绑定群和建群时不选就按默认：多会话开着，话题里不用 @ 也回，主区照旧要 @ 才开话题；单会话关着，要 @ 才回。智能没有这一项，回不回由 bot 判断。bridge 和 s21 之前，被拉进来的单会话群默认关，bot 自己建的单会话群默认开（`D/project/registry.ts` 的 `defaultNoMention`）；s21 起新建的单会话群也是关，已有的群不变。
- 话题群和话题形式群没有主区，一个帖子一条会话，多会话和单会话在那里没有区别。卡上把这两项合成一项"按话题聊"，和"智能"二选一；选了"按话题聊"再选免 @，不选就开，和多会话一样（Claude 2026-10-19 定）。
- 飞书里的设置卡不预选任何一项，也不标"推荐"：产品上主推智能，卡上不替人选。桌面端和网页建群、加入已有的群时，会话方式默认多会话，收在"更多设置"里，收起时摘要行写出当前值，比如"多会话 · 免 @ 开 · 新建文件夹"，不用展开就看得见（owner 2026-10-18，第 11 节）。命令行绑定群和建群时必须带会话方式。
- 副标题说的"一条会话"都指主区。
- 上面的主标题、副标题，免 @ 的默认和话题群的问法，是 Claude 按 owner 的意思定的（`docs/v1-plan.md` 第 5 节）。

**被拉进已有的群时。** owner 2026-10-16 定了绑定时选工作区和会话方式；卡上还有哪几项、发给谁、设置好之前怎么回，是 Claude 定的（`docs/v1-plan.md` 第 5 节）。bot 被拉进来，先不在群里干活，私聊发一张设置卡：拉它进群的人是主人或管理员，就发给这个人；不是，就发给主人，写明谁把它拉进了哪个群。卡上有：
1. 会话方式，按上表；下面还有一项免 @，只对前两种算数，选了智能时不用管它（卡上的表单藏不了它，写在提示里）。
2. 工作区：默认按 3.3 给这个群建目录，也能填本机已有的目录。
3. 后端：默认用 bot 的。
4. 权限：显示默认的只读（不联网，3.8），设置好以后在群详情页或私聊里改。

选好会话方式、点［绑定］才算设置好。设置好之前，有人在这个群里 @ bot，bot 只回一句"主人还没设置好这个群，设置好就能用"，同一个群 10 分钟最多回一次；不 @ 的消息不读。bot 离线时被拉进的群收不到进群事件，不补发设置卡：有人 @ 时只回那一句，主人在网页"加入已有的群"里设置（Claude 2026-10-19 定）。卡不过期，也能在桌面端或网页里设置：Bot 页的群列表里有一组"待设置"，每个群一行"设置"，打开下面"加入已有的群"那张表；提示每个 Bot 合成一条"<Bot> 有 N 个群待设置"，只在 Bot 列表和这个 Bot 的页上显示，不再每个群一条；右下角的浮层只报这次打开页面以后新来的群（owner 2026-10-18，第 11 节）。这张卡是第 4 节拿掉私聊控制台以后，私聊里唯一留下的设置卡。

**在桌面端和网页里建群、加入已有的群。** Bot 页和群聊页都有"新建飞书群"和"加入已有的群"，两者用同一张表：主界面只问群名和后端，没装、没登录的后端灰掉并写原因；会话方式、文件夹和免 @ 收在"更多设置"里，会话方式默认多会话（见上面"会话方式"）。建好后到这个群的详情页，顶部提示"已建好"，下一行写出它的目录，带"在飞书打开"。Bot 还没连上飞书时，表单顶部提示"Bot 还没连上飞书"，提交禁掉，查已加入的群也一样，不等填完提交再被拒；入口灰掉时旁边写原因。这几条是 owner 2026-10-18 挑的（第 11 节），做法见 `docs/v1-plan.md` 的 u07。

**默认值：**
- 新进的群没有默认的会话方式：被拉进已有的群时在设置卡上选（见上面），bot 在私聊里建群时，主人没说就先问（3.7）。只有桌面端和网页的表单默认多会话，默认值写在摘要行，主人看得见、能改（见上面）。选了智能，bot 在群里说一句"我会读群消息，合适时接话"：绑定、建群时并在欢迎卡第一行里，在群详情页改成智能时单发一条；群停用着不说，从智能改回别的方式也不说（`docs/v1-plan.md` 第 5 节）。
- 从 bridge 迁来的群用规则模式，沿用各群原来的回复方式和主区方式，不换算：多话题群就是多会话，单会话群就是单会话。bridge 今天的默认是免 @ 开，只有被拉进来的"连续"群默认关（`D/project/registry.ts:83-85`）。
- 设置好以后，会话方式能在群详情页或私聊里改（3.7）。在多会话和单会话之间切换，免 @ 不自动变，界面提示一句；从智能切到多会话或单会话，免 @ 是关，要开再开。单会话和智能之间切换，主区那条会话接着用。

**三条底线（规则模式）。** 规则模式下，先回答"这条消息是对谁说的"，再轮到回复方式和主区方式：
1. **点名**：@ 了谁、引用了谁的消息，就只有谁回。@ 了别人、@所有人、引用别人的消息，其他 bot 都不回。@ 两个 bot 就两个都回。例外：规则模式的"仅 @"里，引用我的消息不算点名，和 bridge 一致。话题里直接发的消息，`parent_id` 就是话题第一条，算没引用；回复话题里的某一条时，`parent_id` 是那一条，能分出引用了谁（e10，话题群里 s22 补测过）。所以话题第一条被引用分不出来，算没引用。引用自己的消息不算点名别人。
2. **接着聊**：话题里没点名的消息，归最近在这个话题里说过话的 bot。别的 bot 开的话题，我不插嘴。
3. **bot 消息**：别的 bot 发的消息，只有 @ 我才算。

群里只有我一个 bot 时，这三条改变不了谁回，bot 不为它们查任何东西，规则模式和以前一样，比如单会话群里引用同事的话照样回。群里有几个 bot 看群信息（3.11），读不到时按有别的 bot 处理。查被引用的消息或话题里谁最后说话失败时，没点名的这条不回，诊断页记一条（s22）。

这三条顺带修掉今天多 bot 群里的两个毛病：开了免 @ 的 bot 会进别的 bot 的话题；多会话主区不带 @ 的 `/help` 每个 bot 都回（推断，`docs/research/2026-10-14-v1-definition/group-response.md` 结论 3）。单会话群里，免 @ 开着的 bot 每个都回每条，也都回不带 @ 的命令，第一版照旧：每个 bot 只管自己（下面"几个 bot 都会回的时候"）。

智能模式不用这三条：@ 了谁、引用了谁、话题里谁说过话，都作为事实交给判断，由 bot 自己定回不回（下面"智能模式怎么判断"）。规则模式的 bot 收不到别的 bot 的 @，所以群里有几个 bot 时建议都选智能（下面"建议都开智能"）。

**智能模式怎么判断。** 智能群里不靠规则：要不要接话、回在哪、要不要开新话题、接的是哪一条，都由一次判断定；回答里要不要 @ 谁，由 bot 自己的 agent 在回答里定（owner 2026-10-19，第 11 节）。判断在群主区三选一：不回、在主区接着聊、开新话题回；在话题里只判断回不回，不再拆话题。
- 群内“判断规则”使用一个完整的编辑框，预填实际默认正文；“什么时候回应”“什么时候不回应”“消息在群主区时”“消息已经在话题里时”显示为正文内的小标题气泡，标题和正文均可修改，删除气泡只删标题、保留正文，也可全选重写或清空。默认回应相关求助、接着自己的讨论和明确征求意见；闲聊、别人已处理、无新内容、Bot 无事互聊或拿不准时不回应。保存后下一次判断生效，可恢复默认。标题只是编辑呈现，完整文本一起交给模型；决策模型的选项只定义动作，不重复写入默认偏好。旧版本精确匹配的内置默认升级为新默认，自定义的两段内容完整合并；显式清空不会恢复默认。话题内只能不回或在原话题回是程序约束，在输入框下说明。
- 判断看到的是事实：这条消息 @ 了谁、引用了谁、@ 了所有人；这个位置是谁开的、谁在里面说过话；群里还有哪些 bot；自上一条真人消息起 bot 之间来回了几次；bot 为什么现在看（有人 @ 了它、引用了它、叫了它的名字、别的 bot @ 了它，或者它刚在这里说过话、隔了一阵在扫一眼）。怎么用这些事实，写在智能提示词里，内置默认值里有一段，主人能改。自己改过智能提示词的，升级后诊断页提示一次，告诉主人新版默认里多了哪一段。
- 真人 @ 我、引用我的消息、在我的回答下开的话题：也交给判断，只有我一个 bot 的群也一样。判断说不回就不回，消息上什么都不留，原因只记在诊断页（owner 2026-10-19）。判断出错或超时照旧回，免得人白等：在话题里回在话题，在主区回在主区（3.5）。话题里只有一个真人在和我聊时也一样：先判断，出错或超时才直接回。
- 别的 bot @ 我、正文里叫我名字（没 @）：也判断一次。出错或超时不回，诊断页记一条。名字太短（英文少于 3 个字母、中文只有 1 个字）或是常见词（比如"助手""bot"）的，不算叫名字，留到扫一眼时看，判断看得到"提到了和你同名的词"。
- 判断模型分两类（叫法是 Claude 按 owner 2026-10-18 的说法定的，第 11 节）：
  - **语言模型**：各家订阅里的小模型，一次不带工具的调用。能生成文字，"不回"的原因是它自己写的一句话。以前也叫"大模型"。
  - **决策模型**：专门做判断的 API。给它规则、上下文和几个选项，它只回选了哪一项和每一项的概率，不生成文字。第一版只接 TypeSafe 的 Jev，直连 TypeSafe，不经 OpenRouter；以后会加更多（第 10 节），vonvon 里按一张登记表加，不改设置的格式。主人自己在 TypeSafe 开账号、填 key、付钱：只按输入收费，1,000 次判断约 0.05 到 0.10 美元。JP-VPS 上实测判一次约 0.16 秒，订阅小模型多在 3 到 5 秒；不占订阅额度，本机不起进程（`docs/research/2026-10-18-jev/report.md`）。
- 决策 Provider 与执行 Provider 独立。新群在创建时复制全局默认的 Provider、模型与 Effort，之后保存为本群独立配置；更改全局默认或任一家模型配置，都不改变已有群。群设置直接显示具体模型，使用与全局相同的分组搜索选择器，没有跟随或恢复全局默认入口。Codex 推荐可用目录中的 GPT-6-Luna，Claude 推荐 Haiku；未显式选择 Effort 时优先关闭思考，不支持关闭则推荐 low，Jev 无 Effort。显式保存的 Effort 保留原选择，界面推荐与后台默认共用策略。已有完整群配置保持不变；旧版本保存的全局 default/provider 引用在全局变更前固化为当时生效的配置，不猜测历史创建值。旧 Bot 缺省继承和未知配置保持兼容，用户编辑群模型后保存完整配置。
- 本机未配置或无法读取 Jev key 时，模型下拉框里的 Jev 行直接显示设置入口，不改变当前模型；全局打开密钥编辑，群聊跳转全局设置。后端同样拒绝缺少有效密钥的新选择。已有 Jev 群的密钥后来删除或不可用时照下面出错规则处理，不静默切换服务；聊天里不收 key（3.7）。
- 选了决策模型，要判断的那条消息、一起带上的最近几条群消息（连同它们 @ 的人名和引用的话）、群名、话题名、bot 名和智能提示词，会发给那家服务；还有补充职责、身份与职责和本群可信的项目记忆（待确认的条目和 Bot 记忆从不发）。本机决策模型和第三方的一样，没有按群的开关。Jev 的服务在美国。TypeSafe 的条款写着不拿客户数据训练模型；保留多久没写明，零保留只给企业客户；还要客户（这里是主人）保证拿到了发送这些内容需要的同意（`docs/research/2026-10-18-jev/report.md` 第 1 节）。界面上和群里都不另外提示（owner 2026-10-18）。用语言模型判断时，群消息同样会发给 OpenAI 或 Anthropic。
- 判断出错或超时：没点名的不回（真人 @ 我、引用我的照上面回）。决策模型也照这样兜底（owner 2026-10-18）：没填 key、key 不对、限流、断网、服务出错，都不改用订阅小模型再判，诊断页记原因。
- 多 bot 群里，主区不 @ 的命令（`/help` 这类和 `/goal`）不判断也不回，和规则模式一样要 @。
- 决策模型照概率最高的那一项走，不因为把握度低就改判（owner 2026-10-18）。把握度从概率算：0 是几个选项一样可能，1 是完全确定。诊断页显示把握度，日志记下；M5 验收时看日志，再议要不要在把握度低时改问订阅小模型。
- 只回"回"或"不回"，不做"只回一个表情"。"不回"的原因只记在本机诊断页，不发到群里，也不进会话：bot 自己接话的那一轮，开头只加一句固定的说明（这条没 @ 你，是你自己判断该接话，只说有用的），模型给的原因不给 agent。决策模型不写原因，诊断页的"不回"原因写它的选项和把握度，比如"Jev：不回 0.70、回 0.30（把握度 0.40）"。诊断页里判断后不回的（连同下面自己接话后没话说的）最多留 10 条，免得盖住出错的。
- 判断不挡别的消息：一条消息在判断时，同一个群里别的消息照常处理。被真人 @ 的、引用我的消息马上判断，判断期间消息上挂一个表情表示看到了，判完拿掉；判断说要进会话的，比它早到的被 @ 消息先进；进会话时照"运行中来了消息"插话或排队（3.5）。别的 bot @ 我、叫我名字的也马上判断，但不挂表情，别的消息不等它。没点名的消息什么时候判，见下面"关注度和成本"。同一个位置两次判断都说要回、而前一轮已经带上了后一次要回的消息时，只回一次。判断期间消息被撤回、群被停用或改了会话方式，这条就不回。
- 判断用的提示词就是智能提示词。回不回、回在主区还是开新话题，是同一次判断一起给出的，所以只有一段提示词（owner 2026-10-16）。内置默认值在界面上完整显示，主人可以在 bot 层改，群里可以覆盖，改过的能一键恢复默认。程序在提示词后面附的几行（让模型按什么格式回结果）也显示出来，但不能改：改了程序就读不懂结果。决策模型也用同一段智能提示词当规则；格式行换成程序给的几个选项，同样只读显示。
- 开在哪条下面：判断说开新话题时，一起给出它接的是哪一条，话题开在那条下面；那条要是真人发的、没 @ 任何人、还没有话题，而且是这次一起看的几条之一，或者在这条之前 5 条、10 分钟以内；不是的话开在这条自己下面。真人或别的 bot @ 我、引用我、叫我名字的，开在这条自己下面。回在主区的引用判断指出的那一条。
- 自己接话后没话说：bot 自己接话的那一轮（主区没点名、判断说要回的）没写字、没用工具、没发文件，就删掉这张卡，诊断页记一条；删不掉时卡上只留一行"（没有要补的）"，诊断页写明原因。被 @ 的、话题里的、出错或被停下的那一轮，还有插话时另起的卡，照旧留着。

**关注度和成本。** 智能 bot 像人在群里一样，关注程度随情况起伏；程序只决定判断模型什么时候看、一次看几条，不决定回不回（owner 2026-10-19，第 11 节）。
- 群详情「沟通方式」的「聊天方式」右侧，在智能模式下展示只读「主区关注度」圆环仪表，窄窗口排到聊天方式下方。把现有档位固定折算为 0–100：专注 100，留意间隔 1 / 3 / 5 分钟分别为 75 / 50 / 25；暂停主动查看为 0；正常在线但尚无主区关注记录时也显示 0，标注「待互动」及「收到主区消息后，关注度自动更新」。圆心显示数值，四段圆弧对应四档；蓝色表示留意，绿色表示专注，琥珀色表示暂停，灰色表示待互动或未知，并保留文字状态。右侧用一句话解释当前状态；悬停圆环、键盘聚焦或点击可查看档位说明，移出或按 Escape 关闭；它不是回复概率，不新增关注度算法。话题单独展示专注、留意或暂停的数量，不与主区合成分数。45 次预算只把留意中的主区显示为 0，专注仍是 100；60 次预算显示 0，并说明仅处理真人直接找它的消息。未运行、连接断开、群状态过期、项目停用、缺少关注状态接口或遇到未定义的间隔时显示 —，并说明原因或实际间隔，不沿用旧分数。状态随已有实时快照更新，额度到期但新快照未到时显示待更新（owner 2026-10-23）。
- 有人找它就马上看：真人 @ 它、引用它的话、别的 bot @ 它、正文里叫它名字，这一条马上单独判断。
- 刚说过话就盯着：它在一个位置回过话以后（从主区开了话题的，主区和新话题都算），之后那里每条真人消息到就判一次。主区里连着三条都不是它的事，或者过了 10 分钟，就不再逐条看。话题里连着五条都不是它的事才不再逐条看，不看时间：它说过话的话题，隔多久有人回来接着说，都马上看，重启以后也一样。
- 没人找它就隔一阵扫一眼：消息先攒着，等这一阵说完、离上一眼够久了，一次判断看一批，从里面挑该接的那条回。扫了没它的事，下一眼隔久一点（1 分钟、3 分钟，最多 5 分钟）；安静五分钟以上又有人说话，很快看一眼。所以没 @ 的新事多半在一分钟内被看到，夹在闲聊里的最慢约五分钟（一直有人说话时约六分钟）。
- 每个 bot 对每个位置（主区或一个话题）各记各的，只记在内存里，重启后从头开始（它说过话的话题除外，见上）。群切成规则模式、改了智能提示词、解绑或重新绑定，这个群的关注也从头开始。不和别的 bot 商量，同一台电脑上的也一样。
- 每个 bot 在每个群每小时最多判断 60 次，各 bot 各记，按滑动的一小时算，重启清零。真人 @ 它、引用它的判断不算在里面：人找 bot 不是浪费。别的 bot @ 它的判断算在 60 次里，不另设上限（owner 2026-10-19）。用到 45 次起不再扫一眼，只判找它的和刚聊过的位置；额度回来以后只看最近 10 分钟的消息，更早的不再拿出来判。到了 60 次，只剩真人 @ 它、引用它的照常判断，别的都不判也不回：别的 bot @ 它、叫它名字的，诊断页按条记；没点名的，每个群每小时记一条。
- 只对允许使用 bot 的真人消息和别的 bot @ 我的消息判断。延迟和额度 e12 在 JP-VPS 上量过（热判断多在 3 到 5 秒，额度不是瓶颈，见 v1-plan 第 5 节），Mac 上的体验在 M5 验收时看。

**bot 之间。** 智能模式下，别的 bot @ 我时我能收到（要新开一个可选权限，见 3.11），这样能做"小码写、小审查"。群里有几个 bot 时，当它们都开着智能模式来设计，也建议主人都开（下面"建议都开智能"）：别的 bot @ 了我回不回、我要不要 @ 别的 bot，都由 bot 自己判断，不靠规则（owner 2026-10-19，第 11 节）。
- 被别的 bot @：调一次判断，和别的消息一样三选一（话题里只判回不回），开新话题开在这条自己下面。这次判断算进每小时 60 次。到了上限、判断出错或超时，都不回，诊断页记一条。
- B 看到的 A 的消息只有 A 的最终回答，标成"A（bot）"，截到几百字。哪些 id 是 bot 按飞书的群成员列表认。不收别的 bot 的全部消息。
- 没有来回次数的上限。自上一条真人消息起 bot 之间来回了几次，作为事实交给判断，默认智能提示词里写"bot 之间来回几次、真人一直没说话时，除非还有明确没做完的事，不再接"。真要停不下来，每小时 60 次的判断上限是刹车，不另设被 bot @ 的上限；M5 验收时专门看 bot 来回停不停得下来（owner 2026-10-19，第 9 节第 28 项）。
- 群里设了"响应成员"时，只响应名单上的：名单上的 bot 来 @ 我，和没设名单时一样去判断；不在名单上的 bot 的 @ 不判断、不回（owner 2026-10-19）。
- 回答里要不要 @ 谁，由 agent 自己定。回答里写的 @名字（真人或群里的 bot），在回答卡定稿后由程序发成一条带真 @ 的文字消息，能提醒到人、能叫醒 bot。只认群里的 bot 和群成员里名字只有一个人叫的真人；@所有人 一律不发；引用块和代码块里的 @ 不算；一条最多 @ 5 个，多的不发，卡上最后一行写明。智能群不按设置发完成提醒，卡上也没有"完成后提醒我"（3.8"完成提醒"）。

**建议都开智能。** 规则模式的 bot 收不到别的 bot 的 @，也不会自己判断要不要 @ 别的 bot（上面"规则模式"），所以群里有几个 bot 时建议都选智能。群里还有别的 bot 时，绑定群的设置卡、桌面端和网页的绑定表单、群详情页的会话方式下面多一行提示："群里还有别的 bot。几个 bot 都选智能，它们才能互相 @、各自判断接不接话。"只是提示，不预选，不替人改，选了智能也照常显示；读不到群里有几个 bot 时不提示（owner 2026-10-19，第 11 节）。

bot 发的卡片和 markdown 消息里不带 bot 的真 @：agent 写给 bot 的 @ 显示成纯文字"@名字"，因为卡片里的 @ 能叫醒对方，飞书的消息列表却看不到。哪些是 bot 按飞书的群成员列表认；列表读不到时，agent 写的 @ 都显示成纯文字，bot 自己放的 @（提问卡上 @ 能回答的人）照旧。交接按实际消息状态显示接收者和已有消息、话题的位置。发送成功只说明已发出，观察到对方响应才说明对方已开始处理；失败或结果未知如实显示。不为交接另加私有信道、确认循环或新的 bot 身份。

**几个 bot 都会回的时候。** 每个 bot 只管自己：回不回只看这条消息、一起带上的历史消息和自己的智能提示词（规则模式看自己的设置），不看别的 bot 的设置，也不和别的 bot 商量，同一台电脑上的也一样。所以同一条消息几个 bot 都可能回；智能 bot 之间靠各自提示词里的分工错开（下面例子第 3 行）。智能 bot 的判断看得到 @ 了谁、引用了谁、话题里谁说过话、bot 之间来回了几次，怎么用这些由提示词定（owner 2026-10-19，第 11 节）。

**一个例子。** 真人张三、李四。三个 bot 都是智能模式，在同一台 Mac 上：小码（Codex，写代码），小P（Claude，管产品），小审（Claude，管审查）。daemon 刚起，谁也没在群里说过话。

### 3.5 会话和上下文

owner 说这一块很关键：飞书里的位置怎么对应 agent 的会话，上下文是什么关系，哪些要存进会话历史。下面依次回答，再用一个群的时间线走一遍。今天的代码和这里不一样的地方，列在本节末尾。调研见 `docs/research/2026-10-14-session-approval-service/session-map.md`。

**一个飞书位置对应一条会话。** 每个 bot 各有各的会话。下表说的是一个 bot 在一个位置上。群里只有主区和话题两种位置；私聊不在群里，是主人或管理员和 bot 一对一的聊天窗口。

| 飞书里的位置 | 智能 | 单会话（规则模式"连续"） | 多会话（规则模式"开话题"） | 什么时候建 |
|---|---|---|---|---|
| 群主区 | 一条会话，一直接着聊 | 一条会话 | 不留会话，@ bot 就开一个话题 | 这个 bot 第一次在主区回复时 |
| 话题，不管是谁开的，包括话题群里的帖子 | 一条会话 | 一条会话 | 一条会话 | 这个 bot 第一次在这个话题里回复时 |
| 私聊（不在群里，一对一） | 一个私聊窗口一条会话：主人一条，每个管理员各一条 | 同左 | 同左 | 第一次私聊时 |
| 私聊里的话题 | 单独一条会话，和群里一样。用户开的和 bot 开的私聊话题，事件里都带 `thread_id`（e10） | 同左 | 同左 | 第一次在这个话题里回复时 |
| 云文档评论 | 每篇文档一条，和今天一样 | 同左 | 同左 | 和今天一样 |

- 会话就是一条普通的 Codex 线程或 Claude 会话。主人在 Codex 应用里或用 `claude --resume` 打开它，看到的和 bot 看到的一样（e14 在终端里实测过）。主人可以在终端或 Codex 应用里接着 bot 的会话聊：bot 每一轮开口前看一眼这条会话，别人写过（聊了几轮、压缩过）就重新接上，从最新的地方接着说；Codex 那边 bot 每一轮结束就放开线程，终端随时打得开。bot 正在回答的那一轮里终端也在写，两边会分叉，不处理（owner 2026-10-16 定，D6 选 A；s15b 已改）。反过来，终端或 Codex 应用开着这条 Codex 会话时，bot 接不上（Codex 一条线程只许一个写入方），这一轮回"这条会话正在终端或 Codex 应用里打开着，bot 接不上。关掉那边以后再发一次。"，不换新会话。s15b 之前 bot 在最后一轮之后还占着会话 45 到 50 分钟：这期间 Claude 那边终端里写的轮次和 `/compact` bot 看不到，下一轮接着自己的历史写，两边分叉；Codex 那边终端打开会被拒（e14）。
- 每个 Bot 只有一套会话标题开关、Provider、模型和思考强度，所有会话共用，与会话执行的 Provider 无关。关闭时隐藏模型选择；开启后在同一个菜单选择 Provider 和模型，需要模型精炼标题时统一调用这个选择。短消息直接命名、失败时使用消息首句的规则保持不变；设置变更只影响之后新建的会话。旧版按 Provider 保存的配置，优先采用 Bot 默认 Provider 的有效设置，否则按 Codex、Claude 的固定顺序采用第一份有效设置；一旦保存新设置，以新设置为准，关闭即对所有 Provider 关闭。
- 不在同一个位置里悄悄换会话。只有 `/new`、`/clear`、`/resume` 会换，见下面的"命令"。
- 话题群和话题形式群里没有主区对话，每个帖子就是一个话题，也就是一条会话，不判断要不要开话题。
- 子 agent 代替不了新会话：它的结果会回到父会话里，干完就结束，事后没法接着问它。它的用途是把一件事拆开并行做。
- 一个群只有一个权限档，群里谁说话都用这一档、进同一条会话（owner 2026-10-16 去掉了访客档，见 3.8）。以前设了不同访客档的群，升级后取两档里更严的，管理员的会话接着用，访客的会话停着不用（s15c 已改）。
- 云文档评论的会话不在群里，用评论设置里的权限，没设时跟 bot 默认（3.12）。

**主区和话题是什么关系。**
- 主区会话和话题会话互不复制历史。
- 话题开出来时，不管是用户开的，还是 bot 判断后开的，主区会话里只留一行引用，指向这个话题的会话：谁、几点、在哪条消息下开了话题、话题的标题、话题 id，以及话题会话的 id（Codex 的线程 id 或 Claude 的会话 id）。话题会话里也记着主区会话的 id。两边靠这两个 id 互相找到。
- 引用行由 daemon 生成，不带话题里的内容，用户也伪造不出来。
- 会话在 bot 第一次回复时才建。所以 bot 还没在某个话题里说过话时，这个话题还没有会话，引用里只有话题 id；主区会话还没建时，话题的回指里也没有主区会话的 id。这两种情况下用话题 id 或群也能找到对方现在的会话。主区 `/new` 以后，旧话题的回指仍然指向开话题时的那条主区会话。
- 引用行在主区会话下一次开口时，和别的新消息按时间一起写进对话记录块。不在话题一开就单独写进主区会话：Codex 那种写法（`thread/inject_items`）在 Codex 应用里看不到，Claude 那种写法（`shouldQuery: false`）Codex 没有，而且为了一行字要拉起一个会话进程。主区会话在开口之前也用不着知道。
- 不在群主区另发一条带链接的消息。飞书新版客户端会把话题回复直接显示在那条消息下面，主区的人本来就看得到。

**哪些存进会话历史。** 只存 bot 真正开始回复时读到的东西，一共四类：
1. 会话开始时的角色设定、补充职责和记忆；之后变了，下一轮附的"设置更新"，和压缩以后整份再交的那份（3.6"改了什么时候生效"）。
2. 每次回复前，这个位置自上次以来的新消息，合成一个对话记录块。真人的话带真名，包括智能模式判了"不回"的消息；别的 bot 只放最终回答，标成"某某（bot）"，截到几百字。主区的记录块里还有新开话题的引用行。
3. 触发这次回复的消息、它引用的消息、附件路径、语音转写。附件的原件在飞书的消息里；agent 在本机跑，读不到飞书，所以 daemon 把附件下载到本机，把本地路径交给 agent。本地这份只是缓存，留多久、清掉以后怎么办，见下面"daemon 在本机记什么"。

**daemon 在本机记什么。**

### 3.6 角色设定、记忆、skill、MCP

**记忆导图交互。** 使用现有手写 HTML/SVG，不加图库。根使用 App 紫色，固定节点以浅色背景区分，不加锁。单击选中后显示＋；展开的选中节点不显示收拢，未选中的父节点悬停显示收拢，已折叠节点持续显示子节点数。再次点击选中节点或直接键入可在图中编辑，Enter、Esc 或失焦保存，中文输入法组合期间不提交。选中态 Delete/Backspace 软删除节点，文字编辑态只删除文字。固定分类不可删改，自定义分类可改名及连同记忆软删除；失败保留剩余条目并提示进度。分类和记忆的＋均在该分类新增记忆；根的＋允许输入分类名及第一条记忆，沿用“分类 → 记忆”结构。右键菜单保留详情、历史、移动和归档恢复。

**角色设定。** 注入顺序，越后越具体：

每份记忆按分支分小标题，开头列出这份记忆的全部分支名，空的也列。设计和各块的写法见 `docs/plans/memory-projects.md` 4.1。

**记忆。** 按范围分三份，每份的条目按分支分组。

| 记忆 | 在哪里用 | 谁能写 |

| Bot 记忆 | 这个 bot 的所有项目和私聊 | 只有主人、管理员亲手说的话能进，由 daemon 核对这一轮是他们自己手打的消息触发、内容出自这条消息。主人和管理员能在桌面端看、改、移、删 |

### 3.7 在聊天里改设置

主人和管理员可以在私聊里直接跟 bot 说，比如"以后在支付组说话活泼点"、"给支付组加上 X skill"、"建一个发布群，把张三拉进来"。第一版只在私聊里能说，群里不能在聊天里改设置。

**做法**：
1. 扩展已有的 `vonvon` 命令行（`packages/daemon/package.json` 的 `bin`，现在注册了 `daemon`、`open`、`service` 等子命令，`D/cli/index.ts:20-55`），加上设置和飞书两组子命令。设置命令是所有会改东西的命令，包括建群和拉人进群；飞书命令只查不改。命令行照旧给终端用。
2. agent 不在 shell 里调命令行，走 vonvon 自己的 MCP 工具：同一组命令做成 MCP 工具，Codex 拉起 vonvon 的 MCP server，跑在沙箱外，令牌放在只有 vonvon 和它读得到的专用文件里；Claude 的 vonvon 工具跑在 daemon 的 bot 子进程里，不用令牌。原因：在 Mac 上实测，Codex 的只读、读写档里 nvm 装的 Node 起不来，关网时 shell 也连不上本机（e04）；Claude 的沙箱里 TCP 直连本机被拒，只有 Unix socket 和沙箱的代理放行后到得了（e04b）。走 MCP，两家调同一张工具表，也不靠 shell 里的 Node（第 9 节第 2 项）。下文说 agent 用设置命令、飞书命令，指的都是对应的 MCP 工具。
3. vonvon 设置 skill 告诉 agent 怎么用设置命令，飞书 skill 教飞书命令。只有私聊的会话装设置 skill、注册设置工具；别的会话不注册，调用也会被 daemon 拒绝（下面令牌那条）。
4. 只换通路，别的照旧：用户能改的设置、能查的内容不变；谁能改、只在私聊、"聊天改设置"开关这些规则不变。Claude 的进程内 MCP 已在 s46 的 Linux 四轮自测中调通：只读、读写档经过权限回调，完全访问档不经过。Codex 的 `approve`、沙箱外 MCP 和 Mac 上的 Claude Seatbelt 留给 s46b 实测。只读档调不通、又配不上时，群里的飞书查询就用不了，按 `docs/v1-plan.md` 4.2 第 3 条问 owner。

**能改什么**：只限这个 bot 自己的事。命令行能改的这个 bot 的设置，聊天里都能改，因为 agent 调的设置工具和命令行是同一组命令（owner 2026-10-18 定，第 11 节）。

| 能改 | 不能改 |
|---|---|
| 角色设定、补充职责、智能提示词、判断模型；记忆（memory 工具）；skill 和 MCP 的启用名单；仓库和工作区；会话方式和免 @；权限档和网络；完成提醒（只对规则群生效；智能群不按它发，3.8"完成提醒"）、卡片显示、运行中来了消息（插话或排队）和空闲超时这类运行设置、主模型、允许哪些群用、工作区的默认位置、云文档评论的设置（后端、模型、评论提示词、权限档和网络）、会话标题、语音转文字的开关；本机加的管理员、群里允许使用 bot 的成员；建群、拉人进群 | 建新 bot、改别的 bot；填、换、删 API key（在桌面端、网页的密钥页或终端里，聊天里不收、不显示 key，只告诉人去哪里填，3.1）；vonvon 的全局设置；私聊的"聊天改设置"开关（见下） |

- 本机加的管理员、群里允许使用 bot 的成员、评论提示词和语音转文字的开关，今天在设置里走单独的操作，命令行还没有（`docs/v1-plan.md` s07a 留下的）。按 owner 的话，能改的配置聊天里都能改，所以命令行把这四项补上，聊天里一样能改。这是 Claude 按 owner 的话补的（第 11 节）。飞书里来的管理员在飞书里改，聊天里改的只是本机加的那份名单（第 6 节）。本机管理员名单只有主人触发的那一轮能改，加和移除都是；管理员触发的那一轮不能改这份名单，免得管理员给别人加管理员，或者把别的管理员移掉（Claude 定）。加管理员、放开群里允许使用 bot 的成员和改允许哪些群用一样，算扩大能力（3.8"留下的风险"）。打开语音转文字时缺飞书权限，回执里写明，权限照旧在飞书后台开。
- 群里不能在聊天里改设置。某个群自己的设置、bot 的默认设置和别的群的设置，都在私聊里改，说清是哪个群。
- 例外：群里写项目记忆不算改设置。它走 memory 工具，不发回执卡，没有［撤销］，bot 在回复里说一句；主人在桌面端改、移、删（3.6）。
- 判断模型能在聊天里改，包括改成决策模型（3.4）。本机还没填这家的 key 时拒绝新的切换，并告诉主人去桌面端或网页的决策模型设置页填，或者在终端里用 `vonvon secrets set`。聊天里只说填没填，不显示 key，末四位也不显示。有人把 key 发在聊天里，bot 不存、不复述，提醒他这个 key 已经进了会话记录，最好去那家服务换一个新的。设置 skill 不教 `vonvon secrets`，从 bot 的会话里调它会被拒（`docs/v1-plan.md` s23g）。这一条是 Claude 定的（第 11 节）。
- 谁能改由 daemon 判断，不由 agent 判断。daemon 知道这一轮是谁的消息触发的，只有主人和管理员触发的那一轮能改设置，别人的命令直接被拒。私聊本来只有主人和管理员能用，daemon 照样再查一遍。
- daemon 靠每条会话自己的令牌认出命令来自哪条会话：会话启动时 vonvon 把令牌交给这条会话的 MCP server，调用时带上。Claude 的会话不用令牌，工具本身就绑在会话上。没有有效凭证，或者不是私聊会话的设置命令，一律拒绝。
- 改完在卡片上显示改了什么，带［撤销］。角色设定、补充职责、智能提示词和记忆，受影响的会话下一轮就用上；skill 和 MCP 名单要等下一条会话，或者会话进程重开、恢复以后（3.6"改了什么时候生效"）。
- 回执来自 daemon 的已提交结果，列明影响的 bot、群或个人范围、改前改后、版本和生效时机。落盘失败不显示“已改好”；回执发送失败与设置失败分开记录，重发回执不重复修改。撤销核对当前版本和操作人的权限，旧回执不能静默覆盖新修改。不新增设置审批层。
- 回执还多两行：由谁的哪条消息触发（摘消息的前 60 字），和 bot 的说明（agent 写的为什么改，标明是 bot 说的）。诱导出来的修改，比如主人说"总结这个网页"、回执却是启用了一个 MCP 或改了允许的群，一眼就看得出（3.8"留下的风险"）。这两行是 Claude 建议的，owner 2026-10-18 没反对（第 11 节）。
- 私聊有一个"聊天改设置"开关，默认开着。关掉以后，私聊的会话也不装设置 skill，daemon 也拒绝它的设置命令。开关只在桌面端或网页里改，聊天里不改，因为关掉以后聊天里就打不开了。群里没有这个开关，第一版群里不装设置 skill、不能用设置命令；给群加开关放进第 10 节。这是 owner 第 29 题和之后的补充定的。
- 会话中途改了开关：设置命令的拒绝马上生效，因为是 daemon 判断的；skill 装不装跟着能力包走，要等私聊的下一条会话，或者会话进程重开、恢复以后（3.6）。
- 群里不能用的只是设置 skill 和设置命令。飞书 skill 和它用的只读查询命令不受影响，每个会话都能用，因为主区和话题要靠它互相查（3.5）。这一条是 Claude 定的，和 owner 说的"禁止使用 vonvon-bot 的 CLI"字面上不同，见第 11 节第 26 条。

- Claude 的只读、读写两档不再用 `bypassPermissions`。今天用它有两个缺口：关网时 Bash 仍能连外网，Write 能写到工作区以外（`approval-ux.md` 3.3 推断过）。不带沙箱时两个缺口都在（e02 第 1 节）。带上今天的沙箱也都在（e03，Mac 上 SDK 0.3.296，单次实测）：两个关网档的 Bash curl 外网都是 HTTP 200，走的是沙箱给 Bash 的 HTTP 代理（e04b）；读写档的 Write 能写工作区以外。今天的沙箱只挡住了 Bash 写工作区以外和 `/tmp`，只读档的 Bash 写工作区里也挡住了。
  - 换成上表以后（e03，同上）：写文件的 Bash 不进回调，由沙箱直接挡。只读档的 Bash 工作区内外和 `/tmp` 都写不进；读写档的 Bash 写得进工作区，写不进工作区以外和 `/tmp`。

  - Read、Write 出工作区进回调；只读档的 Write 写工作区里也进回调。Bash 读工作区以外不进回调，直接读到。
  - 回调只拒超出这一档的请求，不一律拒。一律拒的话，有两处比今天拒得多（e03、e03b）：
    - Read 读工作区以外：s31b 按真实路径对 `denyRead`、`allowRead` 粗名单放行，多个硬链接的普通文件一律拒绝。工作区内的 Read 也先过同一钩子，防符号链接绕过。Linux Bash 的目录快照缺口见 3.6。
    - 带 shell 变量的 Bash：s31 在 Linux SDK 0.3.296 实测，变量读取以 `decisionReasonType: other` 进回调，ask 规则是 `rule`，可以分开；放行后仍在沙箱里，工作区外写入和 `denyRead` 路径读取均被阻止。因此保留非规则、非安全确认的沙箱 Bash，明确申请退出沙箱的仍拒绝。Mac 任务 74 已在 Seatbelt 下复验变量 Bash 仍受沙箱限制，见 `docs/v1-plan.md` 的 s31 Mac 补验记录。
  - 代价是今天读写档的 Write 能往工作区以外写，换档后会被拒。
  - WebFetch、WebSearch：关网仍去掉工具并由回调兜底拒绝；开网显式允许。s31 Linux 实测，不设允许项的 WebFetch 会进回调；设置裸工具允许项后普通网站不进回调，命中网站 ask 规则的仍以 `rule` 进回调并在只读、读写档拒绝。
  - 各个根里两家的配置文件（3.6）在读写档下用拒绝规则挡：e02、e03b 测到 `.claude/` 下和 `.mcp.json` 的 Write 在 `acceptEdits` 下也走回调；加了拒绝规则后不进回调、直接被拒（e03b，只测了主工作区）。
- Codex 三档都保留 `never`：模型知道不能申请，就不会白白尝试。`never` 下没有标成只读的 MCP 工具会被拒（`approval-ux.md` 1.5），vonvon 自己的 MCP 要配 `approve`（第 9 节第 2 项）。
- 中途改档不用重开会话：Codex 每一轮的 `turn/start` 能带新的设置，Claude 运行中能 `setPermissionMode`，升档降档都是下一轮生效（实测，e02 第 3 节）。升到完全访问要求会话启动时带 `allowDangerouslySkipPermissions`，所以每条会话启动时都带上；resume 不恢复上次的档（`settingSources` 为空时测的），每次都明确传。Codex 一半还是推断。

**完全访问下还会问什么。** 不问权限。Claude 自己在任何模式下都会停下来问的少数几类，照样发卡问，和 Claude 自己的行为一致，比如用户在自己的 Claude 设置里写了"这类操作必须问"、删除关键目录（`approval-ux.md` 2.2）。这种卡只有主人和管理员能点，15 分钟没人点按拒绝。只读、读写两档下，这几类直接拒绝。实测里 `bypassPermissions` 下，没有规则时只有 AskUserQuestion 走到回调，写 `.claude/` 下的文件也直接放行（e02 第 1 节）。规则在 Mac 上测了项目设置里的（e03b，SDK 0.3.296，`settingSources: ['user', 'project']`，单次）：Bash 命中 ask 规则时进回调，放行后照常执行；命中 deny 规则直接被拒，不进回调；普通 Bash 不进回调。s31 在 Linux SDK 0.3.296 实测：项目和隔离用户层的 Bash ask、Edit ask 均进回调并标成 `rule`；删除临时工作区根进 `safetyCheck` 回调（实测拒绝），普通子目录删除不进回调。读写档的 `.claude/rules/`、`.mcp.json` 敏感路径提示同样是 `safetyCheck`，按真实路径判断后放行；完全访问档它们不进回调。这里只报告实测范围，不承诺每一种删除都要确认。`docs/plans/s31.md` 第 6.2 节的 Mac 补验已完成，见 `docs/v1-plan.md` 的 s31 Mac 补验记录；删除工作区根与敏感路径的本轮专项证据来自 Linux。

**卡片。** 所有要人点的卡片一个样：同样的版面、同样的状态、同样的"谁能点"规则。所有会话默认就有，不只在私聊。
- **运行卡**：流式输出、⏹ 停止、工具折叠、上下文仪表、子 agent 区（见 3.9）。等人回答时显示等待图标和"等 张三 回答（见下方卡片）"。
- **选项卡**：agent 问一个带选项的问题时（Claude 的 AskUserQuestion，Codex 的提问；Codex 只在计划模式下会问）。空提交时提示"至少选一项"。
- **确认卡**：只要"是 / 否"的确认，比如 Claude 的计划（ExitPlanMode）。按钮是［按这个方案做］［不行，我来说］。
- 完全访问下 Claude 自己仍要问的那几类，用同样的版面，按钮是［允许这一次］［拒绝］。

- 卡片写清后果：选了会怎样，不选会怎样。今天咖啡一下的卡片，社区群里有人看不懂按钮是干什么的（`approval-ux.md` 第 5 节）。
- 选项卡（含"其他"）和要打字回答的题：回复这张卡片，等于用你的话回答；能回答的人在同一个位置直接发新消息，也算回答。确认卡和完全访问下 Claude 自己要问的那几类只认按钮：等它们时打的字不算回答，照普通消息处理，插话或排队（owner 2026-10-19）。运行卡上的 ⏹，等于不回答并停止这一轮。
- 答完以后按钮去掉，换成一行结果，比如"张三 选了：方案 B 10:03"、"⏱ 15 分钟没人回答"、"⏹ 已停止"、"已失效（后台服务重启过）"。每种结局都改卡，不让按钮一直挂着。bridge 里咖啡一下的卡超时后按钮还在。
- 每张卡单独发一条消息，回复触发这一轮的那条消息，在话题里就发在话题里；卡片里 @ 能回答的人。不把按钮放进运行卡，因为运行卡在流式更新，按钮会和输出抢。卡片里的 @ 会不会提醒人要实测，不会就另发一条带 @ 的文字。

**谁能点。** 由 daemon 按点击人的 open_id 判断，不由 agent 判断。daemon 还要核对这张卡属于这个群和这条会话，转发出去的卡点了无效。

|---|---|
| 选项卡、确认卡 | 发起这一轮的人，管理员也能代答 |
| 完全访问下 Claude 自己要问的 | 主人和管理员 |
| bot 触发的那一轮（bot 之间对话） | 主人和管理员 |
| 云文档评论的会话 | 没地方放卡片：提问按"没人回答"处理，Claude 自己要问的直接拒绝 |

- 点的人不对时，回贴一条去重的小注，比如"只有发起人或管理员能回答"，和今天 ⏹ 的做法一样（`D/bot/handle-message.ts:2384-2397`）。第一次有效的点击生效。

**等待和超时。**
- 15 分钟没人回答：选项卡告诉 agent"用户没有回答"；确认卡和 Claude 自己要问的按拒绝处理。
- 等人回答时，空闲看门狗暂停，不然这一轮会被当成"没输出"杀掉。
- 同一条会话同时只显示一张待回答的卡，其余排队。
- 后台服务重启后，挂着的请求就没了。点到旧卡时，卡片自愈成"已失效（后台服务重启过）"，和今天的 `healDeadRunCard` 一样（`D/bot/handle-message.ts:2398`）。
- 子 agent 发起的卡片，发在父运行卡所在的位置，卡上写"子 agent X 问……"。
- 要填密码这类敏感信息的问题，不在群里显示输入框，请用户去私聊回答：bot 私聊每个能回答的人一张带输入框的卡，群里的卡只写"已在私聊里回答"，答案不显示。能回答的人在私聊里直接发一条消息，恰好只有这一题在等他时也算回答。等这种题时，能回答的人在群里打字不算回答，bot 提示一次去私聊，这条消息照普通消息处理（owner 2026-10-19）。

**完成提醒。** 规则群照 bridge 的四种提醒模式发，手动模式下运行卡上有"完成后提醒我"。智能群不按提醒设置发，卡上也没有这个按钮：做完要不要提醒谁，由 agent 自己在回答里 @ 决定，程序把回答里的 @（真人和 bot）发成一条带真 @ 的文字消息（3.4"bot 之间"），卡片更新本身飞书不提醒。只有一种例外：一轮出错（包括后端失败、超时，或结果未能送到群里，比如最终卡片更新失败），且发起人是真人，程序替 agent @ 他说一声；正常结束且结果已送达、被人停掉、发起人是 bot 的，不发（owner 2026-10-19，第 11 节；“出错”的范围由 Claude 同日澄清）。

**在聊天里改设置。** 不发授权卡，也不按权限档拒绝。owner 第 29 题定了：改 vonvon 设置都走设置 skill 和设置命令（agent 经 vonvon 自己的 MCP 工具调），只有私聊的会话有，群里没有（3.7）。私聊的开关开着时，主人和管理员触发的那一轮改了就直接生效，带撤销。

留下的风险：agent 读到的文档或网页里可能藏着"去装这个 MCP"之类的指令，诱导主人或管理员触发的那一轮去装 MCP、装含脚本的 skill、加目录、升档、开网，或者改允许哪些群用（名单清空就是所有群都能用）、加管理员、放开群里允许使用 bot 的成员。daemon 按触发人判断，挡不住这一种，只读、读写档的会话也能这样给自己升档。第 29 题问的时候写了这个风险，owner 选了按位置装不装设置 skill 来管，所以私聊里有这个风险，群里没有。缓解：这几种扩大能力的改动，改完的卡片上单独标出来，带［撤销］（Claude 加的，第 11 节第 29 条；改允许的群、加管理员和放开群里的成员是 2026-10-18 聊天里能改它们以后加进来的）；每张改设置的回执还写明由谁的哪条消息触发和 bot 的说明（3.7）。

### 3.9 子 agent

- 子 agent 显示在父运行卡的"子 agent 区"，一行一个：状态、名字、在做什么、几步、用了多久，嵌套的缩进。点开看最近 5 步和结果。每行有"停止"，运行卡的 ⏹ 全停。不给每个子 agent 发一张卡：飞书对群里所有 bot 有每秒 5 条的共用限额。
- 每一行绑定稳定的子 agent 身份，最近 5 步之外显示省略计数。折叠过程仍保留待回答入口、失败和停止状态；父回合结束不能隐藏仍在运行或等待输入的子 agent。子 agent 的单独停止不能误停父回合或其他子 agent。
- 子 agent 身份用细线机器人图标；工具类型图标复用主流程。主流程、子 agent 和展开步骤的正常运行与成功完成均不附加状态符号，保留现有计时与进度信息。需要关注的状态共用简洁符号：红色叉表示失败，灰色方框表示停止，橙色暂停符号表示等待，橙色感叹号表示状态未知或异常。逐行状态不重复写“运行中”“已完成”等文字；汇总数量、失败原因、等待谁回答和未收到结束消息的说明照常保留。
- **一张运行卡包含这一轮的所有子 agent，子 agent 都跑完了，这张卡才算结束。**
  - Codex：父回合可以先答完，Vonvon 后端会等运行中的子 agent 都结束，再收尾运行卡。等待时卡上写"主回合已答完，等 N 个子 agent 结束"，整停和单停照常；同一会话的新消息排队，等这张卡收尾再跑（s35）。
  - Claude：不一样。Claude Code 的子 agent 默认在后台跑，经 Agent SDK 用时也是；主回合可以先结束，子 agent 跑完再通知 Claude 起新的一轮（code.claude.com/docs/en/sub-agents）。实测里一条消息出了 4 到 6 个结果。设置 `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` 后，子 agent 一律在前台跑，主回合等它们都结束，一条消息只有一个结果，几个子 agent 之间仍然并行（实测，`docs/research/2026-10-14-v1-spikes/e01-background-tasks.md`）。代价是它同时关掉后台 Bash，比如 bot 不能在后台起一个开发服务器再结束这一轮；模型要在后台跑命令时会先报错一次，再改成前台跑。第一版在 bot 的 Claude 会话里打开这个开关，两家行为就一致了。这是 Claude 的决定。s35 开工前在 JP-VPS 的完全访问档实测：两个前台子任务各执行 20 次 sleep 17，RPC 整停后 4.22 秒运行卡进入已中断，日志为优雅停；30 秒后本次已归属的子命令无残留。Monitor 仍可加载并启动，但三次 tick 没有回传，本次没有验到完整输出。飞书客户端的 ⏹ 点击仍留 M6 owner 验收。
- 子 agent 跑的时候，群里的新消息按今天的规则插话或排队，只给父 agent。第一版不能直接跟某个子 agent 说话。
- Codex 的子 agent 跟着用户自己的 Codex 设置走：Vonvon 不在会话里替用户打开或关掉 `features.multi_agent`，用户开了就显示子 agent，没开 Codex 那一侧就没有子 agent，只有 Claude 一侧有（owner 2026-10-19）。Vonvon 自己的标题任务和判断线程照旧关着子 agent。
- s34a 已修复 Codex 丢弃子线程事件和 Claude 子 agent 步骤混进主过程的问题。Codex 由 `D/agent/codex-appserver/backend.ts` 的 `routeNotification` 登记并接收子线程通知，Claude 由 `D/agent/claude-agent/event-map.ts` 的子通道隔离步骤。

### 3.10 后台服务和崩溃

owner 的话："后台服务不要依赖 Electron，因为 Linux 上没有桌面端，它可能就装一个 Daemon 后台服务。"调研见 `docs/research/2026-10-14-session-approval-service/service.md`。

**后台服务由 daemon 自己装。**
- 用 `vonvon service install`、`uninstall`、`status` 注册、卸载和查看。桌面端只调用打包在里面的同一个命令行。不用 Electron 的 `agentService`，也不用 SMAppService：这两种都要求服务登记在 .app 名下，Linux 上没有对应的东西。
- macOS：用户级 LaunchAgent `com.vonvon.bot.daemon`，plist 写在 `~/Library/LaunchAgents/`（`D/service/identity.ts:33`）。用户登录后启动，能用钥匙串里的 Claude 登录和 Codex 的登录（推断，要实测）。Mac 设成自动登录时，就等于开机启动。
- Linux：systemd 用户服务 `vonvon-bot.service`。安装时检查 linger：没开就问一句，同意后执行 `loginctl enable-linger`。这样开机就启动，退出 SSH 以后 bot 也还在跑。
- 从 dmg 装的，服务用 app 里的 Electron 程序以 Node 模式运行（`ELECTRON_RUN_AS_NODE=1`），不用另带一份 Node；从 npm 装的，用用户自己的 `node`。这只是借 Electron 的 Node 来用，服务的生死由 launchd 管，桌面窗口开不开都一样。代价是 app 被删或挪走以后，服务就起不来了，所以桌面端提供"关闭登录时启动"，文档写清卸载步骤。
- 注册以后，系统的服务管理器是唯一拉起 daemon 的。`vonvon daemon start` 和桌面端都请它去启动，不自己再起一个。停止走 `vonvon daemon stop`：先排空，再正常退出，管理器就不会再拉起它。
- 退出桌面端不停 bot。首次运行清单里加一步"登录电脑时自动运行 bot（推荐）"。跳过的话，就像今天一样起一个分离的 daemon，并提示"这样崩溃后不会自动重启"。
- macOS 桌面端常驻状态栏（owner 2026-10-25）：关闭窗口同时隐藏 Dock 图标，应用和状态栏继续运行；从状态栏打开时恢复窗口和 Dock 图标。用户主动退出只保留状态栏的「退出 Vonvon Bot」，仍经过未保存草稿确认；应用菜单不再提供退出项或 Cmd+Q 快捷键。「应用与启动」不单列「窗口与退出」组，只在启动选项下说明这一行为。系统退出和应用更新继续走原有清理流程。
- 这些代码大部分已经在 main 上，只是没接线：launchd 和 systemd 的安装事务（#271、#274）、服务定义（#246）、退出码（#276）。今天 `vonvon service install` 直接报错（`D/cli/commands/service.ts:5`）。

**崩溃了自动重启。** 服务管理器在 daemon 异常退出后重启它（plist 的 `KeepAlive`、unit 的 `Restart=on-failure`，`D/service/definitions.ts:81`、`:85`）。两边都不会在连环崩溃时自己停下来，所以上限由 daemon 自己判断：
- daemon 和每个 bot 的子进程都加全局的异常兜底：崩溃前在 `~/.vonvon-bot/crash/` 写一条记录（版本、哪个 bot、错误的第一行、运行了多久），再退出。被系统强制结束、没留下记录的，下次启动时补一条"被系统强制结束"。今天没有任何崩溃记录（`D/cli-bridge/ipc.ts:24-25`）。（s17 已加 daemon 主进程的；bot 子进程的在 s18）
- 10 分钟内崩溃 3 次，daemon 进入暂停：网页和桌面端照常能打开，显示原因；bot 不连飞书，不跑 agent。不自动恢复，等主人点"恢复运行"，或执行 `vonvon daemon restart`；`vonvon daemon stop` 再 `vonvon daemon start` 也算恢复。下次登录或开机时重新计数。停止和重启过程中出的错照样记录，不计入 3 次。暂停期间 daemon 自己又起不来（比如端口被占），后台服务就不再拉起它，`vonvon daemon status` 仍显示已暂停，`vonvon daemon restart` 恢复。（s17 已做；网页上的原因和"恢复运行"在 s18）
- 某一个 bot 的子进程 10 分钟内崩溃 3 次，只暂停这一个 bot，别的照常。今天子进程会无限重试（`D/bot/supervisor.ts:115-131`）。

owner 说过"崩溃报错就好了"，让 Claude 斟酌。自动重启是 Claude 加的：后台服务崩了，群里的人只会看到 bot 不回，主人不一定在电脑前。

**怎么告诉主人。**
- 崩了一次、已经自动恢复：桌面端的诊断页记一条；bot 给它的主人发一条私聊"刚才崩溃过一次，已自动恢复。原因：……"。daemon 或这个 bot 重新起来、稳定 30 秒后再发；30 秒内又崩的只发后面那条（"10 分钟内崩溃了 N 次"）。带恢复请求起来的（`vonvon daemon restart`、"恢复运行"）不再补发上一次的"已自动恢复"。
- 连环崩溃、已经暂停：诊断页顶上一条红条，带"恢复运行"按钮；马上私聊"10 分钟内崩溃 3 次，已停止自动重启"。
- daemon 主进程崩溃时所有 bot 一起下线，只由最早加入的 bot 发给它的主人，列出受影响的 bot；几个 bot 的主人不是同一个人时，别的主人收不到这一条（飞书按应用给每个人不同的 open_id，daemon 看不出是不是同一个人）。每个 bot 每 10 分钟最多发一条，进入暂停的那条不受这个限制。
- 私聊只写一行原因，不放调用栈和本机路径。第一版不上传崩溃信息。
- 私聊直接调发消息的接口，不靠长连接，所以暂停时也能发。2026-10-16 实测：没开过 bot 私聊的主人也收得到，手机和电脑都弹通知。发不出去（网络错误、飞书限流）时隔 1 分钟、5 分钟各再试一次；飞书拒绝的不再试，写进 daemon 日志。进入暂停的私聊排上就保存在本机，主进程被强制结束或关闭时没发完，下次启动仍在同一轮暂停、且不超过 24 小时就补发。恢复运行、重启机器或暂停已解除时不补发旧通知。飞书只在 1 小时内按消息标识去重，超过这个时间补发可能重复。（s18b、s18e）
- Linux 上用 `vonvon daemon status` 看服务状态和最近的崩溃。`vonvon service status` 显示服务管理器记的上次退出和自动重启次数；关闭时有几步失败，日志和终端里每一步各一行（s17b）。
- 重启或停止时还在排队、没开始处理的消息（包括 `/new`、`/compact` 期间暂存的、排着的 `/compact` 和等并发槽的那一轮）：bot 起来连上飞书后，每个群在最新的那条下面回一句"刚才重启了，这条没处理，请再发一次"，这个群不止一条时写明还有几条，话题里的回在话题里；停了 10 分钟以上才起来时开头写"bot 停了一阵"，超过 24 小时不回。诊断页"最近没回的消息"每个群记一条。bot 子进程自己出错崩溃时，也记录当时还在排队的消息；正常关闭时，刚收到、还在准备会话的第一条也记录。重启过程中新发来的消息不会丢：关闭一开始就断开长连接，飞书过几分钟重推，bot 起来后照常回答。记不下来的：bot 子进程被系统强制结束（kill -9、内存不够）；macOS 上 daemon 主进程被强制结束时 launchd 连 bot 的子进程一起结束（推断，M4 的 Mac 检查确认）。owner 2026-10-16 让 Claude 定。（s18c、s18e）

**Linux 上只装后台服务。** Linux 没有桌面端，第一版做一个命令行版（代码已有；0.7.0 不发布它，Linux 的发布验收和 npm 发布留到以后，owner 2026-10-26）：

**保留**：

- 群绑定和它们的设置：群类型、免 @、权限、网络、白名单、后端、模型，换算成规则模式。设了访客档、和管理员档不同的群，取两档里更严的那一档，迁移结果里列出这些群。

- 评论提示词、已发文件的记录。

bot 的角色设定、记忆、skill 导入后为空，行为和今天一样。

**会感到的变化**（写进迁移说明）：
- 原来的"群 = 仓库目录"，变成"这个群的主工作区覆盖"，目录本身不动。
- 多 bot 群里，bot 不再进别的 bot 的话题，主区命令要 @。
- "全部回复"里，引用 bot 的消息就算点名它。
- 关了自动压缩的群变成自动压缩。
- 云文档评论的会话没设档时按 bot 默认的工作区可写跑，不再是完全访问（3.12）。
- 网页控制台和 `feishu-codex-bridge` 命令由桌面端替代。
- 私聊控制台没了。
- 要补一项新权限 `im:message:readonly`。

**失去**：Windows、WSL 上的用法（bridge issue #1、#23、#42 的用户，占比不知道，bridge 没有遥测）。owner 说原来没有 Linux 用户，所以不做 Linux 上的导入。还会失去日志、缓存、旧目录已下载的 Claude SDK（需要时由用户选择后重新下载到托管目录）和 Codex Fast。咖啡一下也没了（3.12）：迁移时卸掉 bridge 装进 Claude Code 和 Codex CLI 的 hook，之后这两处的审批照常在终端里问。

**怎么迁**（只做 macOS）：
1. 桌面端首次运行发现 `~/.feishu-codex-bridge`，就显示导入页。
2. 只读预检：每个 bot 的群数、目录是否还在、密钥能否解开、hook 是否装了、bridge 是否在跑、bridge 自己装的 codex 在不在。
   - 有顶层 `processes.json`、没有 `bots.json` 的旧平铺目录，只读提示“这个 bridge 还是旧的目录格式。先照常启动一次原来的 bridge，让它升级目录，再回来重试导入”；不启动或停止 bridge，不改文件，不报没有数据，不跳过 bot。重试重新预检，有 `bots.json` 后照常导入全部 bot（Claude 2026-10-19 定，按 s59 开工说明）。
3. 调 bridge 自己的 `stop`，它会删 plist、去掉自启。
4. 用 bridge 的锁格式给每个 bot 占住它的 `bots/<appId>/processes.json`，防止有人手动 `run`。锁挡不住 `start`：`start` 不看锁，会把自启装回来，launchd 拉起的 `run` 再一遍遍被锁拒掉（e07：锁在函数层面实测过，`run` 和 `start` 的表现是读代码，真机在 e08）。
5. 复制数据，用新密钥重新加密。
6. 找不到别的 codex 时，引用 bridge 那份，或者装一份。
7. 备份后卸掉 bridge 装的 hook。
8. 启动全部 bot，等长连接连上。
9. 再查一次 bridge 的 plist 和 launchd 任务，还在就再 `stop` 一次；然后写迁移标记，显示回执"旧目录不要删，空白项目还在里面"。

任何一步失败就回滚：先放掉 bridge 的锁，再 `start` bridge，不然被拉起的 `run` 会被这把锁拒掉。

- 一次导入全部 bot，因为 bridge 是一个服务带全部 bot。
- 密钥用主机名加用户名派生，改过主机名就解不开，这时让主人扫码刷新。
- 空白项目目录不搬，原地引用。搬了 Claude 会话会找不到。
- 复用草稿 #226（V8 的 bridge 导入事务）里的预检、密钥解密和 hook 改写代码（用来卸掉 hook），约 640 行。不采用它的"准入互斥锁"：那个锁在已发布的 0.6.14 里不存在，会拒绝所有现有用户。
- bridge 出最后一版：从 0.6.14（`6698118`）开分支，只加三样东西：通知所有人，看到迁移标记就拒绝启动，`stop` 和 `status` 时提示。Mac 用户拿到下载地址；其他平台的用户只收到通知，继续用 0.6.14。2026-10-26 起这一版不再是 0.7.0 的发布条件，是否发、发成什么样由 owner 另定（第 8 节第 4 条）。
