## 1. 一句话

Vonvon Bot 是一个 macOS 桌面应用；Linux 上可以只装后台服务，用命令行和网页管理（3.10）。主人在自己的 Mac 上养几个飞书机器人，每个 bot 有自己的个性、记忆、工作区、代码仓库、skill 和 MCP，能进不同的群，在每个群里表现不同。干活用主人本机已经登录的 Codex 或 Claude。

和 feishu-codex-bridge 最大的区别：bridge 的行为大多靠规则设定，Vonvon Bot 主推**智能模式**。bot 自己判断要不要接话、要不要开新话题、要不要和别的 bot 搭话。主人可以直接跟 bot 聊天来改它的设置、让它建群（在私聊里，3.7）。bridge 原来的规则保留为**规则模式**。

给谁用：
1. 正在用 feishu-codex-bridge 的 Mac 用户。迁过来后，群、话题、卡片、命令和旧会话都保留。
2. 有 Codex 或 Claude 订阅、想在飞书群里有一个"像同事"的 bot 的个人和小团队。他们不一定用 GitHub，也不一定会装 Node。

不给谁用：Windows 用户；想在 Linux 上用桌面应用的人，Linux 只有命令行版；没有 Codex 或 Claude 订阅的人；想要云端托管、不开电脑也能用的人。

## 2. 叫法

| 叫法 | 意思 |
|---|---|
| bot | 一个飞书机器人（一个飞书应用）。名字、头像、简介以飞书为准 |
| 主人、管理员 | 能管这个 bot 的人，见第 6 节。两者能做的事一样 |
| 群主区 | 群里不在任何话题里的地方 |
| 话题 | 飞书话题，包括话题群里的帖子 |
| 会话 | 后台的一条 Codex 线程或 Claude 会话。bot 记得的对话内容都在这里 |
| 后端 | 跑会话的那一家：Codex 或 Claude。见 3.11 |
| daemon、后台服务 | daemon 是本机跑着各个 bot 的进程；后台服务是登录电脑后拉起 daemon、崩溃后重启它的系统服务，见 3.1 第 3 条和 3.10 |
| 子 agent | 一个会话临时分出去、并行干活的帮手，干完就结束 |
| 智能模式 | 群设置。bot 自己判断接不接话、开不开话题、和不和别的 bot 搭话 |
| 规则模式 | 群设置。bridge 原来的规则：仅 @ 或全部回复；主区"开话题"或"连续" |
| 会话方式 | 群设置，绑定群时三选一：多会话（@ 我开新会话）、单会话（整群一条会话）、智能。只管群的结构和背后会话的关系，不管要不要 @；前两种是规则模式，后一种是智能模式，见 3.4 |
| 判断模型 | 智能模式里决定回不回、回在哪里的模型。分两类：语言模型是各家订阅里的小模型；决策模型是专门做判断的 API，只回选项和概率，第一版只有 TypeSafe 的 Jev。见 3.4 |
| 工作区 | bot 产出文件的目录，可写。主工作区是会话的工作目录 |
| 代码仓库 | 本机的一个 git 目录。和工作区一样传给 agent，区别在界面和指令 |
| skill、MCP | 给 agent 用的技能包和工具服务。本机各有一个库，bot 和群各有名单 |

产品文案里叫"Claude"，不叫"Claude Code"，这是 Anthropic 的品牌规定（code.claude.com/docs/en/agent-sdk/overview）。界面上 bot 写成"Bot"；界面上每个概念怎么写，见 `docs/v1-plan.md` 第 5 节的叫法表。

## 3. 第一版做什么

### 3.1 桌面端

1. 桌面应用就是控制台，不再引导用户开网页。同一套页面也能用本机浏览器打开，但只在本机：daemon 只监听 `127.0.0.1`（`D/server/http.ts:184`），第一版不开放局域网和远程访问。
2. 签名加公证的 dmg，带更新源。现在更新源是空的（`packages/desktop/src/updates.ts:46`）。出 universal 包，Intel Mac 也能装。
3. 后台服务：bot 跑在后台服务里，登录电脑后自动启动。Mac 设成自动登录时，就等于开机启动。后台服务由 daemon 自己装，不依赖桌面应用，崩溃后自动重启，见 3.10。
4. 首次运行是一张清单，每一步都实时检测：扫码建飞书应用（建好的 bot 默认启用，马上连上飞书）→ 一键开权限 → 检测事件订阅 → 检测应用已发布 → 检测 Codex 或 Claude 已安装、已登录、版本够用 → 登录电脑时自动运行 bot（推荐，3.10）→ 可选从 bridge 导入。v2 里还没有人从头扫码成功过（`docs/research/2026-10-14-strategy/runnable.md` 第 1 节），这一条第一版必须走通。
5. 建新 bot 只走上面的向导，不在聊天里做。Mac 上在桌面端，Linux 上在网页或终端里（3.10）。
6. Bot 页：个性、规矩、工作区、代码仓库、skill、MCP、记忆、智能提示词、判断模型、所在的群（还没设置好的单列一组"待设置"，3.4）。
7. 群详情页：这个 bot 在这个群里的会话方式（3.4）和各项覆盖，见 3.2。被拉进来、还没设置好的群也列在这里，能在这里设置。
8. 状态与诊断页：每个 bot 的连接状态，Codex 和 Claude 的版本检查，最近没回的消息和原因（包括智能模式判断"不回"的原因；用决策模型判断的，写选项和把握度）。选了决策模型、本机却没填它的 key 的 bot 和群，单独列一行。目录放错了位置的旧群（3.3）也单独列一行，写明到哪里换目录。用量页显示判断调用的次数。
9. 密钥页：集中管理要 key 的服务（owner 2026-10-18 要的）。整台机器一份，所有 bot 共用，不按 bot 分。第一版列的是决策模型（3.4），现在只有 TypeSafe 的 Jev。Codex 和 Claude 用本机自己的登录（包括它们自己的 API key 登录），vonvon 不经手它们的 key，不列；以后 provider 要 vonvon 来存 key 时（比如第 8 节第 2 条说的 Claude 改成只支持 API key，或者以后加的后端），也放在这里。
   - 每一项能填、能换、能删。页面只显示填没填和末四位，不回显全文；换的时候整串重填。填完马上试一次能不能用（TypeSafe 是调它列模型的接口，不发群消息），显示"能用""key 不对"或"连不上"。删之前列出哪些 bot 和群选了这家的决策模型，删了以后这些群照 3.4 出错的规矩走：要判断的消息，被 @ 的照常回，没 @ 的不回。
   - key 存在本机，和 bot 的 App Secret 同一个加密库（`~/.vonvon-bot/secrets.enc`，AES-256-GCM，主密钥是同目录下只有本人能读的 `master.key`），不进 `config.json`、快照和日志。bot 的 App Secret 由扫码写入和刷新，不在这页列。
   - 终端里用 `vonvon secrets`：`list` 看状态，`set <名字>` 从标准输入读 key（TypeSafe 的名字是 `typesafe-api-key`；key 不写在命令参数里，免得进 shell 的历史），`remove <名字>` 删。聊天里不收、不显示 key（3.7）。
10. 没有 Windows，也没有 Linux 桌面。Linux 上只装后台服务，见 3.10。

### 3.2 bot 模型

一个 bot 有三层：
1. **飞书身份**：名字、头像、简介，来自飞书应用，vonvon 不改。飞书能不能让同一个机器人在不同的群里显示不同的名字：没查到，所以"千人千面"体现在说话方式、工作区、仓库、skill 和记忆上，外观不变。
2. **bot 默认**：个性、规矩、工作区、仓库、skill、MCP、公共记忆、智能提示词、判断模型。
3. **群内覆盖**：这个 bot 在某个群里另外的设置，以及这个群自己的记忆。没设的项继承 bot 默认；权限档、网络和后端例外，群在建立时写定，见下表。

| 项 | bot 默认 | 群内 | 规则 |
|---|---|---|---|
| 名字、头像 | 来自飞书 | 不能改 | — |
| 个性 `SOUL.md` | 有 | 可补充 | 群的默认加在 bot 后面，也可以选择整段替换 |
| 规矩 `AGENTS.md` | 有，可选 | 不能改 | 只在 bot 层 |
| 工作区 | n 个，1 个主的 | 可覆盖 | 群没设时，在默认位置给这个群建一个目录，见 3.3 |
| 代码仓库 | 0 到 n 个 | 可覆盖 | 只接本机已有的 git 目录，不接 git 地址 |
| skill | 启用名单 | 可增、可减 | 实际生效 =（bot 启用 ∪ bot 自己的 skill ∪ 群增加）− 群移除，bot 自己的 skill 见 3.6 |
| MCP | 启用名单 | 可增、可减 | 实际生效 =（bot 启用 ∪ 群增加）− 群移除 |
| 记忆 | 公共记忆，所有群都看 | 本群记忆，只在本群看 | 见 3.6 |
| 智能提示词 | 有，带内置默认值 | 可覆盖 | 只在智能模式下用 |
| 判断模型 | 有，默认是这个 bot 那家订阅里的小模型 | 可覆盖 | 只在智能模式下用。分语言模型和决策模型两类：语言模型从这个 bot 后端的模型列表里选，或者手填模型 id，再选推理强度；决策模型从 vonvon 支持的列表里选，第一版只有 TypeSafe 的 Jev，要在密钥页填 key（3.1）。见 3.4 |
| 会话方式（智能或规则模式） | 无 | 多会话、单会话或智能 | 只在群层，绑定群时选，见 3.4 |
| 权限档 | 默认值，给私聊用；云文档评论没单独设时也用它（3.12） | 群在建立时写定自己的档，之后可以改 | 改 bot 默认不影响已有的群。bot 自己建的群是完全访问，被拉进的已有群是只读、关网；旧数据没写档的按完全访问、关网。见 3.8 |
| 运行中来了消息：插话或排队 | 默认值 | 可覆盖 | 见 3.5。群里没设就继承 bot 的；Claude 不支持插话，照样排队（s21） |
| 聊天改设置：私聊里装不装 vonvon 设置 skill、能不能用设置命令 | 开，可以关 | 没有这一项：群里不装设置 skill，不能用设置命令 | 只对私聊，见 3.7 |
| 网络、后端、模型 | 默认值，给私聊用；云文档评论没单独设时也用它（3.12） | 群在建立时写定后端和网络，模型可以覆盖 | 和今天一样，改 bot 默认不影响群：新群的网络见 3.8，后端在建群和绑定时选（3.11）；旧数据没写后端的群用 Codex，没写网络的关网。群没设模型时，bot 的默认模型只在后端相同时生效 |

### 3.3 磁盘上的位置

```
~/.vonvon-bot/
  skills/                       本机 skill 库
  mcp/                          本机 MCP 库
  projects/<bot 名>/            bot 主工作区的默认位置
    groups/<群名>/              群没设工作区时的默认目录
  bots/<appId>/
    config.json                 bot 设置，含工作区、仓库
    projects.json               每个群一条，含群的覆盖
    SOUL.md                     bot 个性
    AGENTS.md                   规矩，可选
    SMART.md                    智能提示词，不存在时用内置默认值
    skills.json  mcp.json       启用名单
    skills/                     这个 bot 自己的 skill，只给它用
    memory/shared.md            公共记忆
    memory/dm/<open_id>/dm.md   每个主人或管理员的私聊记忆，一人一个目录
    quarantine/                 记忆文件被换掉时 daemon 挪进来的，不读（3.6）
    groups/<chatId>/
      SOUL.md                   本群个性补充
      SMART.md                  本群智能提示词覆盖
      skills.json  mcp.json     {"add": [...], "remove": [...]}
      memory/group.md           本群记忆
```

- 工作区默认放在隐藏目录 `~/.vonvon-bot/projects/` 下，和今天一样（`D/config/paths.ts:108`），可以在桌面端改到别处。比今天多一层 `<bot 名>/`：今天所有 bot 共用这个目录，两个 bot 的同名项目会落进同一个目录（推断，`docs/research/2026-10-14-v1-definition/v2-fit.md` 第 8 节第 6 条）。
- 每个群默认有自己的目录。共用一个目录的话，B 群的会话能看到 A 群产生的文件，和"每个群的记忆分开"矛盾。
- 目录名按建立时的名字取，之后不跟着改名，重名时加一个短后缀，"/"等字符替换掉。
- vonvon 建的这些目录（bot 的主工作区、`groups/` 和群的默认目录）被删了，下次用到时建一个空的。projects 根也不在了，只在它所在的文件夹还在、而且和它原来在同一块盘上时建回来；外接盘没接上（projects 根在盘里，或者它就是盘的挂载点）时不建，提示接上后重试。整机迁移、从备份恢复或整份复制回来以后，目录还在原来的路径，但已经不是 vonvon 记下的那一个，绑定和注册会停下来，提示主人确认目录没问题后在终端运行 `vonvon bot repair-dir <bot 名>`，按现在的位置重新记录。这类提示和工作区被拒的原因都是中文，不带完整路径，因为群里的卡片也会显示它们。
- 群解绑后再用默认目录绑回来，回到原来的目录，包括早期版本建在 `projects/<群名>/` 下的旧群。早期版本把一些群的目录放错了位置（某个 bot 自己的目录、projects 根本身、数据目录里 `projects/` 以外的地方，或数据目录的上级），这些群不回去，在状态与诊断页列出来（3.1 第 8 条），由主人到群详情页里换目录；vonvon 不搬文件。
- 定义文件都是 markdown 和 json，主人可以直接用编辑器改。它们不进用户的代码仓库。主工作区（会话的 cwd）里的 `AGENTS.md`、`CLAUDE.md` 照旧由 agent 自己读；Claude 默认只在 cwd 和上级目录都没有 `CLAUDE.md` 时才读 `AGENTS.md`，按会话的开关能让它两份都读（Claude Code 2.1.296 实测，`docs/research/2026-10-16-bot-home/multi-workspace.md` 4.2、4.4）。其余工作区和代码仓库里的，两家默认都不读，vonvon 在指令里让 agent 先读（3.6）。
- vonvon 不往工作区写任何文件。个性、规矩、记忆、名单和 bot 自己的 skill 都只在 `bots/<appId>/` 下，由 vonvon 交给会话（3.6）。所以工作区里已有的文件不会被覆盖，工作区只读也不影响 bot 记东西。
- 会话照旧从工作区起，不从 bot 自己的目录起（owner 2026-10-16 定）。这样主工作区里的 `CLAUDE.md`、`AGENTS.md`、skill 和 MCP 由两家原生加载，Codex 一侧还要看 vonvon 传的信任设置（3.6）。原生加载只限主工作区：其余工作区和代码仓库在哪种做法下都是附加目录，那里的 MCP 和 `AGENTS.md` 两家都不加载，Claude 默认也不读那里的 `CLAUDE.md`，只加载 `.claude/skills`，Codex 连 skill 也不读（Claude Code 2.1.296、Codex 0.163.0 实测）。新群的主工作区默认是 vonvon 建的空目录，代码仓库作为附加目录接上（3.2，`docs/v1-plan.md` s36），所以默认情况下仓库自己的 `CLAUDE.md`、MCP 和 Codex 的 skill 都不会原生加载。从 bot 的目录起的话，连主工作区也成了附加目录；今天的代码里，只读档、能发哪些文件也只按会话目录判断。调研见 `docs/research/2026-10-16-bot-home/`。

### 3.4 群：智能模式和规则模式

每个群对每个 bot 有一个开关：智能模式或规则模式。

**智能模式**一起管三件事：
1. 要不要接话。
2. 群主区来了一件新事，要不要开一个新话题来回。
3. 要不要和别的 bot 搭话。

**规则模式**就是 bridge 原来的设置：回复方式选"仅 @"或"全部回复"（界面上叫免 @：关是仅 @，开是全部回复），群主区选"开话题"或"连续"。规则模式下 bot 之间互相看不到，和今天一样。

**会话方式。** 界面上不分"智能模式""规则模式"和"主区方式"，绑定群时只选一项会话方式。它只管群的结构和背后会话的关系，不管要不要 @ 才回：要不要 @ 是另一项"免 @"设置，也就是规则模式的回复方式（owner 2026-10-16）。按下表的顺序列，每项一个主标题、一行副标题：

| 顺序 | 叫法 | 主标题 | 副标题 | 等于 |
|---|---|---|---|---|
| 1 | 多会话 | @ 我开新会话 | 在主区 @ 我就开一个话题，一个话题一条会话，几件事各聊各的 | 规则模式，主区"开话题" |
| 2 | 单会话 | 整群一条会话 | 主区一条会话，上下文一直连着；想另起一件事，开个话题和我聊 | 规则模式，主区"连续" |
| 3 | 智能 | 智能开话题 | 主区一条会话，不用 @ 我也会看情况接话；聊到新的事，我自己开话题、起新会话 | 智能模式 |

- 不管哪种方式，一个飞书话题就是一条新会话（3.5）。三种的区别在主区：多会话的主区不留会话，@ bot 就自动开一个话题；单会话的主区是一条会话，要开新会话就由人开话题、在话题里和 bot 说；智能和单会话一样，只是 bot 自己判断每句话回不回、要不要开新话题，开了新话题也是一条新会话。
- 多会话和单会话再有一项免 @，绑定群和建群时不选就按默认：多会话开着，话题里不用 @ 也回，主区照旧要 @ 才开话题；单会话关着，要 @ 才回。智能没有这一项，回不回由 bot 判断。bridge 和 s21 之前，被拉进来的单会话群默认关，bot 自己建的单会话群默认开（`D/project/registry.ts` 的 `defaultNoMention`）；s21 起新建的单会话群也是关，已有的群不变。
- 话题群和话题形式群没有主区，一个帖子一条会话，多会话和单会话在那里没有区别。卡上把这两项合成一项"按话题聊"，和"智能"二选一；选了"按话题聊"再选免 @，不选就开，和多会话一样（Claude 2026-10-19 定）。
- 飞书里的设置卡不预选任何一项，也不标"推荐"：产品上主推智能，卡上不替人选。桌面端和网页建群、加入已有的群时，会话方式默认多会话，收在"更多设置"里，收起时摘要行写出当前值，比如"多会话 · 免 @ 开 · 新建文件夹"，不用展开就看得见（owner 2026-10-18，第 11 节）。命令行绑定群和建群时必须带会话方式。
- 副标题说的"一条会话"都指主区。
- 上面的主标题、副标题，免 @ 的默认和话题群的问法，是 Claude 按 owner 的意思定的（`docs/v1-plan.md` 第 5 节）。

**被拉进已有的群时。** owner 2026-10-16 定了绑定时选工作区和会话方式；卡上还有哪几项、发给谁、设置好之前怎么回，是 Claude 定的（`docs/v1-plan.md` 第 5 节）。bot 被拉进来，先不在群里干活，私聊发一张设置卡：拉它进群的人是主人或管理员，就发给这个人；不是，就发给主人，写明谁把它拉进了哪个群。卡上有：
1. 会话方式，按上表；下面还有一项免 @，只对前两种算数，选了智能时不用管它（卡上的表单藏不了它，写在提示里）。
2. 工作区：默认按 3.3 给这个群建目录，也能填本机已有的目录。
3. 后端：默认用 bot 的。
4. 权限档和网络：显示默认的只读、关网（3.8），设置好以后在群详情页或私聊里改。

选好会话方式、点［绑定］才算设置好。设置好之前，有人在这个群里 @ bot，bot 只回一句"主人还没设置好这个群，设置好就能用"，同一个群 10 分钟最多回一次；不 @ 的消息不读。bot 离线时被拉进的群收不到进群事件，不补发设置卡：有人 @ 时只回那一句，主人在网页"加入已有的群"里设置（Claude 2026-10-19 定）。卡不过期，也能在桌面端或网页里设置：Bot 页的群列表里有一组"待设置"，每个群一行"设置"，打开下面"加入已有的群"那张表；提示每个 Bot 合成一条"<Bot> 有 N 个群待设置"，只在 Bot 列表和这个 Bot 的页上显示，不再每个群一条；右下角的浮层只报这次打开页面以后新来的群（owner 2026-10-18，第 11 节）。这张卡是第 4 节拿掉私聊控制台以后，私聊里唯一留下的设置卡。

**在桌面端和网页里建群、加入已有的群。** Bot 页和群聊页都有"新建飞书群"和"加入已有的群"，两者用同一张表：主界面只问群名和后端，没装、没登录的后端灰掉并写原因；会话方式、文件夹和免 @ 收在"更多设置"里，会话方式默认多会话（见上面"会话方式"）。建好后到这个群的详情页，顶部提示"已建好"，下一行写出它的目录，带"在飞书打开"。Bot 还没连上飞书时，表单顶部提示"Bot 还没连上飞书"，提交禁掉，查已加入的群也一样，不等填完提交再被拒；入口灰掉时旁边写原因。这几条是 owner 2026-10-18 挑的（第 11 节），做法见 `docs/v1-plan.md` 的 u07。

**默认值：**
- 新进的群没有默认的会话方式：被拉进已有的群时在设置卡上选（见上面），bot 在私聊里建群时，主人没说就先问（3.7）。只有桌面端和网页的表单默认多会话，默认值写在摘要行，主人看得见、能改（见上面）。选了智能，bot 在群里说一句"我会读群消息，合适时接话"：绑定、建群时并在欢迎卡第一行里，在群详情页改成智能时单发一条；群停用着不说，从智能改回别的方式也不说（`docs/v1-plan.md` 第 5 节）。
- 从 bridge 迁来的群用规则模式，沿用各群原来的回复方式和主区方式，不换算：多话题群就是多会话，单会话群就是单会话。bridge 今天的默认是免 @ 开，只有被拉进来的"连续"群默认关（`D/project/registry.ts:83-85`）。
- 设置好以后，会话方式能在群详情页或私聊里改（3.7）。在多会话和单会话之间切换，免 @ 不自动变，界面提示一句；从智能切到多会话或单会话，免 @ 是关，要开再开。单会话和智能之间切换，主区那条会话接着用。

**三条底线**，两种模式共用。先回答"这条消息是对谁说的"，再轮到模式：
1. **点名**：@ 了谁、引用了谁的消息，就只有谁回。@ 了别人、@所有人、引用别人的消息，其他 bot 都不回。@ 两个 bot 就两个都回。例外：规则模式的"仅 @"里，引用我的消息不算点名，和 bridge 一致。话题里直接发的消息，`parent_id` 就是话题第一条，算没引用；回复话题里的某一条时，`parent_id` 是那一条，能分出引用了谁（e10，话题群里 s22 补测过）。所以话题第一条被引用分不出来，算没引用。引用自己的消息不算点名别人。
2. **接着聊**：话题里没点名的消息，归最近在这个话题里说过话的 bot。别的 bot 开的话题，我不插嘴。
3. **bot 消息**：别的 bot 发的消息，只有 @ 我才算。

群里只有我一个 bot 时，这三条改变不了谁回，bot 不为它们查任何东西，规则模式和以前一样，比如单会话群里引用同事的话照样回。群里有几个 bot 看群信息（3.11），读不到时按有别的 bot 处理。查被引用的消息或话题里谁最后说话失败时，没点名的这条不回，诊断页记一条（s22）。

这三条顺带修掉今天多 bot 群里的两个毛病：开了免 @ 的 bot 会进别的 bot 的话题；多会话主区不带 @ 的 `/help` 每个 bot 都回（推断，`docs/research/2026-10-14-v1-definition/group-response.md` 结论 3）。单会话群里，免 @ 开着的 bot 每个都回每条，也都回不带 @ 的命令，第一版照旧：每个 bot 只管自己（下面"几个 bot 都会回的时候"）。

**智能模式怎么判断。** 底线定不下来时，调一次判断模型，结果三选一：不回、在主区接着聊、开新话题回。在话题里只判断回不回，不再拆话题。
- 判断模型分两类（叫法是 Claude 按 owner 2026-10-18 的说法定的，第 11 节）：
  - **语言模型**：各家订阅里的小模型，一次不带工具的调用。能生成文字，"不回"的原因是它自己写的一句话。以前也叫"大模型"。
  - **决策模型**：专门做判断的 API。给它规则、上下文和几个选项，它只回选了哪一项和每一项的概率，不生成文字。第一版只接 TypeSafe 的 Jev，直连 TypeSafe，不经 OpenRouter；以后会加更多（第 10 节），vonvon 里按一张登记表加，不改设置的格式。主人自己在 TypeSafe 开账号、填 key、付钱：只按输入收费，1,000 次判断约 0.05 到 0.10 美元。JP-VPS 上实测判一次约 0.16 秒，订阅小模型多在 3 到 5 秒；不占订阅额度，本机不起进程（`docs/research/2026-10-18-jev/report.md`）。
- 默认用语言模型：这个 bot 那家订阅里的小模型，比如 Codex 的 GPT-6-Luna（走 Codex 订阅的普通调用，不是 Decisions API），推理强度取最低档：Codex 是 low；Claude 的 haiku 请求时关掉思考，但它仍会思考（e12 实测 123 条，中位 173 个 thinking token；s23c 见过 584 个，#366）。主人可以改：从这个 bot 后端的模型列表里选，或者手填模型 id，再选推理强度；也可以改选决策模型，选了才用（owner 2026-10-18）。bot 层设默认，群里可以覆盖（owner 2026-10-16）：群开了智能，群详情页、命令行和私聊里都能改这个群的判断模型，候选分语言模型、决策模型两组。语言模型跟着群实际用的后端走：群覆盖了后端、又没设自己的判断模型时，用那个后端的默认小模型，不用 bot 层为另一个后端选的模型。决策模型和后端无关，选了就用，Codex 群、Claude 群都一样。
- 选了决策模型、本机还没填它的 key：照样能选上，选的地方写明"还没填 key"，告诉主人去密钥页填（3.1），或者在终端里用 `vonvon secrets set`；聊天里不收 key（3.7）。没填 key 期间，这个群照下面出错的规矩走，诊断页写明原因。填了就直接用，不用再改设置。
- 选了决策模型，要判断的那条消息、一起带上的最近几条群消息（连同它们 @ 的人名和引用的话）、群名、话题名、bot 名和智能提示词，会发给那家服务；s38 以后还有 bot 的分工。Jev 的服务在美国。TypeSafe 的条款写着不拿客户数据训练模型；保留多久没写明，零保留只给企业客户；还要客户（这里是主人）保证拿到了发送这些内容需要的同意（`docs/research/2026-10-18-jev/report.md` 第 1 节）。界面上和群里都不另外提示（owner 2026-10-18）。用语言模型判断时，群消息同样会发给 OpenAI 或 Anthropic。
- 判断出错或超时就不回。被 @ 的消息一定回：在话题里直接回；在主区要调一次判断，只决定回在主区还是开新话题，出错或超时就在主区回（3.5）。决策模型也照这样兜底（owner 2026-10-18）：没填 key、key 不对、限流、断网、服务出错，都不改用订阅小模型再判，诊断页记原因。引用我的消息算被 @，群里只有我一个 bot 时也是。
- 多 bot 群里，主区不 @ 的命令（`/help` 这类和 `/goal`）不判断也不回，和规则模式一样要 @。
- 决策模型照概率最高的那一项走，不因为把握度低就改判（owner 2026-10-18）。把握度从概率算：0 是几个选项一样可能，1 是完全确定。诊断页显示把握度，日志记下；M5 验收时看日志，再议要不要在把握度低时改问订阅小模型。
- 只回"回"或"不回"，不做"只回一个表情"。"不回"的原因只记在本机诊断页，不发到群里，也不进会话：bot 自己接话的那一轮，开头只加一句固定的说明（这条没 @ 你，是你自己判断该接话，只说有用的），模型给的原因不给 agent。决策模型不写原因，诊断页的"不回"原因写它的选项和把握度，比如"Jev：不回 0.70、回 0.30（把握度 0.40）"。诊断页里判断后不回的（连同下面自己接话后没话说的）最多留 10 条，免得盖住出错的。
- 判断不挡别的消息：一条消息在判断时，同一个群里被 @ 的、话题里的消息照常回。同一个位置（主区或一个话题）正在判断没点名的消息时又来的，先排着，这次判断回来后合成一次判断，只判最新一条，前面几条当上下文。被 @ 的消息不和别的合并，马上判断，判断期间消息上挂一个表情表示看到了。判断说要进会话的，比它早到的被 @ 的消息先进；进会话时照"运行中来了消息"插话或排队（3.5）。判断期间消息被撤回、群被停用或改了会话方式，这条就不回，被 @ 的照新设置回。
- 判断用的提示词就是智能提示词。回不回、回在主区还是开新话题，是同一次判断一起给出的，所以只有一段提示词（owner 2026-10-16）。内置默认值在界面上完整显示，主人可以在 bot 层改，群里可以覆盖，改过的能一键恢复默认。程序在提示词后面附的几行（让模型按什么格式回结果）也显示出来，但不能改：改了程序就读不懂结果。决策模型也用同一段智能提示词当规则；格式行换成程序给的几个选项，同样只读显示。
- 开在哪条下面：主区没点名的消息判断说开新话题时，判断一起给出它接的是前面哪条（比如补充上一条、回答别人刚问的），话题开在那条下面。那条要是真人发的、没 @ 任何人、还没有话题，而且是一起判断的几条之一，或者在这条之前 5 条、10 分钟以内；不是的话开在这条自己下面。被 @ 的开在自己下面；回在主区的照旧引用要判断的那条。
- 自己接话后没话说：bot 自己接话的那一轮（主区没点名、判断说要回的）没写字、没用工具、没发文件，就删掉这张卡，诊断页记一条；删不掉时卡上只留一行"（没有要补的）"，诊断页写明原因。被 @ 的、话题里的、出错或被停下的那一轮，还有插话时另起的卡，照旧留着。
- 控制成本：只对允许使用 bot 的真人消息调；没点名、要智能 bot 自己判断的消息，每个智能 bot 各判一次，点名的、话题已有归属的和一人聊的不判断（下面"几个 bot 都会回的时候"）；话题里只有一个真人在和我聊时直接回，不判断，也不算进每小时的次数，也就是这个话题里最后说话的 bot 是我，最近 3 页消息（不到 3 页的读到话题开头）里除了发这条的人没有别的真人，更早处有别的 bot 不算（哪一页没读到时照常判断）；每个 bot 在每个群每小时最多判断 60 次，各 bot 各记各的，按滑动的一小时算，重启清零，到了上限，没 @ 的消息不判断也不回，诊断页记一条，主区被 @ 的不判断、直接回在主区。延迟和额度 e12 在 JP-VPS 上量过（热判断多在 3 到 5 秒，额度不是瓶颈，见 v1-plan 第 5 节），Mac 上的体验在 M5 验收时看。

**bot 之间。** 智能模式下，别的 bot @ 我时我能收到（要新开一个可选权限，见 3.11），这样能做"小码写、小审查"。B 看到的 A 的消息只有 A 的最终回答，标成"A（bot）"，截到几百字。自上一条真人消息起，同一个位置（群主区或一个话题）里，bot 叫醒 bot 的 @ 最多 6 次。一来一回算一轮，6 次就是字面上的"来回 3 轮"："写代码 → 审查 → 改 → 再审"能完整走两轮。到了上限，最后被叫醒的照常回答，只是它再 @ 也叫不醒对方，并提示一次；真人说一句就清零。次数按飞书上看得到的消息数，不在本机记，不同电脑上的 bot 数出来一样（owner 2026-10-18 定，第 11 节）；哪些 id 是 bot 按飞书的群成员列表认。不收别的 bot 的全部消息。群里设了"响应成员"时，只响应名单上的：名单上的 bot 来 @ 我，和名单上的人一样叫得醒，照样算在 6 次里；不在名单上的 bot 的 @ 叫不醒我（owner 2026-10-19）。被别的 bot 叫起来的那一轮，完成提醒照我的提醒设置发，@ 叫我的那个 bot，和真人叫我时一样：每个 bot 只知道自己的事，叫它的人都当真人看；这条提醒的 @ 也叫醒对方，算在 6 次里（owner 2026-10-19 定，第 11 节）。

bot 发的卡片和 markdown 消息里不带 bot 的真 @：agent 写给 bot 的 @ 显示成纯文字"@名字"，因为卡片里的 @ 能叫醒对方，飞书的消息列表却看不到，数不进次数。哪些是 bot 按飞书的群成员列表认；列表读不到时，agent 写的 @ 都显示成纯文字，bot 自己放的 @（提问卡上 @ 能回答的人）照旧。交接按实际消息状态显示接收者和已有消息、话题的位置。发送成功只说明已发出，观察到对方响应才说明对方已开始处理；失败或结果未知如实显示。不为交接另加私有信道、确认循环或新的 bot 身份。

**几个 bot 都会回的时候。** 每个 bot 只管自己：回不回只看这条消息、一起带上的历史消息和自己的智能提示词（规则模式看自己的设置），不看别的 bot 的设置，也不和别的 bot 商量，同一台电脑上的也一样。所以同一条消息几个 bot 都可能回；智能 bot 之间靠各自提示词里的分工错开（下面例子第 3 行）。三条底线照旧，它们看的是消息本身：@ 了谁、引用了谁、话题里谁最后说过话（owner 2026-10-19，第 11 节）。

### 3.5 会话和上下文

owner 说这一块很关键：飞书里的位置怎么对应 agent 的会话，上下文是什么关系，哪些要存进会话历史。下面依次回答，再用一个群的时间线走一遍。今天的代码和这里不一样的地方，列在本节末尾。调研见 `docs/research/2026-10-14-session-approval-service/session-map.md`。

**一个飞书位置对应一条会话。** 每个 bot 各有各的会话。下表说的是一个 bot 在一个位置上。群里只有主区和话题两种位置；私聊不在群里，是主人或管理员和 bot 一对一的聊天窗口。

| 飞书里的位置 | 智能 | 单会话（规则模式"连续"） | 多会话（规则模式"开话题"） | 什么时候建 |
|---|---|---|---|---|
| 群主区 | 一条会话，一直接着聊 | 一条会话 | 不留会话，@ bot 就开一个话题 | 这个 bot 第一次在主区回复时 |
| 话题，不管是谁开的，包括话题群里的帖子 | 一条会话 | 一条会话 | 一条会话 | 这个 bot 第一次在这个话题里回复时 |
| 私聊（不在群里，一对一） | 一个私聊窗口一条会话：主人一条，每个管理员各一条 | 同左 | 同左 | 第一次私聊时 |
| 私聊里的话题 | 单独一条会话，和群里一样。用户开的和 bot 开的私聊话题，事件里都带 `thread_id`（e10） | 同左 | 同左 | 第一次在这个话题里回复时 |
| 云文档评论 | 每篇文档一条，和今天一样 | 同左 | 同左 | 和今天一样 |

- 会话就是一条普通的 Codex 线程或 Claude 会话。主人在 Codex 应用里或用 `claude --resume` 打开它，看到的和 bot 看到的一样（e14 在终端里实测过）。主人可以在终端或 Codex 应用里接着 bot 的会话聊：bot 每一轮开口前看一眼这条会话，别人写过（聊了几轮、压缩过）就重新接上，从最新的地方接着说；Codex 那边 bot 每一轮结束就放开线程，终端随时打得开。bot 正在回答的那一轮里终端也在写，两边会分叉，不处理（owner 2026-10-16 定，D6 选 A；s15b 已改）。反过来，终端或 Codex 应用开着这条 Codex 会话时，bot 接不上（Codex 一条线程只许一个写入方），这一轮回"这条会话正在终端或 Codex 应用里打开着，bot 接不上。关掉那边以后再发一次。"，不换新会话。s15b 之前 bot 在最后一轮之后还占着会话 45 到 50 分钟：这期间 Claude 那边终端里写的轮次和 `/compact` bot 看不到，下一轮接着自己的历史写，两边分叉；Codex 那边终端打开会被拒（e14）。
- 不在同一个位置里悄悄换会话。只有 `/new`、`/clear`、`/resume` 会换，见下面的"命令"。
- 话题群和话题形式群里没有主区对话，每个帖子就是一个话题，也就是一条会话，不判断要不要开话题。
- 子 agent 代替不了新会话：它的结果会回到父会话里，干完就结束，事后没法接着问它。它的用途是把一件事拆开并行做。
- 一个群只有一个权限档，群里谁说话都用这一档、进同一条会话（owner 2026-10-16 去掉了访客档，见 3.8）。以前设了不同访客档的群，升级后取两档里更严的，管理员的会话接着用，访客的会话停着不用（s15c 已改）。
- 云文档评论的会话不在群里，用评论设置里的权限档和网络，没设时跟 bot 默认（3.12）。

**主区和话题是什么关系。**
- 主区会话和话题会话互不复制历史。
- 话题开出来时，不管是用户开的，还是 bot 判断后开的，主区会话里只留一行引用，指向这个话题的会话：谁、几点、在哪条消息下开了话题、话题的标题、话题 id，以及话题会话的 id（Codex 的线程 id 或 Claude 的会话 id）。话题会话里也记着主区会话的 id。两边靠这两个 id 互相找到。
- 引用行由 daemon 生成，不带话题里的内容，用户也伪造不出来。
- 会话在 bot 第一次回复时才建。所以 bot 还没在某个话题里说过话时，这个话题还没有会话，引用里只有话题 id；主区会话还没建时，话题的回指里也没有主区会话的 id。这两种情况下用话题 id 或群也能找到对方现在的会话。主区 `/new` 以后，旧话题的回指仍然指向开话题时的那条主区会话。
- 引用行在主区会话下一次开口时，和别的新消息按时间一起写进对话记录块。不在话题一开就单独写进主区会话：Codex 那种写法（`thread/inject_items`）在 Codex 应用里看不到，Claude 那种写法（`shouldQuery: false`）Codex 没有，而且为了一行字要拉起一个会话进程。主区会话在开口之前也用不着知道。
- 不在群主区另发一条带链接的消息。飞书新版客户端会把话题回复直接显示在那条消息下面，主区的人本来就看得到。
- 话题会话开场带四样：一行回指（"这个话题开在主区 10:01 张三的消息下，主区会话 id 是……，主区更早的内容用 vonvon 飞书 skill 查"）、主区在话题第一条消息之前的最近 10 条、话题第一条消息、话题里已有的消息。
- 之后两边要看对方的内容，都用 vonvon 飞书 skill 去查（见下面的"查飞书上下文"）：按会话 id 读对方会话里说过什么，或者按话题 id、时间读飞书消息。查到的内容作为工具结果进 bot 自己的会话。
- 主区会话压缩以后，引用行可能被摘要掉。所以压缩后主区下一次开口时，附一张"本群最近 5 个活跃话题"的短表；skill 也能列出本群所有话题。不管是谁压缩的都附：vonvon 发起的、Claude 空闲时自己压的、主人在终端或 Codex 应用里压的。bot 每次开口前看一眼原生会话，有新的压缩就附（owner 2026-10-16 定，D4 选 B；s15b 已改）。s15b 之前只在 vonvon 自己看到的压缩之后附（e14）。

**哪些存进会话历史。** 只存 bot 真正开始回复时读到的东西，一共四类：
1. 会话开始时的个性和记忆；之后变了，下一轮附的"设置更新"，和压缩以后整份再交的那份（3.6"改了什么时候生效"）。
2. 每次回复前，这个位置自上次以来的新消息，合成一个对话记录块。真人的话带真名，包括智能模式判了"不回"的消息；别的 bot 只放最终回答，标成"某某（bot）"，截到几百字。主区的记录块里还有新开话题的引用行。
3. 触发这次回复的消息、它引用的消息、附件路径、语音转写。附件的原件在飞书的消息里；agent 在本机跑，读不到飞书，所以 daemon 把附件下载到本机，把本地路径交给 agent。本地这份只是缓存，留多久、清掉以后怎么办，见下面"daemon 在本机记什么"。
4. bot 自己的回答、工具步骤和子 agent 的结果，由 Codex 和 Claude 原生记录。

不存的：
- 别的话题、别的群、私聊的内容。
- 主区会话里不放话题里的回复，包括这个 bot 自己在话题里说的话。
- 话题会话里不放话题开出来以后主区的消息。话题第一条只在开场放一次，之后每轮不再重复。
- 别的 bot 的过程和子 agent。
- 自己以前的回复，已经在会话里了。

消息不是一到就塞进会话，而是等 bot 开口时一起带进去。daemon 给每条会话记一个水位，表示它已经读到哪条消息。每送进一条就推进，包括触发、插话、排队和记录块里的消息。

**查飞书上下文。** 每个会话预装一个 vonvon 飞书 skill，背后是 `vonvon` 命令行（见 3.7）。bot 用它查自己能看到的飞书内容：主区要看某个话题里说了什么，话题里要看主区更早的消息，都通过它查；它也能列出本群的话题。

- 只能读同一个 bot、同一个群里的会话。私聊的会话在群里读不到。owner 说过这个 skill 可以以后再做；Claude 把它放进了第一版，因为主区只留话题的引用，没有它就查不到话题里说了什么。
- 用机器人身份查，只能查这个 bot 所在的群；在群里只能查当前这个群。卡片上显示"查了本群 9:00 到 10:00 的 40 条"。
- 不把用户身份的 lark-cli 交给 agent：它能读到主人所在的所有群，包括机器人不在的群（实测，`docs/research/2026-10-14-v1-definition/context-feishu-products.md` 2.3）。

**压缩。** 两家都用原生的自动压缩，一直开，去掉"关闭自动压缩"开关：它只接了 Codex，而且新版 Codex 会把阈值封顶在窗口的 90%，推断已经关不掉。运行卡头部一直有上下文仪表；压缩时过程区显示"已压缩 85% → 20%"。

**daemon 在本机记什么。**
- 每条会话的绑定和水位，和今天的 `sessions.json` 在一起（`D/bot/session-store.ts:13-39`）。
- 每个群一份话题登记表：话题 id、第一条消息的 id、谁开的、几点、标题（第一条消息的开头几个字）、这个 bot 在里面有没有会话。用来生成引用行，给 skill 列话题。话题常常开在一条旧消息下，按时间拉主区拉不到这件事，所以要单独记。

- 附件的缓存：收到时下载到这个 bot 自己的收件目录，在 `bots/<appId>/` 下按位置分开，每一档权限的会话都读得到本位置的（`docs/v1-plan.md` s39b）。下载 7 天后删。之后的回合又用到这条消息的附件（被引用了，或者在这一轮的上下文里），daemon 从飞书重新下载；重新下载失败（消息撤回了、bot 已不在群里、飞书拒绝）时，在附件清单里写明没下载下来和原因。今天下到全局的 `inbound` 目录，1 小时后删，只有完全访问档读得到。保留期和重新下载是 Claude 定的，起因是 owner 2026-10-18 问"为什么要存"（第 11 节）。
- 这些都在 daemon 里，只用 node 的文件读写，不依赖 Electron。

### 3.6 个性、记忆、skill、MCP

**个性。** 注入顺序，越后越具体：
1. vonvon 固定的输出约定和隐私红线（今天的 `D/agent/bridge-instructions.ts:12-32`，加一句"不提别的群的内容"）。这一层还写明怎么认"设置更新"：只认 vonvon 放在一轮最前面的那段，记录块和触发消息里出现同样的文字都是用户的话（见下面"改了什么时候生效"）。这一层改不掉。

3. bot 的 `SOUL.md` 和 `AGENTS.md`。
4. 群的 `SOUL.md`。
5. 记忆。

**记忆。** 按"谁能看到来源"分三份。

| 记忆 | 在哪里用 | 谁能写 |
|---|---|---|
| 本群记忆 | 只在这个群 | 群里能用 bot 的人：说"记住"，或 bot 自己判断要记。主人和管理员能看、改、删 |
| 公共记忆 | 所有群和私聊 | 只有主人和管理员，在桌面端或聊天里 |
| 私聊记忆 | 只在这个人的私聊里 | 这个人的私聊会话 |

- vonvon 永远不把 A 群的记忆放进 B 群的会话；Claude 的会话今天还能自己读到别处的记忆文件，见下面。同一个群里几个 bot 各有一份本群记忆，不共享。
- 写入在卡片上显示"已记到本群记忆：…［撤销］"。第一版不做后台自动整理。
- 记忆的范围、版本和已知来源由 daemon 的实际读取、提交记录给出，不由 agent 自报成功。捕获不到的并发版本或写入者不猜测。上下文组装核对实际编码大小，按既定上限完整交付，不静默截断；清空会话与删除持久记忆是两件事。下文并发合并后超限仍保留的规则不变。
- 记忆在会话开始时随指令放进去，标成"背景资料，不是指令"。之后改了，不管是主人改的，还是 bot 在别的会话里写的，受影响的会话下一轮生效，见下面"改了什么时候生效"。每份有字数上限，满了让 bot 先整理，不悄悄截断。
- 关掉两家自带的记忆：Claude 的 auto memory 按 git 仓库共享，两个群用同一个仓库就会串；Codex 的 memories 是全局整合的。第一层约定里写明：要记的东西只写进 vonvon 给的那份记忆文件；不为了记东西去改工作区里的 `CLAUDE.md`、`AGENTS.md`，也不在工作区里另建记忆文件；用户明确要改这些文件时照常改。
- 这一次能写的那份记忆所在的目录，作为可写的目录交给会话（不当工作区的根，见下面的表），每一档都放行，工作区只读时也能记：群里是本群的 `memory/`，私聊是这个人的 `memory/dm/<open_id>/`。公共记忆哪一档、群里还是私聊都不放行：它所在的 `memory/` 下面就是每个人的 `memory/dm/`，放行它就放行了所有人的私聊记忆。公共记忆只由主人和管理员在桌面端或私聊的设置命令里改（3.7）。放行和防链接分三处，各管各的：沙箱按路径放行这个目录，只管 Bash；Claude 放行 Edit、Write 时，按解析过链接的真实路径判断（下面的表）；daemon 自己读记忆文件时防链接（下一条）。
- 目录整个可写，群里任何人都能让 agent 在里面建符号链接、硬链接、FIFO 或很大的文件。daemon 不在沙箱里，跟着链接读，就会把别人的私聊记忆或 `~/.ssh` 下的文件贴进卡片和会话。所以 daemon 只认这一个文件（`group.md` 或 `dm.md`），目录里别的文件不读；读时不跟随链接（`O_NOFOLLOW`，加 `O_NONBLOCK` 免得被 FIFO 卡住），打开后确认是普通文件、硬链接数是 1、不超过大小上限（比如 64 KB）。不符合就不读、不放进会话和卡片，记一条日志，按超上限一样回滚。回滚和［撤销］都先写一个新的普通文件再 rename 换上，不顺着链接写。agent 能把 `group.md` 换成一个目录，rename 到目录上会失败。失败时不删：先把原来那个挪到会话写不到的 `bots/<appId>/quarantine/` 下（比如 `<chatId 或 open_id>-<时间>`），再 rename，记一条日志。挪走的 daemon 不读。那里每份记忆最多留 3 个，只数 daemon 自己挪进去的，诊断页显示占了多大；agent 碰不到这个目录；满了就不再挪，这一次不写回，卡片上写"记忆没写进去，记忆文件被换掉了，请主人清理"，记日志，诊断页提示主人清理。
- 同一份记忆可能有两条会话同时在写：同群的主区和话题会话能同时跑（私聊的主会话和话题也一样），都直接写同一个 `group.md` 或 `dm.md`，后写的可能盖掉先写的，一轮前后各看一次也分不出是谁写的。规则：
  - 用这份记忆的会话有一条在跑一轮时，daemon 盯着这个文件。文件一变，或者这些会话的工具步骤结束，就按上面防链接那条的方式读一次。读到的每一版都留到这几轮都结束。只在一轮前后看，会漏掉中途被另一条会话盖掉的那一版。
  - 这样也只能尽量读全：两次写挨得太近时，中间那一版可能没读到。只有读到的版本才有保证：没读到的那一版，新增的行可能丢，删掉的行可能回来。一版都没读到时，合并退化成只比对这一轮的前后。
  - 一轮结束时，这一轮期间有别的会话也在跑、文件也变过，就以行为单位做三方合并，按标准 diff3 的规则：
    - 基准是这一轮开始时的内容，把这期间读到的每一版相对基准的改动合进来。卡片上列的改动、［撤销］退回的内容，也都相对这一轮开始时。
    - 两边做了同样的改动，只算一次。比如后写的会话是在先写的那版上改的，它那一版也带着先写那版新增的行，合并后这些行只有一份。别的会话一轮结束时 daemon 写回的合并结果，也会被当成一版读到，里面已经合过的改动同样不会重复。
    - 一边删了某行、另一边没动它，就删掉。两边新增的行都留下。同一行两边改得不一样，两份都留下，标上"（两条会话同时改过）"。
    - 合并结果按防链接那条的方式写回（新文件再 rename）。
    - 读到的每一版怎么认出是哪条会话写的、具体按哪几版合，s40 开工时定。要守住这几条，也是 s40 的验收标准：
      - 读到的版本里新增和改过的行都不丢；
      - 相同的改动只算一次，daemon 写回的合并结果也一样；
      - 合并结果里的每一行都出自基准或读到的某一版，冲突的标记除外；
      - 卡片上列的改动和［撤销］都相对这一轮开始时。
  - 卡片上写"和另一个会话同时改过，已合并"，列出合并后相对这一轮开始时的改动。这时的［撤销］退回这一轮开始时的内容，按钮旁写明另一条会话这段时间记的也会一起撤掉。
  - 这份记忆还有别的会话在跑一轮时，点［撤销］不撤，回"另一条会话正在用这份记忆，等它这一轮结束再点"。不然撤销写回的旧内容，会在那条会话结束时被合并又合回来。另一条会话已经结束的，照上一条连带撤掉它这段时间记的。
  - 合并后超过字数上限，照样写回，不回滚，两条会话下一轮都提示先整理。回滚会把另一条会话记的一起丢掉。
  - 宁可多留，不丢。代价是有意删掉的行偶尔会回来，大多发生在没读到删后那一版的时候。比如另一条会话删了一行，这条会话随后用它这一轮开头读到的旧内容整份写回，删后的那一版又没读到，合并时就看不出删过，这一行留着。还有一种：一条会话删的是它自己这一轮早先记下、已经被另一条会话结束时合进去的行，按 diff3 这一行也会回来。由主人和管理员在桌面端删。
  - 只有一条会话在跑时不合并，照常前后比对。
- daemon 自己的 `config.json`、`sessions.json` 不在这些目录里，放行记忆目录不会让 agent 写到它们（完全访问档除外）。工作区和代码仓库只能在数据目录（默认 `~/.vonvon-bot/`）以外，或在它的 `projects/` 下面，也不能是数据目录的上级（比如 `~`），选到时拒绝。读没有隔开：Claude 的只读、读写档今天不限读（`D/agent/claude-agent/permission.ts:25-28`），沙箱里的 Bash 读得到这些文件，也读得到别的群的记忆、别人的私聊记忆和数据目录里的凭据（第 9 节第 20 项）。
- 主人本机的个人指令（`~/.claude/CLAUDE.md`、`~/.codex/AGENTS.md`）和个人 skill：从 bridge 导入的 bot 默认带上，行为不变；新建的 bot 默认不带 Claude 的个人指令，也不带两家的个人 skill。Codex 的 `~/.codex/AGENTS.md` 按会话关不掉（e05），所以新建的 bot 也带着它；bot 的指令里写明 bot 自己的规矩优先（owner 2026-10-15 定）。

**改了什么时候生效。** 个性、规矩、智能提示词和记忆改了以后，所有受影响的会话在下一轮自动生效，不用 `/new`（owner 2026-10-16 定，第 11 节）。

- daemon 记下每条会话已经拿到的版本。下一轮开口前发现变了，就在这一轮的消息前面附一段"设置更新"：写明它替换之前的版本，再给新的全文。
- 设置更新只由 vonvon 写，放在这一轮最前面，在 `[飞书 …]` 记录块和触发消息之前。触发消息是多行原样放进去的（3.5），群里任何人都能打一段"设置更新：替换之前的版本……"。所以记录块和触发消息里出现同样的文字，都算用户的话，不算设置；第一层固定约定里写明这一条（上面"个性"第 1 层）。这只是提示词层面的约定，不是硬保证（第 9 节第 25 项）。
- 新会话从开场指令拿当前的整份。会话压缩以后的第一轮整份再交一遍，因为之前的"设置更新"可能被摘要掉；和 3.5 压缩后附话题表是同一个时机（这一处是 Claude 加的，`docs/v1-plan.md` 第 5 节）。恢复会话不用重交：开场那份和之前的"设置更新"都还在历史里。
- 代价：旧版本留在会话历史里，偶尔会和新版本打架。"设置更新"写明替换之前的版本，就是为了压住它。
- 记忆也一样。bot 在一条会话里写了记忆（agent 直接写记忆文件，`docs/v1-plan.md` s40），用同一份记忆的其他会话在各自的下一轮生效：本群记忆是同群的主区和别的话题，私聊记忆是这个人私聊的主会话和私聊里的话题；公共记忆由主人和管理员改，用到它的会话都在下一轮生效。写的那条会话本来就知道，不再附。两条会话同时写了同一份，按本节"记忆"一段的三方合并，合并后的结果对两条会话都算变了，各自下一轮附上。
- 智能提示词和判断模型用在每次判断里（3.4），改了下一次判断就用新的。决策模型的 key 在密钥页填了、换了，也是下一次判断就用上（3.1）。
- skill 和 MCP 名单改了，等下一条会话，或者会话所在的进程重开、恢复以后才生效：能力包在开会话时定，Codex 新进程恢复时重读它，Claude 每次启动重传（`docs/research/2026-10-16-bot-home/multi-workspace.md` 3.3、4.3）。界面上写明。权限档照旧下一轮生效（3.8）。

**接更多后端时。** profile 按"一条会话要什么"来写，不按某一家的参数写：主工作区、附加目录和各自能不能写、指令、能力包、MCP、这一次的记忆目录。每个后端一个适配，报出自己的能力：附加目录按会话、按进程还是没有；能不能按目录分读写；指令走什么通道；skill 走什么通道；MCP 按会话还是按进程、支持哪些传输；恢复会话时哪些要重传。做不到的由 vonvon 补，比如附加目录只能按进程给的，一个进程只跑一条会话；没有 skill 通道的，由 vonvon 的 MCP 把 skill 列给 agent；恢复时不认新指令的，靠每轮的"设置更新"。第一版只写 Codex 和 Claude 两个适配（`docs/v1-plan.md` s37），别的后端不做（第 7 节）。13 个后端的情况见 `docs/research/2026-10-16-bot-home/multi-workspace.md` 第 2、6 节。

### 3.7 在聊天里改设置

主人和管理员可以在私聊里直接跟 bot 说，比如"以后在支付组说话活泼点"、"给支付组加上 X skill"、"建一个发布群，把张三拉进来"。第一版只在私聊里能说，群里不能在聊天里改设置。

**做法**：
1. 扩展已有的 `vonvon` 命令行（`packages/daemon/package.json` 的 `bin`，现在注册了 `daemon`、`open`、`service` 等子命令，`D/cli/index.ts:20-55`），加上设置和飞书两组子命令。设置命令是所有会改东西的命令，包括建群和拉人进群；飞书命令只查不改。命令行也能在终端里直接用。
2. vonvon 设置 skill 告诉 agent 怎么用这些命令。只有私聊的会话装它、能用设置命令。

**能改什么**：只限这个 bot 自己的事。命令行能改的这个 bot 的设置，聊天里都能改，因为设置 skill 让 agent 调的就是同一个 `vonvon` 命令行（owner 2026-10-18 定，第 11 节）。

| 能改 | 不能改 |
|---|---|
| 个性、规矩、智能提示词、判断模型；记忆；skill 和 MCP 的启用名单；仓库和工作区；会话方式和免 @；权限档和网络；完成提醒、卡片显示、运行中来了消息（插话或排队）和空闲超时这类运行设置、主模型、允许哪些群用、工作区的默认位置、云文档评论的设置（后端、模型、评论提示词、权限档和网络）、会话标题、语音转文字的开关；本机加的管理员、群里允许使用 bot 的成员；建群、拉人进群 | 建新 bot、改别的 bot；填、换、删 API key（在桌面端、网页的密钥页或终端里，聊天里不收、不显示 key，只告诉人去哪里填，3.1）；vonvon 的全局设置；私聊的"聊天改设置"开关（见下） |

- 本机加的管理员、群里允许使用 bot 的成员、评论提示词和语音转文字的开关，今天在设置里走单独的操作，命令行还没有（`docs/v1-plan.md` s07a 留下的）。按 owner 的话，能改的配置聊天里都能改，所以命令行把这四项补上，聊天里一样能改。这是 Claude 按 owner 的话补的（第 11 节）。飞书里来的管理员在飞书里改，聊天里改的只是本机加的那份名单（第 6 节）。本机管理员名单只有主人触发的那一轮能改，加和移除都是；管理员触发的那一轮不能改这份名单，免得管理员给别人加管理员，或者把别的管理员移掉（Claude 定）。加管理员、放开群里允许使用 bot 的成员和改允许哪些群用一样，算扩大能力（3.8"留下的风险"）。打开语音转文字时缺飞书权限，回执里写明，权限照旧在飞书后台开。
- 群里不能在聊天里改设置。某个群自己的设置、bot 的默认设置和别的群的设置，都在私聊里改，说清是哪个群。
- 判断模型能在聊天里改，包括改成决策模型（3.4）。本机还没填这家的 key 时照样改，回执里写明还没填 key，填之前这个群要判断的消息按出错处理（被 @ 的照常回，没 @ 的不回），告诉主人去桌面端或网页的密钥页填，或者在终端里用 `vonvon secrets set`。聊天里只说填没填，不显示 key，末四位也不显示。有人把 key 发在聊天里，bot 不存、不复述，提醒他这个 key 已经进了会话记录，最好去那家服务换一个新的。设置 skill 不教 `vonvon secrets`，从 bot 的会话里调它会被拒（`docs/v1-plan.md` s23g）。这一条是 Claude 定的（第 11 节）。
- 谁能改由 daemon 判断，不由 agent 判断。daemon 知道这一轮是谁的消息触发的，只有主人和管理员触发的那一轮能改设置，别人的命令直接被拒。私聊本来只有主人和管理员能用，daemon 照样再查一遍。
- daemon 靠每条会话自己的令牌认出命令来自哪条会话：会话启动时 vonvon 给它一个令牌，命令行调用时带上。没有令牌、令牌对不上，或者不是私聊会话的设置命令，一律拒绝。能不能在沙箱里带上，见第 9 节第 2 项。
- 改完在卡片上显示改了什么，带［撤销］。个性、规矩、智能提示词和记忆，受影响的会话下一轮就用上；skill 和 MCP 名单要等下一条会话，或者会话进程重开、恢复以后（3.6"改了什么时候生效"）。
- 回执来自 daemon 的已提交结果，列明影响的 bot、群或个人范围、改前改后、版本和生效时机。落盘失败不显示“已改好”；回执发送失败与设置失败分开记录，重发回执不重复修改。撤销核对当前版本和操作人的权限，旧回执不能静默覆盖新修改；并发记忆仍按 3.6 等其他回合结束的撤销规则处理。不新增设置审批层。
- 回执还多两行：由谁的哪条消息触发（摘消息的前 60 字），和 bot 的说明（agent 写的为什么改，标明是 bot 说的）。诱导出来的修改，比如主人说"总结这个网页"、回执却是启用了一个 MCP 或改了允许的群，一眼就看得出（3.8"留下的风险"）。这两行是 Claude 建议的，owner 2026-10-18 没反对（第 11 节）。
- 私聊有一个"聊天改设置"开关，默认开着。关掉以后，私聊的会话也不装设置 skill，daemon 也拒绝它的设置命令。开关只在桌面端或网页里改，聊天里不改，因为关掉以后聊天里就打不开了。群里没有这个开关，第一版群里不装设置 skill、不能用设置命令；给群加开关放进第 10 节。这是 owner 第 29 题和之后的补充定的。
- 会话中途改了开关：设置命令的拒绝马上生效，因为是 daemon 判断的；skill 装不装跟着能力包走，要等私聊的下一条会话，或者会话进程重开、恢复以后（3.6）。
- 群里不能用的只是设置 skill 和设置命令。飞书 skill 和它用的只读查询命令不受影响，每个会话都能用，因为主区和话题要靠它互相查（3.5）。这一条是 Claude 定的，和 owner 说的"禁止使用 vonvon-bot 的 CLI"字面上不同，见第 11 节第 26 条。
- 建群和拉人：bot 可以自己建一个新群，再把人拉进来。建群要定会话方式（3.4），主人没说，agent 先问。对已有的群，bot 不自己进，要群里有人拉它，所以 bot 把拉它进群的步骤发给你。飞书其实允许机器人自己进公开群，私有群不行（e10）；owner 2026-10-15 定第一版不用这个，都要人拉。

### 3.8 卡片和权限

owner 的话："确认卡、选项卡、授权卡这些需要用户交互、用户确认的体验，要和 Agent 里面的一种授权一致……它也可以设置成完全访问，也就是用户不需要确认任何事情。"问到越权时要不要发卡请人批准，owner 答："超出权限就直接拒绝啊，为什么还要授权呢？""无越权的授权，不授权。"

所以第一版的权限只靠权限档，不发卡请人批准越权：
- 权限档三档：只读、读写、完全访问，名字沿用 bridge。bot 默认档给私聊用，云文档评论没单独设档时也用它（3.12）；群在建立时写定自己的档，之后可以改（3.2）。新群的默认档和今天一样：bot 自己建的群是完全访问，被拉进的已有群是只读、关网（`D/project/lifecycle.ts:165`、`:257`、`:265`）。从 bridge 迁来的群沿用原来的档。一个群只有一档，群里谁触发都用这一档：bridge 的访客档（普通成员用另一档、跑另一条会话）去掉了，owner 2026-10-16 的话："反正管理员问的信息，其他成员也都看得到，还是只保持一个权限就好了"（s15c 已改）。只限主人和管理员的事照旧，比如主区的 `/new`、`/clear`、私聊、点 Claude 自己要问的卡（3.5、第 4 节、下面的表）。
- 只读和读写：agent 要做超出这一档的事，比如写工作区以外的文件（这一次的记忆目录除外，3.6）、写各个根里两家的配置文件（3.6）、关网时联网，直接拒绝。agent 收到拒绝的原因，自己换个办法，或者停下来说明。和今天一样，只多了记忆目录可写、配置文件不可写这两处。
- 完全访问：从不问权限。
- agent 向人提问、请人确认方案时，照样发卡，因为那是在问人的意见，不是要权限。
- 完全访问下，Claude 自己仍会停下来问的少数几类照样发卡（第 25 题 a，见下面"完全访问下还会问什么"）。那是 Claude 自己的行为，不是 vonvon 的越权授权。

调研见 `docs/research/2026-10-14-session-approval-service/approval-ux.md`。调研推荐过一个"超出权限时：问我 / 直接拒绝"的开关，owner 没要。

今天两边都不问。Codex 写死了 `approvalPolicy: 'never'`（`D/agent/codex-appserver/backend.ts:31`），Codex 发来的请求一律回报错（`D/provider/transport/jsonrpc.ts:197-206`），连它在计划模式下的提问都收不到。Claude 三档都用 `bypassPermissions`，没有 `canUseTool`（`D/agent/claude-agent/permission.ts:56`、`:73`），今天只读、读写两档的会话里根本没有提问这个工具，计划模式的两个工具也没有，Claude 只能用文字问（实测，`docs/research/2026-10-14-v1-spikes/e02-claude-permissions-sessions.md` 第 1 节）。推断原因是没有 `canUseTool` 时 SDK 不给 CLI 留提问的通道，完全访问档也一样。第一版要把提问接上。

换成两家的设置（Claude 一列不带沙箱的部分在 JP-VPS 上实测过，见 `docs/research/2026-10-14-v1-spikes/e02-claude-permissions-sessions.md`；沙箱的部分和 Codex 一列还是推断，要实测，第 9 节）：

| 权限档 | Codex | Claude |
|---|---|---|
| 只读 | `never` + 今天的只读沙箱，另加记忆目录可写（3.6） | `default` 模式 + 今天的只读沙箱。`canUseTool` 对要权限的请求一律拒绝并说明原因，对提问发选项卡 |
| 读写 | `never` + 今天的读写沙箱，另加记忆目录可写、各个根里两家的配置文件只读（3.6） | `acceptEdits` + 今天的读写沙箱，`canUseTool` 同上 |
| 完全访问 | `never` + `danger-full-access`，就是今天的行为 | `bypassPermissions`，就是今天的行为。`canUseTool` 只处理提问和 Claude 自己仍要问的几类，见下 |

- Claude 的只读、读写两档不再用 `bypassPermissions`。今天用它，推断有两个缺口：关网时 Bash 可能仍能连外网，Edit 和 Write 可能写到工作区以外（`approval-ux.md` 3.3）。不带沙箱时这两个缺口都在：今天的只读档下 Bash 能写工作区内外的文件、能 curl 出去，`bypassPermissions` 下工作区以外的 Write 也直接放行；带上今天的沙箱还在不在，第 9 节第 12 项在 Mac 上测。换成上表以后，只读档下写文件的 Bash、联网的 Bash、工作区以外的读写都会先到 `canUseTool`；读写档下工作区里的写直接放行，其余同样先到回调（实测，e02 第 1 节）。只读档可以对这些一律拒绝；读写档关网时，回调分不出哪条 Bash 在联网，要看命令文字或者靠沙箱，在 Mac 上测（e03）。代价是今天这两档下能用的 WebFetch、往工作区以外写文件会被拒（这一次的记忆目录除外，3.6）；开网时给 WebFetch、WebSearch 加允许规则。各个根里两家的配置文件（3.6）在读写档下用拒绝规则挡：e02 只测到 `.claude/` 下的写在 `acceptEdits` 下也走回调，其余几处没测。
- Codex 三档都保留 `never`：模型知道不能申请，就不会白白尝试。`never` 下没有标成只读的 MCP 工具会被拒（`approval-ux.md` 1.5），vonvon 自己的 MCP 要配 `approve`（第 9 节第 2 项）。
- 中途改档不用重开会话：Codex 每一轮的 `turn/start` 能带新的设置，Claude 运行中能 `setPermissionMode`，升档降档都是下一轮生效（实测，e02 第 3 节）。升到完全访问要求会话启动时带 `allowDangerouslySkipPermissions`，所以每条会话启动时都带上；resume 不恢复上次的档（`settingSources` 为空时测的），每次都明确传。Codex 一半还是推断。
- Linux 上 Codex 的只读、读写档今天直接拒绝启动（`D/agent/codex-appserver/backend.ts` 的 `sandboxParams`），所以 Linux 上的 Codex 只能用完全访问，界面写明。被拉进的已有群默认只读，在 Linux 上用 Codex 时起不来：bot 回一句说明，等主人在设置里明确改成完全访问，不自动放开。（s20b 已改）

**完全访问下还会问什么。** 不问权限。Claude 自己在任何模式下都会停下来问的少数几类，照样发卡问，和 Claude 自己的行为一致，比如用户在自己的 Claude 设置里写了"这类操作必须问"、删除关键目录（`approval-ux.md` 2.2）。这种卡只有主人和管理员能点，15 分钟没人点按拒绝。只读、读写两档下，这几类直接拒绝。实测里 `bypassPermissions` 下只有 AskUserQuestion 走到回调，写 `.claude/` 下的文件也直接放行；ask 规则和删除关键目录还没测，测试时 `settingSources` 为空，用户层的 ask 规则也没测到（e02 第 1 节，第 9 节第 11 项）。测出来走不到回调的几类，按 `docs/v1-plan.md` 4.2 第 3 条问 owner。

**卡片。** 所有要人点的卡片一个样：同样的版面、同样的状态、同样的"谁能点"规则。所有会话默认就有，不只在私聊。
- **运行卡**：流式输出、⏹ 停止、工具折叠、上下文仪表、子 agent 区（见 3.9）。等人回答时显示"⏸ 等 张三 回答（见下方卡片）"。
- **选项卡**：agent 问一个带选项的问题时（Claude 的 AskUserQuestion，Codex 的提问；Codex 只在计划模式下会问）。空提交时提示"至少选一项"。
- **确认卡**：只要"是 / 否"的确认，比如 Claude 的计划（ExitPlanMode）。按钮是［按这个方案做］［不行，我来说］。
- 完全访问下 Claude 自己仍要问的那几类，用同样的版面，按钮是［允许这一次］［拒绝］。

- 卡片写清后果：选了会怎样，不选会怎样。今天咖啡一下的卡片，社区群里有人看不懂按钮是干什么的（`approval-ux.md` 第 5 节）。
- 选项卡（含"其他"）和要打字回答的题：回复这张卡片，等于用你的话回答；能回答的人在同一个位置直接发新消息，也算回答。确认卡和完全访问下 Claude 自己要问的那几类只认按钮：等它们时打的字不算回答，照普通消息处理，插话或排队（owner 2026-10-19）。运行卡上的 ⏹，等于不回答并停止这一轮。
- 答完以后按钮去掉，换成一行结果，比如"张三 选了：方案 B 10:03"、"⏱ 15 分钟没人回答"、"⏹ 已停止"、"已失效（后台服务重启过）"。每种结局都改卡，不让按钮一直挂着。bridge 里咖啡一下的卡超时后按钮还在。
- 每张卡单独发一条消息，回复触发这一轮的那条消息，在话题里就发在话题里；卡片里 @ 能回答的人。不把按钮放进运行卡，因为运行卡在流式更新，按钮会和输出抢。卡片里的 @ 会不会提醒人要实测，不会就另发一条带 @ 的文字。

**谁能点。** 由 daemon 按点击人的 open_id 判断，不由 agent 判断。daemon 还要核对这张卡属于这个群和这条会话，转发出去的卡点了无效。

| 卡片 | 能点的人 |
|---|---|
| 选项卡、确认卡 | 发起这一轮的人，管理员也能代答 |
| 完全访问下 Claude 自己要问的 | 主人和管理员 |
| bot 触发的那一轮（bot 之间对话） | 主人和管理员 |
| 云文档评论的会话 | 没地方放卡片：提问按"没人回答"处理，Claude 自己要问的直接拒绝 |

- 点的人不对时，回贴一条去重的小注，比如"只有发起人或管理员能回答"，和今天 ⏹ 的做法一样（`D/bot/handle-message.ts:2384-2397`）。第一次有效的点击生效。

**等待和超时。**
- 15 分钟没人回答：选项卡告诉 agent"用户没有回答"；确认卡和 Claude 自己要问的按拒绝处理。
- 等人回答时，空闲看门狗暂停，不然这一轮会被当成"没输出"杀掉。
- 同一条会话同时只显示一张待回答的卡，其余排队。
- 后台服务重启后，挂着的请求就没了。点到旧卡时，卡片自愈成"已失效（后台服务重启过）"，和今天的 `healDeadRunCard` 一样（`D/bot/handle-message.ts:2398`）。
- 子 agent 发起的卡片，发在父运行卡所在的位置，卡上写"子 agent X 问……"。
- 要填密码这类敏感信息的问题，不在群里显示输入框，请用户去私聊回答：bot 私聊每个能回答的人一张带输入框的卡，群里的卡只写"已在私聊里回答"，答案不显示。能回答的人在私聊里直接发一条消息，恰好只有这一题在等他时也算回答。等这种题时，能回答的人在群里打字不算回答，bot 提示一次去私聊，这条消息照普通消息处理（owner 2026-10-19）。

**在聊天里改设置。** 不发授权卡，也不按权限档拒绝。owner 第 29 题定了：改 vonvon 设置都走设置 skill 和 `vonvon` 命令行，只有私聊的会话有，群里没有（3.7）。私聊的开关开着时，主人和管理员触发的那一轮改了就直接生效，带撤销。

留下的风险：agent 读到的文档或网页里可能藏着"去装这个 MCP"之类的指令，诱导主人或管理员触发的那一轮去装 MCP、装含脚本的 skill、加目录、升档、开网，或者改允许哪些群用（名单清空就是所有群都能用）、加管理员、放开群里允许使用 bot 的成员。daemon 按触发人判断，挡不住这一种，只读、读写档的会话也能这样给自己升档。第 29 题问的时候写了这个风险，owner 选了按位置装不装设置 skill 来管，所以私聊里有这个风险，群里没有。缓解：这几种扩大能力的改动，改完的卡片上单独标出来，带［撤销］（Claude 加的，第 11 节第 29 条；改允许的群、加管理员和放开群里的成员是 2026-10-18 聊天里能改它们以后加进来的）；每张改设置的回执还写明由谁的哪条消息触发和 bot 的说明（3.7）。

### 3.9 子 agent

- 子 agent 显示在父运行卡的"子 agent 区"，一行一个：状态、名字、在做什么、几步、用了多久，嵌套的缩进。点开看最近 5 步和结果。每行有"停止"，运行卡的 ⏹ 全停。不给每个子 agent 发一张卡：飞书对群里所有 bot 有每秒 5 条的共用限额。
- 每一行绑定稳定的子 agent 身份，最近 5 步之外显示省略计数。折叠过程仍保留待回答入口、失败和停止状态；父回合结束不能隐藏仍在运行或等待输入的子 agent。子 agent 的单独停止不能误停父回合或其他子 agent。
- **一张运行卡包含这一轮的所有子 agent，子 agent 都跑完了，这张卡才算结束。**
  - Codex：本来就是这样。文档原文是"Codex waits until all requested results are available, then returns a consolidated response"（learn.chatgpt.com/docs/agent-configuration/subagents）。
  - Claude：不一样。Claude Code 的子 agent 默认在后台跑，经 Agent SDK 用时也是；主回合可以先结束，子 agent 跑完再通知 Claude 起新的一轮（code.claude.com/docs/en/sub-agents）。实测里一条消息出了 4 到 6 个结果。设置 `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` 后，子 agent 一律在前台跑，主回合等它们都结束，一条消息只有一个结果，几个子 agent 之间仍然并行（实测，`docs/research/2026-10-14-v1-spikes/e01-background-tasks.md`）。代价是它同时关掉后台 Bash 等所有后台任务，比如 bot 不能在后台起一个开发服务器再结束这一轮；模型要在后台跑命令时会先报错一次，再改成前台跑。第一版在 bot 的 Claude 会话里打开这个开关，两家行为就一致了。这是 Claude 的决定。前台子 agent 跑着时按 ⏹ 多久能停下还没测，s35 开工时补测（e01）；停不下来的话，回头再定。
- 子 agent 跑的时候，群里的新消息按今天的规则插话或排队，只给父 agent。第一版不能直接跟某个子 agent 说话。
- Codex 的子 agent 跟着用户自己的 Codex 设置走：Vonvon 不在会话里替用户打开或关掉 `features.multi_agent`，用户开了就显示子 agent，没开 Codex 那一侧就没有子 agent，只有 Claude 一侧有（owner 2026-10-19）。Vonvon 自己的标题任务和判断线程照旧关着子 agent。
- 今天 Codex 的子线程事件全丢了，Claude 子 agent 的步骤混进了主过程（`D/agent/codex-appserver/backend.ts:333-337`；`D/agent/claude-agent/event-map.ts:92-123`），第一版要修。

### 3.10 后台服务和崩溃

owner 的话："后台服务不要依赖 Electron，因为 Linux 上没有桌面端，它可能就装一个 Daemon 后台服务。"调研见 `docs/research/2026-10-14-session-approval-service/service.md`。

**后台服务由 daemon 自己装。**
- 用 `vonvon service install`、`uninstall`、`status` 注册、卸载和查看。桌面端只调用打包在里面的同一个命令行。不用 Electron 的 `agentService`，也不用 SMAppService：这两种都要求服务登记在 .app 名下，Linux 上没有对应的东西。
- macOS：用户级 LaunchAgent `com.vonvon.bot.daemon`，plist 写在 `~/Library/LaunchAgents/`（`D/service/identity.ts:33`）。用户登录后启动，能用钥匙串里的 Claude 登录和 Codex 的登录（推断，要实测）。Mac 设成自动登录时，就等于开机启动。
- Linux：systemd 用户服务 `vonvon-bot.service`。安装时检查 linger：没开就问一句，同意后执行 `loginctl enable-linger`。这样开机就启动，退出 SSH 以后 bot 也还在跑。
- 从 dmg 装的，服务用 app 里的 Electron 程序以 Node 模式运行（`ELECTRON_RUN_AS_NODE=1`），不用另带一份 Node；从 npm 装的，用用户自己的 `node`。这只是借 Electron 的 Node 来用，服务的生死由 launchd 管，桌面窗口开不开都一样。代价是 app 被删或挪走以后，服务就起不来了，所以桌面端提供"关闭登录时启动"，文档写清卸载步骤。
- 注册以后，系统的服务管理器是唯一拉起 daemon 的。`vonvon daemon start` 和桌面端都请它去启动，不自己再起一个。停止走 `vonvon daemon stop`：先排空，再正常退出，管理器就不会再拉起它。
- 退出桌面端不停 bot。首次运行清单里加一步"登录电脑时自动运行 bot（推荐）"。跳过的话，就像今天一样起一个分离的 daemon，并提示"这样崩溃后不会自动重启"。
- 这些代码大部分已经在 main 上，只是没接线：launchd 和 systemd 的安装事务（#271、#274）、服务定义（#246）、退出码（#276）。今天 `vonvon service install` 直接报错（`D/cli/commands/service.ts:5`）。

**崩溃了自动重启。** 服务管理器在 daemon 异常退出后重启它（plist 的 `KeepAlive`、unit 的 `Restart=on-failure`，`D/service/definitions.ts:81`、`:85`）。两边都不会在连环崩溃时自己停下来，所以上限由 daemon 自己判断：
- daemon 和每个 bot 的子进程都加全局的异常兜底：崩溃前在 `~/.vonvon-bot/crash/` 写一条记录（版本、哪个 bot、错误的第一行、运行了多久），再退出。被系统强制结束、没留下记录的，下次启动时补一条"被系统强制结束"。今天没有任何崩溃记录（`D/cli-bridge/ipc.ts:24-25`）。（s17 已加 daemon 主进程的；bot 子进程的在 s18）
- 10 分钟内崩溃 3 次，daemon 进入暂停：网页和桌面端照常能打开，显示原因；bot 不连飞书，不跑 agent。不自动恢复，等主人点"恢复运行"，或执行 `vonvon daemon restart`；`vonvon daemon stop` 再 `vonvon daemon start` 也算恢复。下次登录或开机时重新计数。停止和重启过程中出的错照样记录，不计入 3 次。暂停期间 daemon 自己又起不来（比如端口被占），后台服务就不再拉起它，`vonvon daemon status` 仍显示已暂停，`vonvon daemon restart` 恢复。（s17 已做；网页上的原因和"恢复运行"在 s18）
- 某一个 bot 的子进程 10 分钟内崩溃 3 次，只暂停这一个 bot，别的照常。今天子进程会无限重试（`D/bot/supervisor.ts:115-131`）。

owner 说过"崩溃报错就好了"，让 Claude 斟酌。自动重启是 Claude 加的：后台服务崩了，群里的人只会看到 bot 不回，主人不一定在电脑前。

**怎么告诉主人。**
- 崩了一次、已经自动恢复：桌面端的诊断页记一条；bot 给它的主人发一条私聊"刚才崩溃过一次，已自动恢复。原因：……"。daemon 或这个 bot 重新起来、稳定 30 秒后再发；30 秒内又崩的只发后面那条（"10 分钟内崩溃了 N 次"）。带恢复请求起来的（`vonvon daemon restart`、"恢复运行"）不再补发上一次的"已自动恢复"。
- 连环崩溃、已经暂停：诊断页顶上一条红条，带"恢复运行"按钮；马上私聊"10 分钟内崩溃 3 次，已停止自动重启"。
- daemon 主进程崩溃时所有 bot 一起下线，只由最早加入的 bot 发给它的主人，列出受影响的 bot；几个 bot 的主人不是同一个人时，别的主人收不到这一条（飞书按应用给每个人不同的 open_id，daemon 看不出是不是同一个人）。每个 bot 每 10 分钟最多发一条，进入暂停的那条不受这个限制。
- 私聊只写一行原因，不放调用栈和本机路径。第一版不上传崩溃信息。
- 私聊直接调发消息的接口，不靠长连接，所以暂停时也能发。2026-10-16 实测：没开过 bot 私聊的主人也收得到，手机和电脑都弹通知。发不出去（网络错误、飞书限流）时隔 1 分钟、5 分钟各再试一次；飞书拒绝的不再试，写进 daemon 日志。进入暂停的私聊排上就保存在本机，主进程被强制结束或关闭时没发完，下次启动仍在同一轮暂停、且不超过 24 小时就补发。恢复运行、重启机器或暂停已解除时不补发旧通知。飞书只在 1 小时内按消息标识去重，超过这个时间补发可能重复。（s18b、s18e）
- Linux 上用 `vonvon daemon status` 看服务状态和最近的崩溃。`vonvon service status` 显示服务管理器记的上次退出和自动重启次数；关闭时有几步失败，日志和终端里每一步各一行（s17b）。
- 重启或停止时还在排队、没开始处理的消息（包括 `/new`、`/compact` 期间暂存的、排着的 `/compact` 和等并发槽的那一轮）：bot 起来连上飞书后，每个群在最新的那条下面回一句"刚才重启了，这条没处理，请再发一次"，这个群不止一条时写明还有几条，话题里的回在话题里；停了 10 分钟以上才起来时开头写"bot 停了一阵"，超过 24 小时不回。诊断页"最近没回的消息"每个群记一条。bot 子进程自己出错崩溃时，也记录当时还在排队的消息；正常关闭时，刚收到、还在准备会话的第一条也记录。重启过程中新发来的消息不会丢：关闭一开始就断开长连接，飞书过几分钟重推，bot 起来后照常回答。记不下来的：bot 子进程被系统强制结束（kill -9、内存不够）；macOS 上 daemon 主进程被强制结束时 launchd 连 bot 的子进程一起结束（推断，M4 的 Mac 检查确认）。owner 2026-10-16 让 Claude 定。（s18c、s18e）

## 6. 主人和管理员

- 沿用飞书应用自己的角色。主人是飞书应用的所有者；管理员是飞书应用的管理员和开发者，运营不算。开发者也算，是按 owner 第 10 题的回答：扫码把应用加进 vonvon 的人，飞书在扫码时会确认是管理员或开发者（owner 的说法，没有实测）。
- 所以扫码的人一定能管这个 bot。今天的代码就是这样认主人的（`creds.operatorOpenId`，`D/bot/wizard.ts:81`），不需要新权限。
- 开了可选权限"管理应用自身资源"（`application:application:self_manage`）后，vonvon 会读飞书应用的所有者和协作者名单，主人在飞书里另外加的管理员和开发者也能管这个 bot。查询方法见 `docs/research/2026-10-14-feishu-app-roles/roles.md`。
  - 协作者接口每分钟只能调 10 次，所以本地缓存 10 分钟。在飞书里去掉一个管理员，最多 10 分钟后这个人就不能私聊、不能改设置了，除非这个人也在下面的本机名单里。
- 桌面端还可以另外加管理员（私聊里也能加，3.7），权限和飞书里的管理员一样，页面上标出每个人是从飞书来的还是本机加的。从 bridge 迁来的本机管理员名单（`preferences.access.admins`）放在这里：bridge 用它决定谁能用管理员档（第一版没有了），谁能用 `/resume`、`/settings`、`/clear` 这类管理命令（`D/bot/handle-message.ts:1206`）。第一版没有访客档了，这份名单只管这些管理命令；不放的话，迁移后这些人用不了它们。本机名单是 Claude 加的，owner 只说了沿用飞书。
