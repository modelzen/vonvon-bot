对应含义：

- 账号服务优先交给提供商；国内/海外以及 Supabase 可行性待答复，不能沿用 Claude 先前“必须国内自建、不用 Supabase”的默认方案。
- 第一批登录方式为 GitHub、Google、Apple；不用 QQ。微信等不属于已定的第一批。
- 用户拒绝把用户自己组织的飞书 Bot 认证拿来充当 vonvon 平台身份。
- 用户早先提出一账号管理多个 OAuth 和手机号，最后又问不同 OAuth 是否分别算账号。需要澄清“首次登录建号”“主动绑定登录方式”“两个既有账号合并”三者，不能直接宣布自动合并或完全永不绑定已经定了。
- 不支持单纯邮箱登录，是用户 L524 的意见。
- 登录不强制手机号；以后升级 Pro、领取免费服务可能要求手机号。公开发布前绑手机号在 L761 对问题三回答中得到认可；这不等于恢复“所有登录强制手机”。手机号登录是否首版就提供仍需随最终范围确定。
- 公司资料在最终确认后再向用户索取。
- 旧 bridge 清理是原会话中的意见。本次恢复上下文没有执行删除，也没有把它当作应立即清理线上服务的任务。

## 本次接续时核实的两个事实

Supabase 的官方文档列有 Google、GitHub、Apple 登录支持，所以它是可研究的候选；这不等于已核实国内访问质量、整个产品的部署适配或合规条件。官方也说明同邮箱的 OAuth 身份可自动关联到同一用户，已登录用户可以手动绑定其他身份。因此“不同 OAuth 必定是不同账号”不能直接假设为其默认行为。

- https://supabase.com/docs/guides/auth/social-sign-in
- https://supabase.com/docs/guides/auth/auth-identity-linking

产品上的接续建议，尚未获用户确认：把“托管登录”与“配方发布、获取、setup、更新”作为本轮可讨论的最小范围，设备互连、中继、租赁和平台内付款继续延后。这样可以保留平台方向，又不把远期功能一起开发。先明确账号绑定的体验，再检查供应商默认行为能否满足。
