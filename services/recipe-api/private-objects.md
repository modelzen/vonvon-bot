# Private recipe objects

Migration 009 adds an object-preparation operation scoped to a business account, intended draft UUID, and byte ceiling. The ceiling covers every simultaneously retained input and output. Reserve enough space for the already prepared finals plus both copies of the next member. A Logo needs up to 2 MiB plus 128 KiB. Sequential files share the same reservation. Expiry is ten minutes from reservation. Each account has a 4 MiB temporary budget, two simultaneous ingress streams, at most three outstanding packages and sixty new object preparations per UTC day.

## Service integration

Use the account returned by the existing verified-identity mapping. On its transaction, the ordinary API calls `recipe_api.reserve_object_package(operationUUIDv7, draftUUID, cap)`, `recipe_api.cancel_object_package(operationUUIDv7)`, or `recipe_api.object_capacity()`. Only the restricted broker can turn an uploaded member into a ready object.

Start the broker separately from the general API. Provision a dedicated LOGIN with only `recipe_object_verifier` membership and pass its TLS-verified PostgreSQL pool to `await createObjectStore(pool)`. Use a direct or session-pooled PostgreSQL connection. The broker holds one session advisory lock per member across its input stream, Storage requests, readbacks, verification and cleanup. Transaction-mode connection pooling cannot carry this lock.

Create the private bucket `recipe-private` with a 2 MiB per-object limit and allow the broker's `application/octet-stream` transport. Remove inherited grants and broad Storage policies that expose this bucket to other users. Only the broker's Storage identity needs permission to create/read/delete its objects. Keep its key and access token on the broker. When using a service-role credential, that credential bypasses Storage RLS across the project. Use an actual restricted Storage identity if the deployment supports one. Disable retries of create requests in client transports, proxies, and gateways. Use server-mediated bytes, with zero public/private signed URLs. [Supabase Storage access control](https://supabase.com/docs/guides/storage/security/access-control)

Apply `src/object-storage-absence.sql` as a separate hosted provisioning transaction after migration 009. Its read-only function checks the private bucket and the exact metadata key. The broker requires both this database check and the Storage response before treating a missing remote key as absent. Supabase documents that a missing-object response can also indicate insufficient permission. Verify the role can see a deliberately seeded row before enabling cleanup, and preserve those exact metadata privileges across deployment changes. [Supabase error codes](https://supabase.com/docs/guides/storage/debugging/error-codes)

```js
const store = await createObjectStore(verifierPool);
const storage = createPrivateStorage({
  origin, bucket: 'recipe-private', apiKey, bearer,
  verifyAbsent: (bucket, key) => store.call('storage_absent', bucket, key),
});
const broker = createObjectBroker({store, storage, validateCanonicalManifest, authorizeRead});
const descriptor = await broker.receive(accountId, operationId, {ordinal, kind, bytes, sha256}, request.body);
```

The input byte length and hash bind an ordinal to precisely one input. An operation can carry 64 text files, one final Logo and one canonical manifest, with distinct ordinals 0–65. Actual GET bytes, length and hash bind the receipt to its database-assigned UUID and owner. Text must decode as UTF-8. The separately supplied shared manifest validator must reject invalid schema, non-canonical bytes, broken descriptor closure and over-limit content by throwing. Logo normalization and output validation run in fresh children. The output descriptor has `{objectId,kind,bytes,sha256,mediaType}`. Only text and final Logo descriptors enter the manifest. The manifest descriptor is part of the release envelope.

At draft CAS, compare every claimed descriptor with `recipe_private.object_descriptor(account_id, object_id)` and the exact intended membership. Check the actual manifest plus distinct verified part bytes against the draft and author budgets. In the **same transaction**, write the draft and logical accounting, then call `recipe_private.attach_object_package(operation_id,draft_id,all_object_ids)`. It requires all members ready, their original operation/draft, and exact membership. During publish, insert `object_version_refs` before dropping the draft refs, with the same owner, quota and release transaction. These private SQL ports execute under the owning draft/publication function. General API clients have no table or ready-verb access. Last-ref removal charges an unattached final against temporary space until GC, and can return `object_capacity` if the author's other preparations occupy that space.

For each download, pass the verified request identity and exact release/object to `broker.readAuthorized(request)`. Supply the access query once at broker construction. It must return a server-derived ready descriptor from that release's actual references after checking current lifecycle and authorization, or deny. This includes Logo and every individual text member. Send private content with `Cache-Control: private, no-store`. The current base has no rich release or HTTP writer. Its later route integration must supply the query, canonical codec, lifecycle/entitlement, expected-revision and quota transaction above before admitting uploads.

## Recovery and cleanup

Each member has one assigned original key and one assigned final key. Persist `writing` before issuing a single create-only POST. The worker never resends that POST, including after a restart or a lost response. Resume by reading the original key or final key as appropriate. An exact matching GET proves arrival of the one allowed write. Negative GET, local socket close, elapsed deadlines and a cancelled request cannot prove an uncertain remote write has stopped. Retry with the same operation and ordinal. A received final can be replayed without supplying the original again.

Cancel the operation or let its deadline pass. Run `store.call('pending_cleanup', accountId)` for a bounded actor-specific list, then `broker.collect(accountId,operationId)`. Busy writers retain their keys and holds. A gone member has confirmed absence for every previously writable lane. Draft refs, all historical version refs, active packages and backup pins inhibit final deletion. Use `pin_backup(actor,operation,ordinal,backupId,true)` while capturing SQL plus physical bytes, and unpin after recording a complete backup. Keep the abandoned package charged while cleanup or any remote outcome is uncertain. The inventory includes pending state and actor-held bytes. `prune_closed(actor)` removes at most 60 fully gone packages per call after the recovery window.

For an indefinitely missing `writing` key, first cancel, stop all affected broker writers and retries including remote requests, and obtain independent Storage-side evidence that the exact allocated key can no longer receive that write. Capture the evidence in a restricted operations record, hash it with SHA-256 and call the private broker's `reconcileQuiescent(actor,operation,ordinal,lane,evidenceSha256)`. This records the evidence digest and permits deletion. Run collection again to delete and confirm absence. If the upstream terminal outcome cannot be established, display the held bytes and leave that key charged. Only the private operator path should expose this reconciliation. A caller-supplied digest alone does not establish remote completion.

Deploy the Logo broker on Linux with hard process/container memory ceilings. The on-demand child has an input, decoded-pixel, output, CPU and wall-clock ceiling, no inherited credentials, and bounded libvips concurrency/cache. Linux additionally sets address-space and heap/data limits before starting Node. Test those limits with the deployed Node build and image library. Darwin uses sampled RSS for local validation. Run the broker under a dedicated OS identity without access to other services' configuration files. Hosted acceptance must exercise the real storage credential and policies, two accounts, private denial, tamper/readback/cleanup, stale authorization after withdrawal/ban and SQL-plus-bytes restoration. Local tests use real PostgreSQL, synthetic fixture metadata tables, an in-memory storage adapter and synthetic HTTP responses.
