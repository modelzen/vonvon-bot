# Rich recipe authoring and delivery

The general API and the private broker are independent processes behind the same HTTPS origin. Build the protocol package from the same revision before running the service. Start the broker with `node src/rich-broker.mjs` and a dedicated verifier login (direct or session pool). See [private objects](private-objects.md) for Storage privileges, confirmed absence and cleanup. Give Storage credentials only to this process. Point PUT member routes and GET object routes below to the broker; direct all other requests to the general API. Both mount paths accept `/v2` and the existing gateway style `/api/v2`. Default: writers off. Set `RECIPE_RICH_WRITES=1` on both only when the native writer, runtime and UI have passed acceptance. Existing readable versions stay readable independent of writer admission.

Use the same Main-held account bearer for account calls. Start with the UUIDv7 already recorded against the local source before sending anything. Do not send tenant/Bot/chat/device/directory identities. Every call is private/no-store. Creation:

1. POST `/v2/authoring/:op/register` with `{format:"rich-v2",purpose:"prepareDraft",targetPublicKey,nonceCommitment}`. It returns the operation record and a server-assigned `destinationDraftId`. For edits use `purpose:"editDraft",draftId,baseRevision`. GET the operation or its `/recovery`; POST `/cancel`. All use the account identity. Pending-count, expiry and terminal receipt retention are shared with v1.
2. POST `/authorize` with `{stage:"dispatch",stateRevision:1,payloadDigest:SHA256(empty)}`, then POST `/dispatch` on the operation with only `{ticket,nonce,proof}`. X25519, SHA-256, HKDF, HMAC, and binary field layouts match authoring v1; transcript and HKDF info begin with `vonvon.recipe.authoring.v2\0` and `vonvon.recipe.authoring.proof-key.v2\0`. A v1 proof never opens this channel.
3. Reserve one package using POST `/v2/objects/:packageUuidV7/reserve` with `{draftId:destinationDraftId,cap}`. Allow each new member's original plus final and all retained finals including the canonical manifest. Upload each selected raw external text or Logo via PUT `/v2/objects/:package/members/:ordinal` with `Content-Type: application/octet-stream`, exact Content-Length, `X-Recipe-Kind: text|finalLogo` and `X-Recipe-Sha256` (lowercase). Use the returned normalized descriptors. Cancel with POST `/v2/objects/:package/cancel`.
4. At the account's existing native source review, freeze exactly the reviewed snapshot by POSTing to `/v2/authoring/:op/freeze`: `{format:"rich-v2",content,access:"direct"|"coded",origins:[{itemId,source}],sourceVersionId?}`. The submitted IDs are snapshot aliases. For each item, including public fields, settings, nested blocks and files, source is `{kind:"accountClaim"}` for independently reviewed native material or `{kind:"releaseItem",versionId,itemId,baselineSha256}` from the native provenance ledger. A different author cannot copy an original Logo. Source intent ownership, exact retained release membership, kind, baseline, lifecycle and parent closure are checked. Same-author updates supply the exact current parent version; its original item IDs/origins survive edits. Copies have new IDs/origins retaining donor ancestry. Account review is an ownership claim, not a cryptographic witness of independent human writing. Native clients must preserve/verify known lineage and refuse unresolved alternatives. The service cannot detect arbitrary manual rewriting.
5. Freeze returns `{format,destinationDraftId,canonical,contentSha256,logicalBytes,payload,payloadDigest}`. Canonical/payload are base64url UTF-8. Retrying the identical reviewed input on the same operation returns identical bytes. Upload the decoded canonical as one additional `manifest` member of the same package. Its returned SHA must equal contentSha256. The actor authorizes stage `accept`, stateRevision 2, for that payloadDigest. Only the dispatch-key holder can POST `/accept` with `{ticket,nonce,proof,payload,canonical,manifestId,packageId}`, without an Authorization header. Replays of the exact commit recover its original receipt. Only broker-verified object bytes can be attached. The database stores the bounded member/provenance index and public text; the complete canonical document stays in its immutable private Storage object.

For edits, POST `/freeze` with `{format:"rich-v2",baseCanonical,payload,newParts?,access?}` where payload is the rich codec's typed edit, requestId and exact base revision. Fetch baseCanonical from the actual current draft manifest. The service verifies its digest under the actor lock. IncludeCandidate refers to an exact item of the retained source intent at the expected revision. It never accepts replacement JSON paths or client-assigned new origin records. After preparing the result use the same manifest upload and device acceptance. For an independently created account draft use a fresh prepare operation and its single source review.

GET `/v2/me/drafts` or `/v2/drafts/:draft` with the owner bearer. GET `/v2/drafts/:draft/objects/:object` at the broker to read each exact referenced member (including the manifest). Publish by POST to `/v2/drafts/:draft/publish` with If-Match, Idempotency-Key, and `{canonical}` for the current broker-verified bytes; DELETE with the same two headers discards. POST `/v1/authoring/source-history` retains the established private correspondence across device publication. A version remains immutable. GET `/v2/recipes/:recipe/versions/:version` returns introduction or full release and manifest descriptor according to current scope. Broker GET `/v2/versions/:version/objects/:object` returns bytes only for exact authorized membership. Use v1 acquisition/code routes and acquisition keys. POST `/v2/versions/:version/withdraw` withdraws as author. POST `/v2/me/profile` with a public displayName; no authentication metadata goes into public creator fields.

The isolated editorial CLI accepts `node src/rich-editor.mjs feature VERSION TESTER_ACCOUNT`, `unfeature VERSION`, or `ban VERSION`. A real editor separately tests the exact release; the command checks tester ownership/grant. Use only a dedicated `recipe_editor` login via RECIPE_EDITOR_DATABASE_URL. It has no HTTP endpoint. Forced banning affects future remote delivery; previously delivered local copies remain on the device.

## Installing or updating an exact rich version

`GET /v2/versions/:version/install-preview` requires an active, entitled account. It returns `{accountId,release,manifest}`. The release hash is the SHA-256 of the actual canonical manifest. The desktop sends this version, its own reviewed target preparation and exact digest to `POST /v2/operations/:uuidV7/authorize`. Wire schemas: `recipeRichInstallIntentSchema`, `recipeRichInstallAuthorizationSchema`, `recipeRichInstallRedemptionSchema`. Use `purpose:"installRichRecipe", format:"rich-v2", generation:2`, never the generation-1 purpose. Private-key possession calls reject bearer headers. POST `/redeem` with ticket, nonce and device proof to get the exact release and manifest descriptor. Fetch the manifest, external text and Logo by POSTing the same possession body to the broker's `/v2/operations/:operation/objects/:objectId` route. Each read verifies active operation, account, source scope, exact version, object membership and current distribution state. Never send these credentials in a URL. Compare received bytes and digest locally. GET `/v2/operations/:op/recovery` and POST `/cancel` use the account bearer. A redeemed operation remains recoverable through its seven-day window.

A new direct version can be previewed before grant through its public detail. For an existing installation, authorize `purpose:"updateDirectRichRecipe"` with `fromVersionId` (earlier release of this same recipe owned/acquired by this account) and `localPlanSha256` (daemon digest of reviewed physical target, previous baseline and choices). Cloud does not receive the physical group identity. Authorization and redemption create no grant. `POST /v2/operations/:op/complete` accepts `{outcome:"applied"|"rejected",ticket,nonce,proof}` with an outcome-specific proof. The device emits the applied proof only after its durable local commit and sends rejected on refusal. The service validates it against the exact operation, recording a direct-update grant exactly once. This is a device report, not independent cloud observation of a group mutation. Withdrawal allows settlement of a previously redeemed direct operation. A forced ban stops delivery, records a blocked disposition and gives no grant. A coded upgrade always requires its own original code grant; this operation cannot qualify it as direct.

For the X25519/HKDF-SHA256/HMAC proof, use `vonvon.recipe.<purpose>.proof-key.v2\0` and transcript prefix `vonvon.recipe.<purpose>.v2\0`. Follow the legacy installation binary field order (operation/account/version UUIDs, content digest, target key, nonce commitment, server key, generation and deadline). An update additionally appends from-version UUID and 32 raw bytes of localPlanSha256. Append UTF-8 `\0complete:applied` or `\0complete:rejected` when signing a completion. The ordinary redemption transcript has no completion suffix. See the synthetic Python/HMAC-derived golden vectors in test/fixtures/rich-install-proof.json.

Public rich catalog pages use GET `/v2/community/recipes?q=&access=direct|coded&cursor=`. Keep the opaque signed cursor unchanged for the same query. It binds the first window upper bound, ordering, search, access filter, hero recipe, and last sort keys. The first default page returns one hero, separate from up to eight cards. Continuations do not repeat the hero. Search includes only public name, summary and creator display name. An author-selected normalized Logo is publicly displayed on an otherwise listed introduction, including a coded version: use `GET /v2/versions/:v/display-logo` only when `hasDisplayLogo` is true. This no-store route takes no object selector and returns only that release's verified final WebP. On withdrawal or ban it returns 404. Draft previews and other member reads remain independently authorized.

The accept transcript additionally appends 32 raw bytes `sourceReviewSha256` after the deadline. The freeze result and authorization both return that SHA-256. It covers the complete reviewed freeze input in sorted canonical JSON, including original aliases, reviewed source edges, access, parent and typed command values. The daemon must compute it from its own reviewed input, compare the result and inspect the remapped payload before signing. Comparing a hash supplied by an untrusted caller would not attest to the original review. For a mixed source use `{kind:"releaseItems",parents:[{versionId,itemId,baselineSha256},...]}`; the service checks each edge, with bounded traversal. GET `/v2/versions/:version/source-items` as a signed-in full reader to obtain trusted exact-source item IDs and complete-item digests. Separate server-only similarity fingerprints recognize exact copies despite changed owner-generated IDs.

A draft's original reviewed snapshot remains privately accessible from the draft's `sourceManifest` descriptor until deletion or publication. A candidate handle's candidateId is the server-issued itemId in this snapshot; expectedRevision is the current draft revision. When re-including after intervening edits, pass `candidates:[{sourceIntentId,canonical}]` containing the original broker-read canonical bytes. The server compares the digest to its immutable index. Extra distinct retained source bytes count toward the account's draft budget (`retainedCandidateBytes`), but not the resulting version's 1 MiB logical size. Publication transfers only the selected manifest and its exact parts. An omitted/removed source member never becomes reachable from a published version.
